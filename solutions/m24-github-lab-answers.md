# Module 24 lab answers, GitHub part: Verification states

Answers to the "Questions" of Lab 24.3 in the [Module 24 GitHub lab manual](../lab-manual/m24-signing-github.md). Statements about Git were checked on Git 2.55.0 in the lab sandbox. Statements about GitHub come from the documentation that [Chapter 21B](../textbook/ch21b-repository-security-incident-response.md), sections 21B.5 to 21B.7, cites, and were not observed by the author.

## Lab 24.3: What GitHub shows for unsigned, signed and forged commits

1. The push. GitHub authenticated the credential that delivered the commit, and the repository's Activity view and the organization's audit log record that account as the pusher, whatever the commit's author and committer lines say. A missing verified signature on a commit that names someone who normally signs is the second piece of evidence; with vigilant mode it is displayed as "Unverified".
2. It proves that the holder of the private key registered on your account created exactly this commit object, and that GitHub verified the signature at the recorded time. It does not prove that the change is correct or reviewed, that the key holder was you and not someone who obtained the key, or that a release artifact built elsewhere corresponds to the commit. The xz-utils case of 2024 is the example: a trusted, authorized contributor, and a build script that existed only in the release tarball.
3. Vigilant mode flags unsigned commits attributed to a person who enabled it, and GitHub attributes by the email addresses in the commit. Commit C names you as its committer. The documented "Unverified" state under vigilant mode includes unsigned commits whose committer or author has enabled the mode.
4. Merging fails for that method. "Rebase and merge" creates new commits on the base branch, and GitHub creates them without a signature: the original signatures cover the old parents and cannot be carried over, and GitHub does not hold the contributors' private keys. The rule accepts only signed and verified commits, so the rebased commits are rejected. Merge commits and squash commits pass, because GitHub signs those itself.
5. Nothing happens to the badge. Since 10 December 2024 a verification record is stored with the commit when it is first verified and persists when the key is later revoked; GitHub does not re-verify earlier commits when a key's state changes. You find the thief's commits by other evidence: the time window between theft and revocation, the pusher in the audit log, the repositories the account could reach, and review of what those commits changed.
6. GitHub's. Commits created in the web interface, including squash commits and merge commits, are signed with GitHub's own key, which can be checked against `https://github.com/web-flow.gpg`. The badge says that GitHub created the commit on behalf of a signed-in user; it says nothing about the signatures of the commits that were squashed.
