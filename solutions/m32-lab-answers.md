# Module 32 lab answers: Branching and release strategy

> **Baseline.** Git 2.55.0 on macOS. These are answers to the "Questions" of the lab in the [Module 32 lab manual](../lab-manual/m32-branching-release-strategy.md). Write your own answers first. Commit IDs quoted here are those of the replay script `labs/ch27/lab-32-1-two-strategies.sh`; commits that you made by hand have other IDs.

## Lab 32.1: One release and one hotfix under two strategies

1. **"The security fix only", from the part A repository.** Nothing that exists. `v1.4.1` is a snapshot of `main`, and `main` contained the batch endpoint (`98cc48f`) before the fix (`fde1267`) was made. To offer a fix-only release you must first create a line for 1.4 to stand on: `git switch -c release/1.4 v1.4.0`, then `git cherry-pick -x fde1267`, then tag the result, with a version number that does not collide with the published `v1.4.1`. That is part B, created after the fact. It works because a branch can be created at any commit at any time; what cannot be undone is that `v1.4.1` was already published with the feature in it.

2. **Three pieces of evidence that the two commits are one fix.** (a) The line `(cherry picked from commit ...)` that `-x` appended to the message of `8444832`, which names `c73fb72`. (b) The patch ID: both commits introduce the same diff, which is why `git log --cherry-pick` and `git cherry` treat them as equivalent. (c) The subject, author and author date, which `cherry-pick` copies; only the committer and committer date are new. A cherry-pick that needs a manual conflict resolution changes the diff, so (b) no longer holds. The manual says the `-x` line "is done only for cherry picks without conflicts", so after a conflict you add the reference yourself when you conclude the pick. (c) survives, and it is weak evidence: two different fixes can share a subject.

3. **Is the fix missing from `main`?** No. `git branch --contains v1.4.1` asks which branches can reach that particular commit object. The commit on `release/1.4` is reachable only from `release/1.4`. `main` contains a different commit with the same change. The command that answers the real question compares patches: `git log --oneline --cherry-pick --right-only --no-merges main...release/1.4` printed nothing at the checkpoint, meaning every change on the release branch has an equivalent on `main`.

4. **Why step 11 printed one commit and not two.** `main...release/1.4` is the symmetric difference: commits reachable from one side and not the other. On the release side that is both `8444832` (the backported fix) and `8196669` (the clamp). `--cherry-pick` then removes every commit that has a patch-equivalent commit on the other side. `8444832` has one, `c73fb72` on `main`, so it is omitted. `8196669` has none, so it is listed. `--right-only` hides the commits that are only on `main`.

5. **Why a new tag and not a moved tag.** The Git reason: a tag is expected to be immutable, and Git enforces that expectation on the receiving side. A fetch does not replace a tag that the clone already has, so every clone that fetched `v1.5.0` keeps the old meaning unless its owner forces the update, and the two meanings then coexist under one name. The platform reason: release assets, package registries, container tags and customers' pinned versions were built from the old commit; with immutable releases enabled GitHub also locks the tag and forbids reusing its name. A version number is a promise about content ([Semantic Versioning](https://semver.org/) says the contents of a released version must not be modified), and `v1.5.1` keeps both promises.

6. **Under merge-upward.** Step 12 would not be a cherry-pick. After committing the clamp on `release/1.4` the engineer runs `git switch main` and `git merge release/1.4`. The invariant a release gate can test is `git merge-base --is-ancestor release/1.4 main`: the release branch is an ancestor of `main`. In this repository that merge would also have brought the cherry-picked copy of the first fix, `8444832`, into `main`, where the same change already exists as `c73fb72`, and it would have stopped with a conflict. Chapter 27, section 27.10 runs exactly this case (`labs/run ch27/mixed-directions`): relative to the merge base, `main` changed one line and the release branch changed that line identically plus the line below it, so the changes overlap; Git removes the identical line from the conflict and leaves the neighbouring line for you. In general the upward merge brings everything on the release branch: version bumps, release-only configuration, and any commit that was picked down earlier. That is why a repository should use one direction only.

7. **The cost of each long-lived branch.** Each supported release branch needs its own CI runs, its own protection rule, dependency and security updates applied to it, a port decision for every fix on `main` ("does 1.4 need this?"), and the port check as a gate. The cost grows with the number of supported lines and with how far they have drifted from `main`, because ports start to conflict. A release branch may be deleted when no supported customer runs that version, which is a contract or policy decision and not a Git one. Deleting the branch loses nothing that was released: the tags keep every released commit reachable. It loses only unreleased commits at the branch tip, so check `git log <last tag>..release/x.y` before deleting.
