# Scene wishes for V182: Operations in progress: what git status and .git tell you

Spots are given as section heading plus the first six words of the paragraph in `video/scripts/V182-*.md`. Every label is copied from the script.

**The format is a quiz.** In the demo the viewer names each operation from the listing of `.git` before `git status` is shown, and one quiz ("Quick quiz before the table. Two") asks which two operations detach HEAD. A picture that names an operation, or shows where HEAD is, must not be on screen during the question it answers. The order per repository is: listing, the viewer's answer, then the picture.

Placed in this pass with today's library: nothing. The six repositories are built separately and have different commit IDs, and the only graph in the transcripts (`01-clean`) is printed without branch names, so no `graph` could be written from the script alone. No library scene shows state files.

## 1. An operation is nothing but files

- **Spot.** CONCEPT, "**Precisely.** Git has no process that", then the three one-line consequences ("A stopped operation survives a reboot", "Deleting the files by hand ends", "And you can diagnose a repository").
- **Picture.** A `.git` folder, open, with two items in it and a terminal line beside it.
- **Steps.**
  1. `files`: a chip `MERGE_HEAD` ("a pseudoref ... that holds a commit ID") and a small folder with "a todo list" ("for multi-step operations").
  2. `status`: an arrow from the two items to a terminal line: "`git status` reads those files and prints its first lines from them".
  3. `reboot`: a calendar flips three weeks and a power symbol blinks; the files are unchanged: "survives a reboot and can be weeks old".
  4. `deleted`: a hand removes the files; the half-finished work in the working tree stays as it is: "ends the operation without undoing it".
  5. `handed`: the folder is passed to a second person who reads the items: "you can diagnose a repository you were handed by listing `.git`".

## 2. Five signatures, one card each

- **Spot.** CONCEPT, "**The signatures.**" and the five paragraphs after it ("Merge: `MERGE_HEAD` is the commit being", "Rebase: a directory, `rebase-merge`, or `rebase-apply`", "Cherry-pick: `CHERRY_PICK_HEAD` is the commit being", "Revert: `REVERT_HEAD` is the commit being", "Bisect: `BISECT_START` is the branch to"), then "Two files aren't signatures. `ORIG_HEAD` and".
- **Picture.** Five cards that arrive one per paragraph. Each card: the proving file or directory in large type, the other files small, and a HEAD chip that is either on a branch label or on a bare commit.
- **Cards.**
  1. Merge: `MERGE_HEAD` ("the commit being merged in"; "becomes the second parent"), `MERGE_MSG`, `ORIG_HEAD`, `AUTO_MERGE`; HEAD "still attached to the branch".
  2. Rebase: `rebase-merge` ("or `rebase-apply` for the older apply backend"), `REBASE_HEAD`; inside: `head-name`, `orig-head`, `onto`, `msgnum`, `end`, `git-rebase-todo`; HEAD "a raw commit ID".
  3. Cherry-pick: `CHERRY_PICK_HEAD`; a `sequencer` folder drawn dashed with the note "when several commits were requested", holding `head` and `todo`; HEAD "stays on the branch".
  4. Revert: `REVERT_HEAD`; note "the same machinery as cherry-pick".
  5. Bisect: `BISECT_START`, `BISECT_LOG`, `BISECT_TERMS`, `refs/bisect/`; HEAD "detached on the commit under test"; note "no conflict and a clean working tree".
  6. `not-signatures`: two grey chips to the side, `ORIG_HEAD` and `FETCH_HEAD`: "records of past commands".
- **Return in the demo, always after the viewer's answer.** Card 1 at "`MERGE_HEAD`. A merge. The message file"; card 2 at "The directory `rebase-merge`: a rebase. HEAD"; card 3 at "`CHERRY_PICK_HEAD` and a `sequencer` directory: a"; card 4 at "`REVERT_HEAD`: a revert, of one commit,"; card 5 at "Six files that begin with `BISECT`.".

## 3. Where HEAD is (the answer to the quiz)

- **When.** Only after the pause of the quiz: at DIAGRAM, "B. Point at the HEAD column".
- **Picture.** The five operation names in a row, each over a tiny graph of one branch.
- **Steps.**
  1. `attached`: under "Merge", "Cherry-pick" and "Revert" the HEAD chip sits beside the branch label: "on the branch".
  2. `detached`: under "Rebase" and "Bisect" the HEAD chip sits on a commit with no label: "detached".
  3. `commit`: a new commit grows in each; in the two detached ones it extends HEAD and the branch label stays behind: "a commit made "on the branch" is not on the branch".
- **Why not today.** `graph` can draw one detached HEAD; it cannot run five small graphs side by side.

## 5. Three kinds of exit

- **Spot.** CONCEPT, "**The exits.** Each operation has up", then "Every "leave and restore" command resets"; again at LIVE TERMINAL DEMO, "**The ways out.** First the one" and "🟡 CAUTION for the other four:".
- **Picture.** A room labelled "operation in progress" with three doors.
- **Steps.**
  1. `continue`: door "continue".
  2. `restore`: door "leave and restore the starting point"; behind it the index and the working tree are wiped back: "uncommitted edits made during the operation are lost".
  3. `keep`: door "leave and keep the current state".
  4. `labels`: on the middle door, five command plates with their risk labels: `git merge --abort` in red with a warning triangle and "🔴 DANGEROUS"; `git rebase --abort`, `git cherry-pick --abort`, `git revert --abort`, `git bisect reset` with "🟡 CAUTION".
  5. `anchor`: a rescue label is tied to a commit inside the room before the middle door opens: "Anchor and then abort ... if commits were made inside it".

## 6. The count on the wall

- **Spot.** MENTAL MODEL, "A picture helps. The textbook's analogy", then "The analogy breaks because Git's list".
- **Picture.** A wall list in an operating room.
- **Steps.**
  1. `count`: the list "says what is still inside the patient"; a second person reads it from the door.
  2. `breaks`: the same list turns over; its back reads "the undo record": "The same files that describe the operation are what `--abort` reads".
  3. `torn`: the list is torn off the wall; neither side can be read: "You've made it impossible to do either with Git's help."
  4. `two-questions`: two lines stay on screen: "which state files exist?" and "is HEAD a branch name or a raw commit ID?".
