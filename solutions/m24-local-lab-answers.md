# Module 24 lab answers, local part: Commit signing and verification

Answers to the Questions in [lab-manual/m24-signing-local.md](../lab-manual/m24-signing-local.md). Read them after you have written your own. Most transcripts of this module are volatile, so no fingerprints or IDs of signed objects are quoted here.

## Lab 24.1: SSH signing locally

1. **The list of keys you trust: `gpg.ssh.allowedSignersFile`.** An SSH signature contains the public key that made it, so the mathematics could be checked at any time. What cannot be derived from the signature is whether that key means anything to you: an SSH key carries no owner and there is no web of trust or certificate chain behind it. Git therefore defines SSH verification as "the key is listed, for a principal, in my allowed-signers file". With no file it does not start `ssh-keygen` at all; it prints the error, and the placeholders report the commit as if it were unsigned.

2. **The commit object without its `gpgsig` header**: the `tree`, `parent`, `author` and `committer` lines and the message. Amending the message creates a new commit object with new bytes, so the old signature would not fit it and is not copied. The new commit is signed only if you sign it: at that point in the lab `commit.gpgSign` was not yet set, so `git commit --amend` without `-S` would have produced an unsigned commit; with `-S`, or after step 5, it carries a new signature made by your key at that moment.

3. **`ssh-keygen` was given the public key file and looked for the private key beside it**, in the file of the same name without `.pub`. An agent is the other place it can look, and the lab had cut that off by unsetting `SSH_AUTH_SOCK`. If the private key file is missing, the commit fails with `error: No private key found for public key "…/signing_2026.pub"?` followed by `fatal: failed to write commit object`. The replay `ch14b/ssh-signing` shows this and two related failures in its last snippet (`labs/run ch14b/ssh-signing`): a wrong path gives "Couldn't load public key", and a literal `key::…` value without an agent gives "Couldn't get agent socket".

4. **It keeps valid every signature whose commit is dated before the rotation day**, and it rejects commits dated later that are signed with the old key. The weakness is the word "dated": the time Git checks the window against is the committer date stored in the commit, and the committer date is whatever the person creating the commit sets (`GIT_COMMITTER_DATE`). Someone who has the old private key creates a commit dated inside the window, signs it, and it verifies. Chapter 14B, section 14B.17, demonstrates exactly that. A validity window is a tool for orderly rotation. For a compromised key the tool is `gpg.ssh.revocationFile`, which rejects the key for every date, at the cost of also invalidating the honest signatures made with it.

5. **Usually not.** A signature is part of the commit object, so "signing an existing commit" means creating a new commit with a new ID, and every descendant gets a new ID too, since each records its parent's ID. For three unpublished commits that is `git rebase --root --gpg-sign --force-rebase`, which replays every commit and signs each replay. For published history it is a full rewrite with a forced push, broken references everywhere the old IDs were recorded, and signatures that claim *you* vouch today for commits made earlier, possibly by other people. The honest state is the one the lab ends in: unsigned before a certain commit, signed after it, and a rule that enforces signatures from that point on.

6. **The option names are historical, not descriptive.** Signing in Git began with GnuPG, and when X.509 (Git 2.19) and SSH (Git 2.34) were added, the existing names were kept: `commit.gpgSign`, `tag.gpgSign`, `--gpg-sign`, the `gpg.` configuration section, the `gpgsig` header, even messages such as "does not have a GPG signature". When you read an older script or tutorial, "GPG" in an option name tells you nothing about which signing format is in use; `git config get gpg.format` does.

## Lab 24.2: A spoofed-author commit

1. **None.** The object would have the same `tree`, the same `parent`, the same `author` and `committer` lines and the same message, hence the same bytes and the same commit ID. A commit records which name and address were *given*; it has no field for the machine, the account or the credentials that created it. That is the whole point of the exercise.

2. **`--author` is the honest one.** It is how you record a change that somebody else wrote and you are committing, for example a patch you received. Its result says so: the `author` line names them, the `committer` line names you, and anyone can see that two people were involved (`git log --format=fuller`). Setting `user.name` and `user.email` to another person's identity makes both lines name them, and the object claims that they created the commit themselves.

3. **It verified that the commit object is unchanged since it was signed, and that the signing key is listed in your allowed-signers file** (for the principal `you@example.com`). It did not verify that the signer is the person named in the `author` or `committer` line, that the change was reviewed, or that it belongs on `main`. The good signature here is, read correctly, evidence *against* the commit's claim: it proves that the key of `you@example.com` signed a commit that says it was made by Asha.

4. **The file must map each address to the key of the person who really controls that address, and nobody who is subject to the check may be able to change it.** In the lab you wrote the file yourself, which is fine for learning and useless as a control: an attacker who can edit the file adds their key under Asha's address and passes the check. The manual sketches the real options: a file generated centrally from the keys of people with push access, or a file kept in the repository so that only already-trusted committers can change it, in which case changes to that file need the strictest review of all.

5. **One commit: the tip of what was merged.** `--verify-signatures` checks "the tip commit of the side branch", and the commits underneath came along unchecked. A real gate has to examine every commit in the range being added (`git log --format='%H %G? %ae %GS' <old>..<new>`), require a good signature on each, compare signer with author or committer according to the team's rule, and run where developers cannot skip it: in a server-side hook or as a required check on the hosting platform, not on the laptop of the person merging.

6. **Because they are published, and because they are evidence.** Removing them would mean rewriting `main` and force-pushing, which disrupts every clone and destroys the record of what happened; reverts restore the content and leave a history that explains itself. Git cannot say who pushed them: no object records it. The server can: its push or audit log ties the update of `refs/heads/main` to an authenticated account. On GitHub that is the repository's activity and audit data (Chapter 21B). That log, not the commit, is where an investigation starts.
