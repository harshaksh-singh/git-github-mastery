# Module 18 lab answers: Transfer, scale, and performance

Answers to the "Questions" of each lab in the [Module 18 lab manual](../lab-manual/m18-transfer-scale.md). Object IDs and counts are the ones printed in the manual; IDs of commits that you made yourself differ. Every statement about behavior was checked on Git 2.55.0 in the lab sandbox, or is quoted from the local manual pages.

## Lab 18.1: Clone one repository three ways and compare what arrived

1. History questions are answered from commits and trees, and blobs are needed only for content. The blobless clone has all 96 commits and all 284 trees; its 33 blobs are the files of the checkout, and it can fetch any other blob when a command needs one. The shallow clone has one commit and the 20 trees of that snapshot; the same 33 blobs are everything it has, and nothing in it describes how the files came to be.
2. The object is identical to the one on the server, parent line included: an object's ID is the hash of its content, so removing the line would produce a different object with a different ID, and the clone would no longer hold the commit that `main` names. Git instead records the ID in `.git/shallow` and treats commits listed there as having no parents when it walks history. That is also what makes deepening possible: the parent ID is still known and can be requested.
3. Question 2 did: `git blame` compares contents, and the old versions of the file were not local, so each one was fetched (twelve new packs in the transcript). Questions 1 and 3 did not: `git log -- <path>` compares trees, and `git describe` reads commits and tags. What decides it is whether the command needs blob contents that are not among the 33 checked-out files.
4. `--depth` implies `--single-branch`, which wrote the refspec `+refs/heads/main:refs/remotes/origin/main`. `--unshallow` changes depth, not the refspec. `git remote set-branches origin '*'` rewrote it to the wildcard form, and the following `git fetch` created `origin/feature/rerank-cache`.
5. A three-dot diff needs the merge base of the two tips and the trees of both ends. The full and the blobless clone have them; the shallow clone does not, unless it is deepened far enough on both branches, which the job cannot know in advance. The cheapest correct shape is a blobless clone made with `--no-checkout`: `git diff --name-only A...B` compares trees and downloads no blob (Chapter 24, section 24.9).
6. Work in the air: `git log`, `git status`, `git commit`, `git diff --name-only`, `git merge-base`, and `git switch` or `git show` for anything whose blobs were already fetched. Fail in the air: `git blame` or `git log -p` on files whose old versions were never fetched, `git show <old-commit>:<path>`, and `git switch` to a branch that needs blobs you do not have. At the gate: `git backfill`, which downloads the blobs reachable from `HEAD` in batches (and `git backfill <branch>` for other branches you will need).

## Lab 18.2: Cone-mode sparse-checkout

1. Not in the working tree (`ls libs` shows only `schemas`). In the index, with the skip-worktree bit (`git ls-files -t libs/tokenizer` prints `S`). In `HEAD` (`git ls-tree -r HEAD libs/tokenizer`). In the object database (`git cat-file -t HEAD:libs/tokenizer/vocab.txt` prints `blob`), because this was a full clone. A sparse checkout changes only the first of the four.
2. In cone mode a named directory is included with everything below it, and every parent of it is included with the files directly inside it (not its other subdirectories); the top level counts as a parent of everything. If a parent directory holds large files, they are checked out whenever any of its subdirectories is in the cone. The remedy is in the repository layout: do not keep bulky files directly in directories that have many subdirectories.
3. Because the definition belongs to one working tree. A repository can have several linked working trees (Chapter 25), each with its own cone, so `git sparse-checkout` stores the switches in the per-worktree file `config.worktree` and enables `extensions.worktreeConfig` so that Git reads it. The pattern file `info/sparse-checkout` is per working tree for the same reason.
4. `git add` refuses to update index entries outside the sparse-checkout definition and exits 1, so the index was unchanged; `git commit` then compared the index with `HEAD`, found no difference, and reported the two untracked files. The two ways: `git add --sparse <path>`, which stages the file although it is outside the cone, or `git sparse-checkout add pipelines/eval`, which brings the directory into the cone so that a plain `git add` works.
5. A tracked file is removed from the working tree and keeps its index entry with the skip-worktree bit; nothing is lost, and widening the cone writes it back. An untracked file that is not ignored is kept, its directory is kept, and Git warns that the directory "contains untracked files, but is not in the sparse-checkout cone". An ignored file is deleted with its directory, without a warning, if everything untracked in that directory is ignored (the manual's rule, shown in Chapter 24, section 24.5). Only the third case loses data.
6. `git sparse-checkout clean` looks at directories that hold tracked files and lie outside the cone, and removes each such directory whole, with untracked and ignored files inside; it needs cone mode. `git clean -fd` looks at untracked paths anywhere in the working tree, honours `.gitignore` unless `-x` is given, and never removes a tracked file. The dry run of the first is not optional because its unit is the directory: one line "Would remove pipelines/" stands for every file in it, and `--verbose` is the only way to see them before they are gone.

## Lab 18.3: A bundle round trip

1. One line per prerequisite: a minus sign, the ID of a commit that the bundle's pack does not contain but builds on, and its subject. `git bundle verify`, `git fetch` and `git clone` check that the receiving repository has those commits and refuse with "Repository lacks these prerequisite commits" if it does not. The manual adds that such a bundle is a thin pack, so its deltas may refer to objects that only the receiver has.
2. A clone starts from an empty repository, which has every object a full bundle needs because a full bundle needs none ("The bundle records a complete history"). An incremental bundle requires at least one commit, and an empty repository has none.
3. It would have fetched `main` into `FETCH_HEAD` and fast-forwarded the current branch. It would not have updated `origin/main`, so `git status` would report the branch as ahead of its upstream by commits that came from that very upstream, and it would not have created `gateway/v1.2.0`, because a fetch from a URL with one source ref stores no other refs (checked in the sandbox: five tags afterwards, and "ahead 1").
4. The tag recorded "what I have bundled", not "what the other site has". When a bundle is lost, the two differ, and the next bundle is cut from a basis the site never received. A rule that cannot fail this way: move the tag only on confirmation, where the confirmation is the commit ID that the site reports as its `origin/main` after applying the bundle (sent back with the next bundle in the other direction, or by any other channel). Until then, cut every new bundle from the last confirmed basis; it is larger than necessary and always applicable.
5. Reflogs; configuration, including remotes; hooks; the index and the working tree with uncommitted and untracked files; refs that were not named when the bundle was created; unreachable objects; and of the stash at most what `refs/stash` reaches if it was named. A bundle carries refs and the objects they reach, and nothing else.
6. When the receiver can reach the server, and the point is to take the bulk of a large clone from a static file (on a CDN or a file share) instead of making the server compute and send it. The clone unpacks the bundle and then fetches only what is newer from the server. It does not help a site with no route to the server, which is the case this lab is about.

## Lab 18.4: The clone that `scalar clone` builds, made by hand

1. Partial clone and sparse checkout. Partial clone is configured in `.git/config` (`remote.origin.promisor=true`, `remote.origin.partialclonefilter=blob:none`) and leaves out objects: blobs are not downloaded until needed. Sparse checkout is configured in `.git/config.worktree` (`core.sparseCheckout`, `core.sparseCheckoutCone`) with its patterns in `.git/info/sparse-checkout`, and leaves out files: paths outside the cone are not written to the working tree. Either works without the other; together, the blobs that are never checked out are never downloaded.
2. Three: with `--sparse` only the top level is checked out, and it has three files (`.gitignore`, `README.md`, `pyproject.toml`). Nine: the cone added `services/ranker` with four files and `libs/tokenizer` with two, and each needed its current blob. 33: `git backfill --sparse` downloaded every historical version of the files inside the cone, 24 more blobs. That this equals the number of tracked files in the repository is a coincidence.
3. `status.aheadBehind=false` saves the walk that counts how many commits your branch and its upstream each have that the other lacks; you give up the numbers and get "Your branch and 'origin/main' refer to different commits" with a hint to run `git status --ahead-behind`. `fetch.showForcedUpdates=false` saves the check, after a fetch, of whether each updated remote-tracking branch's old tip is an ancestor of its new one; you give up the "(forced update)" marking in the fetch output. The manual of `scalar` calls both checks expensive in large repositories.
4. It downloads the objects that a fetch would download and records the remote's branch tips under `refs/prefetch/remotes/origin/`. It uses a refspec of its own and passes `--no-tags`, so `refs/remotes/origin/*` and tags are untouched. The manual gives the reason: users "expect these refs to stay unmoved unless they initiate a fetch". When you later fetch, only refs have to move.
5. The same state as before the command: the cone still lists two directories, no file of `services/gateway` was written, the index and the working tree are clean. That is the right behavior because the operation could not be completed, and a half-widened cone (a definition that names a directory whose files are absent, or some files without the others) would be a state that no single command repairs.
6. A registration of the enlistment in the global configuration (`scalar.repo`), removed by `scalar unregister`, or by `scalar delete`, which also deletes the directory. Scheduler entries for hourly, daily and weekly maintenance and the `maintenance.repo` entry, unless `--no-maintenance` was given; `scalar unregister` stops scheduled maintenance for the repository, and `git maintenance stop` removes the schedule itself. A file-system monitor daemon watching the working tree, stopped with `git fsmonitor--daemon stop` run inside it. The first two are described from `git help scalar` and `git help maintenance`; the daemon was observed in a contained test on Git 2.55.0 for macOS.
