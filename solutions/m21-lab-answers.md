# Module 21 lab answers: Pull requests, review, and the fork workflow

> **Baseline.** Git 2.55.0 on macOS; GitHub facts as of 1 October 2026. These are answers to the "Questions" of each lab in the [Module 21 lab manual](../lab-manual/m21-pull-requests-forks.md). Write your own answers first. Commit IDs quoted here are those of the replay scripts; commits you made by hand have other IDs. Answers about Part B rest on GitHub's documentation, as cited in the manual and in [Chapter 17](../textbook/ch17-pull-requests.md); where they depend on what you observed, the answer says what to compare your notes with.

## Lab 21.1: A full fork and pull request cycle

1. **Where the fetch ran.** `git -C ../../server/ticket-router.git fetch ...` ran inside the upstream repository and fetched from your fork. Upstream gained the commit `c6c03ef` and the ref `refs/pull/1/head`. No branch moved anywhere. That is the Git content of opening a pull request from a fork: the base repository takes a copy of the head commit under a ref that only it controls. Everything else about a pull request (number, title, reviews) is GitHub data.
2. **Who updates the fork.** Your `git push origin main` in step 7, after the fast-forward to `upstream/main`. A fork is never updated by its upstream. Had you not pushed, the fork's `main` would have stayed at `9a383e5`, every branch you later created from `origin/main` would have started from stale code, and GitHub would have reported the fork as behind.
3. **Why `upstream/main`.** The fork's `main` was one commit behind (`1 0`). A branch from the stale `main` gives a pull request that is behind its base from the first minute: it may conflict, its checks run against a test merge with code you never saw, and under strict required checks it must be updated before it can merge. The commit list would still be right, because it is taken against upstream's `main`.
4. **`1 1`.** The left number counts commits reachable from `upstream/main` and not from `origin/main`: the maintainer's `Start the 1.1 cycle`. The right number counts commits only the fork's `main` has: your stray commit. Both non-zero means the two branches have diverged.
5. **The pull request refs.** Expect `refs/pull/N/head` at your commit, and for a mergeable pull request `refs/pull/N/merge`; the documentation promises the first by name in the checkout instructions and the second through the Actions documentation. You can push to neither: the namespace is read-only, and the documented error is `! [remote rejected] ... (deny updating a hidden ref)`, the same line the local replay produces with `receive.hideRefs`.
6. **`git branch -d` after a squash.** After "Create a merge commit" the branch tip is an ancestor of `main`, so `-d` is satisfied. After a squash it is not. What `-d` then does depends on the upstream of the branch: while `origin/docs/queues` still exists, the branch counts as merged into its upstream and is deleted with a warning; once the remote branch is deleted and pruned, Git compares with `HEAD` and refuses. Lab 22.1 shows both.

## Lab 21.2: A pull request against the wrong base

1. **Three commits.** The commit list is every commit reachable from the head and not from the base. The branch was created from `main`, and `main` had two commits that `release/1.0` lacks (`7e13c3d` and `29be88c`). They are reachable from your branch, so they are listed.
2. **The rule of the loop.** For each candidate base, count the commits in `base..branch`; the base the branch was really built on gives the smallest count, which is the number of commits you wrote.
3. **`git rebase --onto A B C`.** Take the commits that are reachable from `C` and not from `B`, replay them in order on top of `A`, and move the branch `C` to the result.
4. **The rejected push.** The rewritten branch is not a descendant of the branch on the server, so the update is not a fast-forward. `--force-with-lease` is acceptable because the branch is yours, nobody has built on it, and the lease refuses if the server's branch is not where your last fetch saw it.
5. **Noticing the non-repair.** By running the same two commands that predict a pull request: `git log --oneline origin/release/1.0..try/plain-rebase` still listed three commits, and the three-dot diff still showed three files. Success of a rebase says the replay had no conflicts. It says nothing about whether you replayed the right commits.
6. **Which repair.** Change the base when the branch started in the right place and the pull request names the wrong target: the fix belongs where the branch grew. Transplant when the target is right and the branch started in the wrong place.

## Lab 21.3: The squash-then-reuse problem

1. **The merge base.** A merge base is found by following parent links. The squash commit `1b2b8ed` has one parent, `9aa221a`, and no link to the branch, so the newest common ancestor of `main` and the branch is still `9a383e5`. After "Create a merge commit" the branch tip `16d4788` would itself be an ancestor of `main` and therefore the merge base.
2. **Three versions.** Base (`9a383e5`): the file does not exist. `main`: the file as pull request 1 delivered it. The branch: the same file plus four lines. Both sides added the file since the base, with different content, which Git reports as an add/add conflict. Nobody else needed to touch it.
3. **Dropped, then a conflict.** Replaying the first commit on `main` changes nothing, because `main` already has that file with that content, and Git drops a commit that becomes empty. The second commit writes the queue name `"escalation"` on lines where `main` already has the corrected `"escalations"` from the squash. Both sides changed the same lines in different ways relative to the commit's parent: a conflict.
4. **`HEAD~2`.** It would replay the last two commits, the queue-name fix and your new commit. Tried in a sandbox: Git dropped the fix as "patch contents already upstream", because `main` already contains exactly that change, and replayed the new commit. The result is the same one-commit branch. `HEAD~1` says what you mean and does not depend on that detection.
5. **Prevention.** The setting: automatic deletion of head branches after a merge (`gh repo edit --delete-branch-on-merge`). The habit: a new branch from the current `main` for every pull request.
6. **After "Rebase and merge".** The same listing problem: the commits on `main` are new copies, so the old ones are not reachable from it and appear again, and the test merge of a follow-up conflicts in the same way. The repair is easier, though. Tried in a sandbox: a plain `git rebase origin/main` printed "skipped previously applied commit" for each of the three old commits and replayed only the new one, because each old commit has a patch-identical twin on `main`. A squash leaves no such twins.
