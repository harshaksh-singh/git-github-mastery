Spots are given as section heading plus the first six words of the paragraph in `video/scripts/V151-*.md`. Every label is copied from the script. The Dockerfile was not built for the book and no GitHub output was captured: no picture may look like a captured run or registry page. One library scene is already placed (`trees` for the uncommitted line and `git restore`, LIVE TERMINAL DEMO, "Here's the same state in the" and "`git restore` on a path is").

## 1. A tag that was pushed four times

- **Spot.** HOOK, "That tag was pushed four times".
- **Picture.** Four image boxes in a row (four pushes this week) and one label `:latest`.
- **Steps.**
  1. `push-1` to `push-4`: with each push a new image box appears and the label `:latest` slides onto it.
  2. `running`: a "production" marker still points at an earlier box; caption "It names whatever was pushed last, not what is running."
  3. `question`: the question "Which commit is running in production?" over the row, with a question mark on the marker.
- **Why not today.** No scene for labels on images.

## 2. Three kinds of names, each with a twin in Git

- **Spot.** MENTAL MODEL, "There are three kinds of names", through "The digest behaves like a commit".
- **Picture.** Two columns, "image" and "Git", with three rows that pair up.
- **Steps.**
  1. `moves`: "A tag like `main` or `latest`" pairs with "a branch": "a name that moves when someone pushes" (the label visibly slides).
  2. `stays`: "A tag like `0.2.0`" pairs with "a release tag": "meant to stay, and nothing but discipline makes it stay".
  3. `identity`: "The digest" pairs with "a commit ID": "computed from the content, so it cannot name anything else".
  4. `breaks`: one commit, built twice, gives two different digests; caption "neither identifier replaces the other. You record both, together".
- **Why not today.** `hash` shows one content and one ID; it cannot pair two kinds of name or show one input giving two outputs.

## 3. The chain that carries the commit ID

- **Spot.** DIAGRAM, "Follow the commit ID along the" (it replaces the ASCII drawing); a return at PRODUCTION EXAMPLE, "The team chooses the first of".
- **Picture.** Four boxes left to right, built in order, with a label on every arrow.
- **Steps.**
  1. `commit`: box "commit on main"; under it `git describe --tags --match 'v*' --dirty`: "says what the commit is called, and whether the tree IS the commit".
  2. `build`: arrow "commit ID in the checkout"; box "build (clean runner checkout)".
  3. `image`: arrow "commit ID in tag `sha-<short ID>` and label"; box "image", "digest: sha256", "tags: names".
  4. `deployment`: arrow "digest + commit ID in the deployment record"; box "deployment by digest", "environment: production".
  5. `backwards`: a highlight travels right to left: "deployment, digest, the commit recorded with it, and `git describe` for a name a human can use".
- **Why not today.** A `text` fence is drawn line by line; the boxes cannot arrive in order or be read backwards.

## 4. Anatomy of a description

- **Spot.** LIVE TERMINAL DEMO, Step 1, "The full ID of HEAD. Then"; then Step 2, "`-dirty`. Git is saying that the"; then Step 3, "After the restore the description is".
- **Picture.** The string `v1.1.0-2-g57c8425`, very large, over a short commit row: the tag `v1.1.0`, two commits, `HEAD`.
- **Steps.**
  1. `tag`: `v1.1.0` lights up with the tag on the row: "The last release".
  2. `count`: `2` lights up with the two commits after the tag: "two commits since".
  3. `id`: `g57c8425` lights up with `HEAD`: "the abbreviated ID".
  4. `dirty`: the suffix `-dirty` is appended in red: "the working tree differs from HEAD".
  5. `release`: the tag `v1.2.0` lands on `HEAD`; the string collapses to `v1.2.0`: "the commit's name is the version, with nothing after it".
- **Why not today.** No scene takes a string apart, and `graph` needs the IDs of the two commits between the tag and `HEAD`, which this script's transcript does not print (only `57c8425`).

## 5. The trap: a release that triggers nothing

- **Spot.** CONCEPT, "**The trap.** B, it doesn't. Events", through "Why does GitHub do this? You"; again at PRODUCTION EXAMPLE, "There is none. The release was".
- **Picture.** Two workflow cards with an event arrow between them.
- **Steps.**
  1. `creates`: the first workflow creates a release "with the job token"; the event arrow leaves it, carrying a `GITHUB_TOKEN` chip.
  2. `blocked`: the arrow stops in front of the second workflow, `on: release`, with a red cross; caption "Events caused by the `GITHUB_TOKEN` do not start new workflow runs, with narrow exceptions."
  3. `why`: a loop arrow from a workflow back to itself, crossed out: "a workflow that pushes with its own token and thereby starts itself again".
  4. `way-out-1`: the two cards merge into one workflow with two jobs joined by `needs`.
  5. `way-out-2`: the arrow carries "a GitHub App token" and passes.
- **Why not today.** `ci` draws one workflow and no event caused by a run.
