# Module 29 lab answers: GitHub Actions security

> **Baseline.** Git 2.55.0 on macOS; GitHub facts as of 1 October 2026. These are answers to the "Questions" of each lab in the [Module 29 lab manual](../lab-manual/m29-actions-security.md). Write your own answers first. Answers about GitHub rest on its documentation, cited in [Chapter 21A](../textbook/ch21a-actions-security.md); nothing here was observed on GitHub by the author. The detailed analysis of the five teaching workflows is in [a separate file](m29-vulnerable-workflows.md).

## Lab 29.1: Find and fix five planted weaknesses

1. **The five findings.** `v1` line 32: expression injection in a `run` step; anyone who can open an issue. `v2` lines 12, 28 and 29: a privileged trigger that checks out and runs the pull request's code; anyone who can open a pull request. `v3` line 15: `write-all`; no direct trigger, it multiplies another compromise. `v4` line 28: an action by mutable tag; whoever controls the tag. `v5` lines 18 and 19: a secret in workflow-level `env:`; any code in any job. Full analysis: [the solutions file](m29-vulnerable-workflows.md).
2. **No access needed versus prior compromise.** `v1` and `v2` need only a GitHub account: opening an issue or a pull request is enough, and `pull_request_target` skips the first-time-contributor gate. `v3`, `v4` and `v5` need something else to go wrong first (a compromised action, tag or dependency) and then decide how much that costs you. Rank the first group higher, and do not dismiss the second: the tj-actions and Trivy incidents were of the second kind.
3. **Why `v2`'s care is not enough.** `persist-credentials: false` and narrow `permissions` limit what the token can do. They do not change whose code runs. The contributor's code executes in a job that belongs to the base repository's trust domain, with a write-capable token available to its steps. The TanStack post-mortem is the proof that a read-only token did not contain that pattern, because cache writes did not use the job token.
4. **Which expressions in `v1`.** Dangerous: the title on line 32, because it is attacker-chosen text placed into script source. The issue number on the same line is inside the script but is a number assigned by GitHub. The three under `env:` (token, repository name, issue number) never enter script text. The rule is where the value lands and who chooses it.
5. **The exposure in `v5`.** Every process in the `lint` and `test` jobs has the deployment token in its environment: third-party actions, the package installer, each dependency's code under test. Not printing it only keeps it out of the log. The fix narrows the set of code that holds it to one step.
6. **Why `v3`'s token matters.** It runs code the team did not write: two actions and the whole dependency tree. Least privilege is not about the trigger; it is about what a compromise of that code is worth. A nightly job is also the run nobody watches.
7. **Policies.** "Require actions to be pinned to a full-length commit SHA" in the allowed-actions policy would have failed `v4`. From 2 November 2026 the default event rule of workflow execution protections blocks `pull_request_target` in affected public repositories unless a maintainer allows it, which would stop `v2` from running.
8. **On `grep`.** A line pattern does not parse YAML: it missed a script that starts on the line after `run: |`, and it would also miss expressions in action inputs that are evaluated as code. Use it to collect evidence quickly, as you did. For a gate in CI, use tools that parse workflows: CodeQL for workflows through code scanning, or zizmor or actionlint (neither is installed in this course's environment, so you run them yourself).

## Lab 29.2: Justify every control of workflow 12

1. **The controls.** The nine with numbered comments: read-only top-level `permissions`; commit-pinned actions; `persist-credentials: false`; the title only under `env:`; the deployment condition (push to `main`); `environment: staging`; `id-token: write` on one job; `cache-mode: none` on that job; OIDC in place of a stored key. Without a numbered comment: the `pull_request` trigger itself; `permissions: {}` on the title job; `timeout-minutes` on every job; the two `concurrency` blocks, where the deployment group never cancels a running deployment; the fixed runner label `ubuntu-24.04` in place of a moving `-latest` label; and the absence of any stored secret.
2. **`{}` on `pr-metadata`.** The job checks nothing out and calls no API, so it needs no scope at all. It is also the one job that handles attacker-controlled text. If the `env:` control were ever removed by mistake, an injection there would hold a token that can do nothing.
3. **Variable versus title.** Two differences. Who sets it: a repository variable is set by people with access to the repository's settings; a title is set by anyone. Where it lands: an action input is passed as a value, and the workflow generates no script from it. The title in a script is outsider text placed into source code.
4. **What protects `main`.** Not the workflow. A ruleset on the default branch that requires a pull request and review (Chapter 18), and a code-owner rule for `.github/workflows/` so that the workflow cannot be weakened without the owners (Chapter 19, section 19.8). The workflow's condition is only as strong as the rule that guards the branch.
5. **Without `environment: staging`.** The subject would take the branch form, `repo:ORG/REPO:ref:refs/heads/main` (or its immutable variant with IDs), where it was `repo:ORG/REPO:environment:staging`. An exact-match trust policy on the environment subject would refuse the token, which is the safe failure. The risk is the opposite repair: loosening the policy to a wildcard so that it works again.
6. **Three mechanisms.** A code-owner review requirement on `.github/workflows/`; the organization policy that requires full commit pins, which would fail the run; a workflow scanner as a required check (CodeQL's `actions/unpinned-tag` query, zizmor's `unpinned-uses` and `artipacked` audits). Dependabot would later propose the pin again, but that is repair and not prevention.
7. **Not protected.** A malicious commit that someone pins on purpose, or an unpinned action nested inside a composite action. A compromised dependency in `uv.lock` running in the test job (it gets a read-only token and no secrets, which is the mitigation). A trust policy in the cloud account that is wider than the workflow assumes. A maintainer account with write access pushing a different workflow.

## Lab 29.3: Review a pull request that changes workflows

**A model review.** Verdict: request changes. Summary for the author: "The goal is right, and fork contributors should see coverage. This change gets there by running fork code with our write token, our PyPI token and our own runner, which is the pattern behind several published compromises; I have proposed a design below that gives the same comment without that, and I am glad to pair on it."

| File and line | Severity | Finding | Requested change |
|---|---|---|---|
| `ci.yml` 4, 22, 23 | Critical | `pull_request_target` with a checkout of the pull request's head commit, then `uv sync` and `pytest` on it: fork code runs with the base repository's token and secrets, without the approval gate. `allow-unsafe-pr-checkout: true` switches off the refusal built into checkout v7 | Keep `pull_request`. Remove `ref` and the flag |
| `ci.yml` 18 | Critical | A self-hosted runner for a workflow that pull requests trigger: outsider code on our machine, which is not ephemeral by default | Stay on GitHub-hosted runners for pull request CI |
| `ci.yml` 12 to 14 | Critical | Two secrets in workflow-level `env:`, one of them the PyPI token, visible to every step including fork code and the remote installer. CI does not publish | Remove both from this workflow |
| `ci.yml` 8 to 10 | High | Top-level `contents: write` and `pull-requests: write` for all jobs | `contents: read` at the top; `pull-requests: write` only on a job that comments and runs no fork code |
| `ci.yml` 30 | High | `${{ github.head_ref }}` inside a script: a branch name is attacker-chosen text | Pass it through `env:` |
| `ci.yml` 28 | High | A remote script piped into a shell: unpinned code, the Codecov class | Install a pinned, checksummed release, or drop the step |
| `ci.yml` 31 | High | A new third-party action by tag, handed the token | Pin to a commit from the action's own repository; justify the dependency |
| `ci.yml` 20 to 23 | Medium | `persist-credentials: false` was removed | Restore it |
| `ci.yml` 17 to 19 | Low | `timeout-minutes` was removed | Restore it |
| `release.yml` (absent line) | High | No `permissions` block: the token follows the repository default | Add `permissions: contents: read` |
| `release.yml` 11 | High | `actions/checkout@v7` in the job that publishes | Pin; add `persist-credentials: false` |
| `release.yml` 14 | High | `enable-cache: true` in a publish job: a restored cache runs next to the publishing credential | Remove the input and set `cache-mode: none` on the job |
| `release.yml` 17 | High | A long-lived registry token, passed on a command line, with no environment in front of it | An environment with reviewers; OIDC trusted publishing in place of the token |
| `release.yml` 4, 5 | Medium | Any pushed tag matching `v*` publishes; nothing restricts who may create such a tag | A tag ruleset, and an environment with deployment tag rules |

Acceptable lines that look alarming: `token: ${{ secrets.GITHUB_TOKEN }}` on line 33 is the job token passed as an action input, which is the normal way to hand it to an action (the problem is the action's reference and the token's scope, not this line). `uv sync --locked` and `uv run pytest` are right under `pull_request`.

1. **Order, and the first fix.** As in the table. Fix the trigger first (line 4, with 22 and 23): it is the line that lets a stranger's code into a privileged job, and most other findings are dangerous mainly because of it. The self-hosted runner is a close second, because its damage can outlast the job.
2. **A design without the findings.** `ci.yml` stays on `pull_request` with a read-only token and no secrets; it runs the tests with coverage and uploads a small text file with the percentage as an artifact. A second workflow on `workflow_run` (completed) with `pull-requests: write` downloads the artifact, checks that the content is a number in range, and posts the comment. It never checks out or executes pull request code and never interpolates artifact content into a script. No coverage service token is needed for that.
3. **The combination.** Fork code in a privileged trigger (4, 22, 23) plus a publish secret in scope (14) plus a write token (9): an outsider's pull request can reach the PyPI token. Nx had the same shape with an injection as the entry point; TanStack had the privileged build of fork code and a path to the publishing identity through the cache. Line 30 adds the Nx entry point as well.
4. **The token of `release.yml`.** Whatever the repository's "Workflow permissions" setting says: read access to `contents` and `packages` for repositories created since February 2023 or set to the restrictive default, read and write for everything in older repositories that were never changed. The answer depends on the creation date and on the organization's setting, which is why the file should say it.
5. **Line 17.** Not injection: a secret's value is chosen by the repository's administrators, not by an outsider. It is still poor: the expression places the secret into the script text and on a command line, where other processes on the runner can see it, and the credential is long-lived. Better: pass it through `env:` to a tool that reads it from the environment. Best: no stored token. PyPI's own advice after the Ultralytics incident is to use Trusted Publishers and remove unused API tokens ([PyPI](https://blog.pypi.org/posts/2024-12-11-ultralytics-attack-analysis/)).
6. **What checkout v7 reveals.** The head checkout under `pull_request_target`. Without the flag the action refuses to fetch the fork's commit and the job fails, so the author had to add `allow-unsafe-pr-checkout: true`, a line whose name is, in the changelog's words, "intentionally named to be easy to spot in code review and static analysis". It does not cover `git fetch` in a `run` step.
7. **Green CI.** The checks ran the old or the new workflow on the author's own branch, as a collaborator, with nothing hostile in it. CI tests whether the workflow works. It does not test who else can make it work for them. For `pull_request_target` the file that runs is the one on the default branch, so the change was not even exercised before merge.
8. **Settings.** A code-owner rule for `.github/workflows/` with a ruleset that requires code-owner review (Chapter 19, section 19.8); the allowed-actions policy with required commit pinning, which fails lines 31 and 11; an event rule that disallows `pull_request_target`; the organization setting that disables repository-level self-hosted runners or a runner group that excludes this repository; code scanning for workflows as a required check.
