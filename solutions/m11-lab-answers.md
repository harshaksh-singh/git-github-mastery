# Module 11 lab answers: History investigation and forensics

Answers to the "Questions" of [Labs 11.1 to 11.7](../lab-manual/m11-history-forensics.md). Write your own answers first. Commit IDs are those of the replays (`labs/run ch14a/<lab>`). Section numbers refer to [Chapter 14A](../textbook/ch14a-history-investigation.md).

## Lab 11.1: Trace a line across a rename

1. **Why `-w` did not help.** `-w` makes blame's diffs ignore whitespace and nothing else. On this line the formatter also replaced `r['prediction']` by `r["prediction"]`. The line differs in non-whitespace characters, so the diff still reports it as changed by `9c8df98`.
2. **Where `run_eval.py` comes from.** From blame's own rename detection. Walking back, blame reached `d38a5aa`, whose parent has no `scorekit/runner.py`. It looked for a file in the parent that is similar enough, found `run_eval.py`, and continued there. The column shows the name the file had in the commit that the line is attributed to. It is an inference from content, made again on every run.
3. **What each command matches.** `git log -- scorekit/runner.py` matches a path: commits whose tree differs from the parent's at exactly that name. The name first exists in `d38a5aa`. `--follow` matches a file as rename detection identifies it, so at `d38a5aa` it switches to the old name and reaches `633e3e6`.
4. **The unchanged `load` function.** Similarity is computed over the whole file, not per function. The rewrite kept about a third of the content: the transcript shows `R033` with `-M30%`. The default threshold is 50%, so the pair is reported as a deletion and an addition. `-M30%` on the command line detects it, but `git log --follow` and `git blame` do not take your threshold from a remembered habit; they use the default.
5. **Two commits instead of one.** For a reviewer: the first commit is a pure rename (100% similar) and needs no reading; the second is a diff of `cli.py` against the old content, in which the unchanged `load` function appears as context at most. For blame: surviving lines keep their original commits. For a later bisect: a regression from the rewrite lands on a commit that contains only the rewrite. A merge with a branch that still edits `runner.py` also benefits, because merge uses the same rename detection.
6. **`log.follow`.** With it, `git log` acts as if `--follow` were given whenever exactly one path is named. The manual states the limits: it "cannot be used to follow multiple files and does not work well on non-linear history" (section 14A.10). It also inherits the similarity heuristic, so it stops at a rename-plus-rewrite like the one in this lab.

## Lab 11.2: Find when a string was removed

1. **What `-S` tests.** For each commit and each file it changed: is the number of occurrences of the string in the file different before and after? `b4b066b` took it from 0 to 1, `ca7e2b7` from 1 to 0. The two commits in between rewrote the line and left exactly one occurrence, so the count did not change.
2. **The formatter under `-G`.** Not a false positive for what `-G` asks. The formatter removed the line with single quotes and added the line with double quotes; both lines match the expression. It is noise for the question "who removed the message" and a correct answer to "which commits touched a line that mentions it".
3. **Choosing the string.** The shortest string that is specific to the thing and unlikely to be edited around: the message text or an identifier. Leave out quotes, parentheses, arguments and indentation. And read the patch of every hit (`-p`, or `git show`) before you name a commit.
4. **Without `--all`.** The walk starts at HEAD. The removal would be missed if it happened on a branch that is not merged (add `--all`), in a commit that was later rebased or amended away (add `--reflog`), or if you had limited the search to a path that the string was not in.
5. **Deliberate or not.** The body of the commit message gives the reasoning ("A silent skip changed the denominator of every average"), and the patch replaces the message by a `raise`. With a message like "cleanup" you would look at the code review that led to the commit, ask the author, and check with `git log -L` whether the line was moved instead of removed.
6. **Moved and reworded in one commit.** `-S` counts per file: the old file goes from 1 to 0, so the commit is still reported for the old string, and `-S` with the new wording reports the same commit for the new file. `-G` reports it as well. Add `-p --pickaxe-all` to see the whole commit and recognize the move.

## Lab 11.3: Find a deleted file

1. **Why the parent.** A commit's tree is the state after the commit. The deleting commit is the first whose tree has no entry for the path. Its parent is the last one that has it.
2. **Which tree was written.** The working tree only, which is why the file showed as untracked (`??`). `git restore --source=d9d075d~1 --staged --worktree -- scorekit/bleu.py` writes the index and the working tree; the file then shows as `A`, staged.
3. **The extra commit.** `d369eac` "Add experimental BLEU scorer". At that time the file was `bleu.py` at the top level, a path that `scorekit/bleu.py` does not match. The pattern `'*bleu*'` matches both names. No rename detection is involved; it is plain path matching with a wildcard.
4. **Revert instead.** `git revert d9d075d` creates a commit that undoes the whole deletion commit: it brings back the file and also the line in `docs/metrics.md`. Prefer it when the deletion itself was the mistake and the shared branch should say so. Prefer `git restore --source` when you want the content for something new and the deletion was right for `main`.
5. **Deleted paths between two points.** `git diff --diff-filter=D --name-only v0.1.0 main`. It compares two snapshots, so it cannot tell which commit deleted the file, who did it, or why, and a file that was both added and deleted between the two points does not appear at all.
6. **Equal blob IDs.** The content was already in the object database. The new commit added a commit object and new tree objects for the directories on the path; no new blob ([Chapter 2](../textbook/ch02-mental-model.md)).

## Lab 11.4: A manual bisect

1. **The 9.** Twenty candidates. Git chose `074d492`, which together with its ancestors accounts for ten of them. If the verdict is bad, those ten remain, and the tested commit is one of them. If it is good, the other ten remain, and the known-bad tip is one of them. Either way nine commits have no verdict yet (section 14A.20).
2. **HEAD and the branch.** HEAD was detached at the commit under test. `main` did not move; bisect never moves a branch. A commit made during the session would sit on the detached HEAD and become unreachable from any branch at the next checkout, findable only through the reflog ([Chapter 7](../textbook/ch07-branches.md), section 7.7).
3. **A crashing commit that can be judged.** The test imports `scorekit.metrics` and calls one function. The crash is in the runner's option handling, which the test never executes. With the runner as the test there is no verdict for that commit, and the right command is `git bisect skip`.
4. **Why bisect cannot notice.** It assumes one transition: every descendant of a bad commit is bad. After `c0c9a30` was marked bad, its descendants were no longer candidates and were never tested, and the true culprit was among them. Every later verdict concerned ancestors of `c0c9a30`, and "all of them good" is perfectly consistent with "`c0c9a30` is the first bad one".
5. **Replay.** Replay re-applies recorded verdicts without running any test. Fourteen steps of ten minutes are more than two hours; with a wrong verdict at step two, replaying the first verdict costs nothing and you redo only the steps after it. The log is also a record you can attach to the incident.
6. **The smallest counterexample.** `token_f1("ha ha", "ha ha")`: identical answers with a repeated word. The multiset overlap is 2 and the score 1.0; the set overlap is 1, precision and recall are 0.5, and the score is 0.5. The fix restores the `Counter` intersection, and this assertion goes into the test suite with it.

## Lab 11.5: An automated `git bisect run`

1. **The protocol.** 0 is good (old); 1 to 127 except 125 is bad (new); 125 is "cannot be tested, skip"; anything else aborts the run. The manual explains the choice of 125 as "the highest sensible value to use for this purpose, because 126 and 127 are used by POSIX shells to signal specific error status".
2. **Scripts outside the repository.** Every step checks out another commit, and tracked files are replaced by that commit's versions. A script committed last week does not exist in older commits; running it there fails with "No such file or directory" and status 127 (section 14A.21 shows what Git does then). A script that does exist in old commits may be an older version that tests something else.
3. **Two questions.** The test given: "does the runner exit with status 0 on the smoke set?" The test meant: "does the runner report `exact_match=0.800` on the smoke set?" They agree on every commit except the two in which the runner crashes, and that was enough.
4. **When "skip" hides the regression.** When the regression is itself a failure to produce a score line: then every bad commit is skipped and bisect ends with a list of skipped candidates. Also when the output format changes for an unrelated reason, so that the pattern no longer matches in a range of commits.
5. **A noisy metric.** Compare numerically against a threshold placed between the two levels, far from both; run the evaluation more than once per commit and use the mean, with fixed seeds where possible; and exit with 125 when the result falls inside the noise band, so that an unclear run becomes a skip and not a verdict.
6. **Candidates and paths.** Twenty, as `git rev-list --count v0.1.0..main` printed. With `-- scorekit/text.py` only the commits that touch that path are considered; run `git rev-list --count v0.1.0..main -- scorekit/text.py` to see that there are four. The risk: if the cause is in another file, the true culprit is not a candidate, and bisect reports the nearest candidate after it.

## Lab 11.6: Blame through a reformatting commit

1. **What `-w` recovered.** Lines 20, 21, 23 and 28 went back to earlier commits: the formatter changed only their indentation. Lines 22, 24 and 25 stayed with `9c8df98`: they contain string literals whose quotes the formatter changed, a difference that is not whitespace.
2. **A line with no counterpart.** It cannot be passed to the parent, so it stays attributed to the ignored commit. The manual documents `blame.markUnblamableLines` for marking such lines with `*`. The formatter in this repository added no lines of its own, so the lab has no example.
3. **File committed, key local.** A teammate who clones tomorrow has the file and not the setting; their blame shows the formatter until they run `git config set blame.ignoreRevsFile` themselves, or a setup script does. GitHub's documentation says its blame view hides the revisions listed in a file named `.git-blame-ignore-revs` in the root of the repository, with no configuration (section 14A.17).
4. **The failure at `v0.2.0`.** The setting names a file in the working tree, not an object in history. At `v0.2.0` the working tree does not contain that file, and blame treats a configured file that cannot be opened as a fatal error. With the `:(optional)` prefix, Git treats the setting as absent when the file does not exist.
5. **Squash and force-push.** The formatter commit gets a new ID. The listed ID no longer occurs in the history that blame walks, the entry matches nothing, and blame shows the formatter again, with no error. Add the ID after the commit has reached the shared branch, and check it after any history rewrite.
6. **Format plus fix.** No. Ignoring the commit hides everything in it. The lines of the bug fix would be attributed to whoever touched them before, with the wrong author, date and message, marked with `?` at best. Split such a commit into the formatting and the fix, and list only the formatting.

## Lab 11.7: Line history with `git log -L`

1. **Where the function ends.** Git takes the first line that it regards as a function header and that matches the expression, and ends the range before the next function header. Function headers are found the same way as the text after `@@` in hunk headers. For a language where the default guess is poor, assign a `diff` driver with a language-specific pattern through `.gitattributes`, or give the range as two regular expressions or two numbers.
2. **Across the renames.** When the path is absent from a parent, `git log -L` runs rename detection, as `--follow` does, and continues in the file it finds. A rename combined with a rewrite below the similarity threshold would have stopped it.
3. **Two meanings of line 14.** `git log -L 14,14:<file>` reads the file as committed in the starting revision, HEAD. `git blame -L 14,14 <file>` without a revision reads the working tree file, including uncommitted edits.
4. **Who removed the Counter-based overlap.** `git log -L` answers directly: its newest patch shows the old line with `-` and the new one with `+`, in `ec4fad7`. `git log -S'Counter(pred)'`, limited to the names this file has had, also answers: it lists the commit that added the expression and the one that removed it. `git blame` shows `ec4fad7` on the replacement line, which is right here because the line was replaced; had the line been deleted without a replacement, blame would have had no row for it.
5. **No pathspec.** `-L` names its file inside the option and follows it across renames by itself; a pathspec would restrict the walk to a fixed name and contradict that. The manual says: "You may not give any pathspec limiters." The file is restricted by the `:<file>` part of the option.
6. **A deleted function.** The range must exist in the starting revision, so start from a commit that still has the function: `git log -L :name:file <commit>`. Find that commit with `git log -S'def name' --oneline`, whose newest hit is the removal; its parent is the starting point, as in Lab 11.2.
