# Work packages, wave 2 — exercises, assessments, interview material, capstone, references

The textbook (chapters 1 to 30), the lab manual and the lab answers exist. Wave 2 builds everything the learner uses to practise and to be tested, and the reference material. Each package is owned by one author; write only the files listed for your package.

## Rules for every wave-2 package

1. Read `authoring/STYLE_GUIDE.md` completely first; it is binding (accuracy protocol, snippets, lab clock, lessons learned, resumable increments).
2. The textbook is the source of truth. Every answer, every expected output and every command in your material must be backed by a textbook section, a lab, or a script you run yourself. Cite the chapter and section in answer keys (for example "Chapter 8, section 8.6"). Find sections with `grep -n '^## ' textbook/*.md`. Do not introduce facts that the textbook does not contain unless you verify them the same way the textbook authors did (run it on Git 2.55.0, or source it from the Phase 0 report, the research notes or an official page, with the link).
3. Questions and answers are in separate files. A learner must be able to open the question file without seeing any answer. Question files never contain answers, hints that give the answer away, or object IDs that reveal a solution.
4. Anything that claims a specific Git output (command-prediction questions, "what does this print") must come from a script that was run: write it under `labs/<your dir>/`, build it with `tools/build-demos.sh <dir>`, and place the output in the answer file through a snippet marker. In the question file, show the setup commands and ask for the prediction.
5. Generated practice repositories follow the generator protocol in `authoring/WORK_PACKAGES.md` ("Generated sandboxes"): `generate.sh` using `sandbox_begin <group> <name>`, a `SYMPTOMS.md` or task card, a read-only `check.sh` that exits 0 when the learner's end state is right, and a replay script under `labs/<your dir>/` that sources the generator with `LAB_REPLAY=1` and captures the model solution. Verify that each `check.sh` fails on the fresh state and passes after the replayed solution. Look at `incidents/01-hard-reset/` and `labs/incidents/` for a finished example.
6. GitHub-side questions are answered from the textbook and the documentation it cites; no GitHub output is shown and `gh` is run only with `--help`.
7. Difficulty levels for exercises: Level 1 follow instructions; Level 2 the goal and limited hints; Level 3 a situation to diagnose independently; Level 4 symptoms only, in a generated repository; Level 5 a production incident with incomplete and partly misleading evidence. Label every exercise with its level.
8. Tone of interview and gate material: a strict, fair CTO. No praise, no trick questions that hinge on trivia; questions test mechanism, diagnosis and judgment.
9. Finish with: `labs/verify-all.sh <your dirs>` green (also with a fresh lab root), `python3 tools/check_course.py <your files>` with no problems, and the hand-back report of style guide section 10. Save to disk in small increments.

## X4 — The nine mastery gates

- **Files:** `assessments/gate-1-fundamentals.md` … `gate-9-production-debugging.md` (nine files: fundamentals 85%, branching 90%, merge-and-rebase 90%, recovery 90%, internals 85%, github 85%, actions 85%, security 90%, production-debugging 90%), `assessments/README.md` (how gates are taken and scored), `answer-keys/gate-N-*.md` for each, generators under `assessments/gen/gate-N-<name>/`, scripts under `labs/gates/`.
- **Each gate has four parts** with the roadmap's weights: Concepts 30% (written questions that require mechanism), Prediction 20% (state plus command: predict output and new state; real outputs in the key), Hands-on diagnosis 30% (one or two generated broken repositories with `check.sh`; for GitHub, Actions and security gates this part is a diagnosis of provided files and described situations), Oral interview 20% (six to eight questions, asked one at a time). Give points per item so that the total is 100, the pass rule (threshold overall and at least 70% in each part), and a remediation map from each item to the chapter section to restudy. Provide a variant B of the hands-on part for retakes. The answer key has model answers, marking guidance with what earns partial credit, and the common wrong answers.
- **Coverage per gate:** as listed in section 4 of `curriculum/Git and GitHub mastery roadmap.md`.

## X5 — The final knowledge test

- **Files:** `assessments/final-test.md`, `answer-keys/final-test-answers.md`, generators under `assessments/gen/final-<name>/`, scripts under `labs/final/`.
- **Content:** eighteen sections in this order: 1 Fundamentals, 2 Git internals, 3 Branching, 4 Merge, 5 Rebase, 6 Undo, 7 Recovery, 8 Remote workflows, 9 GitHub, 10 Pull requests, 11 GitHub Actions, 12 Security, 13 Open source, 14 AI/ML workflows, 15 Production incidents, 16 Debugging, 17 Architecture, 18 CTO interview. Across the test use every item type: multiple choice (at least 60 items, four options, one correct, distractors built from the documented misconceptions), command prediction, debugging, diagram questions (draw or read a commit graph), output interpretation (a real transcript; explain what happened), practical labs (generated repositories with `check.sh`), incident response, and oral questions. About 250 items in total with points, a scoring sheet per section, and a time budget. The answer key is a separate file with explanations and textbook references. Do not reuse gate items; different scenarios.

## X6 — Interview guide and CTO question bank

- **Files:** `interview/senior-engineer-interview-guide.md` (8,000-10,000 words), `interview/cto-question-bank.md` (questions only), `interview/cto-question-bank-answers.md` (model answers), `interview/interview-mode-protocol.md` (short: how an oral session is run and graded).
- **Question bank:** at least 400 questions, numbered, grouped by the eighteen areas of the final test and, inside each area, ordered from foundational to principal-level. Include every example question from the learner's brief: why a rebase changes commit hashes; what exactly a branch is; what HEAD is; the difference between HEAD, a branch and a remote-tracking branch; why `reset --hard` does not necessarily delete commits permanently; how the reflog helps; why a commit can become unreachable; what happens during a three-way merge; why Git can merge two files incorrectly from a human perspective; why `--force-with-lease` exists; why force-push can be dangerous; revert versus reset; why cherry-pick creates a new commit; why a pull request can show unexpected commits; `..` versus `...`; how Git stores data; what a blob, a tree and a commit object are; what reachability is; what garbage collection is; how to recover a deleted branch; how to investigate a leaked secret; how to secure GitHub Actions. Each question has a harder follow-up.
- **Answers file:** for every question a model answer of 60 to 180 words that a strong candidate could say aloud, the key terms a grader listens for, the most common weak answer, and the textbook reference. Answers must agree with the textbook; where the textbook shows a surprising real behavior, use it.
- **Interview guide:** how senior and staff Git and GitHub interviews are conducted and what is being assessed; the structure of a strong answer (state, mechanism, evidence, fix, prevention); twenty fully worked answers at three quality levels (weak, adequate, strong) with commentary; scenario and system-design prompts (branching and governance for a described company, CI security review, incident walk-throughs) with what a strong response covers; a self-assessment rubric on correctness, depth, terminology, reasoning, practical understanding and production awareness; a four-week preparation plan.

## X7 — The capstone production simulation

- **Files:** `capstone/README.md` (the brief: the fictional company, the team, the repository, the rules of the simulation), `capstone/setup.sh` (builds the company repository deterministically: a bare "server", clones for you and for teammates, a main branch, feature branches, release tags, CODEOWNERS, workflow files, a simulated pull-request history), `capstone/stage-NN-<slug>/` for each incident with `inject.sh` (applies the incident on top of the current state), `BRIEFING.md` (what the learner is told) and `check.sh`, `capstone/EVALUATION.md` (the rubric: Git knowledge, GitHub knowledge, debugging ability, production judgment, security awareness, recovery skills, engineering communication, each with observable evidence and a four-level scale), `capstone/DELIVERABLES.md` (what the learner hands in per stage: evidence log, root cause, recovery, verification, prevention, a message to the team and to the CTO, and a final postmortem), `solutions/capstone-walkthrough.md`, replay scripts under `labs/capstone/`.
- **Stages, one at a time and cumulative:** 1 a bug reaches production (find the commit with bisect and blame, fix by revert); 2 a merge conflict between two feature branches that is easy to resolve wrongly; 3 a leaked dummy secret in history, already pushed; 4 failed CI (paper diagnosis from provided workflow files and a described run, plus the Git cause shown locally); 5 an accidental `git reset --hard` on unpushed work; 6 a deleted branch that a teammate needs; 7 a rebased and force-pushed shared branch with a broken pull request (the eleven-step recovery); 8 a production hotfix from a release tag with a backport. Each stage must work when taken in order from the state the previous stage's solution leaves, and `setup.sh --stage N` must be able to build the state for stage N directly so that a learner can retake a stage. The replay scripts play all eight stages end to end and their transcripts feed the walkthrough.

## X8 — Reference set: command references, cheat sheets, glossary, checklists, professional configuration

- **Files:** `reference/git-command-reference.md`, `reference/github-reference.md`, `cheatsheets/git-cheat-sheet.md`, `cheatsheets/github-cli-cheat-sheet.md`, `cheatsheets/github-actions-cheat-sheet.md`, `cheatsheets/security-cheat-sheet.md`, `reference/command-safety.md`, `reference/professional-git-configuration.md`, `reference/glossary.md`, `reference/references.md`, `revision/revision-checklist.md`, scripts under `labs/ref/` where you need to verify a command or an alias.
- **Git command reference:** every command taught in chapters 1 to 14D and 22 to 26, grouped (daily use, history, branches, remotes, undo, recovery, debugging, advanced, plumbing), each with: purpose, synopsis of the forms taught, an example, the risk label, a common mistake, how to recover, and the chapter section. Collect commands by reading the chapters' "Command safety" tables and section headings; do not add commands the textbook does not teach.
- **Cheat sheets:** the table format the learner asked for: Command, Purpose, Example, Risk, Common mistake, Recovery; grouped by daily use, history, branches, remotes, undo, recovery, debugging, advanced; separate sheets for the GitHub CLI, GitHub Actions and security.
- **GitHub reference:** concepts, limits, roles, rule types, merge methods, token types, events and what they check out, with sources, compiled from chapters 15 to 21B.
- **Command safety:** all 🔴 and 🟡 commands of the book in one table: what it changes, what it can destroy, how to preview, how to recover, when it is appropriate.
- **Professional configuration:** a recommended `~/.gitconfig` built from Chapter 14B's settings table, every line explained (what it does, why it matters, downside, optional or not, personal or team), verified by loading it in a sandbox (`git config list` must accept it), plus the aliases, each run.
- **Glossary:** at least 250 terms, each defined in one to three sentences consistent with the textbook and with `git help glossary`, with the chapter where it is taught; mark terms that are GitHub's and not Git's.
- **References:** the consolidated source list per module: primary sources, secondary sources, videos (only those in the Phase 0 report, with their caveats), further reading. Take links from the chapters' "Sources" sections and the report; add none.
- **Revision checklist:** one page per mastery gate: the statements a learner must be able to explain, the commands they must be able to predict, and the labs to redo.
