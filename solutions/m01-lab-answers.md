# Module 1 lab answers: What Git actually is

Answers to the "Questions" of each lab in the [Module 1 lab manual](../lab-manual/m01-what-git-is.md). Blob and tree IDs are the ones printed in the manual, and so are the commit IDs of Lab 1.3; the commit IDs of Labs 1.1 and 1.2 are yours. Every statement about behavior was checked on Git 2.55.0 in the lab sandbox.

## Lab 1.1: Build a commit by hand

1. A commit ID is the hash of the commit object, which contains the tree ID, the parent IDs, the author name, email and date, the committer name, email and date, and the message. For your first commit, the tree, the author and committer identities (the lab shell's `Lab User <you@example.com>`) and the message were identical to the book's; both dates differed, because the lab shell uses the real clock. For your second commit the dates differed again, and so did the `parent` line, because it names your first commit, whose ID already differed. One different input anywhere in a commit changes the ID of every commit built on top of it.
2. `git status` compares HEAD with the index, and reports the result under "Changes to be committed", and it compares the index with the working tree, and reports that under "Changes not staged for commit". The "deleted" line came from the second comparison: the index listed a path that had no file on disk. Nothing was deleted, because nothing had been created; the index is a list of intended content, not a record of files.
3. One tree object per directory that appears in the index paths, including the top level: `README.md` and `configs/eval.yaml` give a top-level tree and a `configs` tree. A later commit writes a new tree only for the directories whose entries changed, which is every directory on the path from the top level to each changed file, and even then only if no identical tree exists already.
4. `git log` walks the graph from a starting point, HEAD or a ref, following parent links; the lost commit was the parent of nothing and the target of no ref, so no walk could reach it. `git fsck` works the other way round: it scans the object database and reports objects that nothing refers to. In a porcelain workflow the reflog would have recorded the branch movement that abandoned the commit, for example a `git reset`, so `git reflog` would have shown its ID. `git commit-tree` writes no reflog entry, because it moves no ref.
5. A compare-and-swap: with a third argument, `git update-ref` writes the new value only if the ref currently holds the expected old value, and otherwise fails without changing anything ([git-update-ref](https://git-scm.com/docs/git-update-ref)). It protects against moving a ref that something else moved in the meantime. Without the third argument the command would have moved `main` to the third commit regardless of what the branch held, which here would have been the intended result by luck; in a script running next to other processes it is the difference between a safe update and a silent overwrite. `git push --force-with-lease` applies the same idea to a ref on a server (Chapter 12).
6. The first two moves of `main` were made with `git update-ref` without `-m`, and update-ref records exactly the reason it is given, here none. The third move was made with `-m 'by hand: describe the project'`. Porcelain commands always supply a reason, such as `commit: …` or `checkout: moving from …`, which is what makes `git reflog` readable during a recovery. Plumbing does only what it is told.

## Lab 1.2: Snapshots share unchanged blobs

1. The second commit added four objects: a blob for the new content of `prompts/judge.txt` (`f827550…`), a new `prompts` tree (`211d835…`) because one of its entries changed, a new top-level tree because its `prompts` entry changed, and the commit. The counts therefore went from 4, 1, 3 to 5, 2, 5. `README.md` and `eval/metrics.py` have the same content as before, so their blob IDs are unchanged and the new top-level tree refers to the existing objects; the `eval` tree is the same object in both commits, `56ebe9f6…`, as `git rev-parse HEAD~1:eval HEAD:eval` showed. Nothing is copied, because a tree holds IDs, not content.
2. Only the commit object: the counts went from 5 blobs, 2 commits, 5 trees to 5, 3, 5. Returning `prompts/judge.txt` to its first content means that the blob `7be668d…`, the first `prompts` tree and the first top-level tree all exist already, so `git commit` reused them. The proof is `git rev-parse 'HEAD~2^{tree}' 'HEAD^{tree}'`, which prints `ee4037ef…` twice: the third commit records the same tree as the first.
3. `git status` makes two comparisons by ID and by cached file information. HEAD against the index compares the blob IDs recorded in the tree with the IDs in the index entries; the index against the working tree compares the size, modification time and other data cached in each index entry with the file on disk, and re-hashes the working-tree file only when that data differs. Neither comparison opens the object in `.git/objects`, so a missing blob is invisible to `git status` until a command needs the content, as `git show` did.
4. `git fsck` reported `missing blob a7f6bbcc…`, naming the type and the ID, and `git ls-tree -r HEAD | grep a7f6bbc` showed the path, `prompts/system.txt`, because trees record which ID belongs to which name. If no file on disk had the content, the next source is any other repository that has the object: an object is defined by its content, so a copy from a colleague's clone is the identical object. If no copy exists anywhere, the content is lost and every commit that refers to it is damaged (Chapter 13: Recovery).
5. Yes. `git add prompts/system.txt` hashes the file and writes the object if it is not in the database, and in the sandbox it rebuilt the missing blob and made `git fsck` silent, even though the index entry was already correct. Restoring from a colleague's clone works for the same reason the local repair worked: the colleague's object has the same ID because it has the same bytes, so printing it there with `git cat-file -p <id>` and writing those bytes here with `git hash-object -w --stdin` recreates the identical object. Chapter 13 covers the ways to transfer objects between repositories.

## Lab 1.3: Same content, same ID, in two repositories

1. The tree ID, which in turn needed the same file name, mode and content; the absence of a parent; the author name and email; the committer name and email; the author date and the committer date, both pinned to `2026-09-07T12:00:00+05:30` on the command line; and the message. The input you did not type is the identity: `user.name` and `user.email` come from `$LAB/hands-on/home/.gitconfig`, which `labs/shell` wrote, and they are the same `Lab User <you@example.com>` that the replay uses. In your own shell, with your own identity, the commit ID would differ although every file is the same.
2. The `author` and `committer` lines: their timestamps are `1788762601` instead of `1788762600`, one second later. Everything else is identical, so the commit ID changes from `95eaa9c6…` to `4fd1085b…`. The tree ID stays `097da7ea…` because a tree is computed from entry names, modes and blob IDs only; no time enters it. That is why two commits with the same tree are proof of identical content.
3. Byte 17 is `\r`, a carriage return (0x0d), followed by the newline `\n`: the file uses Windows-style CRLF line endings. In practice it comes from a file saved on Windows, from a tool that writes CRLF, or from a transfer that converted line endings. Git hashes the bytes it is given; `git hash-object <file>` converts line endings only if a repository's attributes or `core.autocrlf` tell it to, and here the command ran outside any repository, so nothing did. What an editor shows as the same text is not the same content.
4. `git hash-object` without `-w` needed no repository: it computed IDs for files under `export/` and `laptop/` from the sandbox directory, which is not a repository. Everything that stores or records something needed one: `-w`, `git add`, `git write-tree`, `git commit`, `git ls-files`, `git rev-parse HEAD`. An ID is a pure function of an object's type and bytes; a repository is where objects are kept and named, not where IDs come from.
5. A missing or extra newline at the end of the file, a UTF-8 byte-order mark at the start, trailing whitespace, a tab in place of spaces, or the same accented character written in two Unicode normalization forms. Each changes bytes and therefore the blob ID. Line endings are normalized for a team with a tracked `.gitattributes` file containing `* text=auto`, applied to existing files with `git add --renormalize .` ([Chapter 4](../textbook/ch04-working-tree.md), section 4.13; the research report, section 4, with its link to gitattributes).
