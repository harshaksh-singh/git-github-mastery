# Module 28 lab answers

> Answers to the "Questions" of the [Module 28 labs](../lab-manual/m28-runners-debugging-ci.md). The diagnoses of the six broken workflows are in [m28-broken-workflows.md](m28-broken-workflows.md). GitHub behavior is cited from the documentation as in Chapter 20B; nothing here was run on GitHub by the author.

## Lab 28.1: Six broken workflows

1. **What a parser or linter catches.** None of the six. Every file is valid YAML with valid keys, valid expressions and correctly typed values. The faults are in the relation between the file and something outside it: the depth of the history, a ruleset, the token's scopes, the origin of the pull request, other runs, the content of a lock file. A linter that knows conventions might flag the constant cache key or the bare group name as suspicious; `actionlint` was not installed for this course, so that is not claimed.
2. **Workflow 2, two possible changes.** Change the workflow: remove the `paths` filter (or move the condition to job level and require an aggregate job). Changing the ruleset instead, by no longer requiring `unit-tests`, makes the documentation pull request mergeable and also lets code changes merge with failing or missing tests. The ruleset expresses the policy "nothing reaches `main` untested"; the workflow must be shaped so that the policy can always be evaluated.
3. **Why not `pull_request_target`.** It runs in the context of the base repository's default branch, with secrets and a token that can write, and the job would then build and run code from the fork. The contributor's code could read `SUPPLIER_API_KEY` and use the token. The documentation says to avoid the event when you need to build or run code from the pull request, and `actions/checkout` v7 refuses the fork checkout under that event unless `allow-unsafe-pr-checkout: true` is set. Chapter 21A treats it in full.
4. **The group expression.** `${{ github.workflow }}-${{ github.ref }}` with `cancel-in-progress: true`. `github.workflow` is the workflow's name, so another workflow using the same pattern has its own groups. `github.ref` is the branch or tag ref of the run (`refs/heads/lab-28-1-a`), so only runs for the same ref compete. Both contexts are allowed in a workflow-level `concurrency`, which permits only `github`, `inputs` and `vars`.
5. **An exact hit as the problem.** The key is the cache's whole identity. An exact hit means "a cache with this key exists", not "this cache matches your dependencies". Because the key never changed, the first `.venv` ever saved was restored forever, and because a hit does not save again, it was never refreshed. The workflow then trusted the hit and skipped the install.
6. **Layers.** Git: the mechanism of workflow 1 (a shallow history has no reachable tag) and the three-dot diff that a path filter is evaluated on in workflow 2. GitHub: the ruleset that requires the check in workflow 2, and the fork relationship in workflow 4. GitHub Actions: the checkout default (1), the filter semantics (2), token permissions (3), secret handling for forks (4), concurrency (5), the cache (6). Saying "Git is broken in CI" for workflow 1 names the wrong layer: Git behaved identically; the job was given a different repository.

## Lab 28.2: The investigation order, applied to a failing run

1. **The row that points to step 2.** "Commit the job checked out: a commit ID that is in nobody's clone; detached HEAD", together with the event `pull_request`. The run did not build `34f82ef`, the commit you tested. For that event the job checks out `refs/pull/N/merge`, a test merge of the head into the current base. Everything else in the table is a reason to rule a step out: no workflow change (1), no API calls (3), an unremarkable runner and a 20-second job (4), no environment (5), no dependencies (6), no secrets (7), unchanged pins (8), no artifacts or cache (10, 11), not cancelled (12).
2. **Why the re-runs told you nothing.** A re-run uses the same `GITHUB_SHA` and `GITHUB_REF` as the original run. The test merge commit was the same, so the result was the same. A re-run tests the hypothesis "the failure is not deterministic". Once it fails identically, that hypothesis is dead, and repeating it adds no information. A new push would have created a new run with a new test merge.
3. **What "clean" means.** `git merge-tree --write-tree` exiting with status 0 and printing only a tree ID means the three-way merge of the files produced no textual conflict: the two sides changed different files or different regions. It guarantees that a merge commit can be created mechanically. It says nothing about whether the merged code works. Here one side changed a function's signature and the other added a caller of the old signature, in different files.
4. **The ruleset option.** "Require branches to be up to date before merging", the strict mode of required status checks (Chapter 18, section 18.8): the head branch must contain the latest base, so you must merge or rebase, and you would have seen the failure locally or on the next run. Cost: in a busy repository every merge to `main` makes every other open pull request out of date again, and they queue up behind each other. The merge queue removes that cost: it tests each pull request together with the ones ahead of it on a temporary branch, and merges only what passed (workflows must also trigger on `merge_group`).
5. **Root-cause statement.** "The pull request's check failed although the branch passes on its own, with a `TypeError` for a missing argument. On pull request events GitHub Actions tests the merge of the branch into the current `main`, not the branch; `main` had gained a change to the function's signature after the branch was created, and the two changes merge without a textual conflict. We fixed the caller on the branch after merging `main` into it; to catch this earlier we keep the pull request trigger as it is, which did its job, and reproduce the test merge locally before asking for review on long-lived branches."
6. **The other description.** "First run after a two-week shutdown, fails right after the cache restore, passes afterwards." Steps 1 to 5 are ruled out quickly if the workflow, event, token, runner and environment are the usual ones. Step 11, cache, opens first: cache entries that have not been accessed for seven days are evicted, so after two weeks the restore is a miss, and the run exercises the path that normally never runs. Step 6, dependencies, opens with it: on a miss the job downloads everything again, and anything not held by the lock file may have a newer version. Facts to check: the cache step's log line for hit or miss, `gh cache list`, whether the install uses `--locked`, and what refilled the cache before the second run. The lesson is the one of workflow 6 seen from the other side: a job must be correct on a cache miss, because a miss is guaranteed to happen.
