# Git and GitHub learning resources (non-video), misconception evidence, tutorial gaps, branching and scale literature — research notes as of 1 October 2026

Method note for the report writer (not a section): every resource below was checked for existence on 1 Oct 2026. Verification levels are marked where they matter: **[V]** = page fetched and read directly in this session; **[S]** = confirmed only through a search-engine result/summary (page not opened or blocked, e.g. O'Reilly, ACM, Springer pages return 403/login walls) — treat details as lower confidence; **unverified** = could not be confirmed. ## 1. Official documentation map: which official Git and GitHub documents are the primary source for which topics (Pro Git, man pages/guides, technical docs, docs.github.com, GitHub Skills, Microsoft Learn, certifications)?

### Takeaway
The primary-source layer is git-scm.com (Pro Git 2nd edition, frozen at v2.1.450 since May 2024, plus man pages that track Git 2.56.0 released 28 Sep 2026) and docs.github.com. Pro Git 2e is still authoritative for the object model and internals but is checkout/master/GPG-era and has no real coverage of switch-first workflows, worktrees, sparse-checkout, partial clone or SSH signing, so those topics must be sourced from the man pages (which are current and now include a new `gitdatamodel` page) and the GitHub Blog; a third edition of Pro Git is being written in the open (progit3.com, launched Aug 2026).

### Cited Findings

#### 1.1 State of Git itself on 1 Oct 2026 (needed to judge currency of every resource)
- [V] The current release is Git 2.56.0, dated 2026-09-28 on the git-scm.com man pages — [gitglossary](https://git-scm.com/docs/gitglossary).
- [V] GitHub's release post for 2.56 (Elijah Newren, 28 Sep 2026) highlights `git add --resolved` (stage only resolved conflict paths, refusing if markers remain), a faster merge-base computation (up to ~70x in some cases), path-walk repacking that now works with reachability bitmaps and delta islands, `git history drop <commit>`, new `git refs create/update/delete/rename` subcommands, `git branch --delete-merged`, and a bisect `--reset-when-found` option — [GitHub Blog: Highlights from Git 2.56](https://github.blog/open-source/git/highlights-from-git-2-56/).
- [V] Git 3.0 has not shipped. The official BreakingChanges document (last changed in 2.55.0) lists the planned 3.0 changes: SHA-256 as default hash for new repositories (SHA-1 repos keep working), reftable as default ref storage, `main` as default branch name, Rust becoming a mandatory build dependency (auto-detected in 2.52, default-enabled in 2.55, mandatory in 3.0), `safe.bareRepository` default changing to `explicit`; removals of `.git/info/grafts`, `git pack-redundant`, the legacy `branches/` and `remotes/` directories, `git whatchanged`, `core.commentString=auto` and writing symref-as-symlink; it states that `git checkout` will NOT be removed even though switch/restore cover it; and it says no release date has been set — [BreakingChanges](https://git-scm.com/docs/BreakingChanges).
- [V] LWN (Jonathan Corbet, 18 Sep 2026, with a later update) reports the project's plan as: the December 2026 release will be numbered 2.98 to signal the transition, 2.99 follows in April 2027 as a long-term-support release, and 3.0 is released at the same time — [LWN: Looking forward to Git 2.56 — and 3.0](https://lwn.net/SubscriberLink/1094575/2385e98583715c2b/). Conflict to flag: the official doc still says no date is set — [BreakingChanges](https://git-scm.com/docs/BreakingChanges); several blog posts surfaced by search predicted "around end of 2026" — [S] [DeployHQ blog](https://www.deployhq.com/blog/git-3-0-on-the-horizon-what-git-users-need-to-know-about-the-next-major-release).
- [V] The SHA-256 transition design (why SHA-1 is being replaced after SHAttered in Feb 2017, selection of SHA-256 in late 2018, `extensions.objectFormat`, `compatObjectFormat`, bidirectional mapping, `gpgsig-sha256` header, caveats for shallow clones/alternates) is specified in — [hash-function-transition](https://git-scm.com/docs/hash-function-transition) (last changed 2.55.0, 2026-06-29).

#### 1.2 Pro Git (the book on git-scm.com)
- [V] Edition and status: "Pro Git", 2nd Edition (2014), Scott Chacon and Ben Straub, Apress, CC BY-NC-SA 3.0, current build version 2.1.450, free online plus PDF/EPUB — [git-scm.com/book](https://git-scm.com/book/en/v2).
- [V] The source repository's latest tagged release is 2.1.450 on 25 May 2024 (previous: 2.1.449 on 12 Dec 2023; 2.1.448 on 25 Jul 2023) — [progit2 releases](https://github.com/progit/progit2/releases). The repo shows ~2,912 commits, 172 open issues and 47 open PRs; it is written in AsciiDoc and translations live in separate repos — [progit/progit2](https://github.com/progit/progit2).
- [V] Table of contents (10 chapters + 3 appendices): 1 Getting Started; 2 Git Basics; 3 Git Branching; 4 Git on the Server; 5 Distributed Git; 6 GitHub (account setup, contributing, maintaining, managing an organization, scripting GitHub); 7 Git Tools (revision selection, interactive staging, stashing/cleaning, signing, searching, rewriting history, Reset Demystified, advanced merging, rerere, debugging/bisect, submodules, bundling, replace, credential storage); 8 Customizing Git (config, attributes, hooks, example policy); 9 Git and Other Systems; 10 Git Internals (plumbing/porcelain, objects, references, packfiles, the refspec, transfer protocols, maintenance and data recovery, environment variables); App. A Git in other environments; App. B embedding Git (libgit2, JGit, go-git, Dulwich); App. C command index — [git-scm.com/book](https://git-scm.com/book/en/v2).
- [V] What it does not cover well (each checked on the live pages):
  - The core branching chapter uses `git checkout` and `master` throughout and never mentions `git switch` — [Basic Branching and Merging](https://git-scm.com/book/en/v2/Git-Branching-Basic-Branching-and-Merging).
  - `git restore` exists only as a bolted-on subsection ("Undoing things with git restore") that says the command arrived in Git 2.23.0 and then repeats the reset/checkout examples — [Undoing Things](https://git-scm.com/book/en/v2/Git-Basics-Undoing-Things).
  - The command appendix for branching/merging has entries for branch, checkout, merge, mergetool, log, stash, tag only — none for switch, restore, worktree or sparse-checkout — [Appendix C: Branching and Merging](https://git-scm.com/book/en/v2/Appendix-C:-Git-Commands-Branching-and-Merging).
  - No section title in the whole TOC mentions switch, restore, sparse-checkout, partial clone, worktree or SSH signing — [git-scm.com/book](https://git-scm.com/book/en/v2).
  - "Signing Your Work" covers GPG only (key generation, `git tag -s`, `git commit -S`, `--verify-signatures`); no `gpg.format ssh` or X.509 — [Signing Your Work](https://git-scm.com/book/en/v2/Git-Tools-Signing-Your-Work).
  - Partial clone (blobless/treeless) is absent; adding it is an open proposal — [progit2 issue #1597](https://github.com/progit/progit2/issues/1597).
  - "Advanced Merging" does teach index stages (`git show :1:`/`:2:`/`:3:`), `--conflict=diff3`, undoing merges and subtree merging, but refers to the "recursive" strategy and does not mention `zdiff3` or merge-ort — [Advanced Merging](https://git-scm.com/book/en/v2/Git-Tools-Advanced-Merging).
- [V] A third edition is in progress and being revised publicly: the site progit3.com (launched August 2026) says every chapter is being revised for Git 3.0 (main default, SHA-256, reftable, Rust toolchain), that the restructure added two chapters and a worktrees section, and lists chapters including "Git and Agents" and "Git at Scale"; licence stays CC BY-NC-SA 3.0; source at progit/progit3 — [progit3.com](https://progit3.com/); the repo had 84 commits and 13 stars when checked — [progit/progit3](https://github.com/progit/progit3).

#### 1.3 Man pages and guides on git-scm.com — what each is the primary source for
(Version in brackets = the Git release in which the page last changed, as displayed by git-scm.com; all pages were live on 1 Oct 2026.)
- [V] The docs landing page lists these "Guides": gitattributes, gitcli (command-line conventions), giteveryday, gitfaq, gitglossary, githooks, gitignore, gitmodules, gitrevisions, gitsubmodules, gittutorial, gitworkflows; the other documents below are live but not linked from that index — [git-scm.com/docs](https://git-scm.com/docs).
- [V] **gittutorial** [2.54.0, 2026-04-20] — first-contact tutorial (import a project, make changes, "Git tracks content not files", history, branches, collaboration, exploring history); uses `git switch`/`git restore`; points to gittutorial-2 (object database and index), gitcore-tutorial, gitglossary, the User Manual, giteveryday, gitworkflows — [gittutorial](https://git-scm.com/docs/gittutorial).
- [V] **giteveryday** [2.43.0, 2023-11-20] — minimum command set by role: Individual Developer (Standalone), Individual Developer (Participant), Integrator, Repository Administration; already uses switch/restore — [giteveryday](https://git-scm.com/docs/giteveryday).
- [V] **gitworkflows** [2.35.0, 2022-01-24] — the git.git project's own workflow: separate small logical commits; integration branches maint/master/next/seen; rules "merge upwards" (fix on the oldest supported branch, then merge up), topic branches forked from the oldest branch they will merge to, merge downstream only at well-defined points, throw-away integration branches; merge workflow vs patch (format-patch/am) workflow — [gitworkflows](https://git-scm.com/docs/gitworkflows).
- [V] **gitglossary** [2.56.0, 2026-09-28] — canonical definitions (100+ terms) for HEAD, detached HEAD, index, ref/symref/pseudoref/per-worktree ref, refspec, reflog, remote-tracking branch, upstream branch, origin, merge base, fast-forward, tree-ish/commit-ish, reachable/dangling, pack, plumbing/porcelain, pathspec, shallow, stash, worktree, evil merge, octopus — [gitglossary](https://git-scm.com/docs/gitglossary).
- [V] **gitrevisions** [2.56.0] — primary source for revision and range syntax: abbreviated hashes, describe output, refnames, `@`, `@{date}`, `@{n}`, `@{-n}`, `@{upstream}`/`@{u}`, `@{push}`, `^n`, `~n`, `^{type}`, `^{/text}`, `:/text`, `rev:path`, and index stage syntax `:n:path` (stage 1 = common ancestor, 2 = current branch's version, 3 = the version being merged, 0 = normal entry); ranges `..`, `...`, `^rev`, `rev^@`, `rev^!`, `rev^-n` — [gitrevisions](https://git-scm.com/docs/gitrevisions).
- [V] **gitcore-tutorial** [2.43.1, 2024-02-09] — plumbing-level tutorial (creating/populating a repo by hand, committing state, how merge works, packing, publishing); explicitly aimed at people who want to understand the plumbing and tells ordinary users to start with gittutorial — [gitcore-tutorial](https://git-scm.com/docs/gitcore-tutorial).
- [V] **Git User's Manual** [2.56.0] — book-length official manual: repositories and branches, exploring history, developing with Git, sharing development, rewriting history and patch series, advanced branch management, Git concepts (object database, index), submodules, low-level operations, hacking Git, glossary, quick reference; uses switch/restore — [user-manual](https://git-scm.com/docs/user-manual).
- [V] **gitdatamodel** [first shipped 2.53.0, 2026-02-02; changed again in 2.56.0] — new short official explanation of objects (commit, tree, blob, tag object), references (branches, tags, HEAD, remote-tracking branches), the index and reflogs — [gitdatamodel](https://git-scm.com/docs/gitdatamodel), [2.53.0 version](https://git-scm.com/docs/gitdatamodel/2.53.0). It was written by Julia Evans and Marie Flanagan (~1,600 words) — [jvns.ca, 8 Jan 2026](https://jvns.ca/blog/2026/01/08/a-data-model-for-git/).
- [V] **gitrepository-layout** [2.49.0, 2025-03-14] — what every file/dir in `.git` is: objects/ (loose, pack/, info/alternates), refs/ (heads, tags, remotes, replace), packed-refs, HEAD, config and config.worktree, index and sharedindex, hooks/, info/exclude, info/attributes, info/sparse-checkout, logs/, shallow, commondir, modules/, worktrees/; the fetched page text did not mention reftable — [gitrepository-layout](https://git-scm.com/docs/gitrepository-layout).
- [V] **gitformat-pack** [2.54.0, 2026-04-20] — binary spec for `.pack`, object types incl. OFS_DELTA/REF_DELTA, delta encoding, `.idx` v1/v2, `.rev` reverse index, `.mtimes`, multi-pack-index (MIDX), cruft packs — [gitformat-pack](https://git-scm.com/docs/gitformat-pack).
- [V] **gitformat-index** [2.55.0, 2026-06-29] — binary spec of `.git/index` (header, entry fields incl. the 2-bit stage, extensions: cache tree, resolve-undo, split index, untracked cache, fsmonitor, EOIE, IEOT, sparse directory entries) — [gitformat-index](https://git-scm.com/docs/gitformat-index).

- [V] **githooks** [2.54.0] — all client and server hooks (applypatch-msg … pre-commit, prepare-commit-msg, commit-msg, pre-rebase, post-checkout, pre-push, pre-receive, update, proc-receive, post-receive, reference-transaction, post-rewrite, fsmonitor-watchman, p4-*, post-index-change; 28 in total) and `core.hooksPath` — [githooks](https://git-scm.com/docs/githooks).

- [V] **gitignore** [2.55.0] — precedence (command line, per-directory .gitignore, `$GIT_COMMON_DIR/info/exclude`, `core.excludesFile`), pattern grammar, and the rule that already-tracked files are unaffected (use `git rm --cached`) — [gitignore](https://git-scm.com/docs/gitignore).

- [V] **gitnamespaces** [2.32.0] — `GIT_NAMESPACE`, refs under `refs/namespaces/…`, and the warning that namespaces are not an access-control boundary — [gitnamespaces](https://git-scm.com/docs/gitnamespaces).
- [V] **gitfaq** [2.53.0, 2026-02-02] — 23 official FAQ answers: what to put in user.name, http.postBuffer, credentials/tokens and multiple accounts over HTTP/SSH, syncing a working tree, amending vs reverting, ignoring changes to tracked files, fetch vs pull, problems with squash merges on long-lived branches, why a change reverted on one branch still merges, hooks for policy, CRLF and "always modified" files, storing files — [gitfaq](https://git-scm.com/docs/gitfaq).
- [V] An official cheat sheet exists on the Git site and shows switch/restore alongside the checkout equivalents — [git-scm.com/cheat-sheet](https://git-scm.com/cheat-sheet).

#### 1.4 Technical/protocol documents
- [V] **reftable** [2.43.0, 2023-11-20] — design and file format of the reftable backend; motivates it with packed-refs costs (e.g. a 62 MB packed-refs for Android; ~866k refs: cold lookup by name ~410 ms with packed-refs vs ~34 µs with reftable), block layout, `tables.list` stack and compaction, enabling via `extensions.refStorage = reftable` — [reftable](https://git-scm.com/docs/reftable).
- [V] **partial-clone** [2.56.0] — design of partial clone: promisor remotes, `.promisor` packfiles, filter specs, on-demand fetching, `--refetch`, multiple promisor remotes, limitations (one fetch per missing object, repack partitions); states that it is independent of shallow clone/single-branch mechanisms — [partial-clone](https://git-scm.com/docs/partial-clone).
- [V] **bundle-uri** [2.50.0, 2025-06-16] — bundle URIs for seeding clones/fetches from static HTTP(S)/CDN, bundle list format (`bundle.mode=all|any`, `creationToken` heuristic, `filter`), server advertisement through protocol v2 — [bundle-uri](https://git-scm.com/docs/bundle-uri).
- [V] **gitprotocol-pack** [2.54.0] (formerly "pack-protocol") — reference discovery, want/have negotiation, upload-pack/receive-pack, push certificates, report-status, transports — [gitprotocol-pack](https://git-scm.com/docs/gitprotocol-pack). **gitprotocol-v2** [2.56.0] — capability advertisement, command model (`ls-refs`, `fetch`, `object-info`, `bundle-uri`), stateless design, how v2 is requested over git/ssh/http — [gitprotocol-v2](https://git-scm.com/docs/gitprotocol-v2). [S] These existed as man pages (gitformat-*/gitprotocol-*) by Git 2.38.0 — [gitprotocol-v2 at 2.38.0](https://git-scm.com/docs/gitprotocol-v2/2.38.0.html).

#### 1.6 docs.github.com — primary pages per topic
- [V] **Pull requests** — hub at docs.github.com/en/pull-requests: about PRs, branches, forks, commits, creating/reviewing/merging, merge conflicts (web and CLI), merge queue, auto-merge, reverting; in 2026 it also contains a full set of pages on native stacked pull requests — [Pull requests docs](https://docs.github.com/en/pull-requests). Stacked PRs entered public preview for all repositories on 30 Jul 2026 with a `gh-stack` CLI extension; merge-queue support was rolling out afterwards — [GitHub Changelog](https://github.blog/changelog/2026-07-30-stacked-pull-requests-are-now-in-public-preview/).
- [V] **GitHub flow** — six steps (create a branch, make changes, create a pull request, address review comments, merge, delete the branch) — [GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow).
- [V] **Rulesets** — a ruleset is a named list of rules for branches/tags (fnmatch targets) or pushes; up to 75 rulesets per repository; several rulesets can apply to the same branch and are aggregated with the most restrictive rule winning, and they layer with classic branch protection rules; enforcement can be switched (Active/Disabled) without deleting; anyone with read access can see active rulesets; push rulesets (file path, path length, extension, size) apply across the fork network; organization-level rulesets depend on plan — [About rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets). Available rules: restrict creations/updates/deletions, require linear history, require deployments to succeed, require signed commits, require a pull request (required approvals, dismiss stale approvals, code-owner approval, approval by someone other than the last pusher, resolved conversations, allowed merge methods, required reviewers for teams/files), require status checks, block force pushes, require code scanning / code quality results, plus the push rules — [Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).
- [V] **CODEOWNERS** — searched in `.github/`, repo root, then `docs/` (first found wins); per-branch; gitignore-style patterns except that `\#` escaping, `!` negation and `[ ]` ranges do not work; the last matching pattern takes precedence; owners need write access; file must be under 3 MB; invalid lines are skipped and errors are shown in the UI and via the REST API; with "require review from code owners", approval from any one listed owner satisfies the rule — [About code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners).
- [V] **Merge queue** — temporary `gh-readonly-queue/{base}` branches, CI must listen to the `merge_group` event, FIFO merging of groups, settings for merge method, build concurrency, group size and timeouts — [Managing a merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue).
- [V] **Authentication** — hub covering account security, 2FA (incl. mandatory 2FA), passkeys, SSH keys and troubleshooting, commit signature verification, personal access tokens, removing sensitive data, SSH key fingerprints, sudo mode, SSO — [Authentication docs](https://docs.github.com/en/authentication).
- [V] **GitHub Actions** — hub organised as Get started / Concepts / How-tos / Reference / Tutorials; canonical reference pages include workflow syntax, events, contexts, expressions, the secure-use reference and OIDC reference — [Actions docs](https://docs.github.com/en/actions), [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax).
- [V] **Security hardening for Actions** — now the "Secure use reference": secrets handling and masking, script-injection mitigation (use an action or an intermediate environment variable instead of interpolating untrusted context into `run:`), pinning third-party actions to a full-length commit SHA, least-privilege `GITHUB_TOKEN`, OIDC instead of long-lived cloud secrets, risks of `pull_request_target`, self-hosted runner hardening, Dependabot/code scanning for workflows, OpenSSF Scorecards — [Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use).
- [V] **Secret scanning** — scans the entire Git history on all branches plus issues, PRs, discussions, wikis and secret gists; partner alerts vs user alerts; validity checks, custom patterns, generic/AI detection; free on public repos, private repos need GitHub Secret Protection — [About secret scanning](https://docs.github.com/en/code-security/secret-scanning/introduction/about-secret-scanning). Push protection blocks secrets in CLI pushes, web UI commits, file uploads, REST API requests and (public repos) GitHub MCP server calls; bypass requires a reason and delegated bypass can be configured; push protection for users is on by default for public pushes on GitHub.com — [About push protection](https://docs.github.com/en/code-security/secret-scanning/introduction/about-push-protection).
- [V] **Secret-leak incident response** — nine-step guidance: identify the secret and owner, assess risk, revoke/rotate with the provider first (deleting the code does not stop exploitation), update dependants, review GitHub and provider audit logs for misuse, then consider history removal, close the alert, document lessons, enable push protection — [Remediating a leaked secret](https://docs.github.com/en/code-security/secret-scanning/working-with-secret-scanning-and-push-protection/remediating-a-leaked-secret).
- [V] **Removing sensitive data** — recommends `git-filter-repo` (v2.47+ with `--sensitive-data-removal`), says to revoke/rotate first, lists side effects (recontamination from old clones, changed hashes, broken PR diffs, lost signatures), then force-push and contact GitHub Support to dereference/delete affected PR refs and garbage-collect; collaborators must rebase rather than merge old history; the fetched text did not mention BFG — [Removing sensitive data from a repository](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository).
- [V] **Code security** — hub: getting started, secret scanning, code scanning (CodeQL), supply chain (dependency graph, Dependabot), security advisories, security overview and campaigns; the products are now packaged as GitHub Secret Protection, GitHub Code Security and GitHub Code Quality — [Code security docs](https://docs.github.com/en/code-security).
- [V] **Commit signature verification** — GPG, SSH and S/MIME supported; Verified / Partially verified / Unverified; vigilant mode; verification records persist even if a key later expires or is revoked; rebase-and-merge on GitHub produces commits GitHub cannot sign for you — [About commit signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification).

### Inferences
- Pro Git 2e should be cited for concepts whose mechanics have not changed (objects, refs, packfiles, reset, rebase, merge stages, rerere, bisect, refspecs, hooks, attributes) and avoided as the command-level authority for branch switching/undo, signing, large-repo features and default branch naming; the man pages and User Manual (both already switch/restore-first) are the safer command-level primary source.
- Because BreakingChanges states `git checkout` will stay, a course can teach switch/restore first without telling learners that checkout is deprecated — it is not.
- The 3.0 defaults (SHA-256, reftable, main) mean any curriculum text that hard-codes 40-hex object IDs, "`.git/refs/heads/<name>` is a file", or `master` should be written with a caveat; `gitdatamodel` and `gitrepository-layout` should be re-checked when 2.98/3.0 land.
- The git.git "merge upwards" rule in gitworkflows is the opposite direction from the "fix on main, cherry-pick to release" rule used by Google, Microsoft, GitLab Flow and trunkbaseddevelopment.com (section 6); both are legitimate primary/authoritative positions and should be presented as such.
- GitHub certifications are useful as a syllabus checklist for the GitHub-platform half of a course (rulesets, CODEOWNERS, Actions security all appear in the 2026 exam outlines) but contain almost no Git internals.

## 2. Books: do they exist, who wrote them, which edition/year, and how good/current is each?

### Inferences
One-paragraph evaluations of each book (researcher's assessment, based on the verified facts above):
- **Pro Git 2e** — Still the best free, comprehensive reference and the natural spine for a course: chapters 3, 7 and 10 (branching model, reset, rebase, advanced merging with stages, rerere, bisect, refspecs, objects, packfiles) remain mechanically correct because Git's data model is unchanged. Partially outdated: command idiom (checkout-only branching, `master`), GPG-only signing, no worktrees/sparse-checkout/partial clone/scalar/maintenance, and a GitHub chapter that pre-dates Actions, rulesets, CODEOWNERS and security tooling. Use with the man pages; watch progit3.com.
- **Version Control with Git 3e (2022)** — The most recent full-length commercial Git text; reasonable as a paid companion when a learner wants one linear book newer than Pro Git. Its coverage of post-2020 features was not inspected here, so claims about switch/restore or scale features should not be attributed to it without checking.
- **Building Git (2019)** — Unique: the only book that teaches Git by reimplementing it (index, diff, three-way merge, packs, protocol). Ideal for the "internals" tier and for instructors; cost of entry is Ruby and length (700+ pages). Pre-dates reftable/SHA-256 work, which does not affect its core value. Current.
- **Git Internals (PeepCode, 2008)** — Historical. Short and well illustrated, but superseded for practical purposes by Pro Git ch. 10 (same author) and by the 2022 GitHub Blog internals series; repo is archived.
- **Head First Git (2022)** and **Learning Git (2023)** — Both are beginner, visual, mental-model-first books; good recommendations for absolute beginners and non-developers. Neither is an advanced reference (Learning Git's own scope statement stops at rebasing and pull requests). Current for their scope.
- **Git in Practice (2014)** — Technique catalogue that maps well onto "intermediate recipes"; idioms are 2014-era (no switch/restore, no worktrees). Partially outdated but conceptually sound.
- **Git for Teams (2015)** — Distinctive for treating workflow as a people/process design problem; tooling screenshots and platform details are dated, the facilitation material is not. Partially outdated.
- **Boost Your Git DX (2023, updated 2024)** — The most current practical book on everyday CLI ergonomics (config, aliases, rebase/bisect habits); complements rather than replaces a conceptual text. Current.
- **Learning GitHub Actions (2023)** and **GitHub Actions in Action (2024)** — The two verified Actions books. Actions changes quickly (the 2026 GH-200 outline mentions immutable actions, artifact attestations and SHA pinning), so both should be paired with the docs.github.com secure-use reference; the Manning title is newer and has stronger runner/enterprise coverage by its description.
- **Git Pocket Guide (2013)** — Historical/partially outdated (Git 1.8.2); still a compact conceptual introduction but not a 2026 command reference.
- **Software Engineering at Google, ch. 16 (2020)** — Best single authoritative statement of the trunk-based / one-version position; must be read knowing Google does not use Git for its main repository and operates at unusual scale.
- **Accelerate (2018) + DORA** — The evidence base normally cited for trunk-based development and small batches; survey-based and correlational, so it supports "associated with/predicts" wording rather than universal prescriptions.
- **Julia Evans' zines** — "How Git Works" (2024) is the most current short mental-model resource and is explicitly built on her 2023–24 research into what confuses users; "Oh Shit, Git!" (2018) is a recovery cookbook that uses older command idioms. Both recommended as supplements.
- **High Performance Git (2026)** — Fills the scale/performance gap left by every other book (commit-graph, MIDX, bitmaps, sparse index, partial clone, scalar). Free; note the author's disclosure of LLM-assisted assembly and the absence of a stated target Git version — verify specifics against man pages.
- **Beej's Guide to Git (2024–25)** and **Mastering Git 2e (2024)** — Respectively a free beginner-to-intermediate guide and an advanced Packt text by a long-time Git community member; both are credible optional recommendations.

## 4. Evidence on what developers most commonly misunderstand about Git (Stack Overflow votes, Julia Evans' surveys/posts, academic papers, empirical studies, adoption figures)

### Takeaway
Independent evidence streams converge on the same clusters of misunderstanding: (a) "undo" — the HEAD/index/working-tree model behind reset, revert, restore, checkout and amend; (b) the three different things called a branch (local branch, remote-tracking ref, branch on the server) plus "tracking/upstream"; (c) tracked vs untracked vs ignored files; (d) HEAD and detached HEAD; (e) overloaded terminology (ours/theirs, fast-forward, reference, index/staged/cached). The confusion is not confined to beginners: a 2022 TOSEM study found Git-question askers on Stack Overflow are disproportionately long-registered users, and in Julia Evans' 2024 polls about half of respondents were not confident they understood HEAD and roughly 70% did not know that ours/theirs differ between merge and rebase.

#### 4.2 Large-scale Stack Overflow study (Yang, Zhang, Pan, Xu, Zhou, Huang — "Do Developers Really Know How to Use Git Commands? A Large-Scale Study Using Stack Overflow", ACM TOSEM)
- [V] Method: Stack Exchange data dump of 7 Dec 2020 (51.3M posts); 198,626 questions tagged with "git", of which 80,370 mention an actual Git command (classification validated on 600 samples; Cohen's kappa 0.844); plus a survey of 92 developers (74 industry, 18 academia; median 8 years of Git use) — [author preprint PDF](https://cs.nju.edu.cn/changxu/1_publications/22/TOSEM22.pdf); publisher record — [S] [ACM DL, DOI 10.1145/3494518](https://dl.acm.org/doi/10.1145/3494518).
- [V] At the time of writing, three of the five highest-voted questions on all of Stack Overflow were about Git commands — [preprint](https://cs.nju.edu.cn/changxu/1_publications/22/TOSEM22.pdf).
- [V] Most "popular" commands by average question views (commands with ≥200 questions): git revert (21,726 average views), git reflog (20,330), git stash (19,202), git clean (18,592), git reset (17,544); the authors note that all but `git clean` are about recovery. By raw number of questions: git push 17,977; git checkout 16,505; git commit 15,311; git add 12,659; git pull 10,996; git branch 9,048; git merge 8,006 — [preprint, Table 4](https://cs.nju.edu.cn/changxu/1_publications/22/TOSEM22.pdf).
- [V] Git-command questions average 8,440 views and score 13.7 versus 2,444 views and 2.1 for all Stack Overflow questions — [preprint](https://cs.nju.edu.cn/changxu/1_publications/22/TOSEM22.pdf).
- [V] Experience does not remove the problem: in 2020, 40.0% of people asking Git-command questions had been registered more than five years, versus 21.2% of all askers; since 2017 the largest group of Git askers has been the >5-year group — [preprint, Table 3](https://cs.nju.edu.cn/changxu/1_publications/22/TOSEM22.pdf).
- [V] Difficulty: among frequently used commands, `git credential` and `git submodule` were among the hardest to get accepted answers for; 81.7% of the learning approaches reported in the survey were self-learning (documentation and the internet) — [preprint](https://cs.nju.edu.cn/changxu/1_publications/22/TOSEM22.pdf).

#### 4.3 Conceptual-design analyses (MIT)
- [V] "What's Wrong with Git? A Conceptual Design Analysis" — Santiago Perez De Rosso and Daniel Jackson, Onward! 2013 (29–31 Oct 2013, Indianapolis), pp. 37–52, DOI 10.1145/2509578.2509584 — [author PDF](https://spderosso.github.io/onward13.pdf), [S] [ACM DL](https://dl.acm.org/doi/10.1145/2509578.2509584). It models Git's concepts (tracked, untracked, assumed-unchanged, ignored files; working, staged, committed and stashed versions; branch; stash) and shows violations of Brooks' orthogonality, propriety and generality criteria using four scenarios: changes lost because staged and working versions are coupled through commands like reset; committing made non-trivial by the intrusion of staging; inability to switch branches with conflicting uncommitted changes without stashing; and the difficulty of telling Git to stop tracking a committed file (assume-unchanged vs untracked). It cites the 2012 Git User's Survey, where UI and documentation were the top areas needing improvement. It proposes Gitless (no staging area, no stash, working versions kept per branch) — [author PDF](https://spderosso.github.io/onward13.pdf).
- [V] "Purposes, Concepts, Misfits, and a Redesign of Git" — same authors, OOPSLA 2016 (2–4 Nov 2016, Amsterdam), pp. 292–310, DOI 10.1145/2983990.2984018 — [author PDF](https://spderosso.github.io/oopsla16.pdf), [S] [ACM DL](https://dl.acm.org/doi/10.1145/2983990.2984018). Seven "operational misfits": saving changes, switching branches, detached head, file rename, file tracking, untracking a file, empty directory; explained by violations of design criteria (motivation, coherence, fulfillment, non-division, decoupling), e.g. the commit concept serving two purposes (make changes persistent and group logical changes) and stash having no version-control purpose of its own — [author PDF](https://spderosso.github.io/oopsla16.pdf).
- [V] Its Stack Overflow validation (18 Jul 2016): the authors hand-examined roughly 2,400 git-tagged questions with more than 30 upvotes and conservatively matched 41 highly ranked questions to the misfits, e.g. "How can I add an empty directory to a Git repository?" (2,383 upvotes at the time), "Ignore files that have already been committed to a Git repository" (1,588), "Making git 'forget' about a file that was tracked but is now in .gitignore" (1,458), "Git: How can I reconcile detached HEAD with master/origin?" (784), "The following untracked working tree files would be overwritten by checkout" (365) — [author PDF, Table 3](https://spderosso.github.io/oopsla16.pdf).
- [V] Its user study (24–28 Aug 2015): 11 MIT-affiliated participants (self-rated 10 regular, 1 expert), within-subjects, six tasks in Git 2.5 and Gitless 0.8.2. Task success Git vs Gitless: 81.8% vs 100%; 90.9% vs 63.6%; 72.7% vs 81.8%; 54.6% vs 63.6%; 54.6% vs 90.9%; 63.6% vs 81.8%. Mean satisfaction 3.91 (Git) vs 5.09 (Gitless) and frustration 4.73 vs 2.91 on 7-point scales; the conflict-during-branch-switch task was significantly faster in Gitless (p = 0.003). The authors flag the small, MIT-only sample as a threat to validity — [author PDF](https://spderosso.github.io/oopsla16.pdf).

#### 4.4 Julia Evans' crowd-sourced evidence (Mastodon audience; self-selected, mostly practising developers)
- [V] "Confusing git terminology" (1 Nov 2023), compiled from replies to a Mastodon question about which Git jargon people find confusing; headings in order: HEAD and "heads"; "detached HEAD state"; "ours" and "theirs" while merging or rebasing; "Your branch is up to date with 'origin/main'"; HEAD^, HEAD~, HEAD^^, HEAD~~, HEAD^2, HEAD~2; `..` and `...`; "can be fast-forwarded"; "reference", "symbolic reference"; refspecs; "tree-ish"; "index", "staged", "cached"; "reset", "revert", "restore"; "untracked files", "remote-tracking branch", "track remote branch"; checkout; reflog; merge vs rebase vs cherry-pick; `rebase --onto`; commit; more confusing terms. She explains that the "up to date" message only reflects the last fetch, and that ours/theirs swap meaning between merge and rebase — [post](https://jvns.ca/blog/2023/11/01/confusing-git-terminology/).
- [V] "Some Git poll results" (28 Mar 2024; 684–2,661 respondents per poll): knew that the two sides' order differs between merge and rebase conflicts — yes 15%, mostly 14%, no 48%, "what?" 21% (n=1,511); confident about HEAD — 100% 10%, pretty 36%, somewhat 38%, no idea 14% (n=1,783); think of HEAD as pointer to current commit 67% vs current branch 25% (n=1,386); "detached HEAD" vs "no branch checked out" seen as the same thing 52%, different 27%, "what?" 17% (n=1,278); confident about "fast-forward" — 25/31/20/21% (n=1,629); confident about "ref/reference" — 9/28/31/29% (n=1,117); understand the "up to date" status message — yes 63%, mostly 15%, no 7%, "what?" 13% (n=2,332); think of a commit as a diff 50%, snapshot 42%, whole history 3% (n=2,466); think of a branch as just the commits that branched off 58%, as full history 22%, as a pointer 15% (n=1,966); usually rebase 41%, usually merge 29%, both 24% (n=1,872); merge conflicts weekly 10%, monthly 33%, rarely/never 52% (n=2,009); have seen production bugs caused by a bad conflict resolution — many times 14%, once or twice 47%, no 32% (n=1,482); resolve conflicts by editing text 58% vs a dedicated tool 34% (n=2,380); have lost work to a Git problem — yes 17%, no 76% (n=1,475); only pull 37%, mix of fetch and pull 48%, only fetch 12% (n=2,036); use the command line regularly 80%, a GUI regularly 29% (n=2,661) — [post](https://jvns.ca/blog/2024/03/28/git-poll-results/).
- [V] "How HEAD works in git" (8 Mar 2024) reports an earlier ~1,700-vote poll (10% fully confident, 36% pretty confident, 39% somewhat, 15% no idea) and separates three meanings of HEAD (the `.git/HEAD` file, HEAD as a revision argument, and HEAD in output such as status, log decorations and conflict markers); it notes Git talks about a "detached HEAD" but has no name for the normal attached state — [post](https://jvns.ca/blog/2024/03/08/how-head-works-in-git/).
- [V] "Do we think of git commits as diffs, snapshots, and/or histories?" (5 Jan 2024): poll 51% diff, 42% snapshot, 4% history; argues the technically "wrong" diff model is practically useful for rebase/cherry-pick thinking while the snapshot model explains checkout and merges — [post](https://jvns.ca/blog/2024/01/05/do-we-think-of-git-commits-as-diffs--snapshots--or-histories/).
- [V] "git branches: intuition & reality" (23 Nov 2023): people picture a branch as an offshoot with a parent, but Git stores only a pointer and has no notion of a parent branch, so rebase/merge targets must be given explicitly and "backwards" rebases are accepted silently — [post](https://jvns.ca/blog/2023/11/23/branches-intuition-reality/).
- [V] "git rebase: what can go wrong?" (6 Nov 2023), from Mastodon replies: resolving the same conflict repeatedly; rebasing many commits; undoing a rebase; force-pushing shared branches; force-pushes disrupting review; losing metadata such as signatures; harder reverts; broken intermediate commits; running `commit --amend` instead of `rebase --continue`; splitting commits; long-lived branches; stopping a rebase incorrectly; interactions with merge commits. Mitigations listed include rerere, reflog, `rebase --abort`, squashing first, `--force-with-lease`, backup branches and `rebase -x` — [post](https://jvns.ca/blog/2023/11/06/rebasing-what-can-go-wrong-/).
- [V] "How git cherry-pick and revert use 3-way merge" (10 Nov 2023): cherry-pick is not patch application; it is a three-way merge whose base is the picked commit's parent, and revert is the same with base and "theirs" swapped — [post](https://jvns.ca/blog/2023/11/10/how-cherry-pick-and-revert-work/).
- [V] "Dealing with diverged git branches" (1 Feb 2024): how divergence shows up (status message, non-fast-forward push rejection, the pull hint about reconciling divergent branches) and the four ways out (merge, rebase, reset to remote, force push), with `pull.rebase`/`pull.ff` settings — [post](https://jvns.ca/blog/2024/02/01/dealing-with-diverged-git-branches/).
- [V] "The 'current branch' in git" (22 Mar 2024): the term has two workable definitions (what `.git/HEAD` says vs the branch remembered during a rebase) — [post](https://jvns.ca/blog/2024/03/22/the-current-branch-in-git/).
- [V] Documentation-testing evidence (8 Jan 2026): about 80 test readers, many with 5+ years of Git use, could not understand terms in official man pages such as "pathspec", "reference" and Git's sense of "upstream"; this drove the new gitdatamodel page and rewrites of the add, checkout, push and pull pages — [post](https://jvns.ca/blog/2026/01/08/a-data-model-for-git/).

#### 4.5 Classroom evidence
- [V] "Challenges and Confusions in Learning Version Control with Git" — Ville Isomöttönen and Michael Cochez (University of Jyväskylä); survey answered by 21 of 26 students in a project course (spring 2013) plus teaching observations from courses with ~170 students — [author PDF](https://www.cochez.nl/papers/dvcs-misconceptions-final.pdf); published in ICTERI 2014, Springer CCIS vol. 469, pp. 178–193 — [S] [Springer](https://link.springer.com/chapter/10.1007/978-3-319-13206-8_9).

### Inferences
- The top-30 Stack Overflow list is dominated by state-manipulation questions rather than conceptual ones: by the researcher's count of the top 30, 11 are undo/rewrite/discard questions (ranks 1, 5, 10, 11, 13, 14, 16, 17, 23, 27, 28), 12 concern remotes and the local / remote-tracking / server-branch distinction including tracking and refspecs (ranks 2, 3, 6, 7, 12, 15, 18, 19, 22, 24, 25, 30), 3 concern tracked/untracked/ignored semantics (ranks 8, 9, 20), and the remaining 4 are branch rename, conflict resolution, submodule removal and current-branch name. A "what most developers misunderstand" section can be organised around those three clusters plus HEAD and terminology.
- The same questions that the 2016 OOPSLA paper mapped to design misfits have kept accumulating votes for a decade (e.g. the "forget a tracked file now in .gitignore" question went from 1,458 upvotes in 2016 to 8,647 in 2026; the empty-directory question from 2,383 to 5,527), which supports the claim that these are stable conceptual problems rather than passing documentation gaps.
- Three independent sources (TOSEM registration-age data, Evans' polls of practising developers, Evans' 2026 man-page test readers) show experienced users share the confusion; a course should not treat these topics as "beginner only".
- The commit-as-diff majority (≈50%) and branch-as-offshoot majority (58%) in the polls are mental models a course must explicitly reconcile with the snapshot/pointer reality, because cherry-pick, rebase, and "three-dot" comparisons only make sense once both views are held together.
- Survey trajectory (SO 2022: 83.6% CLI; JetBrains 2023: IDE overtakes terminal) suggests teaching must cover both CLI and IDE/GUI surfaces; the two surveys measure different populations and question wording, so they should not be combined into a single trend line.

### Gaps
- Stack Overflow scores are a popularity signal accumulated since 2008 and skewed toward early, generic questions; they do not measure current prevalence. No per-year breakdown was collected.
- The TOSEM paper's final volume/issue/article number was not confirmed (the preprint carries template placeholders); the ACM page was blocked.
- Brindescu et al. and Ghiotto et al. were not read first-hand (publisher sites blocked); figures come from search summaries of abstracts and citing papers.
- No Stack Overflow survey after 2022 with a Git-usage percentage was found (the 2025 survey lists GitHub/GitLab as collaboration tools, not Git); JetBrains 2024/2025 version-control percentages were not located. The JetBrains 2023 sample size and dates (reported elsewhere as 26,000+ respondents, mid-2023) were seen only in a secondary summary.
- Julia Evans' polls are self-selected Mastodon samples; they indicate direction, not population estimates.
- No rigorous, recent (2023+) academic study quantifying Git usage errors in industry was found.

## 5. Gaps in common beginner tutorials and crash courses: which advanced topics do they omit?

### Takeaway
Across ten popular beginner resources whose outlines were verified (four YouTube crash courses with roughly 10 million views between them — plus a 3.3-million-view 2017 predecessor of one — and W3Schools, Atlassian, Software Carpentry, The Odin Project, Microsoft Learn and GitHub's Hello World), none covers index internals, conflict stages, rerere, range-diff, bisect, worktrees, force-with-lease, rulesets, CODEOWNERS, Actions security, secret-leak response or forensics. Only Atlassian (reflog, refspecs, three-way merge) and W3Schools (reflog, commit signing) touch any item on the list; the MIT "Missing Semester" lecture is the notable exception that teaches the data model first and lists bisect and (2026) worktree.

## 6. Branching and release strategy literature: GitHub Flow, Git Flow, GitLab Flow, trunk-based development, release branches and backports, feature flags, DORA findings, merge queues, stacked diffs, and how Google, Meta and Microsoft describe their practice

### Takeaway
The reputable literature does not crown one strategy; it ties the choice to context. Sources agree that long-lived divergent branches are costly and that integration frequency is the variable that matters (Fowler; DORA's 2016–2017 findings on at-most-daily-lived branches and three or fewer active branches), but they disagree on mechanics: Git Flow's author himself restricts it to explicitly versioned, multi-version software; GitHub Flow and trunk-based development assume one continuously deployed version; large companies (Google, Microsoft, Meta) combine trunk-based development with late-cut release branches, cherry-picked fixes and feature flags; and there are evidence-backed cases for feature branching (open source, less experienced or larger teams, teams without a reliably healthy mainline).

### Cited Findings

#### 6.1 GitHub Flow
- [V] Official description: a lightweight branch-based workflow in six steps (branch, change, pull request, address review, merge, delete branch) — [GitHub Docs](https://docs.github.com/en/get-started/using-github/github-flow).
- [V] Original essay (Scott Chacon, 31 Aug 2011): six rules — anything on master is deployable; descriptively named branches off master; push to the server constantly; open a pull request at any time; merge only after review; deploy immediately after merging — and the stated reason GitHub did not use git-flow: GitHub deploys many times a day, whereas git-flow is organised around releases — [scottchacon.com](https://scottchacon.com/2011/08/31/github-flow/).
- [V] Fowler's reading: GitHub Flow assumes a single production version with high-frequency integration onto a release-ready mainline, so release and hotfix branches disappear; it uses feature branching with pre-integration review, and feature branches may run from one line to a couple of weeks — [Fowler, Patterns for Managing Source Code Branches](https://martinfowler.com/articles/branching-patterns.html).
- [V] Microsoft's critique at scale: a strict GitHub Flow deploys each pull request to production before merge, which becomes a deployment queue when a repository completes 200+ PRs per day, so Microsoft batches deployments into sprint releases instead — [Microsoft Learn: How Microsoft develops with DevOps](https://learn.microsoft.com/en-us/devops/develop/how-microsoft-develops-devops).

#### 6.2 Git Flow
- [V] Vincent Driessen, "A successful Git branching model" (5 Jan 2010): long-lived `master` and `develop`, supporting feature, release and hotfix branches, merges with `--no-ff` to keep feature history visible. His note of reflection (5 Mar 2020) says the model was conceived for explicitly versioned software that may need several versions supported in the wild; teams doing continuous delivery of a web app should adopt a simpler workflow such as GitHub flow; and readers should weigh their own context because no model is a cure-all — [nvie.com](https://nvie.com/posts/a-successful-git-branching-model/).
- [V] Fowler: git-flow uses a mainline called develop, treats master as a production maturity branch, and adds release and hotfix branches; it says nothing about feature-branch length or mainline health; it fits products with multiple live versions and easily becomes over-complex for a single-production web app; many teams who say they use git-flow actually do something closer to GitHub Flow — [Fowler](https://martinfowler.com/articles/branching-patterns.html).
- [V] Atlassian now labels Gitflow a legacy workflow that has fallen in popularity in favour of trunk-based workflows, notes it can be hard to combine with CI/CD, and says its page is kept for historical purposes — [Atlassian: Gitflow workflow](https://www.atlassian.com/git/tutorials/comparing-workflows/gitflow-workflow).
- [V] GitLab's critique: making `develop` the default forces constant branch switching, and release/hotfix branches are overkill for most organisations practising CI/CD — [GitLab blog, 5 Mar 2020](https://about.gitlab.com/blog/what-is-gitlab-flow/).

#### 6.3 GitLab Flow
- [V] Defined by GitLab as a simplified strategy combining feature-driven development and issue tracking, working directly with main; variants add a production branch, environment branches (e.g. staging, pre-production, production) or release branches for software shipped in versions — [What is GitLab Flow?](https://about.gitlab.com/topics/version-control/what-is-gitlab-flow/).
- [V] Its eleven best-practice rules: use feature branches rather than direct commits on main; test all commits, not only those on main; run every test on all commits; review code before merging into main; deployments are automatic based on branches or tags; tags are set by the user, not CI; releases are based on tags; pushed commits are never rebased; everyone starts from main and targets main; fix bugs in main first and release branches second; commit messages reflect intent — [GitLab Flow best practices](https://about.gitlab.com/topics/version-control/what-are-gitlab-flow-best-practices/).
- [S] The original documentation calls merging to master first and then cherry-picking into the release branch an "upstream first" policy and attributes the practice to Google and Red Hat as well — [mirror of GitLab docs](https://docs.gitlab.co.jp/ee/topics/gitlab_flow.html).

#### 6.4 Trunk-based development (TBD)
- [V] Definition (Paul Hammant's site): developers collaborate in a single branch (trunk) and resist creating other long-lived development branches; very small teams may commit straight to trunk; larger teams use short-lived feature branches for review and CI; release branches are optional; feature flags and branch-by-abstraction handle long-running changes; cites Google, Facebook and Microsoft as practitioners — [trunkbaseddevelopment.com](https://trunkbaseddevelopment.com/).
- [V] Short-lived feature branches in TBD should last no more than a couple of days, belong to one developer (or a pair), and be deleted after merge; anti-patterns include sharing a feature branch among several developers and merging between feature branches; a story should produce several small pull requests rather than one — [TBD: short-lived feature branches](https://trunkbaseddevelopment.com/short-lived-feature-branches/).
- [V] Fowler treats TBD as essentially a synonym for continuous integration: all work on mainline, short-lived branches of at most a couple of days for larger teams, with either "branch for release" or "release from trunk" — [Fowler](https://martinfowler.com/articles/branching-patterns.html).
- [V] DORA defines TBD as each developer splitting work into small batches and merging to trunk at least once a day, and reports (2016–2017 research) that higher delivery performance is associated with three or fewer active branches, merging to trunk at least daily, and no code freezes or integration phases; pitfalls listed are heavyweight and asynchronous code review and skipping automated tests before commit — [DORA: trunk-based development](https://dora.dev/capabilities/trunk-based-development/).

#### 6.5 Release branches, hotfixes and the direction of backports
- [V] TBD site: release branches are cut late (a few days before release), may start from a commit older than trunk's head, are never merged back, and are deleted after use; bugs are reproduced and fixed on trunk first and then cherry-picked to the release branch, because fixing on the release branch risks a regression when someone forgets to port the fix; high-throughput teams may instead release from a tag on trunk — [TBD: branch for release](https://trunkbaseddevelopment.com/branch-for-release/).
- [V] Google: development on branches is unusual; release branches are cut from a specific revision, fixes are developed on mainline and cherry-picked in, and long-lived parallel branches are exceedingly rare — [Potvin and Levenberg, CACM 2016](https://cacm.acm.org/research/why-google-stores-billions-of-lines-of-code-in-a-single-repository/). The Google book regards release branches limited to cherry-picks as generally benign — [SWE at Google ch. 16](https://abseil.io/resources/swe-book/html/ch16.html).
- [V] Microsoft "Release Flow": short-lived topic branches merged to main via pull request with branch policies; a release branch per three-week sprint (e.g. `releases/M129`); a hotfix is made in main first and then cherry-picked to the release branch through its own pull request; release branches never merge back to main and the old one is abandoned after the next sprint ships — [Microsoft Learn](https://learn.microsoft.com/en-us/devops/develop/how-microsoft-develops-devops).
- [V] GitLab: fix bugs in main first, release branches second — [GitLab Flow best practices](https://about.gitlab.com/topics/version-control/what-are-gitlab-flow-best-practices/).
- [V] The opposite convention, from the Git project itself: commit a fix on the oldest supported branch that needs it (maint) and periodically merge integration branches upward (maint → master → next); cherry-pick only when a change must travel downward — [gitworkflows](https://git-scm.com/docs/gitworkflows).
- [V] Fowler catalogues the relevant patterns separately — Release Branch, Maturity Branch, Environment Branch, Hotfix Branch, Release Train, Release-Ready Mainline — so they can be combined per context — [Fowler](https://martinfowler.com/articles/branching-patterns.html).

#### 6.6 Feature flags
- [V] Pete Hodgson's taxonomy: release toggles (ship incomplete code dark, enabling trunk-based development), experiment toggles, ops toggles, permissioning toggles; they differ in longevity and dynamism and should be managed differently; costs include added complexity, combinatorial testing, and "toggle debt" — toggles should be treated as inventory and removed proactively (the Knight Capital incident is cited as a cautionary example) — [Feature Toggles](https://martinfowler.com/articles/feature-toggles.html).
- [V] Google: new and old code paths commonly coexist behind conditional flags, which avoids a development branch and allows switching off a faulty implementation by configuration; flags are eventually retired — [CACM 2016](https://cacm.acm.org/research/why-google-stores-billions-of-lines-of-code-in-a-single-repository/).
- [V] Microsoft: developers avoid long-running feature branches by using feature flags, decoupling deployment from exposure — [Microsoft Learn](https://learn.microsoft.com/en-us/devops/develop/how-microsoft-develops-devops).
- [V] Fowler's caveat: with flags the unfinished code still ships inside the product, and continuous integration therefore demands a strong self-testing regimen to keep mainline healthy — [Fowler](https://martinfowler.com/articles/branching-patterns.html).

#### 6.7 DORA evidence on trunk-based development and small batches
- [V] Small batches: work split into units finishable in hours to a couple of days (never more than a week); working in small batches predicts software delivery and organisational performance, pairs with daily merges to trunk and with feature toggles/dark launches, and is described as a safety net for AI adoption — [DORA: working in small batches](https://dora.dev/capabilities/working-in-small-batches/).
- [V] Version control as a capability: comprehensive use of version control (code, configuration, infrastructure scripts, tests, and now prompts and agent configuration) predicts continuous delivery; with AI-generated code DORA recommends small frequent commits and warns about unmanaged merge conflicts from high-volume generation — [DORA: version control](https://dora.dev/capabilities/version-control/).
- [V] 2024 report: AI adoption raised individual productivity, flow and job satisfaction but was associated with lower delivery stability and throughput; the report stresses that fundamentals such as small batch sizes and robust testing remain crucial — [DORA 2024 report](https://dora.dev/research/2024/dora-report/). 2025 report ("State of AI-assisted Software Development"): AI acts as an amplifier of existing strengths and weaknesses; its AI Capabilities Model lists version control and working in small batches among seven capabilities — [DORA 2025 report](https://dora.dev/research/2025/dora-report/), [DORA capabilities catalogue](https://dora.dev/capabilities/).
- [V] Fowler quotes the 2016 State of DevOps Report's finding that branches living less than a day and fewer than three active branches contribute to higher performance, and says this research programme is a rare exception to his usual scepticism about software-practice studies — [Fowler](https://martinfowler.com/articles/branching-patterns.html).
- [V] The book-length statement of the research is Accelerate (2018) — [IT Revolution](https://itrevolution.com/product/accelerate/); the Google book cites the same research for trunk-based development — [SWE at Google ch. 16](https://abseil.io/resources/swe-book/html/ch16.html).

#### 6.8 The other side: where feature branching or pre-merge gates are defended
- [V] Fowler lists genuine advantages of feature branching (a feature's code can be assessed as a unit; code enters the product only when complete; fewer merges) and costs of continuous integration (requires commitment to a healthy mainline and self-testing code; no late decision about including a feature); he judges feature branching better for teams that cannot keep mainline healthy and for open-source projects where maintainers integrate work from occasional, not-yet-trusted contributors; his personal preference is CI but he says context decides — [Fowler](https://martinfowler.com/articles/branching-patterns.html).
- [V] An interview-and-survey study of Brazilian developers (Lopes, Accioly, Borba, Menezes; arXiv 2507.08943, July 2025) concludes trunk-based workflows suit fast-paced projects with experienced, smaller teams, while branch-based workflows suit less experienced and larger teams despite management overhead — [arXiv](https://arxiv.org/abs/2507.08943).
- [V] "Ship / Show / Ask" (Rouan Wilsenach, 8 Sep 2021) proposes choosing per change: merge directly (Ship), open a PR and merge without waiting for review (Show), or wait for discussion (Ask); it presupposes trust, good CI/CD and feature toggles — [martinfowler.com](https://martinfowler.com/articles/ship-show-ask.html).
- [V] Git's own FAQ has an entry on the problems that arise when long-lived branches are integrated with squash merges (the answer text itself was not extracted in this session) — [gitfaq](https://git-scm.com/docs/gitfaq).
- [V] Driessen's 2020 note explicitly warns against treating any model as dogma — [nvie.com](https://nvie.com/posts/a-successful-git-branching-model/).

#### 6.9 Merge queues
- [V] GitHub's merge queue creates temporary branches containing the base plus queued changes, runs required checks on the `merge_group` event and merges in order, removing the need for authors to keep rebasing onto a busy branch — [GitHub Docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue).
- [V] GitHub's own experience (Will Smythe and Lawrence Gripper, 6 Mar 2024): the queue replaced hand-managed "trains"; about 2,500 pull requests a month from 500+ engineers land in the main monorepo through it; average wait to ship fell by 33% — [GitHub Blog](https://github.blog/engineering/engineering-principles/how-github-uses-merge-queue-to-ship-hundreds-of-changes-every-day/).
- [V] Shopify (Jack Li, 14 Nov 2019): roughly 40 deploys and ~400 merged commits per day; merge queue v2 runs CI on a predicted post-merge branch before merging, ejects failing pull requests, and batches changes, to keep master green — [Shopify Engineering](https://shopify.engineering/successfully-merging-work-1000-developers).
- [S] Uber's SubmitQueue ("Keeping Master Green at Scale", Ananthanarayanan et al., EuroSys 2019) guarantees an always-green mainline for thousands of daily commits in large monorepos — [ACM DL](https://dl.acm.org/doi/pdf/10.1145/3302424.3303970).

#### 6.10 Stacked diffs / stacked pull requests
- [V] Concept and history: per-commit review units stacked on mainline, popularised by Phabricator at Facebook and chained changelists at Google — [Jackson Gabbard, 2018](https://jg.gg/2018/09/29/stacked-diffs-versus-pull-requests/), [Pragmatic Engineer, 2023](https://newsletter.pragmaticengineer.com/p/stacked-diffs). Stated benefits: authors are not blocked while waiting for review, reviews are smaller; stated costs: requires fluency with rebasing and good tooling, little benefit for small teams — [Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/stacked-diffs).
- [V] Tooling: Sapling treats stacks as first-class — [Meta engineering](https://engineering.fb.com/2022/11/15/open-source/sapling-source-control-scalable/); jj auto-rebases descendants — [jj docs](https://docs.jj-vcs.dev/latest/git-comparison/); git-branchless adds restack/sync/move to Git — [git-branchless](https://github.com/arxanas/git-branchless); Graphite sells a hosted workflow — [Graphite guide (vendor)](https://graphite.com/guides/stacked-diffs).
- [V] GitHub made stacked pull requests native in 2026: each PR targets the layer below, layers are reviewed and checked independently, a stack (or its lower layers) can be merged in one operation with automatic rebase/retarget of the rest, and existing branch protections and required checks still apply; public preview from 30 Jul 2026 — [GitHub Changelog](https://github.blog/changelog/2026-07-30-stacked-pull-requests-are-now-in-public-preview/).

#### 6.11 How large companies describe their practice
- [V] **Google** (data as of January 2015): ~1 billion files, ~35 million commits, 86 TB, ~2 billion lines of code in 9 million source files; 25,000+ developers; on a typical workday 16,000 human and 24,000 automated commits; one trunk in a custom centralized system (Piper, on Spanner) accessed mostly through a cloud workspace filesystem (CitC); trunk-based development with pre-commit code review, presubmit checks and automatic rollback of breaking changes; branches used almost only for releases — [CACM 2016](https://cacm.acm.org/research/why-google-stores-billions-of-lines-of-code-in-a-single-repository/). Bibliographic record: Rachel Potvin and Josh Levenberg, Communications of the ACM 59 (2016), pp. 78–87 — [research.google](https://research.google/pubs/why-google-stores-billions-of-lines-of-code-in-a-single-repository/).
- [V] **Meta/Facebook** ("Rapid release at massive scale", Chuck Rossi, 31 Aug 2017): the web front end moved from three pushes a day built from a release branch fed by 500–700 cherry-picks per day to quasi-continuous "push from master" between April 2016 and April 2017, releasing tens to hundreds of diffs every few hours through tiered rollout (employees, 2% of production, 100%), with the Gatekeeper system separating code deployment from feature release; the old model stopped scaling as master took in over 1,000 diffs a day — [Engineering at Meta](https://engineering.fb.com/2017/08/31/web/rapid-release-at-massive-scale/). Meta's monorepo runs on its own tooling (Sapling client with first-class commit stacks) rather than stock Git — [Engineering at Meta, 2022](https://engineering.fb.com/2022/11/15/open-source/sapling-source-control-scalable/).
- [V] **Microsoft**: trunk-based "Release Flow" (6.5) on Git; pull-request validation runs about 60,000 tests in under five minutes; some repositories complete 200+ pull requests a day producing 300+ CI builds; feature flags and ring-based deployment — [Microsoft Learn](https://learn.microsoft.com/en-us/devops/develop/how-microsoft-develops-devops). The Windows repository itself (2017): ~3.5 million files, ~300 GB, ~4,000 engineers, 8,421 pushes and 2,500 pull requests per day, 4,352 active topic branches — [Brian Harry, 24 May 2017](https://devblogs.microsoft.com/bharry/the-largest-git-repo-on-the-planet/).

### Inferences
- A defensible, non-dogmatic framing for a course: first ask how many versions are live at once and how often you release. One continuously deployed version → GitHub Flow or trunk-based development (they differ mainly in branch lifetime and whether review is pre-merge); several supported versions or shipped/installed software → release branches, with Git Flow as one historical arrangement of them; the "fix on main then cherry-pick" versus "fix on oldest branch then merge up" choice should be taught as a real trade-off (risk of forgotten ports versus merge-graph cleanliness and guaranteed containment).
- The DORA evidence is survey-based and correlational and is expressed in terms of branch lifetime, number of active branches and batch size — not in terms of named workflows. Saying "DORA proves trunk-based development is best" overstates it; "short-lived branches and small batches are associated with better delivery performance" is what the sources support.
- Merge queues and stacked PRs are complementary mitigations for the two main costs of pre-merge review at scale (stale branches/broken main, and blocked authors/huge reviews). With GitHub shipping native stacks in 2026, stacked workflows are no longer a "big tech only" topic.
- Company case studies come from organisations with heavy CI, feature-flag and tooling investment; Google and Meta do not use stock Git for their main repositories, so their practices support the principle (one trunk, small changes, flags) more than any specific Git command sequence.

### Gaps
- The DORA 2024 and 2025 PDFs were not read; only the landing pages and capability pages were. No numeric effect sizes for trunk-based development were captured.
- GitLab's original 2014 "GitLab Flow" document is no longer publicly reachable on docs.gitlab.com; the "upstream first" wording is from a mirror.
- No controlled experiment comparing branching strategies was found; the arXiv study is qualitative and its participant count was not captured.
- Uber's SubmitQueue paper was not read first-hand (search summary only); a vendor-published 2025 Shopify merge-queue case study that surfaced in search was deliberately not used.

## 7. Monorepo and Git-at-scale sources

### Takeaway
The verified canon is: Google's CACM paper (monorepo rationale on a non-Git system), Microsoft's GVFS/VFS for Git → Scalar story (now upstreamed into Git as `scalar`, partial clone, cone-mode sparse-checkout, sparse index, FSMonitor, commit-graph, multi-pack-index and background maintenance), Meta's Sapling, GitHub's engineering posts by Stolee/Blau/Hostetler, and practitioner reports from Dropbox (2020 and 2026), Canva (2022) and Uber (2026). The common lesson across them is that stock Git scales to very large repositories only when these opt-in features are configured, and that repository layout can silently defeat Git's heuristics.

### Cited Findings
- [V] **Google** — monorepo benefits listed: unified versioning/one source of truth, extensive code sharing, simplified dependency management (no diamond dependencies), atomic changes, large-scale refactoring, cross-team collaboration, flexible ownership and code visibility; costs: heavy investment in bespoke tooling, codebase complexity (unnecessary dependencies) and code-health effort; Google found no commercial or open-source VCS able to host that scale in one repository and built Piper — [CACM 2016](https://cacm.acm.org/research/why-google-stores-billions-of-lines-of-code-in-a-single-repository/). The Google book adds that a single repository is not strictly required if a "virtual monorepo" preserves one-version semantics — [SWE at Google ch. 16](https://abseil.io/resources/swe-book/html/ch16.html).
- [V] **Microsoft, Windows on Git** — "The largest Git repo on the planet" (Brian Harry, 24 May 2017): 3.5M files / ~300 GB; GVFS virtualises the working directory and `.git` so only needed objects are downloaded; clone ~127 s and status ~10 s at the 80th percentile at the time — [devblogs.microsoft.com](https://devblogs.microsoft.com/bharry/the-largest-git-repo-on-the-planet/).
- [V] **VFS for Git** — Windows-only; README now recommends Scalar for new deployments; MIT; ~6.1k stars — [microsoft/VFSForGit](https://github.com/microsoft/VFSForGit).
- [V] **Scalar** — "Introducing Scalar" (Derrick Stolee, 12 Feb 2020): achieves performance without filesystem virtualisation by using cone-mode sparse-checkout, background maintenance (config, hourly fetch, commit-graph, loose-object cleanup, multi-pack-index) and partial clone/GVFS protocol; for Windows developers pack data dropped from 150–200 GB to 30–50 GB — [Azure DevOps Blog](https://devblogs.microsoft.com/devops/introducing-scalar/). "The Story of Scalar" (Stolee and Victoria Dye, 13 Oct 2022): VFS for Git was built for the Windows repo; the Office monorepo's macOS needs and Apple's kernel-extension deprecation forced a non-virtualised design; Scalar was rewritten in C and merged into Git 2.38 — [GitHub Blog](https://github.blog/open-source/git/the-story-of-scalar/). Reference: [scalar man page](https://git-scm.com/docs/scalar).
- [S] Microsoft's older "Git at Scale" and "GVFS design history" documentation is archived under previous-versions — [Microsoft Learn (archived)](https://learn.microsoft.com/en-us/previous-versions/azure/devops/all/git/git-at-scale?view=azure-devops-2020).
- [V] **Commit-graph** — "Supercharging the Git Commit Graph" (Stolee, 25 Jun 2018): introduced in Git 2.18; `git log --graph -10` went from 5.90 s to 0.74 s on the Linux repo and 24.30 s to 5.30 s on the Windows repo — [Azure DevOps Blog](https://devblogs.microsoft.com/devops/supercharging-the-git-commit-graph/); generation numbers and reachability queries — [Git's database internals II](https://github.blog/open-source/git/gits-database-internals-ii-commit-history-queries/); file format — [gitformat-commit-graph](https://git-scm.com/docs/gitformat-commit-graph).
- [V] **Multi-pack-index, bitmaps, geometric repacking** — "Scaling monorepo maintenance" (Taylor Blau, 29 Apr 2021): multi-pack reachability bitmaps, `.rev` reverse indexes (about 35% less CPU for fetches), `git repack --geometric=2`; average repack time at GitHub fell from about a minute to 15 seconds — [GitHub Blog](https://github.blog/open-source/git/scaling-monorepo-maintenance/).
- [V] **Sparse-checkout and sparse index** — cone mode (Git 2.25) and sparse index (index 180 MB → <10 MB, status 1.3 s → <0.2 s in a 2M-file repo) — [sparse-checkout post](https://github.blog/open-source/git/bring-your-monorepo-down-to-size-with-sparse-checkout/), [sparse index post](https://github.blog/open-source/git/make-your-monorepo-feel-small-with-gits-sparse-index/); the command is still marked experimental in 2.56 — [git-sparse-checkout](https://git-scm.com/docs/git-sparse-checkout).
- [V] **Partial vs shallow clone** — guidance in [Stolee, 2020](https://github.blog/open-source/git/get-up-to-speed-with-partial-clone-and-shallow-clone/); design in [partial-clone](https://git-scm.com/docs/partial-clone).
- [V] **FSMonitor** — built-in daemon since Git 2.37 (`core.fsmonitor=true`), with untracked cache brings `git status` from 17–85 s to under 1 s on repos of 393K–2M files — [Jeff Hostetler, 29 Jun 2022](https://github.blog/engineering/infrastructure/improve-git-monorepo-performance-with-a-file-system-monitor/).
- [V] **Sharding strategies** — multi-repo, submodule super-repo, monorepo, time-based splitting, alternates; monorepos fit code that ships and merges together — [Git's database internals V](https://github.blog/open-source/git/gits-database-internals-v-scalability/).
- [V] **Meta — Sapling** — a monorepo of tens of millions of files, commits and branches; Meta built a Git-compatible client plus (non-public at announcement) Mononoke server and EdenFS virtual filesystem rather than splitting the repo — [Engineering at Meta, 15 Nov 2022](https://engineering.fb.com/2022/11/15/open-source/sapling-source-control-scalable/).
- [V] **Dropbox (2020)** — "Speeding up a Git monorepo at Dropbox with <200 lines of code" (Utsav Shah, 10 Jun 2020): 250k+ files; fsmonitor with Watchman, split index, untracked cache, upstream bug fixes, applied through a small wrapper — [dropbox.tech](https://dropbox.tech/application/speeding-up-a-git-monorepo-at-dropbox-with--200-lines-of-code).
- [V] **Dropbox (2026)** — "Reducing our monorepo size to improve developer velocity" (Ishan Mishra, 25 Mar 2026): repository shrank from 87 GB to 20 GB and clones from over an hour to under 15 minutes; root cause was Git's delta-candidate heuristic keying on the tail of the path, which paired translation files across languages because of the i18n directory layout; the fix was an aggressive server-side repack performed with GitHub (large window/depth) after evaluating the experimental path-walk option — [dropbox.tech](https://dropbox.tech/infrastructure/reducing-our-monorepo-size-to-improve-developer-velocity). Git 2.56 subsequently made path-walk repacking compatible with bitmaps and delta islands — [Highlights from Git 2.56](https://github.blog/open-source/git/highlights-from-git-2-56/).
- [V] **Canva** — "We Put Half a Million files in One git Repository, Here's What We Learned" (Anh Le, 16 Jun 2022): ~500k files, ~60M lines; `git status` 10 s → about 3 s using fsmonitor/Watchman, `feature.manyFiles` with untracked cache, scheduled `git maintenance`, and sparse checkout to exclude generated translation files that were ~70% of all files — [Canva Engineering](https://www.canva.dev/blog/engineering/we-put-half-a-million-files-in-one-git-repository-heres-what-we-learned/).
- [V] **Uber** — "GitFarm: Git as a Service for Large-Scale Monorepos" (9 Jul 2026): cloning the Go monorepo takes ~15 minutes and 40+ GB of disk; GitFarm runs Git operations for internal services through a gRPC API on pre-warmed sandboxes, giving repository access in under 500 ms and cutting client resource use by over 80% — [Uber Blog](https://www.uber.com/us/en/blog/gitfarm-as-a-service/).
- [V] **Shopify** — the verified Shopify source concerns merge throughput (merge queue, 2019), not Git client performance — [Shopify Engineering](https://shopify.engineering/successfully-merging-work-1000-developers).
- [V] Practitioner summaries: Scott Chacon's "Git Tips 3: Really Large Repositories" (prefetch, commit-graph, fsmonitor, partial clone, sparse-checkout, scalar; e.g. Linux blobless clone 4.6 GB → 1.4 GB) — [GitButler blog](https://blog.gitbutler.com/git-tips-3-really-large-repositories/); book-length treatment in "High Performance Git" — [gitperf.com](https://gitperf.com/).
- [V] Ongoing upstream work: Git Rev News 138 (Aug 2026) covers a merge-base optimisation measured at 537x on one case — [Git Rev News](https://git.github.io/rev_news/).

### Inferences
- For a course, "Git at scale" can be taught as a short checklist of opt-in features, each with a primary source: `scalar clone` (or blobless partial clone + cone sparse-checkout), `git maintenance`, commit-graph with changed-path filters, multi-pack-index/geometric repack, FSMonitor + untracked cache, sparse index — plus the warning from Stolee's post that shallow clones belong only in throwaway CI.
- The Dropbox 2026 and Canva cases show that repository content and layout (generated/translation files, path naming) matter as much as Git settings; this is a concrete, citable argument for teaching `.gitattributes`, sparse-checkout and "what not to commit".
- Google's and Meta's papers justify monorepos but on non-Git or heavily modified tooling; the fair statement is that monorepos trade tooling investment for consistency, and that Git-based monorepos are viable with the features above (Microsoft, GitHub, Dropbox, Canva, Uber evidence).

### Gaps
- No Shopify engineering post specifically about Git performance was verified; Uber's earlier monorepo/Git posts were not searched exhaustively.
- Microsoft's current (non-archived) "Git at scale" documentation page was not found (404 at the guessed URL).
- Performance numbers are each from the publisher's own environment and dates (2017–2026) and are not comparable with one another.

## 8. Submodules versus subtrees versus alternatives: best sources and documented pain points

### Takeaway
Primary sources are git-submodule(1), gitsubmodules(7), gitmodules(5), Pro Git's "Submodules" section and the contrib `git-subtree` documentation; Pro Git itself documents five concrete submodule failure modes, and independent evidence (a 4,783-vote Stack Overflow question on merely removing one, and the TOSEM finding that `git submodule` questions are among the hardest to answer) confirms the pain. Secondary sources broadly advise: use a package manager where one exists, subtree (or subrepo) for vendoring third-party code, a monorepo with sparse-checkout for tightly coupled first-party code, and submodules for genuinely independent, slowly changing dependencies.

### Cited Findings
- [V] **What a submodule is (primary)** — a repository embedded in another; the superproject records a gitlink entry (a commit ID) plus `.gitmodules`; the submodule's Git directory lives under `$GIT_DIR/modules/<name>`; stated use cases are using another project while keeping history separate, and splitting a logically single project to limit repository size, transfer size or access — [gitsubmodules](https://git-scm.com/docs/gitsubmodules).
- [V] **Command reference** — subcommands add, status, init, deinit, update, set-branch, set-url, summary, foreach, sync, absorbgitdirs; the default `update` mode checks out the recorded commit on a detached HEAD (alternatives: `--rebase`, `--merge`); `--remote` follows the submodule's remote-tracking branch; `--init --recursive` for nested submodules — [git-submodule](https://git-scm.com/docs/git-submodule).
- [V] **Pain points documented by Pro Git** — (1) switching between branches with and without the submodule leaves stray directories unless `--recurse-submodules` is used; (2) converting a tracked subdirectory into a submodule collides with the index; (3) `submodule update` leaves a detached HEAD, so local work can be lost on the next update; (4) pushing the superproject without pushing the submodule commits breaks collaborators (mitigated by `push --recurse-submodules=check|on-demand`); (5) diverged submodule pointers are not merged automatically — [Pro Git: Submodules](https://git-scm.com/book/en/v2/Git-Tools-Submodules).
- [V] **More documented limitations** — multiple worktrees of a superproject with submodules are not recommended because support is incomplete — [git-worktree](https://git-scm.com/docs/git-worktree); SHA-256 transition has caveats for unfetched submodules — [hash-function-transition](https://git-scm.com/docs/hash-function-transition).
- [V] **Evidence of difficulty** — "How do I remove a submodule?" has 4,783 votes (rank 26 among git questions) — [Stack Overflow](https://stackoverflow.com/questions/tagged/git?tab=Votes); `git submodule` is among the hardest frequently used commands to get answered — [Yang et al., TOSEM preprint](https://cs.nju.edu.cn/changxu/1_publications/22/TOSEM22.pdf).
- [V] **Best secondary explanation** — "Demystifying git submodules" (Dmitry Mazin, 20 Mar 2024): a submodule is always pinned to a specific commit via a `160000` tree entry; Git does not fetch or update submodules automatically, so people accidentally commit pointer rollbacks; recommends `git submodule update --init --recursive` and `submodule.recurse=true` — [cyberdemon.org](https://www.cyberdemon.org/2024/03/20/submodules.html).
- [V] **GitHub's position** — "Working with submodules" (Joshua Wehner, 1 Feb 2016, updated 2024): suitable for simple, fairly static parent/child relationships; advises looking at a language package manager first; warns that contents are not downloaded by default and that fast-moving interdependent repos become frustrating — [GitHub Blog](https://github.blog/open-source/git/working-with-submodules/).
- [V] **Critical view** — "Reasons to avoid Git submodules" (Tim Hutt's blog, 4 Dec 2024): they break worktrees, checkouts, branch switching and mirroring (absolute URLs); poor tool support; each submodule becomes a public interface; cross-repo testing and refactoring get harder; transitive dependencies are duplicated; alternatives suggested are a package manager, a monorepo with a suitable build system, `git subtree` for third-party code, or git-subrepo — [blog.timhutt.co.uk](https://blog.timhutt.co.uk/against-submodules/).
- [V] **Subtree (primary)** — `git subtree` (contrib) merges a subproject into a subdirectory, optionally with its history; commands add, merge, split, pull, push; options `--prefix`, `--squash`, `--rejoin`, `--annotate`; needs no `.gitmodules` or gitlinks, so consumers of the repo need not know it is used — [git-subtree documentation](https://github.com/git/git/blob/master/contrib/subtree/git-subtree.adoc). The underlying subtree merge (`read-tree --prefix`, `-Xsubtree`) is shown in Pro Git — [Advanced Merging: Subtree Merging](https://git-scm.com/book/en/v2/Git-Tools-Advanced-Merging).
- [V] **Atlassian's subtree article** — "Git subtree: the alternative to Git submodule" (Nicola Paolucci): advantages — simple workflow, code present right after clone, no new metadata files, consumers need learn nothing new, contents can be modified in place; drawbacks — a new merge strategy to learn, contributing back upstream is more complicated, and you must avoid mixing super- and sub-project changes in one commit; available in stock Git since v1.7.11 (May 2012); also mentions Google's `repo` tool as another alternative — [Atlassian](https://www.atlassian.com/git/tutorials/git-subtree).
- [V] **git-subrepo** — third-party command (Ingy döt Net; MIT; ~3.6k stars) that clones an external repo into a subdirectory with a `.gitrepo` marker; users of the parent repo need not install it; pitched as fixing usability problems of both submodules and subtree — [git-subrepo](https://github.com/ingydotnet/git-subrepo).
- [V] **Architectural framing** — a submodule-based "super repository" is one of several sharding strategies alongside multi-repo and monorepo — [Git's database internals V](https://github.blog/open-source/git/gits-database-internals-v-scalability/); submodule-related config that practitioners recommend: `status.submoduleSummary`, `diff.submodule log`, `submodule.recurse` — [jvns.ca: popular git config options](https://jvns.ca/blog/2024/02/16/popular-git-config-options/). Practice material: the Git Katas "submodules" kata and the Git Flight Rules submodule section — [git-katas overview](https://raw.githubusercontent.com/eficode-academy/git-katas/master/Overview.md), [Git Flight Rules](https://github.com/k88hudson/git-flight-rules).

### Inferences
- The well-documented submodule pain points reduce to one fact a course should teach first: the superproject stores a commit ID, not a branch, and Git's defaults do not keep the nested checkout in sync. Most "gotchas" (detached HEAD, stale pointers, missing pushes, branch-switch debris) follow from that.
- Decision guidance supported by the sources: package manager if the ecosystem has one (GitHub Blog, Hutt); subtree/subrepo for vendored third-party code you rarely push back (Atlassian, Hutt); monorepo + sparse-checkout/partial clone for tightly coupled first-party code (Stolee, section 7); submodules for independent components with separate release cycles or access control (gitsubmodules' own use cases).

### Gaps
- gitmodules(5) and Atlassian's separate "Git submodules" page were not read (the latter's body could not be extracted).
- `git subtree` lives in contrib and has no page in the git-scm.com reference index; its availability depends on how Git was packaged.
- No quantitative study comparing submodule and subtree outcomes was found.

## 9. Commit signing and identity: GPG vs SSH vs Sigstore gitsign, and the commit-author-spoofing problem

### Takeaway
Git's author and committer fields are unauthenticated metadata, and GitHub attributes commits by matching the email, so impersonation is trivial unless commits are signed and verification is enforced (rulesets' "require signed commits", vigilant mode). The best explanatory set is: GitHub's commit-signature-verification docs (GPG, SSH, S/MIME; SSH is the simplest), Git's own gitformat-signature page and the Git 2.34 release notes for SSH signing, Ken Muse's comparison article, and the Sigstore gitsign README for keyless signing (which GitHub does not display as "Verified"). Pro Git 2e covers GPG only.

### Cited Findings
- [V] **The spoofing problem (primary acknowledgement)** — GitHub links a commit to an account by matching the email address in the commit to an email on a GitHub account; commits show up under the wrong user when the local Git configuration carries someone else's email — [GitHub Docs: why are my commits linked to the wrong user](https://docs.github.com/en/pull-requests/committing-changes-to-your-project/troubleshooting-commits/why-are-my-commits-linked-to-the-wrong-user). GitHub's vigilant-mode page states that Git lets you set the author and committer identity yourself, which is why unsigned commits attributed to you can be flagged — [GitHub Docs: vigilant mode](https://docs.github.com/en/authentication/managing-commit-signature-verification/displaying-verification-statuses-for-all-of-your-commits).
- [V] **Worked demonstration (secondary)** — "How to Spoof Any User on GitHub…and What to Do to Prevent It" (Matt Calhoun, Gruntwork, 8 Oct 2020): setting `user.name`/`user.email` to another person's values and pushing (with write access) makes GitHub display that person's avatar and name; mitigations are signed commits, requiring signed commits via branch protection, and additional checks — [Gruntwork blog](https://www.gruntwork.io/blog/how-to-spoof-any-user-on-github-and-what-to-do-to-prevent-it).
- [V] **GitHub verification model** — supports GPG, SSH and S/MIME; statuses Verified, Partially verified, Unverified; with vigilant mode every commit attributed to you gets a status, and unsigned ones show as Unverified (enable only if you sign everything); verification is recorded persistently so a later key rotation or expiry does not flip old commits; commits created by "rebase and merge" on GitHub cannot carry your signature; SSH is presented as the simplest option for most users — [GitHub Docs: about commit signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification), [vigilant mode](https://docs.github.com/en/authentication/managing-commit-signature-verification/displaying-verification-statuses-for-all-of-your-commits).
- [V] **SSH signing setup** — needs Git 2.34 or later; `gpg.format ssh` and `user.signingkey` pointing at the public key file — [GitHub Docs: telling Git about your signing key](https://docs.github.com/en/authentication/managing-commit-signature-verification/telling-git-about-your-signing-key). Git 2.34 added SSH signing, with verification driven by an allowed-signers file — [Highlights from Git 2.34 (Taylor Blau, 15 Nov 2021)](https://github.blog/open-source/git/highlights-from-git-2-34/).
- [V] **How signatures are stored (primary)** — `gpg.format` selects PGP, SSH or X.509; tag signatures are appended to the tag object, commit signatures live in the `gpgsig` header, signed tags merged into a commit are embedded as `mergetag` — [gitformat-signature](https://git-scm.com/docs/gitformat-signature); SHA-256 repositories add a `gpgsig-sha256` header — [hash-function-transition](https://git-scm.com/docs/hash-function-transition).
- [V] **Pro Git** — "Signing Your Work" covers GPG key creation, signed tags and commits, `--show-signature`, `merge --verify-signatures`; nothing on SSH or X.509 — [Pro Git](https://git-scm.com/book/en/v2/Git-Tools-Signing-Your-Work).
- [V] **Comparison article** — "Comparing GitHub Commit Signing Options" (Ken Muse, 7 Oct 2022): GPG — decentralised web of trust, best documented and most widely supported, expiry handled by the key owner, steep learning curve and hard to manage centrally; SSH — keys developers already have, simplest setup, but plain SSH keys have no expiry and SSH certificates are not accepted for commit verification on GitHub; S/MIME — X.509 certificates from a CA with central issuance and revocation, enterprise-friendly but needs extra tooling (smimesign) — [kenmuse.com](https://www.kenmuse.com/blog/comparing-github-commit-signing-options/).
- [V] **Sigstore gitsign (primary)** — keyless signing: Git is configured to use the X.509 format with gitsign as the signing program; each signature uses a short-lived certificate issued against an OIDC identity (e.g. a GitHub or Google login) and is recorded in the Rekor transparency log; signing therefore needs network access; `gitsign verify` (with expected certificate identity and issuer) is preferred over `git verify-commit`; GitHub does not show these commits as verified because Sigstore's CA is not in GitHub's trust roots and the certificates expire quickly — [sigstore/gitsign README](https://github.com/sigstore/gitsign).
- [V] **Practical gitsign walkthrough** — "Using Gitsign for Keyless Git Commit Signing" (Ken Muse, 12 Apr 2025): use in GitHub Actions needs `id-token: write`; commits show as Unverified in the GitHub UI; Rekor logging cannot currently be turned off; GitOps tools have limited X.509 support — [kenmuse.com](https://www.kenmuse.com/blog/using-gitsign-for-keyless-git-commit-signing/).
- [V] **Enforcement** — rulesets include a "require signed commits" rule (only signed and verified commits may be pushed to matching refs) — [GitHub Docs: available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).
- [V] **Interactions worth teaching** — history rewriting (filter-repo) strips signatures — [GitHub Docs: removing sensitive data](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository); rebasing drops signatures and trailers unless re-signed — [jvns.ca: rebase problems](https://jvns.ca/blog/2023/11/06/rebasing-what-can-go-wrong-/); push signing (`git push --signed`) exists but the major hosts do not support it — [GitButler: Git Tips 2](https://blog.gitbutler.com/git-tips-2-new-stuff-in-git/); `gpg.format ssh` appears among options practitioners commonly set — [jvns.ca: popular git config options](https://jvns.ca/blog/2024/02/16/popular-git-config-options/).
- [V] Curriculum signals: the 2026 GH-200 outline expects candidates to know artifact attestations/provenance and SHA pinning, and commit signing appears as a W3Schools topic but in none of the video crash courses reviewed — [GH-200 study guide](https://learn.microsoft.com/en-us/credentials/certifications/resources/study-guides/gh-200), [W3Schools](https://www.w3schools.com/git/).

### Inferences
- A signature proves that the holder of a key (or, with gitsign, of an OIDC identity at signing time) produced the commit object; it does not prove the named author wrote the code, nor that the content is safe. A course should separate three questions: who is displayed (email matching), who signed (key/identity), and what is enforced (rulesets, vigilant mode).
- Practical recommendation consistent with the sources: SSH signing as the default for individuals (lowest friction, supported by Git ≥ 2.34 and GitHub); GPG where cross-platform/toolchain compatibility or key expiry matters; S/MIME or gitsign where an organisation wants central identity — with the explicit caveat that gitsign commits are not shown as Verified on GitHub as of the sources checked.
- Because squash/rebase merges and history rewrites create new commits, "require signed commits" interacts with merge-method choice; this belongs in the rulesets lesson, not only the signing lesson.

### Gaps
- The official Sigstore documentation page for gitsign returned 404 at the guessed URL; the README was used instead. gitsign's latest release number/date was not captured.
- git-config's entries for `gpg.ssh.allowedSignersFile`, `gpg.ssh.revocationFile` and related options could not be extracted (page truncated), so option semantics beyond those named in GitHub's docs and the 2.34 notes are not sourced here.
- Whether GitHub has changed its handling of Sigstore-signed commits or SSH certificates since the 2022–2025 articles was not verified against a 2026 primary source.
- No measured data on how many repositories enforce signing, or on real-world impersonation incidents, was found.
