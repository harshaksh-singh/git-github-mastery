# Verified 2026 facts retire most Git tutorials

**PHASE 0 — DEEP RESEARCH REPORT · Git and GitHub Deep Mastery program · factual baseline as of 1 October 2026**

As of 1 October 2026 the latest stable Git is **2.56.0 (released 28 September 2026)**, Git 3.0 is announced but unreleased, and GitHub has changed enough since January 2025 (rulesets as the recommended governance layer, generally available fine-grained tokens, a re-packaged security suite, a Node 24-only Actions runtime, `actions/checkout` v7, stacked pull requests in preview) that most pre-2025 teaching material is now wrong in specific, checkable places. The learner's Homebrew **Git 2.55.0 is exactly one feature release behind and already contains every published core-Git security fix**, so upgrading it is optional; the learner's **GitHub CLI 2.88.1 is 14 feature releases behind and misses six security-fix releases**, so upgrading it is advised; git-lfs 3.7.1 is one release behind 3.8.0 with no security consequence recorded. The right factual spine for the program is primary documentation (the git-scm.com man pages including the new `gitdatamodel` page, the release notes, the BreakingChanges document, docs.github.com and the GitHub Changelog), because Pro Git's second edition has been frozen since May 2024 and GitHub's own documentation lags its releases in several verified places. No single video or book covers the zero-to-senior path: CampusX has no current free Git course, CodeWithHarry's July 2026 one-shot is the most current Hindi starting point but teaches no history undo, and the strongest material is spread across MIT's 2026 Missing Semester lecture, Boot.dev's 2024 course, Git Merge contributor talks and security-conference talks. The topics that popular tutorials omit are precisely the production-critical ones (the index and conflict stages, reflog recovery, safe force-pushing, rulesets and CODEOWNERS, Actions security, secret-leak response), so the program must build those from primary sources. Evidence quality is uneven and is marked throughout: several items rest on secondary reporting or could not be confirmed (for example GitHub's reported SHA-256 private preview and the calendar months for Git 2.98, 2.99 and 3.0), and every such flag recorded in the research notes is carried forward at the end of the section it belongs to.

**How to read this report.** Every factual statement comes from seven sets of research notes compiled on 1 October 2026; nothing has been added from memory. Eight labels separate kinds of statement: **[STABLE]** marks fundamentals unchanged for many years; **[GIT]** marks current behavior of Git the tool (true in 2.55 and 2.56 unless a version is named); **[GITHUB]** marks current behavior of GitHub the platform per live documentation on 1 October 2026; **[VERSION]** marks behavior tied to a named version or date; **[OUTDATED]** marks deprecated or superseded practice; **[UNVERIFIED]** marks anything the notes could not confirm from an authoritative source, and **[CONFLICT]** marks disagreement between sources. **[INFERENCE]** marks reasoning by the researchers or by this synthesis rather than a sourced fact. Git man-page facts were read from the documentation sources at the `v2.56.0` and `v2.55.0` tags of the official repository; "local check" means the behavior was reproduced on the learner's own Mac (Homebrew Git 2.55.0, macOS 26.5.2) with only built-in defaults active. Video assessments rest on caption searches, chapter lists and descriptions, not on full viewing, and book data marked "search-index only" could not be opened at the publisher. Git (the tool) and GitHub (the platform) are kept apart throughout: a pull request, a ruleset, a release, a "Verified" badge and a workflow are GitHub objects; commits, refs, the index, reflogs, merges and rebases are Git.

### Git 3.0 is announced, undated in official documentation, and preceded by 2.98 and 2.99

**[GIT]** The official BreakingChanges document, byte-identical at 2.55.0, 2.56.0 and on `master` on 1 October 2026, still states that no release date is planned for the breaking version, and records that the previous breaking releases were 1.6.0 (August 2008) and 2.0 (May 2014) ([BreakingChanges](https://github.com/git/git/blob/v2.56.0/Documentation/BreakingChanges.adoc)). **[VERSION]** On 28 September 2026 the maintainer announced that the next release will be numbered **2.98**, scheduled near the end of 2026, followed by **2.99** to prepare for 3.0 ([mailing-list mirror](https://ratatoskr.run/git/2026/09/17654892)). Calendar months come only from secondary reports: LWN reports December 2026 for 2.98 and April 2027 for 2.99 as a long-term-support release with 3.0 released at the same time ([LWN](https://lwn.net/Articles/1094575/)), and GitLab's 2.56 post gives December 2026 and spring 2027, adding that 2.99 and 3.0 ship together and differ only in the breaking-changes flag ([GitLab](https://about.gitlab.com/blog/whats-new-in-git-2-56-0/)). The official text promises only that the last version before 3.0 will be a long-term-support release receiving important bug fixes for at least four release cycles and security fixes for six ([BreakingChanges](https://github.com/git/git/blob/v2.56.0/Documentation/BreakingChanges.adoc)).

**[VERSION]** The planned 3.0 changes affect **newly created repositories only**: SHA-256 becomes the default hash (conditional on libraries, applications and forges being ready, with no plan to deprecate SHA-1), reftable becomes the default ref storage (conditional on JGit, libgit2 and Gitoxide support), `main` becomes the default branch name, Rust becomes a mandatory build dependency (auto-detected in 2.52, enabled by default in 2.55), and `safe.bareRepository` changes from `all` to `explicit`. Scheduled removals are grafts, `git pack-redundant`, the `.git/branches/` and `.git/remotes/` directories, `git name-rev --stdin`, `git whatchanged`, `core.commentString=auto` and `core.preferSymlinkRefs=true`. The same document records an explicit decision that **`git checkout` will not be deprecated**: `checkout`, `switch` and `restore` all stay ([BreakingChanges](https://github.com/git/git/blob/v2.56.0/Documentation/BreakingChanges.adoc)). A proposal to accept only lowercase hexadecimal object IDs was still awaiting review on 28 September 2026 and is not an accepted decision ([What's cooking](https://ratatoskr.run/git/2026/09/17654892)). **[INFERENCE]** The safest classroom sentence is that Git 3.0 is announced but unreleased, that transitional releases 2.98 and 2.99 come first, and that no date is committed in official documentation; learners can opt in or out of each default ahead of time with `init.defaultObjectFormat`, `init.defaultRefFormat`, `init.defaultBranch` and `safe.bareRepository`.

### Object formats and ref storage: SHA-1 with collision detection and the "files" backend remain today's defaults

**[GIT]** `sha1` is still the default object format in 2.56, and the SHA-1 implementation has been the collision-detecting variant by default since 2.13; the learner's build reports `SHA-1: SHA1_DC`, `default-hash: sha1` and `default-ref-format: files` ([git-init](https://github.com/git/git/blob/v2.56.0/Documentation/git-init.adoc), [RelNotes 2.13](https://github.com/git/git/blob/master/Documentation/RelNotes/2.13.0.adoc)). **[VERSION]** SHA-256 repositories were marked experimental in 2.29 and have been a supported format since 2.42, but there is still **no interoperability between SHA-256 and SHA-1 repositories**; cloning always adopts the remote's format, and the `compatObjectFormat` extension exists only for development and is not meant for end users ([disclaimer](https://github.com/git/git/blob/v2.56.0/Documentation/object-format-disclaimer.adoc), [extensions](https://github.com/git/git/blob/v2.56.0/Documentation/config/extensions.adoc)). Hosting is the bottleneck: Forgejo has supported SHA-256 repositories since v7.0 ([Forgejo](https://forgejo.org/2024-04-release-v7-0/)), GitLab announced experimental support in August 2024 ([GitLab](https://about.gitlab.com/blog/gitlab-now-supports-sha256-repositories/)), and **GitHub had no publicly available SHA-256 support on 1 October 2026**. A GitHub private preview is reported by GitLab's blog, by a community comment quoting a GitHub employee's conference slide, and by a Git Merge 2026 speaker who corrected her own slide on stage, but no GitHub blog, changelog or documentation page announces it ([GitLab](https://about.gitlab.com/blog/whats-new-in-git-2-56-0/), [community discussion](https://github.com/orgs/community/discussions/12490), [Git Merge 2026 talk](https://www.youtube.com/watch?v=eJJp0RE7cd4)). **[INFERENCE]** Every exercise repository that touches GitHub must therefore stay SHA-1, and any tool or regular expression that assumes 40 hexadecimal digits will break on SHA-256 repositories.

**[VERSION]** reftable, a binary block-structured store for refs and reflogs, has been available since 2.45 and is opt-in through `git init --ref-format=reftable`, `init.defaultRefFormat` (2.47) or `git refs migrate --ref-format=<format>` (2.46), whose documented limitations are that repositories with worktrees cannot be migrated and concurrent writes cannot be blocked during migration ([git-refs](https://github.com/git/git/blob/v2.55.0/Documentation/git-refs.adoc), [RelNotes 2.45](https://github.com/git/git/blob/master/Documentation/RelNotes/2.45.0.adoc)). In a reftable repository the refs live under `$GIT_DIR/reftable/`, and `.git/HEAD` is a stub containing `ref: refs/heads/.invalid` ([reftable design](https://github.com/git/git/blob/v2.56.0/Documentation/technical/reftable.adoc)). The stated reasons for making it the default are case and Unicode-normalisation clashes on Windows and macOS filesystems, the cost of rewriting `packed-refs`, and non-atomic multi-ref updates in the "files" backend ([BreakingChanges](https://github.com/git/git/blob/v2.56.0/Documentation/BreakingChanges.adoc)). **[INFERENCE]** Any lesson that reads `.git/refs/heads/<branch>` by hand must say "in a files-format repository"; the format-independent habit is plumbing such as `git for-each-ref`, `git rev-parse`, `git symbolic-ref` and `git refs list`.

## 2. Current GitHub capabilities: rulesets, short-lived tokens and a Node 24-only Actions runtime define the 2026 platform

Everything in this section is GitHub platform behavior layered on top of Git, read from docs.github.com, the GitHub Changelog and cli.github.com on 1 October 2026. One meta-fact matters for anyone citing documentation: GitHub restructured its pull-request and code-security documentation, so older URLs now redirect to `/pull-requests/reference/...`, `/pull-requests/how-tos/...` and `/code-security/concepts|how-tos|reference/...` ([example redirect target](https://docs.github.com/en/pull-requests/reference/pull-request-merges)).

### Governance: rulesets are the recommended mechanism, and classic branch protection still exists

**[GITHUB]** A ruleset is a named list of rules that targets branches, tags or pushes in one repository or across an organization; a repository can have up to 75, several can apply to the same branch at once, their enforcement status can be changed without deleting them, and anyone with read access can see the active ones, including by appending `/rules` to the repository URL ([About rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets), [Managing rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/managing-rulesets-for-a-repository)). Classic branch protection rules remain a documented, current feature, but only one classic rule can apply to a branch at a time ([About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)). **[VERSION]** On 7 July 2026 GitHub stated in its changelog that rulesets are the recommended way to protect branches ([changelog](https://github.blog/changelog/2026-07-07-restrict-who-can-dismiss-reviews-in-rulesets/)), and since 11 August 2026 a "Convert to ruleset" control under Settings → Branches migrates one classic rule at a time into one or more Active rulesets; the conversion covers every classic setting except the standalone conversation-resolution requirement, which in rulesets exists only inside the pull-request rule ([changelog](https://github.blog/changelog/2026-08-11-automatically-migrate-branch-protection-rules-to-repository-rulesets/), [conversion docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/converting-branch-protections-to-rulesets)). No changelog entry or documentation page between January 2025 and 1 October 2026 announces a deprecation or sunset date for classic rules.

**[GITHUB]** Rulesets have no priority order. When several target the same ref their rules are aggregated, the most restrictive version of each rule wins, and they also layer with any classic rule on the same branch, so a change must satisfy all of them ([rule layering](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets#about-rule-layering)). An organization-level ruleset can be made stricter by a repository-level one but never looser; forks do not inherit branch or tag rulesets, but they do inherit push rulesets ([organization rulesets](https://docs.github.com/en/enterprise-cloud@latest/organizations/managing-organization-settings/creating-rulesets-for-repositories-in-your-organization)). Bypass is explicit: eligible actors are repository admins, organization and enterprise owners, the maintain or write roles, non-secret teams, GitHub Apps and Dependabot, each either always allowed or allowed for pull requests only ([bypass permissions](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository#granting-bypass-permissions-for-your-branch-or-tag-ruleset)); individual users became eligible on 7 May 2026 ([changelog](https://github.blog/changelog/2026-05-07-repository-rulesets-user-bypass-and-branch-renaming/)), and an "exempt" type that silently skips enforcement was added on 10 September 2025 ([changelog](https://github.blog/changelog/2025-09-10-github-ruleset-exemptions-and-repository-insights-updates/)). Classic rules work differently: by default they do not apply to repository admins unless the setting that forbids bypassing is enabled ([About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)). Branch and tag targets use `fnmatch` syntax in which `*` does not cross a `/`, so `qa/*` does not match `qa/foo/bar` while `qa/**/*` does ([fnmatch syntax](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository#using-fnmatch-syntax)).

| Ruleset rule (GitHub) | Verified facts that matter in practice |
|---|---|
| Restrict creations, updates, deletions | Only bypass actors may create, push to or delete matching refs; "Restrict deletions" is selected by default ([available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)) |
| Block force pushes | Enabled by default in a new ruleset; side effect: the default branch cannot be changed or renamed without bypass rights ([available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#block-force-pushes)) |
| Require linear history | Blocks merge commits on the target; pull requests must use squash or rebase merge |
| Require a pull request before merging | Sub-options: required approvals, dismiss stale approvals, code-owner review (any one owner suffices), restrict who can dismiss reviews, approval of the most recent reviewable push, resolved conversations, allowed merge methods, required team reviewers by file pattern (GA 17 Feb 2026, up to 15 teams) ([required reviewers](https://github.blog/changelog/2026-02-17-required-reviewer-rule-is-now-generally-available/)) |
| Require status checks | "Strict" mode (branch must be up to date) is the default; a check can be pinned to an expected GitHub App; job check name is the job name, and for reusable workflows it is the caller job name, a slash, then the reusable job name ([troubleshooting rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/troubleshooting-rules)) |
| Require signed commits | Rulesets check only commits not reachable from other branches; unsigned commits on the head branch can block even a squash merge, because GitHub evaluates the commits introduced by the test merge ([signed commits rule](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-signed-commits)) |
| Require merge queue; require deployments | Merge-queue rule is documented only in the Enterprise Cloud view and is unavailable in organization-level rulesets |
| Require code scanning, code quality, coverage, secret-scanning results | Code quality went GA 20 July 2026; coverage thresholds (30 June 2026) and "secret scanning alerts are resolved" (9 Sept 2026) are public previews ([secret-scanning rule](https://github.blog/changelog/2026-09-09-block-pull-requests-with-exposed-secrets-from-merging/), [coverage rule](https://github.blog/changelog/2026-06-30-github-code-coverage-merge-protection-for-pull-requests/)) |
| Require workflows to pass | Configured at organization or enterprise level; triggers limited to `pull_request`, `pull_request_target`, `merge_group`; the workflow's own filters are ignored; blocks direct pushes ([Enterprise view](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-workflows-to-pass-before-merging)) |
| Metadata restrictions | Enterprise plan; restrict commit message, author or committer email, branch and tag names; rejected commits still enter the repository as retrievable but unreachable objects ([Enterprise view](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#metadata-restrictions)) |
| Push rules (push rulesets only) | Restrict file paths, path length, extensions and file size across the whole fork network; at most 1,000 ref updates per push; path exceptions in preview since 25 Aug 2026 ([push rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets#push-rulesets), [changelog](https://github.blog/changelog/2026-08-25-push-rules-in-rulesets-now-support-path-exceptions/)) |

**[GITHUB]** Availability is plan-gated in ways a learner will hit immediately. Rulesets and classic protections work in public repositories on GitHub Free and in public and private repositories on Pro, Team and Enterprise Cloud; organization-level rulesets came to the Team plan on 16 June 2025 ([changelog](https://github.blog/changelog/2025-06-16-organization-rulesets-now-available-for-github-team-plans/)); enterprise-level rulesets became generally available on 24 March 2025 ([changelog](https://github.blog/changelog/2025-03-24-enterprise-custom-properties-enterprise-rulesets-and-pull-request-merge-method-rule-are-all-now-generally-available/)); push rulesets need the Team plan and a private or internal repository; the "Evaluate" enforcement status, metadata restrictions and ruleset history (180 days) appear only in the Enterprise Cloud documentation ([Enterprise view of About rulesets](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)). Rulesets can be imported and exported as JSON, with prebuilt examples in `github/ruleset-recipes` ([changelog](https://github.blog/changelog/2025-02-13-repositories-ruleset-history-import-and-export-are-generally-available/)). When a classic protection refuses a push, the Git client shows `remote: error: GH006: Protected branch update failed` ([About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)).

### A pull request is a GitHub object built on hidden Git refs and a test merge commit

**[GITHUB]** Opening a pull request creates read-only Git references for its head and, when possible, for a simulated merge result. The head is fetchable with plain Git as `git fetch origin pull/ID/head:BRANCH_NAME`, and a push to the `refs/pull/` namespace is rejected as an update to a hidden ref ([checking out pull requests locally](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/checking-out-pull-requests-locally)). GitHub computes mergeability by creating a test merge commit whose parents are the latest base-branch commit and the pull request's head; it is added to neither branch ([REST pulls](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request)). **[VERSION]** Since 19 February 2026 that test merge is regenerated only when the pull-request branch is pushed, when the merge base changes, or when the existing one is older than 12 hours, no longer on page view ([changelog](https://github.blog/changelog/2026-02-19-changes-to-test-merge-commit-generation-for-pull-requests/)). The diff a pull request shows is a three-dot diff, from the merge base to the head, which is why it describes what the pull request introduces rather than how the two tips differ ([branches reference](https://docs.github.com/en/pull-requests/reference/branches#three-dot-and-two-dot-git-diff-comparisons)); the base is pinned to a commit when the pull request is opened ([changing the base](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/changing-the-base-branch-of-a-pull-request)).

The three merge buttons are GitHub server-side operations whose results differ from the local Git commands with similar names, and the differences explain a large share of "why did my SHA change" questions.

| Merge method (GitHub) | What lands on the base branch | Commit IDs and committer | Signature on the result |
|---|---|---|---|
| Create a merge commit | All head-branch commits plus a merge commit, using `--no-ff` | Original commit IDs preserved | Merge commit signed by GitHub's web-flow key ([merge methods](https://docs.github.com/en/pull-requests/reference/pull-request-merges), [signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification)) |
| Squash and merge | One new commit, fast-forwarded onto the base | New commit; individual authorship and timing detail is lost; reusing the head branch later re-lists squashed commits and repeats conflicts | Signed by GitHub ([signed commits rule](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-signed-commits)) |
| Rebase and merge | Each commit replayed individually, no merge commit; limited to 100 commits ([limits](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits#rebase-limits)) | **Always new commit IDs and updated committer**; commits that were empty are dropped | **Unsigned**: GitHub cannot sign on the user's behalf ([signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification#signature-verification-for-rebase-and-merge)) |

**[GITHUB]** Reviews have three outcomes (comment, approve, request changes); a request for changes blocks merging only when a ruleset or classic rule requires a pull request ([reviewing changes](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request)). An approval is dismissed as stale when the diff changes after approval, including when the merge base introduces new changes ([pull request rule](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-a-pull-request-before-merging)). Draft pull requests cannot be merged and do not trigger code-owner review requests; since 1 May 2025 they are free in every repository ([changelog](https://github.blog/changelog/2025-05-01-draft-pull-requests-are-now-available-in-all-repositories/)). A pull request is marked merged if its head commits become reachable from the base by any route, even when protections on that pull request were not satisfied ([indirect merges](https://docs.github.com/en/pull-requests/reference/pull-request-merges#indirect-merges)). Closing keywords such as `fixes #N` act only when the pull request targets the default branch ([linking issues](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)).

**[GITHUB]** Merge queue is available in public repositories owned by organizations and in private repositories on Enterprise Cloud; it builds temporary `gh-readonly-queue/{base_branch}` branches that contain the base, the queued changes ahead and the pull request, and required checks are reported only if the workflow also triggers on the `merge_group` event ([merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)). Auto-merge merges once required reviews and checks pass and is available on public repositories on Free and on public and private repositories on paid plans ([auto-merge](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/automatically-merging-a-pull-request)). Display limits are real causes of confusion: a pull-request diff stops at 20,000 loadable lines or 1 MB, 300 files, and commit listings at 250 commits ([repository limits](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits)).

**[VERSION]** The pull-request surface changed heavily in 2025 and 2026: a redesigned "Files changed" page became the default on 22 January 2026 ([changelog](https://github.blog/changelog/2026-01-22-improved-pull-request-files-changed-page-on-by-default/)); **stacked pull requests** entered public preview on 30 July 2026 with the `github/gh-stack` CLI extension, same-repository branches only, and rules evaluated against the base of the stack ([changelog](https://github.blog/changelog/2026-07-30-stacked-pull-requests-are-now-in-public-preview/), [reference](https://docs.github.com/en/pull-requests/reference/stacked-pull-requests)); an asynchronous merge API became generally available on 1 October 2026 and is now the recommended programmatic merge path and the only one that supports stacks ([changelog](https://github.blog/changelog/2026-10-01-github-async-merge-api-generally-available/)); Copilot code review has been generally available since 4 April 2025 and since 1 September 2026 can, in preview and off by default, submit an approving review that counts toward required approvals ([changelog](https://github.blog/changelog/2026-09-01-copilot-code-review-can-now-approve-pull-requests/)); the Copilot coding agent was renamed Copilot cloud agent on 1 April 2026 and has signed its commits since 3 April 2026 ([rename](https://github.blog/changelog/2026-04-01-research-plan-and-code-with-copilot-cloud-agent/), [signing](https://github.blog/changelog/2026-04-03-copilot-cloud-agent-signs-its-commits/)); repositories can disable pull requests or restrict them to collaborators (13 February 2026) and admins can archive pull requests (16 July 2026) ([PR access](https://github.blog/changelog/2026-02-13-new-repository-settings-for-configuring-pull-request-access/), [archiving](https://github.blog/changelog/2026-07-16-repository-admins-can-archive-pull-requests/)).

### CODEOWNERS requests reviews; only a rule makes them mandatory

**[GITHUB]** A `CODEOWNERS` file is looked up in `.github/`, then the repository root, then `docs/`, and the first one found wins; it is read from the pull request's **base** branch, must be under 3 MB, uses gitignore-like patterns with three documented exceptions (no `\#` escaping, no `!` negation, no `[ ]` ranges), is case-sensitive, and resolves ownership by the **last matching pattern**. Owners need explicit write access, and a team must be visible and hold write access itself. Invalid lines are skipped and are listed by a REST endpoint for CODEOWNERS errors. On its own the file only requests reviews; enforcement requires the code-owner review option in a ruleset or classic rule, where approval from any single listed owner suffices ([About code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners), [REST endpoint](https://docs.github.com/en/rest/repos/repos#list-codeowners-errors)). The newer "Required reviewers" ruleset rule supports negation and per-team approval counts and is described by GitHub as augmenting, not replacing, CODEOWNERS ([changelog](https://github.blog/changelog/2026-02-17-required-reviewer-rule-is-now-generally-available/)).

### Authentication uses tokens and keys; account passwords stopped working for Git in 2021

**[OUTDATED]** GitHub.com has not accepted account passwords for Git operations since **13 August 2021** ([GitHub Blog](https://github.blog/security/application-security/token-authentication-requirements-for-git-operations/)). **[GITHUB]** Git over HTTPS authenticates with a token, normally supplied by GitHub CLI or Git Credential Manager rather than typed ([caching credentials](https://docs.github.com/en/get-started/git-basics/caching-your-github-credentials-in-git)); `gh auth login` runs a browser flow and stores a token in the system credential store, and `gh auth setup-git` registers `gh` as Git's credential helper ([gh auth login](https://cli.github.com/manual/gh_auth_login), [gh auth setup-git](https://cli.github.com/manual/gh_auth_setup-git)). GitHub recommends fine-grained personal access tokens over classic ones; fine-grained tokens became generally available on 18 March 2025, are scoped to one owner and optionally to specific repositories, and by default need organization-owner approval ([managing tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens), [changelog](https://github.blog/changelog/2025-03-18-fine-grained-pats-are-now-generally-available/)). Their documented gaps are material for open-source work: they cannot be used to contribute to public repositories where the user is not a member, to act as an outside collaborator, to span several organizations, to access Packages or to call the Checks API. A classic token, by contrast, reaches every repository the user can reach. Token prefixes identify the type (`ghp_` classic, `github_pat_` fine-grained, `gho_` OAuth, `ghu_` App user, `ghs_` installation, `ghr_` refresh), and since 27 April 2026 newly minted installation tokens, including the Actions `GITHUB_TOKEN`, use a roughly 520-character format, which breaks code that assumes 40 characters ([token formats](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-authentication-to-github#githubs-token-formats), [changelog](https://github.blog/changelog/2026-04-24-notice-about-upcoming-new-format-for-github-app-installation-tokens/)).

**[GITHUB]** For SSH the documented key generation is `ssh-keygen -t ed25519 -C "your_email@example.com"`; DSA keys have been unsupported since 15 March 2022, the same change that removed the unencrypted `git://` protocol ([generating a key](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/generating-a-new-ssh-key-and-adding-it-to-the-ssh-agent), [GitHub Blog](https://github.blog/security/application-security/improving-git-protocol-security-github/)). **[VERSION]** A further tightening announced on 22 September 2026 takes effect after this report's date: RSA keys uploaded after 14 October 2026 must be at least 3072 bits, and the SHA-1 `ssh-rsa` signature type and one Diffie-Hellman key exchange are removed on 13 January 2027 after brownouts on 4 November and 9 December 2026; Ed25519 and ECDSA keys are unaffected ([changelog](https://github.blog/changelog/2026-09-22-security-improvements-for-ssh/)). SHA-1 in HTTPS/TLS was disabled on 15 September 2026 ([changelog](https://github.blog/changelog/2026-09-15-sha-1-in-https-on-github-sunset/)). GitHub Apps with one-hour installation tokens are the preferred integration identity over OAuth apps and machine users; deploy keys are single-repository SSH keys that are read-only by default and never expire ([Apps versus OAuth](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/deciding-when-to-build-a-github-app), [deploy keys](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys)). Under SAML single sign-on, classic tokens and SSH keys must be separately authorized for each organization ([SSO](https://docs.github.com/en/enterprise-cloud@latest/authentication/authenticating-with-single-sign-on/about-authentication-with-single-sign-on)), and two-factor authentication has been mandatory for code contributors since March 2023 ([mandatory 2FA](https://docs.github.com/en/authentication/securing-your-account-with-two-factor-authentication-2fa/about-mandatory-two-factor-authentication)).

### Roles, organizations and fork networks

**[GITHUB]** Organization repositories have five built-in roles in increasing order of access (Read, Triage, Write, Maintain, Admin), and personal-account repositories have only an owner and collaborators ([repository roles](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization), [personal repositories](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/permission-levels-for-a-personal-account-repository)). Merging, pushing, applying suggestions and acting as a code owner need Write; managing rulesets and branch protection, changing visibility, managing deploy keys and merging on protected branches without approving reviews are Admin-only. The Maintain role's documented ability to push to protected branches applies to classic rules only, because rulesets use a separate bypass model. Custom repository roles (up to 20) exist only on Enterprise Cloud ([custom roles](https://docs.github.com/en/enterprise-cloud@latest/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/about-custom-repository-roles)). **[INFERENCE]** Effective access is the highest of the organization's base permission, team grants (inherited down nested teams), direct grants and organization-owner admin rights; outside collaborators receive direct grants only.

**[GITHUB]** A fork is a separate repository with its own settings, but **every repository in a fork network shares Git data**: GitHub documents that commits pushed to any repository in the network can be accessible from the others, including the upstream, even after a fork is deleted, and that upstream owners can read all forks ([forks reference](https://docs.github.com/en/pull-requests/reference/forks#important-security-considerations)). Forks of public repositories are public and forks of private repositories are private; deleting a private repository deletes its private forks, while deleting a public one promotes an active public fork to be the new upstream. A fork is synchronised in the web interface with "Sync fork" or from the terminal with `gh repo sync`, which fast-forwards by default and performs a hard reset when `--force` is given ([syncing a fork](https://docs.github.com/en/pull-requests/how-tos/work-with-forks/syncing-a-fork), [gh repo sync](https://cli.github.com/manual/gh_repo_sync)). A deleted repository can be restored within 90 days unless it belonged to a fork network that is not empty ([restoring a repository](https://docs.github.com/en/repositories/creating-and-managing-repositories/restoring-a-deleted-repository)).

### Issues, projects, releases and packages

**[VERSION]** Issues gained real structure: sub-issues (up to 100 per parent, eight levels deep) and organization-level issue types became generally available on 9 April 2025, blocked-by and blocking dependencies on 21 August 2025, and typed issue fields on 2 July 2026 ([issues GA](https://github.blog/changelog/2025-04-09-evolving-github-issues-and-projects/), [dependencies](https://github.blog/changelog/2025-08-21-dependencies-on-issues/), [issue fields](https://github.blog/changelog/2026-07-02-issue-fields-are-now-generally-available/)). **[OUTDATED]** Projects (classic) was sunset on GitHub.com on 23 August 2024 and its REST API on 1 April 2025; today's Projects is the table, board and roadmap product with up to 50,000 items ([sunset notice](https://github.blog/changelog/2024-05-23-sunset-notice-projects-classic/), [About Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/about-projects)).

**[GITHUB]** A Git tag and a GitHub Release are different things. A tag is Git data under `refs/tags/`; a release is a GitHub object that points at a tag and adds a title, notes, assets and draft, pre-release and latest flags ([About releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)). Creating a release can create the tag: `gh release create` creates a missing tag from the latest state of the default branch unless `--verify-tag` is passed, and deleting a release leaves the tag unless `--cleanup-tag` is given ([gh release create](https://cli.github.com/manual/gh_release_create), [gh release delete](https://cli.github.com/manual/gh_release_delete)). **[VERSION]** Since 28 October 2025 releases can be made **immutable**: the tag is locked to its commit and cannot be deleted while the release exists, assets cannot be modified, the tag name can never be reused, and a signed release attestation is generated and can be checked with `gh release verify` ([immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases), [GA changelog](https://github.blog/changelog/2025-10-28-immutable-releases-are-now-generally-available/), [gh release verify](https://cli.github.com/manual/gh_release_verify)). Tag protection rules were retired on 30 August 2024 in favor of tag rulesets ([sunset notice](https://github.blog/changelog/2024-05-29-sunset-notice-tag-protections/)).

**[GITHUB]** GitHub Packages hosts npm, RubyGems, Maven, Gradle, Docker and NuGet registries, and the Container registry at `ghcr.io` is the Docker and OCI home since the legacy Docker registry was retired on 24 February 2025; Packages accepts only classic personal access tokens outside Actions, which is a documented exception to the advice to prefer fine-grained tokens ([Packages](https://docs.github.com/en/packages/learn-github-packages/introduction-to-github-packages#authenticating-to-github-packages), [legacy registry](https://github.blog/changelog/2025-01-23-legacy-docker-registry-closing-down/)). Artifact attestations are signed provenance claims built on Sigstore, verified with `gh attestation verify`, and available for public repositories on every plan but for private repositories only on Enterprise Cloud ([artifact attestations](https://docs.github.com/en/actions/concepts/security/artifact-attestations), [availability](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)).

## 3. Important recent changes: three waves since 2024 changed what must be taught

Three waves of change overlap in the period the notes cover. Git itself modernised its interface and declared its 3.0 direction; GitHub rebuilt governance, tokens, issues and the pull-request surface; and GitHub Actions turned years of security guidance into platform enforcement after a run of supply-chain incidents. A fourth, quieter wave changed the learning resources and the ML tooling around Git.

### Git, 2024 to September 2026: a cleaner interface and a declared direction

**[VERSION]** The Git changes that alter instruction, rather than merely adding options, are these. Subcommands for `git config` arrived in 2.46 and the old mode options were deprecated ([RelNotes 2.46](https://github.com/git/git/blob/master/Documentation/RelNotes/2.46.0.adoc)). The policy for breaking changes was written down in 2.48 as the BreakingChanges document, and later releases declared the planned 3.0 defaults in it: reftable and SHA-256 in 2.51, `main` in 2.52 ([RelNotes 2.48](https://github.com/git/git/blob/master/Documentation/RelNotes/2.48.0.adoc), [RelNotes 2.52](https://github.com/git/git/blob/master/Documentation/RelNotes/2.52.0.adoc)). `git switch` and `git restore` lost their experimental label in 2.51 ([RelNotes 2.51](https://github.com/git/git/blob/master/Documentation/RelNotes/2.51.0.adoc)). An official plain-language data-model page shipped in 2.53; it was written by Julia Evans and Marie Flanagan, who also rewrote the `git add`, `git checkout`, `git push` and `git pull` man pages after about 80 test readers, many with five or more years of Git use, could not understand terms such as pathspec, reference and upstream ([jvns.ca](https://jvns.ca/blog/2026/01/08/a-data-model-for-git/)). Version 2.54 made the geometric maintenance strategy the default, allowed hooks to be defined in configuration and introduced the experimental `git history` ([RelNotes 2.54](https://github.com/git/git/blob/master/Documentation/RelNotes/2.54.0.adoc)). Version 2.55 disabled most terminal control sequences arriving from remotes ([RelNotes 2.55](https://github.com/git/git/blob/master/Documentation/RelNotes/2.55.0.adoc)). Version 2.56 added `git add --resolved`, which stages only conflict-resolved paths and aborts if conflict markers remain ([RelNotes 2.56](https://github.com/git/git/blob/master/Documentation/RelNotes/2.56.0.adoc)). On security, coordinated releases in May 2024, January 2025 and July 2025 fixed clone-time code-execution flaws, the most serious being CVE-2024-32002 (recursive clones on case-insensitive filesystems) and CVE-2025-48384 (a carriage-return quirk in submodule paths), the latter added to CISA's Known Exploited Vulnerabilities catalog on 25 August 2025 ([advisory](https://github.com/git/git/security/advisories/GHSA-8h77-4q3w-gfgv), [advisory](https://github.com/git/git/security/advisories/GHSA-vwqx-4fm8-6qc9), [CISA](https://www.cisa.gov/news-events/alerts/2025/08/25/cisa-adds-three-known-exploited-vulnerabilities-catalog)). No core-Git advisory was published in 2026 up to 1 October ([advisories](https://github.com/git/git/security/advisories)).

## 4. Deprecated and outdated concepts: most old habits still run, which is why they persist

Almost every deprecated Git form still executes, so learners meet both forms and must be able to read the old one while writing the new one. The tables give, for each item, the older behavior, the current behavior, the version or date, and the recommended approach.

### Git (the tool)

| Older habit or claim | Current behavior | Version or date | Recommended current approach |
|---|---|---|---|
| `git checkout` for both switching branches and restoring files | `git switch` and `git restore` are stable; `checkout` remains supported and is explicitly not slated for removal | Introduced 2.23; non-experimental 2.51 ([BreakingChanges](https://github.com/git/git/blob/v2.56.0/Documentation/BreakingChanges.adoc)) | Teach `git switch <branch>`, `git switch -c <new>`, `git restore <path>`, `git restore --staged <path>`; teach `checkout` for reading other people's scripts |

| Expecting `git pull` to merge silently | Unconfigured pull on diverged branches is fatal | 2.33.1 and 2.34 ([RelNotes 2.34](https://github.com/git/git/blob/master/Documentation/RelNotes/2.34.0.adoc)) | Choose deliberately: set `pull.rebase` to true or false, or `pull.ff only`, or pass `--rebase`, `--no-rebase` or `--ff-only` |

## 5. Official documentation sources: man pages and changelogs outrank Pro Git and GitHub's own examples

### The primary-source layer and how current each part is

The primary layer has two halves. For Git it is git-scm.com: the man pages and guides, which track 2.56.0, the release notes, and the BreakingChanges document. For GitHub it is docs.github.com, the GitHub Changelog and the CLI manual at cli.github.com. Pro Git sits between primary and secondary: it is hosted on the official site and remains authoritative for the object model and internals, but its second edition (2014, Scott Chacon and Ben Straub) has been frozen at build 2.1.450 since 25 May 2024 ([Pro Git](https://git-scm.com/book/en/v2), [releases](https://github.com/progit/progit2/releases)). Checked against the live pages, its core branching chapter uses `git checkout` and `master` throughout and never mentions `git switch` ([chapter](https://git-scm.com/book/en/v2/Git-Branching-Basic-Branching-and-Merging)); `git restore` appears only as an added subsection ([Undoing Things](https://git-scm.com/book/en/v2/Git-Basics-Undoing-Things)); signing covers GPG only ([Signing Your Work](https://git-scm.com/book/en/v2/Git-Tools-Signing-Your-Work)); no section covers worktrees, sparse-checkout or partial clone ([open proposal](https://github.com/progit/progit2/issues/1597)); and Advanced Merging still speaks of the recursive strategy and does not mention `zdiff3` ([Advanced Merging](https://git-scm.com/book/en/v2/Git-Tools-Advanced-Merging)). A third edition is being revised in public for Git 3.0, with new material on worktrees, agents and scale ([progit3.com](https://progit3.com/)). **[INFERENCE]** Pro Git 2e should be cited for mechanics that have not changed (objects, refs, packfiles, reset, rebase, merge stages, rerere, bisect, refspecs, hooks, attributes) and avoided as the command-level authority for branch switching, undo, signing, large-repository features and default branch naming.

### Where the official documentation itself lags

Primary sources are not uniformly current, and the notes caught several lags that a careful course should name. GitHub's docs examples still show `actions/checkout@v6`, `actions/cache@v4` and `actions/upload-artifact@v4` although newer majors exist ([action releases](https://github.com/actions/checkout/releases)). And the BreakingChanges document carries no dates even though the maintainer has announced 2.98 and 2.99. The working rule that follows is to prefer the most specific and most recent primary source: a changelog entry or release note over a general documentation page, and source code or a local check over both when they disagree.

## 7. Best Git and GitHub videos: a complete path exists only by combining about a dozen sources

### How the videos were chosen and what "current" means

Videos were selected for technical content and currency, never for view counts. Every video listed was confirmed to exist on YouTube on 1 October 2026, and its title, channel, length and upload date come from the watch page. Titles in the tables of sections 7 to 10 are shortened where long, and the vertical bars and emoji that many titles contain are dropped or rendered as hyphens so that the tables display correctly; each link leads to the exact video. Assessments rest on targeted searches of caption transcripts, chapter lists and descriptions; nobody watched the videos end to end, Hindi videos were audited through auto-generated captions or their machine translation, and a command shown on screen but never spoken would have been missed. "Current" means the commands, authentication and defaults shown still match Git 2.56 and GitHub as of October 2026. Two kinds of datedness must be kept apart: using `master` or `git checkout` is dated style, because Git still creates `master` by default and has decided to keep `checkout`; password authentication, plain force-pushing and unpinned or obsolete action versions are substantive problems.

Because the curriculum roadmap is a later phase, placements below use a provisional ladder, which is a planning device of this report and not a finished syllabus: **S1** first contact (install, configure, add, commit, first push); **S2** mental model (snapshots, commits, refs, HEAD, the index); **S3** branching, merging and conflicts; **S4** remotes and collaboration (fetch, pull, push, forks, pull requests); **S5** undo and recovery (restore, reset, revert, reflog); **S6** history editing and investigation (rebase, interactive rebase, cherry-pick, stash, bisect); **S7** internals (objects, index file, packfiles, ref storage); **S8** power tools and scale (worktrees, rerere, sparse-checkout, partial clone, maintenance); **S9** GitHub platform and governance; **S10** GitHub Actions; **S11** security and incident response; **S12** AI/ML workflows; **S13** engineering judgment (branching strategy, review, history quality); **S14** the frontier (Git 3.0, SHA-256, reftable, Rust).

## 12. Topics most developers misunderstand: undo, the three things called a branch, and HEAD lead the evidence

### Four independent evidence streams point at the same clusters

**Stack Overflow votes.** Of 153,604 questions tagged `git`, the 30 highest-scored are dominated by state manipulation rather than concepts: by the researcher's count, 11 are undo, rewrite or discard questions, 12 concern remotes and the distinction between a local branch, a remote-tracking ref and the branch on the server, and 3 concern tracked, untracked and ignored files ([Stack Overflow](https://stackoverflow.com/questions/tagged/git?tab=Votes)). The last column below is interpretation, not a claim made by Stack Overflow.

| Rank | Question (score on 1 Oct 2026) | Underlying concept the popularity suggests |
|---|---|---|
| 1 | How do I undo the most recent local commits in Git? (27,242) | No single "undo"; reset modes only make sense with the HEAD, index and working-tree model |
| 2 | How do I delete a Git branch locally and remotely? (20,355) | A local branch, the remote-tracking ref and the server's branch are three separate things |
| 3 | What is the difference between 'git pull' and 'git fetch'? (14,059) | Pull is fetch plus integration; remote-tracking refs as a local cache are not understood |
| 5 | How do I undo 'git add' before commit? (11,626) | The index and how to unstage |
| 6 | How do I force "git pull" to overwrite local files? (9,974) | Pull is assumed to mean "download latest" |
| 7 | How can I check out a remote Git branch? (8,889) | `origin/x` is not a local branch |
| 8 | How do I make Git forget about a file that was tracked, but is now in .gitignore? (8,647) | Ignore rules affect only untracked files |
| 11 | How do I revert a Git repository to a previous commit? (7,607) | checkout versus reset versus revert |
| 17 | How do I squash my last N commits together? (5,855) | History rewriting and its consequences |
| 21 | How do I resolve merge conflicts in a Git repository? (5,444) | Conflict markers and three-way merge are opaque |
| 28 | Undoing a git rebase (4,481) | The reflog as safety net is unknown |
| 30 | Message 'src refspec master does not match any' (4,274) | Refspecs; pushing before any commit; `master` versus `main` |

**A large-scale study.** An ACM TOSEM study of the Stack Exchange data dump of December 2020 found 80,370 questions that mention a Git command, with the most-viewed commands being `git revert`, `git reflog`, `git stash`, `git clean` and `git reset`, four of the five about recovery. It also found that experience does not remove the problem: in 2020, 40.0% of people asking Git-command questions had been registered for more than five years, against 21.2% of all askers, and `git credential` and `git submodule` were among the hardest commands to get answered ([author preprint](https://cs.nju.edu.cn/changxu/1_publications/22/TOSEM22.pdf)).

**Conceptual-design analysis.** Two MIT papers model Git's concepts and identify seven operational misfits (saving changes, switching branches, detached HEAD, file rename, file tracking, untracking a file, empty directory), validated against highly ranked Stack Overflow questions; their user study had only 11 MIT-affiliated participants, which the authors flag as a threat to validity ([Onward! 2013](https://spderosso.github.io/onward13.pdf), [OOPSLA 2016](https://spderosso.github.io/oopsla16.pdf)). The same questions kept accumulating votes for a decade, which supports reading them as stable conceptual problems.

**Practitioner polls and documentation testing.** In Julia Evans' 2024 polls of a self-selected, mostly professional audience, only 10% were fully confident they understood HEAD and 14% had no idea (n=1,783); 48% did not know that the two sides of a conflict swap between merge and rebase and a further 21% did not recognise the question (n=1,511); 50% think of a commit as a diff and 42% as a snapshot (n=2,466); 58% think of a branch as just the commits that branched off and 15% as a pointer (n=1,966); 17% had lost work to a Git problem; and 61% had seen a production bug caused by a bad conflict resolution at least once ([poll results](https://jvns.ca/blog/2024/03/28/git-poll-results/)). In 2026, about 80 test readers, many with more than five years of Git use, could not understand terms in the official man pages such as pathspec, reference and upstream ([jvns.ca](https://jvns.ca/blog/2026/01/08/a-data-model-for-git/)). A classroom study adds beginner-specific errors: treating branches as folders, confusing `origin/master` with `origin master`, and "resolving" conflicts by re-cloning ([Isomöttönen and Cochez](https://www.cochez.nl/papers/dvcs-misconceptions-final.pdf)). One empirical study of 143 open-source projects, known to the researchers only through its abstract, reports that nearly one in five merges conflicts and that code involved in a conflict is about twice as likely to contain a bug ([Brindescu et al.](https://link.springer.com/article/10.1007/s10664-019-09735-4)).

For context on who the learners are: the 2022 Stack Overflow survey, the last located with a version-control section, had Git at 93.87% of respondents and command-line use at 83.57% ([survey](https://survey.stackoverflow.co/2022/)); JetBrains' 2023 survey had IDE-based use at 64% ahead of the terminal at 59% ([JetBrains](https://www.jetbrains.com/lp/devecosystem-2023/team-tools/)); and GitHub's Octoverse 2025 reports more than 180 million developers and 630 million repositories ([Octoverse 2025](https://github.blog/news-insights/octoverse/octoverse-a-new-developer-joins-github-every-second-as-ai-leads-typescript-to-1/)). The two surveys measure different populations and should not be combined into one trend.

### The misconceptions, each paired with the verified reality

| Common belief | Verified reality | Layer | Source |
|---|---|---|---|
| A commit stores a diff | A commit records a full snapshot (the tree ID of the top-level directory), its parents, author, committer and message; Git computes diffs on demand. A commit that changes 2 of 1,000 files creates 2 new blobs and reuses 998 | Git | [gitdatamodel](https://github.com/git/git/blob/v2.56.0/Documentation/gitdatamodel.adoc) |
| Cherry-pick and revert apply patches | Cherry-pick is a three-way merge whose base is the picked commit's parent; revert is the same with base and "theirs" swapped. The diff view is still a useful way to think about them | Git | [jvns.ca](https://jvns.ca/blog/2023/11/10/how-cherry-pick-and-revert-work/) |
| A branch is a copy of the code, with a parent branch | A branch is a ref that names a commit. Git has no notion of a parent branch, so rebase and merge targets must be given explicitly | Git | [gitdatamodel](https://github.com/git/git/blob/v2.56.0/Documentation/gitdatamodel.adoc), [jvns.ca](https://jvns.ca/blog/2023/11/23/branches-intuition-reality/) |
| HEAD is the latest commit | HEAD is either a symbolic reference to the current branch or a direct reference to a commit ID, in which case there is no current branch (detached HEAD) | Git | [gitdatamodel](https://github.com/git/git/blob/v2.56.0/Documentation/gitdatamodel.adoc) |
| `origin/main` is the branch on the server; "up to date" means nothing new upstream | A remote-tracking branch is Git's record of the last-known state of the remote branch, updated by `git fetch`; the status message reflects only the last fetch | Git | [gitdatamodel](https://github.com/git/git/blob/v2.56.0/Documentation/gitdatamodel.adoc), [jvns.ca](https://jvns.ca/blog/2023/11/01/confusing-git-terminology/) |
| `git pull` downloads the latest and merges it | Pull is fetch plus an integration step, and with diverged branches and no configuration it stops with a fatal error | Git | [pull.c](https://github.com/git/git/blob/v2.56.0/builtin/pull.c#L1150) |
| The staging area is a list of files to commit | The index is a flat list of entries, each with a file type, a blob ID, a stage number (0 normally; 1, 2 and 3 during a conflict) and a path, plus stat data and flags | Git | [gitdatamodel](https://github.com/git/git/blob/v2.56.0/Documentation/gitdatamodel.adoc), [gitformat-index](https://github.com/git/git/blob/v2.56.0/Documentation/gitformat-index.adoc) |
| "Ours" and "theirs" always mean my side and the other side | Stage 2 is the branch being merged into and stage 3 the branch being merged; during a rebase the roles are swapped relative to intuition | Git | [gitrevisions](https://github.com/git/git/blob/v2.56.0/Documentation/revisions.adoc), [jvns.ca](https://jvns.ca/blog/2023/11/01/confusing-git-terminology/) |
| `A..B` and `A...B` mean the same thing everywhere | For `git log`, `A..B` is commits reachable from B but not A and `A...B` is the symmetric difference. For `git diff`, `A..B` compares the two endpoints and `A...B` compares the merge base with B | Git | [gitrevisions](https://github.com/git/git/blob/v2.56.0/Documentation/revisions.adoc), [git-diff](https://github.com/git/git/blob/v2.56.0/Documentation/git-diff.adoc) |
| Adding a path to `.gitignore` stops tracking it | Ignore rules never affect files already tracked; the documented fix is `git rm --cached`, which does nothing for history | Git | [gitignore](https://git-scm.com/docs/gitignore) |
| Amend and rebase edit commits | Objects never change after creation; amend and rebase create new commits with new IDs, and the old ones linger until reflogs expire | Git | [gitdatamodel](https://github.com/git/git/blob/v2.56.0/Documentation/gitdatamodel.adoc), [gc configuration](https://github.com/git/git/blob/v2.56.0/Documentation/config/gc.adoc) |
| The reflog will always save me, even for a deleted branch or on the server | Reflogs are local and are not shared with remotes; deleting a branch deletes its reflog; bare repositories keep none by default | Git | [gitdatamodel](https://github.com/git/git/blob/v2.56.0/Documentation/gitdatamodel.adoc), [git-branch](https://github.com/git/git/blob/v2.56.0/Documentation/git-branch.adoc), [core configuration](https://github.com/git/git/blob/v2.56.0/Documentation/config/core.adoc) |
| `--force-with-lease` makes a force push safe | The bare form is defeated by anything that fetches in the background; the documentation itself calls the non-explicit forms experimental | Git | [git-push](https://github.com/git/git/blob/v2.56.0/Documentation/git-push.adoc) |
| Git tracks renames and directories | Git does not record renames explicitly, and it tracks file content, not directories | Git | [Git User's Manual](https://github.com/git/git/blob/v2.56.0/Documentation/user-manual.adoc) |
| `git checkout` is deprecated and `master` is gone | Neither is true in 2.56 | Git | [BreakingChanges](https://github.com/git/git/blob/v2.56.0/Documentation/BreakingChanges.adoc), [git-init](https://github.com/git/git/blob/v2.56.0/Documentation/git-init.adoc) |
| A shallow clone is the efficient way to work on a big repository | GitHub's own engineering guidance reserves shallow clones for throwaway CI and recommends blobless partial clones for developers | Git | [GitHub Blog](https://github.blog/open-source/git/get-up-to-speed-with-partial-clone-and-shallow-clone/) |
| A submodule follows a branch of the other project | The superproject records a commit ID, and `git submodule update` leaves a detached HEAD by default | Git | [gitsubmodules](https://git-scm.com/docs/gitsubmodules), [git-submodule](https://git-scm.com/docs/git-submodule) |
| Hooks enforce policy for everyone | Client-side hooks are not copied by clone and can be bypassed with `--no-verify` | Git | [Pro Git](https://git-scm.com/book/en/v2/Customizing-Git-Git-Hooks), [githooks](https://github.com/git/git/blob/v2.56.0/Documentation/githooks.adoc) |
| The author name on a commit proves who wrote it | Git lets anyone set author and committer; GitHub attributes commits by matching the email address | Git and GitHub | [GitHub Docs](https://docs.github.com/en/authentication/managing-commit-signature-verification/displaying-verification-statuses-for-all-of-your-commits) |
| A pull request is a Git feature | It is a GitHub object backed by hidden refs, a test merge commit and a three-dot diff | GitHub | [Pull requests reference](https://docs.github.com/en/pull-requests/reference/pull-requests) |
| After squash or rebase merging, my commits are on the base branch | New commits with new IDs are; the originals are not ancestors of the base, which is why a local `git branch -d` then refuses | GitHub | [merge methods](https://docs.github.com/en/pull-requests/reference/pull-request-merges) |
| "Request changes" blocks a merge; CODEOWNERS enforces review | Both are advisory unless a ruleset or classic rule requires them | GitHub | [reviewing changes](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request), [code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners) |
| Admins and maintainers can always push to a protected branch | Under rulesets only actors on the bypass list can; the Maintain role's push right applies to classic rules only | GitHub | [repository roles](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization) |
| A "Verified" badge is re-checked and proves the code is safe | It records that a signature matched a registered key at verification time; the record persists even if the key is later revoked | GitHub | [signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification) |

| "Repository not found" means the repository does not exist | GitHub returns "not found" for private resources the credential cannot access | GitHub | [REST troubleshooting](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api#404-not-found-for-an-existing-resource) |
| CI on a pull request tests my branch | On `pull_request` events the default checkout is the merge ref, a merge of the head into the current base, in detached HEAD; `GITHUB_SHA` is a commit that does not exist in the contributor's clone | Actions | [events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#how-the-merge-branch-affects-your-workflow) |

**[INFERENCE]** Three independent sources (registration-age data, polls of practising developers, and the 2026 man-page test readers) show that experienced users share these confusions, so the program should not file them under "beginner". The commit-as-diff and branch-as-offshoot majorities are mental models the course must reconcile with the snapshot-and-pointer reality rather than simply call wrong, because cherry-pick, rebase and three-dot comparisons only make sense when both views are held together.

## 13. Production-critical topics: recovery windows, safe rewrites, merge mechanics and CI defaults decide how incidents end

This section collects, topic by topic, the verified facts a senior engineer needs in order to recover from a production incident and to explain its root cause. Each fact is labelled by layer, because most real incidents cross the boundary between Git and GitHub and the explanation depends on knowing which side did what.

### Recovery on the developer's machine: what Git keeps, and for how long

**[STABLE]** Git deletes nothing that is reachable. Garbage collection keeps every object referenced by branches, tags, the index, remote-tracking branches and reflogs, and anything else under `refs/`; a note attached to an object does not keep it alive ([git-gc](https://github.com/git/git/blob/v2.56.0/Documentation/git-gc.adoc)). Reflog entries expire after 90 days, or after 30 days when the entry is no longer reachable from the current tip, which is the case for commits orphaned by `git commit --amend` or `git rebase`; unreachable objects are then pruned after a further two-week grace period ([gc configuration](https://github.com/git/git/blob/v2.56.0/Documentation/config/gc.adoc)). `ORIG_HEAD` records where HEAD was before `git am`, `git merge`, `git rebase` or `git reset` moved it ([gitrevisions](https://github.com/git/git/blob/v2.56.0/Documentation/revisions.adoc)). **[INFERENCE]** On a default non-bare repository, a commit orphaned by reset, amend or rebase therefore stays recoverable through reflogs for at least 30 days and then survives up to two more weeks once maintenance actually runs.

Four exceptions shorten or remove that window, and each has caused real data loss. **[STABLE]** Deleting a branch deletes that branch's reflog immediately; its commits usually stay reachable through the `HEAD` reflog only if they were ever checked out, and commits never checked out locally are protected by nothing but the two-week object grace period ([git-branch](https://github.com/git/git/blob/v2.56.0/Documentation/git-branch.adoc)). Bare repositories, which is what a server holds, keep no reflogs unless `core.logAllRefUpdates` is enabled ([core configuration](https://github.com/git/git/blob/v2.56.0/Documentation/config/core.adoc)). Stash entries live in the reflog of `refs/stash` and are exempt from default expiry, but a stash that is dropped or cleared cannot be recovered through the normal safety mechanisms; the man page offers only a `git fsck --unreachable` recipe that works while the objects still exist ([git-stash](https://github.com/git/git/blob/v2.56.0/Documentation/git-stash.adoc)). And the documented way to make deletion immediate, `git reflog expire --expire=now --all` followed by `git gc --prune=now`, is also the documented way to destroy the safety net, with the additional warning that pruning immediately risks corruption if another process is writing to the repository ([git-reflog](https://github.com/git/git/blob/v2.56.0/Documentation/git-reflog.adoc), [git-gc](https://github.com/git/git/blob/v2.56.0/Documentation/git-gc.adoc)). **[GIT]** Since 2.54 the default automatic maintenance is the geometric strategy rather than `git gc`, but it applies the same expiry values: a traced run on the learner's 2.55.0 expired reflogs and repacked unreachable objects into a cruft pack with a two-week expiration ([maintenance configuration](https://github.com/git/git/blob/v2.56.0/Documentation/config/maintenance.adoc)).

### Recovery on GitHub after a force push or a deleted branch

**[GITHUB]** GitHub exposes no server-side reflog, but it provides five documented instruments. The repository **Activity view** lists pushes, merges, force pushes, branch creations and branch deletions with the authenticated user, can be filtered by activity type, and offers "Compare changes" on each entry ([Activity view](https://docs.github.com/en/repositories/viewing-activity-and-data-for-your-repository/using-the-activity-view-to-see-changes-to-a-repository)). A closed pull request offers **"Restore branch"** for its head branch ([restoring branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-branches-in-your-repository/deleting-and-restoring-branches-in-a-pull-request)). The **Events API** returns `PushEvent` records whose `before` and `head` fields give the commit IDs on either side of a push, limited to the last 300 events and 30 days, with latency between 30 seconds and 6 hours ([event types](https://docs.github.com/en/rest/using-the-rest-api/github-event-types#pushevent), [events API](https://docs.github.com/en/rest/activity/events)). The **Git references REST API** can create a ref pointing at a given commit ID ([create a reference](https://docs.github.com/en/rest/git/refs#create-a-reference)). And the **audit log** records events for 180 days at organization level, while the enterprise log retains Git events such as `git.push` for only seven days and exposes them only through the REST API, streaming or exports ([organization audit log](https://docs.github.com/en/organizations/keeping-your-organization-secure/managing-security-settings-for-your-organization/reviewing-the-audit-log-for-your-organization), [enterprise events](https://docs.github.com/en/enterprise-cloud@latest/admin/monitoring-activity-in-your-enterprise/reviewing-audit-logs-for-your-enterprise/audit-log-events-for-your-enterprise)). GitHub's own troubleshooting page adds the plain-Git route: if a branch was deleted or force-pushed, ask a collaborator who still has the commit locally to push it to a new branch ([troubleshooting commits](https://docs.github.com/en/pull-requests/how-tos/commit-changes/troubleshooting-commits#a-commit-exists-on-github-but-not-in-your-local-clone)). A deleted repository can be restored within 90 days unless it was part of a non-empty fork network ([restoring a repository](https://docs.github.com/en/repositories/creating-and-managing-repositories/restoring-a-deleted-repository)).

**[INFERENCE]** The recovery recipe that follows from these pieces, which is not itself a single documented procedure, is to find the pre-force-push commit ID from the Activity view or from a `PushEvent`'s `before` field and then create a branch at it through the references API, for example `gh api repos/OWNER/REPO/git/refs -f ref=refs/heads/recovered -f sha=<SHA>`. This works only while GitHub has not garbage-collected the unreferenced commit, and GitHub publishes no retention period for such commits. Researchers who mined force-pushed commits at scale concluded that GitHub appears to keep them indefinitely, but that is their observation and not a GitHub statement ([Truffle Security](https://trufflesecurity.com/blog/guest-post-how-i-scanned-all-of-github-s-oops-commits-for-leaked-secrets)). The same persistence that makes recovery possible is the reason a force push is not a way to remove a secret; the two lessons belong together.

### Force-push safety

**[GIT]** Plain `git push --force` disables the fast-forward check and every other safety check and can make the remote lose commits. `--force-with-lease` overrides the restriction only if the remote ref still has the expected value, in three forms: bare (expect the value of the corresponding remote-tracking branch for every ref being updated), `--force-with-lease=<refname>`, and `--force-with-lease=<refname>:<expect>`. The documentation warns that the forms without an explicit expected value interact very badly with anything that runs `git fetch` in the background, because the fetch silently updates the remote-tracking branch the lease is compared against, and it labels those forms as still experimental. `--force-if-includes`, added in 2.30, additionally verifies that the tip of the remote-tracking ref has been integrated locally by checking the local branch's reflog, and it is a no-op when no lease is given or when the lease already names an explicit expected value ([git-push](https://github.com/git/git/blob/v2.56.0/Documentation/git-push.adoc)). **[INFERENCE]** The safe recipe the documentation supports is `git push --force-with-lease --force-if-includes`, or the explicit `<refname>:<expect>` form; editor auto-fetch features are the usual modern way the bare form is defeated, whereas Git's own scheduled prefetch writes to `refs/prefetch/` precisely to avoid disturbing remote-tracking branches ([git-maintenance](https://github.com/git/git/blob/v2.56.0/Documentation/git-maintenance.adoc)).

**[GITHUB]** On the server side, "Block force pushes" is enabled by default in a new ruleset, and every classic branch protection rule disables force pushes and deletions by default; GitHub's documentation notes that force pushing can also be used to delete branches or to point a branch at commits that were never approved in a pull request, and that it can corrupt pull requests built on the old history ([available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#block-force-pushes), [About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)). Several audited tutorials teach "`git reset --hard`, then `git push -f`" as a routine undo, including on the main branch ([example](https://www.youtube.com/watch?v=GTFaLDXag08&t=4115s)); the research notes call this the single most dangerous habit in the video catalogue for team settings.

### History rewriting, from one commit to a whole repository

**[GIT]** For targeted rewrites the stable tools are interactive rebase with `--autosquash`, `--update-refs` (which force-updates other branches pointing into the rebased range, except those checked out in a worktree) and `--rebase-merges` (which recreates merge commits, whose conflict resolutions must be re-applied by hand) ([git-rebase](https://github.com/git/git/blob/v2.56.0/Documentation/git-rebase.adoc)). The newer `git history` (`reword`, `split`, `fixup`, and `drop` in 2.56) and `git replay` are labelled experimental; `git history` updates all descendant branches by default, works in bare repositories, runs no hooks, and does not yet handle histories containing merges or operations that would conflict ([git-history](https://github.com/git/git/blob/v2.56.0/Documentation/git-history.adoc)). Practitioners' recorded rebase failures include resolving the same conflict repeatedly, force-pushing shared branches, losing signatures and running `commit --amend` where `rebase --continue` was needed; the mitigations they list are rerere, the reflog, `rebase --abort`, backup branches and `--force-with-lease` ([jvns.ca](https://jvns.ca/blog/2023/11/06/rebasing-what-can-go-wrong-/)).

**[STABLE]** A whole-repository rewrite replaces the first affected commit and every descendant with new commits that have new IDs, and it is an operation, not a command. The facts that make it one are these. git-filter-repo refuses to run outside a fresh clone unless forced, ends by pruning reflogs and old objects, and records its work in `.git/filter-repo/` as `commit-map`, `ref-map`, `changed-refs` and `first-changed-commits`; other contributors should be told to stop work during the cleanup; all refs, including tags, must be force-pushed; the forge's read-only pull-request refs cannot be rewritten by the owner; signatures on commits and tags are removed, including for commits that pre-date the removed data; force-push protections must be switched off temporarily; forks keep the old history; orphaned LFS objects must be purged separately; and the easiest way to clean other clones is to delete and re-clone them, because an ordinary pull followed by a push from a stale clone puts the removed data back ([git-filter-repo manual](https://github.com/newren/git-filter-repo/blob/main/Documentation/git-filter-repo.txt), [GitHub: removing sensitive data](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)). Where re-cloning is impossible, the manual prescribes deleting all tags and running `git fetch --prune --tags`, rebasing local work onto the new history, expiring reflogs and pruning, and then confirming that `git cat-file -t <first-changed-commit>` fails. Colleagues must not re-run the same filter command themselves, because identical commands can still produce different commit IDs. Collaborators must rebase rather than merge old branches, since one merge commit can reintroduce the removed history. Few forges can ban a specific commit from being pushed again, and the notes found no documented built-in control of that kind on GitHub. **[INFERENCE]** For ML teams the broken commit IDs have a specific cost: every experiment record, model card or deployment manifest that stored an old ID now points at a commit that no longer exists on the remote, so the `commit-map` file belongs in the incident record.

### Merges, conflicts and the choice of integration method

**[GIT]** `ort` has been the default merge strategy since 2.34 and uses the histogram diff algorithm; conflict presentation defaults to the `merge` style, with `diff3` adding the original text and `zdiff3` (2.35) trimming lines common to both sides ([merge strategies](https://github.com/git/git/blob/v2.56.0/Documentation/merge-strategies.adoc), [merge configuration](https://github.com/git/git/blob/v2.56.0/Documentation/config/merge.adoc)). During a conflict the index holds up to three entries per path: stage 1 the common ancestor, stage 2 the current branch's version, stage 3 the version being merged, addressable as `:1:path`, `:2:path` and `:3:path` ([gitrevisions](https://github.com/git/git/blob/v2.56.0/Documentation/revisions.adoc)). `rerere` records resolved conflicts so identical hunks resolve automatically next time, but it is active only when `rerere.enabled` is set or an `rr-cache` directory already exists ([rerere configuration](https://github.com/git/git/blob/v2.56.0/Documentation/config/rerere.adoc)). `git log --remerge-diff` (2.36) shows how a recorded merge differs from a mechanical re-merge, which is the direct way to audit what a human changed while resolving ([diff options](https://github.com/git/git/blob/v2.56.0/Documentation/diff-options.adoc)). In 2.56 only, `git add --resolved` stages resolved paths and aborts if conflict markers remain. The stakes are documented: 61% of roughly 1,480 poll respondents had seen a production bug from a bad conflict resolution at least once ([poll results](https://jvns.ca/blog/2024/03/28/git-poll-results/)).

**[GITHUB]** The merge button chosen on GitHub has consequences that surface later as "mystery" problems. Squash merging loses per-commit authorship and timing, and continuing to work on the same head branch afterwards makes later pull requests list the already-squashed commits and repeat conflicts ([merge methods](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github)); Git's own FAQ has an entry on the same problem with squash merges on long-lived branches ([gitfaq](https://git-scm.com/docs/gitfaq)). Rebase merging always produces new commit IDs and unsigned commits, so under a "require signed commits" rule it is effectively unusable. With a merge queue the method is fixed by the queue, not chosen per pull request.

### Why a pull request shows unexpected commits or refuses to merge

**[GITHUB]** The documented causes of an unexpectedly large or strange pull request are a reused head branch after a squash merge, a wrong or changed base branch, a base branch that moved since the pull request was opened (the pull-request page and the compare page can compute changes from different merge bases), rewritten or force-pushed history, and a diff truncated by size limits or hidden by `.gitattributes` ([pull request merges](https://docs.github.com/en/pull-requests/reference/pull-request-merges#squashing-and-merging-a-long-running-branch), [pull requests reference](https://docs.github.com/en/pull-requests/reference/pull-requests#differences-between-commits-on-compare-and-pull-request-pages), [branches reference](https://docs.github.com/en/pull-requests/reference/branches#comparing-branches-in-pull-requests)). **[INFERENCE]** A pull request opened against the wrong base lists every commit not reachable from that base, which follows directly from the merge-base definition.

A merge that will not complete usually traces to one of a short list of documented rules. Required checks must pass on the latest commit; `success`, `skipped` and `neutral` count as passing; a check and a commit status with the same name must both pass; a required check must have completed successfully in the repository within the past seven days to be selectable; and only runs triggered by `push`, `pull_request`, `pull_request_review`, `pull_request_target`, `deployment` and `deployment_status` produce checks that count for a pull request, so a manually dispatched run does not ([troubleshooting required status checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)). A workflow skipped by a path filter, a branch filter or a `[skip ci]` commit message leaves its required check pending forever, whereas a job skipped by a conditional reports success ([skipping workflow runs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/skip-workflow-runs)). With a merge queue, required checks are reported only by workflows that also trigger on `merge_group`. Rulesets and classic rules aggregate, so relaxing one layer can leave the merge blocked by the other; the `/rules` page and Settings → Branches show both. **[INFERENCE]** The robust design for path-conditional CI is therefore to start the workflow always, decide inside it what to run, and require one aggregate job that fails when any needed job failed or was cancelled.

### CI failures: the documented causes of "passes locally, fails on GitHub Actions"

Most local-versus-CI differences trace to documented defaults rather than to flakiness. The table lists each cause with its mechanism and the documented remedy; all rows are GitHub Actions behavior except the two marked as Git.

| Cause | Mechanism | Remedy |
|---|---|---|

| The job is not testing the pushed commit | On `pull_request`, CI checks out `refs/pull/N/merge`, a merge of the head into the current base, in detached HEAD; base-branch changes are included, and the workflow does not run at all while the pull request has a merge conflict ([events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#how-the-merge-branch-affects-your-workflow)) | Rebase or merge the base locally to reproduce; use `github.event.pull_request.head.sha` to test only the head |

**[GITHUB]** The documented debugging instruments are step and runner debug logging through `ACTIONS_STEP_DEBUG` and `ACTIONS_RUNNER_DEBUG` or the debug checkbox on a re-run ([debug logging](https://docs.github.com/en/actions/how-tos/monitor-workflows/enable-debug-logging)); re-running failed jobs only, which reuses the original commit and ref and the original actor's privileges, up to 50 times per run ([re-running](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs)); the CLI commands `gh run view --log-failed`, `gh run rerun --failed --debug` and `gh run watch` ([gh run view](https://cli.github.com/manual/gh_run_view), [gh run rerun](https://cli.github.com/manual/gh_run_rerun)); and, since January 2026, skipped-job logs that show the original and expanded `if` expression ([troubleshooting](https://docs.github.com/en/actions/how-tos/troubleshoot-workflows#debugging-job-conditions)). The third-party `act` runs workflows locally in Docker but ignores concurrency, permissions, environments and OIDC, so it cannot reproduce security or deployment behavior ([act: unsupported functionality](https://nektosact.com/not_supported.html)); `actionlint` catches syntax and expression errors before a push ([actionlint](https://github.com/rhysd/actionlint/blob/main/README.md)). **[INFERENCE]** A practical triage order is: read the failed-step log; identify which commit CI actually built; compare tool versions printed by setup steps; check whether the run came from a fork or Dependabot; look for cache restores through broad restore keys; re-run failed jobs with debug logging; and only then reproduce in the same container image.

### Releases, tags and version numbers

**[GITHUB]** A release is a GitHub object layered on a Git tag, and creating a release from the web interface or with `gh release create` can create a tag on the server that the local clone does not have until it fetches tags ([About releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases), [gh release create](https://cli.github.com/manual/gh_release_create)). Immutable releases lock the tag and assets and forbid reuse of the tag name; the recommended flow is to create a draft, attach all assets, then publish ([immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases)). **[STABLE]** `git describe` derives a name from the most recent reachable annotated tag, which is the mechanism behind tag-derived package versions; such versioning fails or falls back in CI when the checkout is shallow or tagless ([git-describe](https://git-scm.com/docs/git-describe)). Because events created with the `GITHUB_TOKEN` do not trigger `push` or `release` workflows, release pipelines that chain workflows need either a GitHub App or personal token for the creating step or a single workflow whose jobs are chained.

**[STABLE]** On the direction of fixes there are two legitimate, opposite conventions that a senior engineer should be able to name. The Git project itself commits a fix on the oldest supported branch that needs it and merges upward through its integration branches ([gitworkflows](https://git-scm.com/docs/gitworkflows)). Trunk-based practice, as described by trunkbaseddevelopment.com, Google, Microsoft's Release Flow and GitLab, fixes on the main line first and cherry-picks to the release branch, on the argument that fixing on the release branch risks a regression when someone forgets to port the fix ([branch for release](https://trunkbaseddevelopment.com/branch-for-release/), [Microsoft Release Flow](https://learn.microsoft.com/en-us/devops/develop/how-microsoft-develops-devops)).

### Branching strategy: the literature ties the choice to context

The reputable sources do not crown one strategy. DORA's capability research, from 2016 and 2017, associates higher delivery performance with three or fewer active branches, merging to trunk at least daily and no code freezes ([DORA](https://dora.dev/capabilities/trunk-based-development/)); the evidence is survey-based and correlational and is expressed in branch lifetime and batch size, not in named workflows. Git Flow's own author restricted it in 2020 to explicitly versioned software with several supported versions ([nvie.com](https://nvie.com/posts/a-successful-git-branching-model/)); GitHub Flow assumes one continuously deployed version ([GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow)); Martin Fowler lists real advantages of feature branching for teams that cannot keep a mainline healthy and for open-source projects with occasional, not-yet-trusted contributors ([Fowler](https://martinfowler.com/articles/branching-patterns.html)); and a 2025 interview-and-survey study concludes that trunk-based workflows suit fast-paced projects with experienced, smaller teams while branch-based workflows suit less experienced and larger ones ([arXiv](https://arxiv.org/abs/2507.08943)). Merge queues and stacked pull requests address the two main costs of pre-merge review at scale: GitHub reports about 2,500 pull requests a month from more than 500 engineers landing through its own queue, with average wait to ship down 33% ([GitHub Blog](https://github.blog/engineering/engineering-principles/how-github-uses-merge-queue-to-ship-hundreds-of-changes-every-day/)). **[INFERENCE]** The defensible framing for a CTO is to ask first how many versions are live at once and how often the team releases; saying that DORA proves trunk-based development is best overstates what the sources support.

### Scale, submodules and large files

**[GIT]** Stock Git scales to very large repositories only when opt-in features are configured, and each has a primary source: `scalar clone` (a blobless partial clone with cone-mode sparse-checkout and background maintenance) ([scalar](https://github.com/git/git/blob/v2.56.0/Documentation/scalar.adoc)); partial-clone filters such as `--filter=blob:none` ([rev-list options](https://github.com/git/git/blob/v2.56.0/Documentation/rev-list-options.adoc)); `git maintenance start`; the commit-graph with changed-path filters; the multi-pack-index; and the filesystem monitor. Shallow clones belong only in throwaway CI ([GitHub Blog](https://github.blog/open-source/git/get-up-to-speed-with-partial-clone-and-shallow-clone/)). Practitioner reports show that repository content and layout matter as much as settings: Dropbox shrank a monorepo from 87 GB to 20 GB in 2026 after finding that Git's delta heuristic was pairing translation files across languages ([Dropbox](https://dropbox.tech/infrastructure/reducing-our-monorepo-size-to-improve-developer-velocity)), and Canva cut `git status` from 10 seconds to about 3 with the filesystem monitor, scheduled maintenance and sparse checkout ([Canva](https://www.canva.dev/blog/engineering/we-put-half-a-million-files-in-one-git-repository-heres-what-we-learned/)).

**[STABLE]** Submodule pain reduces to one fact: the superproject records a commit ID, not a branch, and Git's defaults do not keep the nested checkout in sync. Pro Git itself documents the resulting failure modes: stray directories when switching branches, a detached HEAD after `submodule update` that can lose local work, collaborators broken by a superproject pushed without its submodule commits, and diverged submodule pointers that are not merged automatically ([Pro Git](https://git-scm.com/book/en/v2/Git-Tools-Submodules)). **[GITHUB]** For Git LFS the facts with production consequences are that every pushed version of a file is stored in full against the repository owner's quota, that collaborators and CI without the LFS client silently receive pointer files, and that removing files from LFS frees no storage until the repository is deleted or Support purges the objects ([LFS billing](https://docs.github.com/en/billing/concepts/product-billing/git-lfs), [collaboration with LFS](https://docs.github.com/en/repositories/working-with-files/managing-large-files/collaboration-with-git-large-file-storage)).

### Governance that can be explained after an incident

**[GITHUB]** Governance at scale is built from repository custom properties that rulesets can target, roles and teams, required two-factor authentication, token policies and the audit log ([custom properties](https://docs.github.com/en/organizations/managing-organization-settings/managing-custom-properties-for-repositories-in-your-organization)). The points that matter when something has gone wrong are that Rule Insights records every pass, failure and bypass per ref update; that a "for pull requests only" bypass forces even privileged actors through a pull request and leaves an audit trail, whereas an "exempt" actor skips enforcement silently, without the audit signals a bypass generates; that the audit log's `protected_branch.policy_override` event records an administrator overriding a classic protection; and that deploy keys keep working after the person who added them leaves the organization ([managing rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/managing-rulesets-for-a-repository#viewing-insights-for-rulesets), [repository roles](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization)). **[INFERENCE]** A control chain that can be taught end to end is: define custom properties, target organization rulesets with them, roll out in Evaluate mode where the plan allows, inspect Rule Insights, activate with a narrow bypass list, and monitor through the audit log.

**[INFERENCE]** For the learner's stated goal of explaining root causes to a CTO, every production topic above reduces to the same four-part account: the symptom as observed; the mechanism, named at the right layer (a Git default, a GitHub rule, or an Actions default); the evidence that confirms it (a reflog entry, an Activity-view entry, a ruleset insight, a workflow log); and the control that prevents recurrence. The tables in this section are organised to supply the second and fourth parts.

## 14. Git and GitHub security topics: rotate first, pin everything, and treat every pushed commit as published

### The Git client: cloning is generally safe, running Git inside an untrusted `.git` is not

**[STABLE]** Git's own security statement draws the line precisely. Configuration and hooks can run arbitrary commands, but neither is copied by `git clone`, so cloning a remote repository and inspecting it is generally safe; running Git commands inside a `.git` directory, or the working tree around it, that itself came from an untrusted source (an unpacked archive, a shared directory) is not, and the documented way to obtain a clean copy is `git clone --no-local` ([git(1)](https://github.com/git/git/blob/v2.56.0/Documentation/git.adoc)). The standing defences were added in 2022: `safe.directory` makes Git refuse to parse the configuration of a repository owned by another user, `safe.bareRepository` can restrict Git to bare repositories named explicitly (the default in 3.0), and `protocol.file.allow` defaults to `user` so that the file protocol is not used by commands that clone without user input, such as recursive submodule initialisation ([safe configuration](https://github.com/git/git/blob/v2.56.0/Documentation/config/safe.adoc), [protocol configuration](https://github.com/git/git/blob/v2.56.0/Documentation/config/protocol.adoc)).

**[VERSION]** The recurring vulnerability theme is the recursive clone of an untrusted repository. CVE-2024-32002 (critical, fixed in 2.45.1 and backports in May 2024) let a repository with submodules, on a case-insensitive filesystem that supports symbolic links, write a hook into `.git/` and execute it during the clone ([advisory](https://github.com/git/git/security/advisories/GHSA-8h77-4q3w-gfgv)); the follow-up 2.45.2 reverted over-aggressive hardening that had broken Git LFS ([RelNotes 2.45.2](https://github.com/git/git/blob/master/Documentation/RelNotes/2.45.2.adoc)). CVE-2025-48384 (high, fixed in 2.50.1 and backports in July 2025) used a trailing carriage return in a submodule path to check content out to an unintended location where a hook could run; the advisory's workaround is to avoid recursively cloning submodules of untrusted repositories ([advisory](https://github.com/git/git/security/advisories/GHSA-vwqx-4fm8-6qc9)). CVE-2025-48385 concerned bundle URIs, which are not enabled by default ([advisory](https://github.com/git/git/security/advisories/GHSA-m98c-vgpc-9655)). CVE-2024-52005 concerned unfiltered terminal sequences from a remote; core Git changed the default in 2.55 ([advisory](https://github.com/git/git/security/advisories/GHSA-7jjc-gg6m-3329)). No core-Git advisory was published in 2026 up to 1 October, while Git for Windows published several Windows-specific ones, including credential-hash leaks to attacker-controlled servers fixed in 2.53.0(2) and 2.53.0(3) ([Git for Windows advisories](https://github.com/git-for-windows/git/security/advisories)). **[INFERENCE]** The learner's 2.55.0 already contains every published core-Git fix, as does Apple's 2.50.1; a defensible rule set is never to run Git inside an unpacked copy of someone else's `.git`, to treat `git clone --recurse-submodules` of an untrusted repository as a code-execution risk, to consider `git config --global safe.bareRepository explicit` now, and to leave `protocol.file.allow` at its default.

**[GIT]** Hooks deserve a note of their own. githooks(5) documents 28 hooks, six of them run on the receiving side of a push; client-side hooks live in `$GIT_DIR/hooks` unless `core.hooksPath` redirects them, are not cloned, and `pre-commit` and `commit-msg` are bypassed by `--no-verify` ([githooks](https://github.com/git/git/blob/v2.56.0/Documentation/githooks.adoc)). Since 2.54 hooks can also be declared in configuration, including system and global configuration, so the diagnostic for "why did a hook run" now includes `git hook list --show-scope <event>` ([git-hook](https://github.com/git/git/blob/v2.56.0/Documentation/git-hook.adoc)). For an engineer who routinely clones research code, the ecosystem risk is as real as the client risk: researchers documented a network of more than 3,000 GitHub accounts distributing malware through repositories made to look popular ([Check Point](https://research.checkpoint.com/2024/stargazers-ghost-network/)), hundreds of fake project repositories that stole about 5 BTC ([Kaspersky](https://www.kaspersky.com/about/press-releases/kaspersky-exposes-hidden-malware-on-github-stealing-personal-data-and-485000-in-bitcoin)), and about six million suspected fake stars ([arXiv](https://arxiv.org/abs/2412.13459)). Stars are not evidence of legitimacy.

### Identity: author fields are assertions, signatures are evidence, rules are enforcement

**[STABLE]** Git records whatever author and committer identity the user configures, and GitHub attributes a commit to an account by matching the commit's email address ([GitHub Docs](https://docs.github.com/en/pull-requests/committing-changes-to-your-project/troubleshooting-commits/why-are-my-commits-linked-to-the-wrong-user)). Impersonation in history is therefore trivial for anyone with push access unless signatures are used and verification is enforced ([demonstration](https://www.gruntwork.io/blog/how-to-spoof-any-user-on-github-and-what-to-do-to-prevent-it)).

**[GIT]** Git signs with one of three backends chosen by `gpg.format`: `openpgp` (default), `x509` (since 2.19) or `ssh` (since 2.34). For SSH signing, `user.signingKey` holds the key path or a literal `key::` public key, `commit.gpgSign` and `tag.gpgSign` turn signing on, and local verification depends on `gpg.ssh.allowedSignersFile`: a signature whose key is in that file is fully trusted, and otherwise verification fails, because SSH has no trust levels ([gpg configuration](https://github.com/git/git/blob/v2.56.0/Documentation/config/gpg.adoc), [user configuration](https://github.com/git/git/blob/v2.56.0/Documentation/config/user.adoc)). Signatures live in a `gpgsig` header on commits and are appended to tag objects ([gitformat-signature](https://github.com/git/git/blob/v2.56.0/Documentation/gitformat-signature.adoc)).

**[GITHUB]** GitHub verifies GPG, SSH and S/MIME signatures and shows "Verified", "Partially verified" (in vigilant mode) or "Unverified". Verification records are persistent: once verified, a commit stays verified within its repository network even if the key is later rotated, revoked or expired. Commits made in the web interface, including merge and squash commits, are signed by GitHub; commits produced by "rebase and merge" are not signed at all ([signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification), [vigilant mode](https://docs.github.com/en/authentication/managing-commit-signature-verification/displaying-verification-statuses-for-all-of-your-commits)). Enforcement is the "require signed commits" rule. Sigstore's keyless `gitsign` signs with short-lived certificates tied to an OIDC identity, and per its README GitHub does not display those commits as verified ([gitsign](https://github.com/sigstore/gitsign)). **[INFERENCE]** A course should separate three questions that tutorials conflate: who is displayed (email matching), who signed (a key or identity), and what is enforced (rules). A signature proves that a key holder created the commit, not that the change is benign: the xz-utils backdoor of 2024 was introduced by a contributor who had earned commit rights over more than two years, and the build script that activated it was present only in the release tarball, not in the Git repository ([timeline](https://research.swtch.com/xz-timeline)).

### Credentials: prefer short-lived, narrowly scoped identities, and know what a stolen one can reach

**[GITHUB]** The credential facts that set blast radius are documented. A classic personal access token reaches every repository its owner can reach; fine-grained tokens are limited to one owner and optionally to chosen repositories; GitHub App installation tokens expire after one hour; the Actions `GITHUB_TOKEN` lasts for the job; deploy keys and SSH keys are long-lived ([credential types](https://docs.github.com/en/organizations/managing-programmatic-access-to-your-organization/github-credential-types)). GitHub automatically revokes its own tokens when they are pushed to a public repository or gist and removes tokens unused for a year ([token expiration](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/token-expiration-and-revocation)). A GitHub App's private key, however, never expires: of 4,802 leaked App private keys tested in September 2026, 474 still authenticated, 44 of them with organization admin access ([GitGuardian](https://blog.gitguardian.com/github-app-private-keys-leaked/)). After a compromise, the audit log can be searched by token: compute the token's SHA-256 with `echo -n TOKEN | openssl dgst -sha256 -binary | base64` and search for `hashed_token:"VALUE"`; Git events are excluded from interface and API searches and require an export ([token forensics](https://docs.github.com/en/enterprise-cloud@latest/admin/monitoring-activity-in-your-enterprise/reviewing-audit-logs-for-your-enterprise/identifying-audit-log-events-performed-by-an-access-token)).

**[VERSION]** Real compromises rarely break Git; they abuse tokens, sessions and developer machines. Stolen OAuth tokens issued to Heroku and Travis CI were used in April 2022 to clone private repositories of dozens of organizations ([GitHub Blog](https://github.blog/news-insights/company-news/security-alert-stolen-oauth-user-tokens/)). Malware on a CircleCI engineer's laptop stole an already authenticated session in December 2022, bypassing two-factor authentication, and all customers were told to rotate their secrets ([CircleCI](https://circleci.com/blog/jan-4-2023-incident-report/)). In May 2026 GitHub itself reported that a poisoned third-party VS Code extension on an employee device led to exfiltration of GitHub-internal repositories, after which it rotated critical secrets including the GitHub Enterprise Server signing key ([GitHub Blog](https://github.blog/security/investigating-unauthorized-access-to-githubs-internal-repositories/)). **[INFERENCE]** The hierarchy for automation credentials that follows is: OIDC-issued tokens or the job-scoped `GITHUB_TOKEN` where possible; otherwise App installation tokens with the App's private key in a secrets manager; otherwise fine-grained tokens with expiry and approval; deploy keys only for single-repository read access; classic tokens and shared machine users last. Two-factor authentication is necessary but does not replace short session lifetimes and device security.

### Secrets in repositories: common, long-lived, and not removable by deletion

**The scale.** GitGuardian counted 28,649,024 new secrets on public GitHub in 2025, up 34% and the largest single-year jump recorded; 1,275,105 were tied to AI services, up 81%; 24,008 unique secrets sat in MCP configuration files; commits co-authored by Claude Code leaked secrets at roughly twice the baseline rate; 64% of secrets confirmed valid in 2022 were still valid when retested; and internal repositories were about six times more likely than public ones to contain a hardcoded secret ([State of Secrets Sprawl 2026](https://www.gitguardian.com/state-of-secrets-sprawl-report-2026)). GitHub's own figure is more than one million leaked secrets detected on public repositories in the first eight weeks of 2024 ([GitHub Blog](https://github.blog/news-insights/product-news/keeping-secrets-out-of-public-repositories/)).

**Why deletion does not work.** **[STABLE]** A commit that deletes a secret adds a new snapshot and leaves the old one in history. GitHub states that after a rewrite and force push the old commits can still be accessible in clones and forks, directly by commit ID in cached views, and through pull requests that reference them ([removing sensitive data](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)), and that Git data pushed to any repository in a fork network may be accessed from any other repository in that network even after a fork is deleted ([forks reference](https://docs.github.com/en/pull-requests/reference/forks#important-security-considerations)). Researchers showed in 2024 that this can be exploited at scale, finding 40 valid API keys in commits from deleted forks of three commonly forked repositories ([Truffle Security](https://trufflesecurity.com/blog/anyone-can-access-deleted-and-private-repo-data-github)), and in 2025 that commits orphaned by force pushes can be enumerated from public event archives and scanned, which yielded thousands of secrets including a GitHub token with admin access to all repositories of the Istio project ([Truffle Security guest post](https://trufflesecurity.com/blog/guest-post-how-i-scanned-all-of-github-s-oops-commits-for-leaked-secrets)). A scan of AI companies using the same idea found that 65% of the Forbes AI 50 companies with a GitHub footprint had leaked verified secrets ([SecurityWeek](https://www.securityweek.com/many-forbes-ai-50-companies-leak-secrets-on-github/)). **[INFERENCE]** "Private", "deleted" and "force-pushed" change discoverability, not accessibility; the exposure window starts at the first push and does not end at deletion.

**What GitHub blocks and what it does not.** **[GITHUB]** Secret scanning scans the entire history on all branches plus issues, pull requests, discussions and wikis; it is free on public repositories and needs GitHub Secret Protection on private ones ([secret scanning](https://docs.github.com/en/code-security/secret-scanning/introduction/about-secret-scanning)). Push protection for users has been on by default since 29 February 2024 and stops pushes of recognised secrets to public repositories; push protection for repositories requires Secret Protection and is off by default; a block can be bypassed with a stated reason unless delegated bypass restricts who may do so ([push protection](https://docs.github.com/en/code-security/secret-scanning/introduction/about-push-protection)). Coverage varies by provider, which matters directly for LLM application work:

| Credential type | Provider notified for public leaks | Blocked by push protection | Validity check |
|---|---|---|---|
| OpenAI API key; Anthropic API key; Hugging Face user access token; xAI, Groq, OpenRouter, Replicate, Databricks tokens | Yes | Yes | Yes |
| Google API key | Yes | **No** | Yes |
| Google Gemini API key | **No** | **No** | User alert only |
| Mistral AI, Cohere, DeepSeek, Pinecone | **No** | Yes | Yes |
| Perplexity, LangSmith, Weights & Biases API keys | **No** | Yes | No |

Source for the table: GitHub's supported-pattern data as read on 1 October 2026 ([supported patterns](https://docs.github.com/en/code-security/secret-scanning/introduction/supported-secret-scanning-patterns)). Partner notification does not guarantee revocation. GitHub revokes its own leaked tokens; Anthropic documents automatic deactivation of keys found in public GitHub repositories ([Anthropic](https://support.claude.com/en/articles/9767949-api-key-best-practices-keeping-your-keys-safe-and-secure)); Hugging Face lets anyone invalidate a leaked token through a revocation endpoint ([Hugging Face](https://huggingface.co/docs/hub/en/security-tokens)); but an xAI key flagged on 2 March 2025 stayed valid until 30 April 2025 ([Krebs on Security](https://krebsonsecurity.com/2025/05/xai-dev-leaks-api-key-for-private-spacex-tesla-llms/)). **[INFERENCE]** GitHub's default protection is narrower than people assume: it covers pushes to public repositories and high-confidence patterns only, generic secrets such as passwords and connection strings are not blocked, and for providers that are not partners nobody but the repository owner is alerted. A local or CI scanner is still needed.

**Scanners.** As of 1 October 2026, TruffleHog (v3.97.9, AGPL-3.0) verifies candidate secrets against provider APIs and can enumerate deleted and hidden commits ([TruffleHog](https://github.com/trufflesecurity/trufflehog/blob/main/README.md)); gitleaks (v8.30.1) declares itself feature-complete with security patches only, its author having moved to Betterleaks (v1.9.0, MIT) ([gitleaks](https://github.com/gitleaks/gitleaks/blob/master/README.md), [Betterleaks](https://github.com/betterleaks/betterleaks)); detect-secrets' last release is 1.5.0 of May 2024 ([detect-secrets](https://github.com/Yelp/detect-secrets)); and git-secrets has no tagged releases ([git-secrets](https://github.com/awslabs/git-secrets)).

### GitHub Actions security: a short-lived token, untrusted input, and code you did not write

**[GITHUB]** The model has five parts. First, each job receives a `GITHUB_TOKEN`, an installation token limited to the workflow's repository that expires when the job ends; its default has been read-only for new repositories and organizations since February 2023 (existing ones were not changed), and the `permissions` key raises or lowers it per workflow or job, with every unspecified scope set to none once any scope is named ([GITHUB_TOKEN](https://docs.github.com/en/actions/concepts/security/github_token), [permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)). Second, workflows triggered by `pull_request` from a fork get a read-only token and no secrets, and by default only first-time contributors need approval to run workflows, a gate that one merged typo fix removes ([settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository#controlling-changes-from-forks-to-workflows-in-public-repositories)). Third, `pull_request_target` runs in the context of the base repository with a read-write token and access to secrets, and always runs regardless of approval settings; it is safe only while the workflow does not fetch and execute the fork's code. Checking out the pull request's head or merge ref and then running a build, install or test step is the pattern GitHub's documentation calls a "pwn request", and the same applies to `issue_comment` and `workflow_run` workflows that fetch and run fork code ([pull_request_target guidance](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)). Fourth, expressions inside `${{ }}` are substituted into the script text before the shell runs, so attacker-controlled fields such as a pull-request title or a branch name become code; the documented mitigation is to pass the value through an intermediate environment variable or to an action input ([script injections](https://docs.github.com/en/actions/concepts/security/script-injections)). Fifth, a third-party action runs with the job's token and secrets, a tag can be moved by whoever controls the action's repository, and pinning to a full-length commit SHA is the only immutable reference ([secure use](https://docs.github.com/en/actions/reference/security/secure-use#using-third-party-actions)).

Around that core, four further facts are routinely misunderstood. Anyone with write access to a repository can effectively read all its secrets by editing a workflow, and log redaction of secrets is not guaranteed ([secure use](https://docs.github.com/en/actions/reference/security/secure-use#use-secrets-for-sensitive-information)). OIDC federation replaces stored cloud keys with a short-lived token valid for a single job; it needs `id-token: write`, the cloud trust policy must constrain the token's subject, and repositories created after 15 July 2026 use an immutable subject format that includes owner and repository IDs ([OIDC reference](https://docs.github.com/en/actions/reference/security/oidc)). Self-hosted runners should almost never be used with public repositories, because any pull request can run code on them and they are not ephemeral by default ([hardening self-hosted runners](https://docs.github.com/en/actions/reference/security/secure-use#hardening-for-self-hosted-runners)). And caches are neither confidential nor verified: anyone who can open a pull request can read caches of the base branch, which is why default-branch caches are read-only for low-trust triggers since June 2026 ([dependency caching](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#cache-access-for-low-trust-workflow-triggers)). Static analysis exists at three levels: CodeQL analysis of workflow files, generally available since April 2025 and included in default setup ([changelog](https://github.blog/changelog/2025-04-22-github-actions-workflow-security-analysis-with-codeql-is-now-generally-available/)); the third-party zizmor and actionlint ([zizmor audits](https://docs.zizmor.sh/audits/), [actionlint](https://github.com/rhysd/actionlint/blob/main/README.md)); and the OpenSSF Scorecard checks for dangerous workflows, token permissions and pinned dependencies ([Scorecard checks](https://github.com/ossf/scorecard/blob/main/docs/checks.md)).

**[VERSION]** The platform mitigations shipped in 2025 and 2026 line up with these incidents (the dates are sourced; the pairing is the researchers' inference): enforceable SHA pinning and blocklists (August 2025), default-branch-only `pull_request_target` (December 2025), `actions/checkout` v7's refusal to fetch fork pull-request code in privileged triggers (June and July 2026), read-only caches and `cache-mode` (June and September 2026), holds on suspicious workflow runs (July 2026), and workflow execution protections whose default rule will block `pull_request_target` in public repositories from 2 November 2026 unless a maintainer explicitly allows it ([execution protections](https://github.blog/changelog/2026-09-17-workflow-execution-protections-in-github-actions-generally-available/)). **[INFERENCE]** A defensible secure-by-default workflow in late 2026 therefore has top-level `permissions: contents: read` with per-job additions; uses `pull_request`, not `pull_request_target`, for CI; pins actions to full commit SHAs with a version comment and lets Dependabot update them; passes untrusted event fields only through `env:`; uses OIDC and environment-scoped trust for deployments; sets `persist-credentials: false` where the job does not push; and declares `cache-mode: read` or `none` in release jobs. The technique that recurs across incidents, dumping the runner worker's memory to harvest secrets and OIDC tokens, makes masked logs irrelevant once attacker code runs in a job; the robust controls are preventing untrusted code from running in privileged jobs and limiting which secrets a job holds. SHA pinning protects against moved tags but not against a malicious commit pinned deliberately or against unpinned actions nested inside composite actions.

### AI-specific exposure that an LLM engineer should plan for

**[VERSION]** Three findings concern the learner's field directly. AI-service credentials are the fastest-growing class of leaked secret, with growth multiples reported for several LLM providers and tens of thousands of secrets found in MCP configuration files ([GitGuardian](https://www.gitguardian.com/state-of-secrets-sprawl-report-2026)). An LLM API key can expose far more than billing: the xAI key above reached private and fine-tuned models. And AI agents running inside workflows read attacker-controlled text while holding secrets: an automated account ran a week-long campaign in February and March 2026 that combined `pull_request_target` abuse, branch-name and filename injection and prompt injection against an AI reviewer ([StepSecurity](https://www.stepsecurity.io/blog/hackerbot-claw-github-actions-exploitation)), and researchers reported in April 2026 that AI coding agents run as GitHub Actions could be steered by text in pull-request titles, issue bodies or comments into revealing CI secrets ([Techzine](https://www.techzine.eu/news/security/140524/ai-agents-on-github-leak-api-keys-via-prompt-injection/)). **[INFERENCE]** An agent in a workflow should receive a dedicated low-privilege, spend-capped key, no write token unless required, and should not run automatically on untrusted contributions.

### Governance controls that limit blast radius

**[GITHUB]** The controls that matter are the ones that limit what a leaked credential can do and that leave a trail: fine-grained or App tokens with expiry and organization approval ([token policy](https://docs.github.com/en/organizations/managing-programmatic-access-to-your-organization/setting-a-personal-access-token-policy-for-your-organization)); mandatory two-factor authentication and SSO authorization; rulesets on branches, tags and pushes, where push rulesets can block file paths, extensions and sizes across the whole fork network; code-owner review of `.github/workflows/` and of the CODEOWNERS file itself, which GitHub's documentation recommends placing in `.github/` with the repository owner as its owner ([code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners#codeowners-and-branch-protection)); and an audit log that covers 180 days at organization level and should be exported or streamed if Git events are to be available long after the fact ([audit log](https://docs.github.com/en/organizations/keeping-your-organization-secure/managing-security-settings-for-your-organization/reviewing-the-audit-log-for-your-organization)). **[INFERENCE]** These controls reduce blast radius rather than prevent leaks: the cases with the worst outcomes involved single credentials with estate-wide read access, and detection came from outsiders in nearly every case, so organizations that want to be first need their own monitoring of public GitHub, including employees' and contractors' personal accounts.

## 15. AI/ML-specific Git workflows: keep code and pointers in Git, and keep data, weights and outputs out of it

### Notebooks: a JSON file that stores code, outputs and counters together

**[STABLE]** A Jupyter notebook is a JSON document whose code cells carry their source, a list of outputs (including base64-encoded images) and an execution counter, so line-based diff and merge behave badly, a conflicted merge can leave an invalid notebook, and outputs can carry data or printed credentials into history ([nbformat](https://nbformat.readthedocs.io/en/latest/format_description.html), [nbdime](https://nbdime.readthedocs.io/en/latest/), [GitGuardian](https://blog.gitguardian.com/how-to-handle-secrets-in-jupyter-notebooks/)). **[GITHUB]** GitHub renders `.ipynb` files as static HTML; its rich notebook diff is still the feature preview announced on 1 March 2023, in which lines cannot be commented on, and no general-availability announcement was found ([changelog](https://github.blog/changelog/2023-03-01-feature-preview-rich-jupyter-notebook-diffs/), [feedback thread](https://github.com/orgs/community/discussions/37376)).

The maintained tools are complementary rather than alternatives. **nbstripout** (0.9.1, February 2026) is a Git clean filter that strips outputs and some metadata from what is committed while leaving the file on disk untouched; `nbstripout --install` writes the filter into the clone's configuration, the `--attributes .gitattributes` variant writes the attribute lines into a committed file, the filter is declared required so that a misconfigured filter aborts instead of being skipped, and `--verify` fails if anything would have been stripped, which is the form suited to CI ([nbstripout](https://github.com/kynan/nbstripout/blob/main/README.md)). **nbdime** (4.0.4, February 2026) provides content-aware `nbdiff`, `nbmerge` and web viewers, registered for Git with `nbdime config-git --enable` ([nbdime Git integration](https://nbdime.readthedocs.io/en/latest/vcs.html)). **jupytext** (1.19.5, July 2026) pairs a notebook with a plain-text file, for example with `jupytext --set-formats ipynb,py:percent notebook.ipynb`, so that review happens on an ordinary Python diff ([jupytext](https://github.com/jupytext/jupytext/blob/main/README.md)). ReviewNB is a commercial GitHub app for teams that deliberately commit outputs and need to comment on them ([ReviewNB](https://www.reviewnb.com/)). **[STABLE]** One limitation shapes all of this: Git filters and drivers live in each clone's configuration and cannot be activated by cloning, by design, so that a clone never executes arbitrary code. **[INFERENCE]** A team that depends on nbstripout must therefore also enforce it centrally, for example with a CI job that runs `nbstripout --verify`; stripping outputs is also a data-protection control, because outputs can contain query results or personal data that no secret-scanning pattern will match.

### Data and model versioning: Git holds the reference, another system holds the bytes

**[GITHUB]** The platform limits define what does not belong in Git: files over 100 MiB are blocked, repositories should stay well under 5 GB, and GitHub's documentation states that Git is not designed to serve as a backup tool ([large files](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)). **[INFERENCE]** Git should hold source code, tests, configuration, prompts and evaluation specifications, lock files, Dockerfiles, CI workflows and small pointer or metadata files; raw and processed datasets, checkpoints and exported weights, experiment-tracking stores, caches and build outputs belong elsewhere.

### Reproducibility: the commit alone does not identify what ran

**[INFERENCE]** A reproducible ML or LLM-evaluation result needs several things recorded together: the Git commit and whether the tree was dirty, a committed lock file, an immutable container reference, the resolved configuration, and the data and model versions. The tools record less than people assume. **[VERSION]** MLflow's classic run context sets `mlflow.source.git.commit`, the branch and the repository URL when the entry point is inside a Git repository, but it does not inspect or record uncommitted changes; a newer opt-in function, marked experimental, records the dirty state and the diff ([system tags](https://mlflow.org/docs/latest/ml/tracking/tracking-api/), [git context source](https://github.com/mlflow/mlflow/blob/master/mlflow/tracking/context/git_context.py), [genai versioning source](https://github.com/mlflow/mlflow/blob/master/mlflow/genai/git_versioning/git_info.py)). Weights & Biases generates a patch of uncommitted changes when code is logged, but code saving is disabled by default for all teams ([W&B code saving](https://docs.coreweave.com/models/app/features/panels/code)). Hydra writes the resolved configuration and the command-line overrides into a `.hydra` directory for every run ([Hydra](https://hydra.cc/docs/tutorials/basic/running_your_app/working_directory/)). **[INFERENCE]** With MLflow's classic tracking, two different code states can therefore share one commit ID; the defensible practice is to refuse tracked training runs from a dirty tree or to log the status and diff as artifacts.

**[VERSION]** For environments, uv (0.12.21) documents that `uv.lock` is a cross-platform lock file that should be committed, with `--locked` raising an error when it is out of date ([uv](https://docs.astral.sh/uv/concepts/projects/layout/), [locking](https://docs.astral.sh/uv/concepts/projects/sync/)); GitHub's Python ignore template likewise recommends committing lock files for applications ([template](https://github.com/github/gitignore/blob/main/Python.gitignore)). Container image tags are mutable, and pinning to a digest guarantees the same image at the price of opting out of automatic fixes, which Docker suggests offsetting with Dependabot ([Docker](https://docs.docker.com/build/building/best-practices/)). Package versions derived from tags (`git describe`, setuptools-scm 10.3.4, hatch-vcs 0.5.0) fail or fall back in CI when the checkout is shallow, because the default `actions/checkout` fetch contains one commit and no tags ([git-describe](https://git-scm.com/docs/git-describe), [setuptools-scm](https://github.com/pypa/setuptools-scm/blob/main/docs/index.md)).

### Ignore rules, attributes and hooks for ML repositories

**[GITHUB]** GitHub's Python `.gitignore` template covers interpreter, packaging, environment and tool caches and contains nothing ML-specific ([template](https://github.com/github/gitignore/blob/main/Python.gitignore)). **[INFERENCE]** ML projects add data directories, checkpoint and export formats (`*.pt`, `*.pth`, `*.ckpt`, `*.safetensors`, `*.onnx`, `*.gguf`), tracker output (`wandb/`, `mlruns/`, `mlflow.db`), Hydra output directories and `.env` files, with editor and operating-system noise kept in each developer's global ignore file. **[STABLE]** Three rules prevent recurring mistakes: ignore patterns never affect files that are already tracked; filter, diff and merge drivers are defined in Git configuration and only named in `.gitattributes`, so a committed attribute that names an uninstalled driver is either a silent no-op or, for a required filter, a hard failure; and `* text=auto` with `git add --renormalize .` is the documented way to normalise line endings for everyone ([gitignore](https://git-scm.com/docs/gitignore), [gitattributes](https://git-scm.com/docs/gitattributes)). An ignore file is not a security control: a secret or checkpoint committed before the rule existed stays in history.

**[VERSION]** The pre-commit framework is actively maintained (4.6.2, August 2026): hooks are declared in `.pre-commit-config.yaml`, `pre-commit install` installs the Git hook, `pre-commit run --all-files` is the documented CI usage, and `rev` must be an immutable tag or commit ([pre-commit](https://pre-commit.com/)). Typical hooks for an ML repository are Ruff's `ruff-check` and `ruff-format`, `check-added-large-files` (default threshold 500 kB), `detect-private-key`, nbstripout and one secret scanner ([pre-commit-hooks](https://github.com/pre-commit/pre-commit-hooks/blob/main/README.md), [ruff-pre-commit](https://github.com/astral-sh/ruff-pre-commit/blob/main/README.md)). prek (v0.5.4) is a Rust reimplementation that is compatible with pre-commit configurations ([prek](https://github.com/j178/prek/blob/master/README.md)). **[INFERENCE]** Local hooks fail open: they are not installed by cloning, are skipped with one flag, and are bypassed by commits made through the web interface, the API or an agent's own Git client. Every hook that matters must also run in CI as a required check, and secrets and large files should additionally be stopped server-side by push protection and push rulesets.

### CI for ML projects on GitHub Actions

**[GITHUB]** The mechanics are ordinary: a Python version matrix, lock-file-driven installs and caches. uv's guide pins `astral-sh/setup-uv` to a full commit SHA and installs with `uv sync --locked` ([uv with GitHub Actions](https://docs.astral.sh/uv/guides/integration/github/)). Three pressure points are specific to ML. GPU capacity is limited to one hosted shape, a 4-vCPU machine with a single T4, available only to Team and Enterprise Cloud organizations and always billed per minute ([larger runners](https://docs.github.com/en/actions/reference/runners/larger-runners)). Caches are free only up to 10 GB per repository and are readable by any pull request author, which makes them suitable for package caches and small test models rather than multi-gigabyte checkpoints. And LLM evaluations need provider API keys in CI: promptfoo's GitHub Action runs a before-and-after evaluation of edited prompts on pull requests, and DeepEval integrates with pytest and fails the build when a metric falls below its threshold; Inspect AI, Ragas and the LangSmith SDK are also maintained ([promptfoo](https://www.promptfoo.dev/docs/integrations/github-action/), [DeepEval](https://deepeval.com/docs/evaluation-unit-testing-in-ci-cd)). CML, once the usual way to post model metrics on pull requests, has had no release since October 2024 ([CML releases](https://github.com/iterative/cml/releases)).

**[INFERENCE]** LLM evaluations in CI are non-deterministic, cost money per run and need secrets, and the last property collides with the fork model: secrets are not available to `pull_request` runs from forks, and the tempting workaround of `pull_request_target` with a checkout of the contributor's code is the exact pattern behind the compromises in section 14, several of which hit ML projects (PyTorch's self-hosted runners, Ultralytics, LiteLLM). Self-hosted GPU runners concentrate risk because they are expensive, long-lived and hold cached models and cloud credentials; the defensible configuration is private repositories or approval for all outside contributors, ephemeral runners, runner groups scoped to named repositories, and OIDC instead of keys on the host.

### Repository structure, and the Java and backend side

**[VERSION]** Two reference points are well documented. Cookiecutter Data Science v2 (run with `ccds`) generates a layout with `data/` split into raw, interim, processed and external, a `notebooks/` directory with a naming convention, `models/`, `reports/` and an importable source package, and its generated `.gitignore` ignores `/data/` ([CCDS](https://github.com/drivendataorg/cookiecutter-data-science/blob/master/README.md)). The Python Packaging Authority describes the trade-off between the flat and `src/` layouts without issuing a blanket recommendation ([PyPA](https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/)). For model-serving repositories no single authoritative layout was found; the sourced building blocks are that secrets must not be passed as build arguments or environment variables because they persist in the image, that secret mounts exist for this purpose, and that weights should be fetched by pinned reference rather than committed ([Docker build secrets](https://docs.docker.com/build/building/secrets/), [Hugging Face download guide](https://huggingface.co/docs/huggingface_hub/guides/download)).

**[GITHUB]** On the Java side, GitHub's templates ignore `target/`, `build/`, `.gradle` and `*.class`, but they treat the two wrappers differently: the Maven wrapper JAR is ignored, while the Gradle template explicitly un-ignores `gradle-wrapper.jar`, which Gradle's own documentation says is expected to be committed ([Maven template](https://github.com/github/gitignore/blob/main/Maven.gitignore), [Gradle template](https://github.com/github/gitignore/blob/main/Gradle.gitignore), [Gradle Wrapper](https://docs.gradle.org/current/userguide/gradle_wrapper.html)). That committed JAR is the one place in a typical Java repository where a pull request can change executable code that reviewers cannot read in a diff, which is why `gradle/actions/wrapper-validation` exists and why `setup-gradle` has validated wrappers automatically since its v4 ([wrapper validation](https://github.com/gradle/actions/blob/main/docs/wrapper-validation.md)). Dependabot covers the ecosystems of a polyglot ML backend with separate entries: `pip`, `uv` (version updates since 13 March 2025, security updates since 16 December 2025), `maven`, `gradle` and `github-actions`, with `docker` and `pre-commit` receiving version updates only ([supported ecosystems](https://docs.github.com/en/code-security/dependabot/ecosystems-supported-by-dependabot/supported-ecosystems-and-repositories)).

### AI coding agents as participants in the workflow

**[VERSION]** By October 2026 agents are first-class actors on GitHub: Copilot can review and, in preview, approve pull requests, and the Copilot cloud agent opens pull requests and signs its commits (section 2). DORA's 2025 research describes AI as an amplifier of an organisation's existing strengths and weaknesses and lists version control and working in small batches among the capabilities that matter, recommending small frequent commits for AI-generated code ([DORA 2025 report](https://dora.dev/research/2025/dora-report/), [DORA: version control](https://dora.dev/capabilities/version-control/)). The learning resources are following: the third edition of Pro Git lists a chapter on Git and agents, and MIT's 2026 Missing Semester adds an agentic-coding lecture ([progit3.com](https://progit3.com/), [Missing Semester](https://missing.csail.mit.edu/)). **[INFERENCE]** For this learner the practical consequence is that the fundamentals in sections 12 to 14 matter more, not less, when an agent writes the commits: small reviewable changes, a lock on who can bypass rules, hooks and scanners enforced in CI because an agent's Git client does not run local hooks, and narrowly scoped credentials for anything an agent can read.

## Conclusion

The research changes the design problem for the program. Git and GitHub knowledge has two very different half-lives: the data model, the index, refs, reflogs and merge mechanics have been stable for many years and are precisely what popular teaching skips, while defaults, platform policy and action versions now change on a scale of months, fast enough that GitHub's own documentation, a 2024 video with a recent upload date and a frozen edition of Pro Git were all caught out of date in this single snapshot. A curriculum built on that observation teaches the stable layer once and deeply, packages everything version-sensitive as dated, replaceable modules that state the older behavior, the current behavior and the version involved, and treats the habit of checking a primary source (the local `git version`, a release note, a changelog entry, a `/rules` page) as a skill to be practised rather than an appendix. That habit is also what the learner's stated goal requires: every root-cause explanation in sections 13 and 14 turned on knowing which layer acted, whether a Git default, a GitHub rule or an Actions default, and where its evidence is kept.

Several facts in this report will expire on known dates, which gives the later phases a built-in re-verification calendar: the `ubuntu-latest` migration from 19 October 2026, GitHub Universe on 28 and 29 October, enforcement of the default `pull_request_target` rule on 2 November, the SSH changes between 14 October 2026 and 13 January 2027, Git 2.98 near the end of 2026, and Git 3.0 with its SHA-256, reftable and `main` defaults some time after that. The items flagged as unverified, above all GitHub's SHA-256 support, the retention of unreachable commits on GitHub and the dates of the Git 3.0 transition, should be re-checked against primary sources before the textbook states them, and the core video picks should be watched by a human before they are assigned, since their assessment here rests on captions rather than viewing.
