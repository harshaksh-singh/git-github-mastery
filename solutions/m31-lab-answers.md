# Module 31 lab answers: Secret-leak response

Answers to the "Questions" of Lab 31.1 in the [Module 31 lab manual](../lab-manual/m31-secret-leak-response.md). Commit IDs are the ones printed in the manual; commits you created by hand have other IDs. Statements about Git were checked on Git 2.55.0 in the lab sandbox. Statements about GitHub and git-filter-repo come from the documentation that [Chapter 21B](../textbook/ch21b-repository-security-incident-response.md) cites.

## Lab 31.1: The tabletop

1. Until the issuer revokes the key, it works for everyone who has a copy, and revocation is the only action that reaches every copy at once: clones, forks, caches, screenshots. Nothing done to the repository shortens that window. At a real issuer you would also check what the stand-in cannot show: the usage log for the exposure window (was the key used, from where, for what), the scope of the key (what it could reach), whether other keys of the same owner or project need rotating, and that every consumer runs on the replacement.
2. A commit ID is a hash over the tree, the parent IDs, the author, the committer and the message. `987a49d` is an ancestor of the first changed commit: its tree and its parents were untouched, so the rewrite produced the identical object. `64b9b89` has `0805fd8` as its parent. That parent became `0ac4257`, so the parent line of the recreated commit differs and the hash with it: `66a99cc`. The same holds for every later commit and for the tag object that points at one of them.
3. `--mirror` makes the remote's refs equal to the local ones. It deletes every remote ref that the cleanup clone does not have, for example a branch a colleague pushed after you cloned, and it pushes every local ref, which would have included the backup refs under `refs/original/` had you not deleted them. The precautions: freeze pushes before taking the mirror clone, delete the tool's backup refs first, and preview with `git push --dry-run --force --mirror origin`.
4. Neither was a force push. Both were fast-forwards from the clean tip to a merge commit that has the clean tip as one parent. The difference was the guard: the `pre-receive` hook examined the content of the incoming commits and declined Ravi's push; for Asha's it had been switched off. A rule that only forbids force pushes stops neither. On GitHub the corresponding controls are push protection, when the secret matches a supported or custom pattern, and a push ruleset that blocks the file path. The git-filter-repo manual notes that few hosting services can ban a specific commit from being pushed again, and the Phase 0 notes found no documented built-in control of that kind on GitHub.
5. `git rebase origin/main` replays the commits that are in `main` and not in `origin/main`. After the rewrite that set contains her commit and the whole old history from `0805fd8` on, because those commits have other IDs than their rewritten versions. Git skips commits whose patch is identical to one upstream, but "Add staging settings" is not identical: the old version adds `.env`. Chapter 21B, section 21B.18 shows that rebase stopping with a conflict on `0805fd8`. `--onto origin/main $old` names the base explicitly, so the range is exactly the commits after the tip she cloned. A `git pull --rebase` as her clone's *first* contact with the new history replayed only her commit when it was run for the chapter (`labs/run ch21b/stale-clone-rebase`), because the pull still knew the previous value of `origin/main`. In the lab she had already merged and pushed, so that information was no longer usable, and the explicit form is the one that does not depend on what happened before.
6. A fetch does not overwrite an existing local tag. Her clone's `v0.2.0` still pointed at the old tag object `c38ee42`, which points into the old history and keeps all of it reachable, so pruning would have removed nothing. Deleting the tags and fetching them again installs the rewritten tag `17124a2`.
7. Unreachable commits in the repository, readable by commit ID in cached views: GitHub Support, through garbage collection and removal of cached views. Pull request refs (`refs/pull/N/head`) that still point at old commits: GitHub Support, by dereferencing or deleting the affected pull requests. Forks: each fork's owner; GitHub cannot give you their contact details. Clones: their owners. Orphaned LFS objects, if any: GitHub Support. Support assists only where it determines that rotating the credentials cannot mitigate the risk.
8. The key was revoked within the hour and the issuer's log can show whether it was used; from that moment the string in history is harmless. The rewrite, in exchange, cost every collaborator their clone, changed every commit ID from the first changed commit on (breaking references in tickets, experiment records and deployment manifests), removed signatures, required switching off force-push protection, and created the recontamination risk that the failure scenario demonstrated. On a public repository it also would not have recalled a single existing copy. The proportionate response was: rotate, read the provider's log, fix the tip, add the guard, document. Practise the rewrite on a sandbox, as this lab does, not on the production repository.
