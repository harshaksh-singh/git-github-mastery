## 1. Rulesets versus classic branch protection rules

### Takeaway
Rulesets are GitHub's stated strategic governance mechanism ("Rulesets are the recommended way to protect your branches"; GitHub is "investing in rulesets as the foundation for repository governance") and classic branch protection rules still exist and layer with them; since 11 Aug 2026 there is a one-click "Convert to ruleset" migration. Rulesets add layering (most-restrictive-wins aggregation), enforcement statuses (Active / Evaluate / Disabled; Evaluate is documented only for Enterprise), read-access visibility, bypass lists with pull-request-only and "exempt" modes, tag and push rulesets, and organization- and enterprise-level scope; a large set of new rules arrived in 2025–2026 (merge-method rule, required team reviewers, restrict review dismissal, Copilot review, code quality/coverage, secret-scanning merge blocking, push-rule path exceptions).

### Cited Findings

#### What each mechanism is, and which one GitHub recommends
- **[CURRENT]** "A ruleset is a named list of rules that applies to a repository or to multiple repositories in an organization for customers on GitHub Team and GitHub Enterprise plans. You can have up to 75 rulesets per repository, and 75 organization-wide rulesets." — [About rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)
- **[CURRENT]** Three ruleset target types exist in the UI: "New branch ruleset", "New tag ruleset", "New push ruleset". — [Creating rulesets for a repository](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository)
- **[CURRENT]** Docs' own comparison: "Rulesets and branch protection rules can both protect branches in a repository. They work alongside each other, and all applicable rules are enforced." Rulesets' listed advantages: "Multiple rulesets can apply to the same branch at the same time, while only one branch protection rule applies"; "You can change a ruleset's enforcement status without deleting the ruleset"; "Anyone with read access to a repository can view its active rulesets"; "Rulesets can also control commit metadata, such as commit messages and author email addresses." — [About rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)
- **[CURRENT]** Classic rules' limitation, stated in the classic docs: "Only a single branch protection rule can apply at a time, which means it can be difficult to know which rule will apply when multiple versions of a rule target the same branch. This restriction does not apply to rulesets." — [About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)
- **[CHANGED 2026-07-07] GitHub's recommendation, verbatim:** "Rulesets are the recommended way to protect your branches." — [Changelog 2026-07-07: Restrict who can dismiss reviews in rulesets](https://github.blog/changelog/2026-07-07-restrict-who-can-dismiss-reviews-in-rulesets/)
- **[CHANGED 2026-08-11]** "You can now convert your existing branch protection rules to repository rulesets directly from your repository settings... As we continue investing in rulesets as the foundation for repository governance on GitHub, this tool makes it easy to bring your existing policies forward." Path: Settings → Branches → "Convert to ruleset". Available "for all repositories where rulesets are available." — [Changelog 2026-08-11](https://github.blog/changelog/2026-08-11-automatically-migrate-branch-protection-rules-to-repository-rulesets/)
- **[CURRENT]** Conversion details: one branch protection rule converted at a time; GitHub "generates one or more rulesets that preserve the original rule's behavior"; optional checkbox "Delete branch protection rule once migration is done"; new ruleset is created **Active**; if you keep the classic rule "An Active ruleset is enforced alongside it, so changes must satisfy both." Caveat: "The conversion covers all branch protection types with the exception of the 'Require conversation resolution before merging' setting. In branch protections, this setting exists on its own. In rulesets, conversation resolution is part of the pull request rule and only applies when that rule is enabled." — [Converting branch protections to rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/converting-branch-protections-to-rulesets)
- I found **no** changelog entry or doc announcing a deprecation or sunset date for classic branch protection rules (searched all changelog slugs Jan 2025–1 Oct 2026 for "branch-protect", "ruleset", "deprecat", "sunset", "closing-down"). Classic rules remain documented as a current feature. — [About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

#### Enforcement statuses
- **[CURRENT]** Free/Pro/Team version of the docs lists two statuses: "Active: your ruleset will be enforced upon creation" and "Disabled: your ruleset will not be enforced." — [About rulesets (Free/Pro/Team view)](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)
- **[PLAN-GATED: GitHub Enterprise]** The Enterprise Cloud version of the same article lists three: "Active", "Evaluate: your ruleset will not be enforced, but you will be able to monitor which actions would or would not violate rules on the 'Rule Insights' page", "Disabled: your ruleset will not be enforced or evaluated." - **[CURRENT]** The enforcement control in the UI defaults to "Disabled" in the creation flow ("Optionally, to change the default enforcement status, click Disabled and select an enforcement status"); if set to Active "the ruleset takes effect immediately." — [Creating rulesets for a repository](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository)

#### Layering
- **[CURRENT]** "A ruleset does not have a priority. Instead, if multiple rulesets target the same branch or tag in a repository, the rules in each of these rulesets are aggregated. If the same rule is defined in different ways across the aggregated rulesets, the most restrictive version of the rule applies. As well as layering with each other, rulesets also layer with protection rules targeting the same branch or tag." Worked example in the docs: repo ruleset (signed commits + 3 reviews) + classic rule (linear history + 2 reviews) + org ruleset (block force pushes + 1 review) ⇒ signed commits, linear history, force pushes blocked, 3 reviews. — [About rulesets (Enterprise Cloud view)](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets#about-rule-layering)
- **[CURRENT]** Org-level rulesets cannot be loosened at repo level: "If a repository is targeted by a ruleset created at the organization level, only owners of the organization can edit the ruleset. However, people with admin access to the repository... can create additional rulesets at the repository level... creating a new ruleset can make the rules targeting a branch or tag more restrictive, but never less restrictive." — [Creating rulesets for repositories in your organization](https://docs.github.com/en/enterprise-cloud@latest/organizations/managing-organization-settings/creating-rulesets-for-repositories-in-your-organization)
- **[CURRENT]** Forks: "Forks do not inherit branch or tag rulesets from their upstream repositories. However, forks owned by your organization are subject to the rulesets you create, like any other repository." "Forks *do* inherit push rulesets from their root repository." — [Creating rulesets for repositories in your organization](https://docs.github.com/en/enterprise-cloud@latest/organizations/managing-organization-settings/creating-rulesets-for-repositories-in-your-organization)

#### Bypass lists
- **[CURRENT]** Eligible bypass actors for a repository ruleset: "Repository admins, organization owners, and enterprise owners"; "The maintain or write role, or custom repository roles based on the write role"; "Teams, excluding secret teams"; "GitHub Apps"; "Dependabot". Bypass mode per actor: "Always allow" or "For pull requests only" ("The selected actor is now required to open a pull request to make changes to a repository, creating a clear trail of their changes in the pull request and audit log. The actor can then choose to bypass any branch protections and merge that pull request"). — [Creating rulesets for a repository](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository#granting-bypass-permissions-for-your-branch-or-tag-ruleset)
- **[PLAN-GATED: Enterprise Cloud docs]** Additional eligible actors at org/enterprise level: "Enterprise teams, enterprise apps, and enterprise roles (public preview)", "Copilot cloud agent"; the enterprise list also names "deploy keys". — [Creating rulesets for repositories in your organization](https://docs.github.com/en/enterprise-cloud@latest/organizations/managing-organization-settings/creating-rulesets-for-repositories-in-your-organization); [Enforcing code governance in your enterprise with rulesets](https://docs.github.com/en/enterprise-cloud@latest/admin/enforcing-policies/enforcing-policies-for-your-enterprise/enforcing-policies-for-code-governance)

- **[CHANGED 2025-09-10]** New "exempt" bypass type: "Unlike a standard bypass (i.e., a 'break glass' action that requires an explicit actor bypass and generates prominent audit signals), an exemption silently skips enforcement." #### Targeting syntax
- **[CURRENT]** Branch/tag/repo-name targeting uses Ruby `File.fnmatch` with `File::FNM_PATHNAME`: "`*` wildcard does not match directory separators (`/`)... `qa/*` will match all branches beginning with `qa/` and containing a single slash, but will not match `qa/foo/bar`. You can include any number of slashes after `qa` with `qa/**/*`." Unsupported: backslash quoting, `[^charset]` complement, `File::FNM_EXTGLOB`. Multiple include/exclude criteria can be combined (e.g. include default branch, include `*feature*`, exclude `not-a-feature`). — [Creating rulesets for a repository](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository#using-fnmatch-syntax)
- **[CHANGED 2025-06-24] [PLAN-GATED: Team, Enterprise]** Org/enterprise ruleset repository targeting modes: "Repositories matching a filter" (search syntax, e.g. `visibility:private props.team:infra -language:java`), "All repositories", "Only selected repositories", "Repositories matching a name" (`fnmatch`); filter targeting is the default. Also targeting by deployment context (`deployed:true` / `deployable:true`) and a "Prevent renaming of target repositories" option. — [Changelog 2025-06-24](https://github.blog/changelog/2025-06-24-filter-based-ruleset-targeting/); [Creating rulesets for repositories in your organization](https://docs.github.com/en/enterprise-cloud@latest/organizations/managing-organization-settings/creating-rulesets-for-repositories-in-your-organization)

#### Full list of rules available in rulesets (as documented 1 Oct 2026)
Source for all unless noted: [Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets) (Free/Pro/Team view) and its [Enterprise Cloud view](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).
- **Restrict creations** — "only users with bypass permissions can create branches or tags whose name matches the pattern."
- **Restrict updates** — "only users with bypass permissions can push to branches or tags whose name matches the pattern."
- **Restrict deletions** — only bypassers can delete matching refs. "This rule is selected by default."
- **Require linear history** — "prevents collaborators from pushing merge commits to the targeted branches or tags"; PRs must use squash or rebase merge; the repository must allow squash or rebase merging first.
- **Require merge queue** — **[PLAN-GATED]** documented only in the Enterprise Cloud view; "This rule is not available for rulesets created at the organization level." Settings: Merge method; Build concurrency; Minimum/maximum group size; Wait time to meet minimum group size (minutes); Require all queue entries to pass required checks; Status check timeout (minutes).
- **Require deployments to succeed before merging** — changes must deploy successfully to named environments first.
- **Require signed commits** — "contributors and bots can only push commits that have been signed and verified." Documented ruleset-vs-classic difference: "with rulesets, we check only the commits that aren't accessible from other branches, whereas with branch protection rules, we do not verify signed commits unless you restrict pushes that create matching branches." With vigilant mode, "Partially verified" commits are permitted. Gotcha: when evaluating a PR GitHub "creates a test merge commit whose parents are the latest commit on the base branch and the pull request's head commit. GitHub checks the commits introduced by this test merge, including commits from the head branch. As a result, unsigned commits on the head branch can block a squash merge, even though GitHub would sign the final squash commit."
- **Require a pull request before merging** — "The pull request doesn't necessarily have to be approved, but it must be opened." Sub-options: required number of approving reviews; **Dismiss stale pull request approvals when new commits are pushed**; **Require review from code owners** (approval from *any* listed owner suffices); **Restrict who can dismiss pull request reviews** (users, teams, or GitHub Apps; **[CHANGED 2026-07-07]** GA in rulesets — [changelog](https://github.blog/changelog/2026-07-07-restrict-who-can-dismiss-reviews-in-rulesets/)); **Require approval of the most recent reviewable push** (approval from someone other than the last pusher); **require all conversations/comments to be resolved** (in rulesets this is a sub-option of the PR rule, not a standalone rule); **allowed merge methods** ("require a merge type of merge, squash, or rebase"; **[CHANGED 2025-03-24]** GA — [changelog](https://github.blog/changelog/2025-03-24-enterprise-custom-properties-enterprise-rulesets-and-pull-request-merge-method-rule-are-all-now-generally-available/); if the repository has disabled the method the ruleset requires, "the merge will be blocked"); **Require an additional approval for unattributed Copilot pull requests** (**[PREVIEW]**, "enabled by default, for both new and existing rulesets"; when Copilot opens a PR not attributed to a person the ruleset requires one more approval than configured; no effect if zero approvals required); **Required reviewers** (**[CHANGED 2025-11-03 preview → 2026-02-17 GA]**: require review/approval from specific *teams* for file patterns; "up to 15 different teams"; approvals per team 0–10 where 0 = added for visibility only; team must have write access; patterns follow `.gitignore` format including `!` negation; "not available on user-owned repositories" — [changelog GA](https://github.blog/changelog/2026-02-17-required-reviewer-rule-is-now-generally-available/)).
- **Require status checks to pass before merging** — "strict" (checkbox **Require branches to be up to date before merging** checked; default) vs "loose"; can pin the expected source GitHub App for a check ("The app must be installed in the repository with the `statuses:write` permission, must have recently submitted a check run"); Enterprise view adds "Do not require status checks on creation". Check-name formats: workflow job = `<job name>`; reusable workflow = `<job name> / <reusable job name>` — [Troubleshooting rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/troubleshooting-rules).
- **Block force pushes** — "This rule is enabled by default." Side effect: "organization owners or repository administrators will be unable to change or rename the default branch unless they are authorized to bypass the ruleset."
- **Require secret scanning alerts are resolved** — **[PREVIEW] [CHANGED 2026-09-09] [PLAN-GATED: GitHub Secret Protection or GitHub Advanced Security]** blocks merge if the secret scan for the head commit is incomplete or a commit in the PR introduced an open alert of a selected type; provider, custom, and generic patterns supported, "AI-detected secrets are not supported." REST rule type `require_secret_scanning_alert_resolution`. — [Changelog 2026-09-09](https://github.blog/changelog/2026-09-09-block-pull-requests-with-exposed-secrets-from-merging/)
- **Require code scanning results** — blocks merge when a required tool finds an alert at/above the configured severity, analysis is in progress, or the tool is not configured.
- **Require code quality results** — blocks merge based on GitHub Code Quality analysis (in progress, failed, or findings at/above a severity). GitHub Code Quality GA was 2026-07-20 — [changelog](https://github.blog/changelog/2026-07-20-github-code-quality-is-now-generally-available/).
- **Restrict code coverage** — **[PREVIEW] [CHANGED 2026-06-30]** thresholds: "Minimum line coverage percentage" and "Maximum line coverage drop" relative to the default branch; requires Code Quality + uploaded coverage. — [Changelog 2026-06-30](https://github.blog/changelog/2026-06-30-github-code-coverage-merge-protection-for-pull-requests/)
- **Require workflows to pass before merging** — **[PLAN-GATED: Enterprise Cloud view; "configured at the organization or enterprise level"]** supported triggers `pull_request`, `pull_request_target`, `merge_group`; event filters are ignored; "Applying this rule will block direct pushes... you should not apply this rule to a ruleset that targets all branches." (Mechanics belong to the Actions researcher.)
- **Metadata restrictions** — **[PLAN-GATED: "Organizations on a GitHub Enterprise plan"]** restrict commit message, author email, committer email, branch name, tag name by literal or regex; committer-email patterns "must also include `noreply@github.com` for web-based merges"; for squash merges "restrictions are only validated against the metadata of the single, resulting merge commit"; use `\n?$` rather than `$` for end anchors. Important behavior: metadata restrictions "block 'ref updates'... the commits still enter your repository: the commits will be 'retrievable'... but not 'reachable'."
- **Automatically request Copilot code review** — **[CHANGED 2025-09-10]** standalone branch rule (UI: under "Branch rules," select "Automatically request Copilot code review"; optional sub-settings "Review new pushes" and "Review draft pull requests" — the 2025 changelog called them "Run on each push" and "Run on drafts"); previously a sub-setting of the PR rule; available in repository, organization and enterprise rulesets. Not described on the Available-rules page; documented in the Copilot docs and changelog. — [Configuring code review by GitHub Copilot](https://docs.github.com/en/copilot/how-tos/copilot-on-github/set-up-copilot/configure-code-review); [Changelog 2025-09-10](https://github.blog/changelog/2025-09-10-copilot-code-review-independent-repository-rule-for-automatic-reviews/); [About Copilot code review](https://docs.github.com/en/copilot/concepts/agents/code-review)
- **Push rules (push rulesets only):** **Restrict file paths** ("Limit is 200 entries and up to 200 characters in each entry"; `fnmatch`); **Restrict file path length**; **Restrict file extensions** (200 entries × 200 chars); **Restrict file size**. **[PREVIEW] [CHANGED 2026-08-25]** "Allowed exceptions" for *Restrict file paths* and *Restrict file size* only (e.g. `**/gradle/wrapper/*.jar`). — [Changelog 2026-08-25](https://github.blog/changelog/2026-08-25-push-rules-in-rulesets-now-support-path-exceptions/)

#### Push rulesets specifics
- **[CURRENT] [PLAN-GATED: Team (and Enterprise), private/internal repos]** "With push rulesets, you can block pushes to a private or internal repository and that repository's entire fork network based on file extensions, file path lengths, file and folder paths, and file sizes. Push rules do not require any branch targeting because they apply to every push to the repository." Bypass is inherited from the root repository only. — [About rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets#push-rulesets)
- **[CURRENT]** "When utilizing push rulesets, a maximum of 1000 reference updates are allowed per push." Push rulesets also "apply to the 'Create a blob', 'Create a tree', and 'Create or update file contents' endpoints in the REST API." — [Troubleshooting rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/troubleshooting-rules)
- **[PLAN-GATED: Enterprise Cloud] [CHANGED 2025-04-09 GA]** Delegated bypass for push rules: contributors "request 'bypass privileges'"; requests go to the bypass list; requests expire after 7 days; statuses Cancelled / Completed / Denied / Expired / Open; managed on the "Bypass Requests" page. — [About rulesets (Enterprise Cloud view)](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets); [Managing rulesets for a repository (Enterprise Cloud view)](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/managing-rulesets-for-a-repository); [Changelog 2025-04-09](https://github.blog/changelog/2025-04-09-push-rule-delegated-bypass-and-custom-property-regex-support-are-generally-available-and-repository-policy-delegated-bypass-is-in-preview/)

## 2. Pull requests: mechanics, reviews, merge queue, auto-merge, merge methods, 2025–2026 features, and why a PR shows unexpected commits

### Takeaway
A pull request is a GitHub object (not a Git one) backed by hidden, read-only refs under `refs/pull/N/`; GitHub computes mergeability with a background *test merge commit* (generation policy changed 19 Feb 2026), shows a three-dot (merge-base) diff, and offers three merge methods with distinct, documented effects on SHAs, committer, and signatures (rebase-and-merge always creates new SHAs and unsigned commits). The PR surface changed heavily in 2025–2026: new "Files changed" page (default since 22 Jan 2026), stacked pull requests (public preview 30 Jul 2026), async merge API (GA 1 Oct 2026), Copilot code review/cloud agent, PR access limits, and archiving of PRs.

### Cited Findings

#### What technically exists when a PR is opened (GitHub behavior on top of Git)
- **[CURRENT]** "When you open a pull request, GitHub creates temporary Git references that point to the pull request's head branch and, when possible, to a simulated merge result. These refs help GitHub and integrations evaluate the pull request without changing the base branch." — [Pull requests (reference)](https://docs.github.com/en/pull-requests/reference/pull-requests#pull-request-refs-and-merge-branches)
- **[CURRENT]** The head ref is fetchable with plain Git: `git fetch origin pull/ID/head:BRANCH_NAME`. "After a pull request is opened, GitHub stores all of the changes remotely. Commits in a pull request are available in a repository even before the pull request is merged." "The remote `refs/pull/` namespace is *read-only*"; pushing to it fails with `! [remote rejected] HEAD -> refs/pull/1/head (deny updating a hidden ref)`. — [Checking out pull requests locally](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/checking-out-pull-requests-locally)
- **[CURRENT]** The merge ref: for `pull_request`-triggered workflows `GITHUB_REF` is "PR merge branch `refs/pull/PULL_REQUEST_NUMBER/merge`" and `GITHUB_SHA` is the "Last merge commit on the `GITHUB_REF` branch"; "For open, mergeable pull requests... `actions/checkout`... checks out the merge branch. Your CI tests run against the merged result, not just the head branch alone"; use `github.event.pull_request.head.sha` to get the real head commit. "Workflows will not run on `pull_request` activity if the pull request has a merge conflict." — [Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request)
- **[CURRENT]** Test merge commit: "When you get, create, or edit a pull request, GitHub creates a merge commit to test whether the pull request can be automatically merged into the base branch. This test commit is not added to the base branch or the head branch." "The value of the mergeable attribute can be true, false, or null. If the value is null, then GitHub has started a background job to compute the mergeability... If mergeable is true, then merge_commit_sha will be the SHA of the test merge commit." — [REST API endpoints for pull requests](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request)
- **[CURRENT]** The test merge commit's parents: "it creates a test merge commit whose parents are the latest commit on the base branch and the pull request's head commit." — [Available rules for rulesets, Require signed commits](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-signed-commits)
- **[CHANGED 2026-02-19]** "Test merge commits will only be generated when one of the following is true: Changes are pushed to the pull request branch. The merge base between the pull request and base branches changes. The current test merge commit is older than 12 hours. Previously, test merge commits were also generated when viewing the pull request page. This change does not impact mergeability checks, reporting of merge conflicts, or rule enforcement." — [Changelog 2026-02-19](https://github.blog/changelog/2026-02-19-changes-to-test-merge-commit-generation-for-pull-requests/)
- **[CURRENT, but partly stale]** REST guide warning: "Please do not depend on using Git directly or `GET /repos/{owner}/{repo}/git/refs/{ref}` for updates to `merge` Git refs, because this content becomes outdated without warning." The same guide still says "A *test* merge commit is created when you view the pull request in the UI and the 'Merge' button is displayed" — [Using the REST API to interact with your Git database](https://docs.github.com/en/rest/guides/using-the-rest-api-to-interact-with-your-git-database#checking-mergeability-of-pull-requests); contradicted on the "viewing" trigger by [Changelog 2026-02-19](https://github.blog/changelog/2026-02-19-changes-to-test-merge-commit-generation-for-pull-requests/) (docs lag; trust the changelog).
- **[CURRENT]** PR page tabs as documented now: Conversation, Commits, Checks, Files changed, and **Findings** ("automated code review results, such as code scanning alerts"); plus a **merge status** indicator "in the pull request header and in the merge box." — [Pull requests (reference)](https://docs.github.com/en/pull-requests/reference/pull-requests)
- **[CURRENT]** Base is pinned to a commit at open time: "When you open a pull request, GitHub sets the base to the commit that branch references. If the branch is updated in the future, GitHub does not update the base branch's commit." — [Changing the base branch of a pull request](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/changing-the-base-branch-of-a-pull-request)

#### The diff shown is a three-dot diff
- **[CURRENT]** "Pull requests on GitHub show a three-dot diff." Three-dot (`git diff A...B`) compares "The most recent common commit of both branches (merge base) and the most recent version of the topic branch"; two-dot (`git diff A..B`) compares the tips. "Because the three-dot comparison uses the merge base, it focuses on 'what a pull request introduces.'" "When you use a two-dot comparison, the diff changes when the base branch is updated, even if you haven't made any changes to the topic branch." "The **Files changed** tab shows what would change if the pull request merged." — [Branches (reference)](https://docs.github.com/en/pull-requests/reference/branches#three-dot-and-two-dot-git-diff-comparisons)
- **[CURRENT]** "Compare pages and pull request pages can calculate changed files from different merge bases. As a result, the same branches can sometimes show different diffs in each place. This usually matters when the base branch has changed since the pull request was created. Pull request pages focus on what the pull request introduced, while compare pages reflect the current comparison between two refs." — [Pull requests (reference)](https://docs.github.com/en/pull-requests/reference/pull-requests#differences-between-commits-on-compare-and-pull-request-pages)

#### Draft PRs and review states
- **[CURRENT]** "Draft pull requests cannot be merged, and code owners are not automatically requested to review them." Marking ready "will request reviews from any code owners." "You can convert a pull request to a draft at any time." — [Pull requests (reference)](https://docs.github.com/en/pull-requests/reference/pull-requests#draft-pull-requests); [Changing the stage of a pull request](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/changing-the-stage-of-a-pull-request)
- **[CHANGED 2025-05-01]** Draft PRs no longer plan-gated: "Previously, GitHub Free users could only create draft pull requests in public repos... You can now create draft pull requests in any repository, public or private, completely free of charge." — [Changelog 2025-05-01](https://github.blog/changelog/2025-05-01-draft-pull-requests-are-now-available-in-all-repositories/)
- **[CURRENT]** Review decision types: **Comment** ("Leaves general feedback without explicitly approving or requesting changes"), **Approve**, **Request changes**. "Anyone with read access can review and comment on proposed changes." To *request* a review you need write access. — [Pull request reviews](https://docs.github.com/en/pull-requests/reference/pull-request-reviews)
- **[CURRENT]** "The **Request changes** option is purely informational and will not prevent merging unless a ruleset or classic branch protection rule is configured with the 'require a pull request' option. Line comments are "*pending* and only visible to you" until the review is submitted. — [Reviewing proposed changes in a pull request](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request)
- **[CURRENT]** Dismissal: "repository administrators or people with write access can dismiss a review. Dismissing a review changes the status of the review to a review comment. When you dismiss a review, you must add a comment explaining why." — [Dismissing a pull request review](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/dismissing-a-pull-request-review)
- **[CURRENT]** Stale-approval dismissal semantics: "GitHub records the state of the diff at the point when a pull request is approved... If the diff changes from this state (for example, because a contributor pushes new changes to the pull request branch or clicks **Update branch**, or because a related pull request is merged into the target branch), the approving review is dismissed as stale." Also "approving reviews will be dismissed as stale if the merge base introduces new changes after the review was submitted." — [Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-a-pull-request-before-merging)
- **[CURRENT]** "Require approval of the most recent reviewable push": "require an approval from someone other than the last person to push to a branch"; with it "'stale' reviews are not dismissed, and the pull request remains approved as long as someone other than the person who made the most recent changes approves it... If you are concerned about pull requests being 'hijacked' (where unapproved content is added to approved pull requests), it is safer to dismiss stale reviews." With either setting, "manually creating the merge commit for a pull request and pushing it directly to a protected branch will fail, unless the contents of the merge exactly match the merge generated by GitHub for the pull request." — [Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-a-pull-request-before-merging)
- **[CURRENT]** Cross-PR blocking: "collaborators cannot merge the pull request if there are other open pull requests that have a head branch pointing to the same commit with pending or rejected reviews." — [About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-pull-request-reviews-before-merging)
- **[CURRENT]** Suggested changes: applying one suggestion or a batch "creates a single commit on the compare branch of the pull request. Each person who suggested a change included in the commit will be a co-author of the commit. The person who applies the suggested changes will be a co-author and the committer of the commit." Requires write access (or maintainer-edit permission on a fork PR). Buttons: "Commit suggestion", "Add suggestion to batch", "Commit suggestions". — [Incorporating feedback in your pull request](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/incorporating-feedback-in-your-pull-request)

#### Merge methods: exact documented semantics
- **[CURRENT] Merge commit:** "all commits from the feature branch are added to the base branch in a merge commit. The pull request is merged using the `--no-ff` option." — [Pull request merges](https://docs.github.com/en/pull-requests/reference/pull-request-merges#merge-your-commits)
- **[CURRENT] Squash and merge:** "the pull request's commits are squashed into a single commit... Pull requests with squashed commits are merged using the fast-forward option." Default message: "the commit title and message if the pull request contains only 1 commit, or the pull request title and list of commits if the pull request contains 2 or more commits" (configurable: PR title; PR title + commit details; PR title + description). Documented downsides: "You lose information about when specific changes were originally made and who authored the squashed commits"; continuing to use the head branch afterwards makes later PRs list already-squashed commits and repeat conflicts. — [Pull request merges](https://docs.github.com/en/pull-requests/reference/pull-request-merges#squash-and-merge-your-commits); [Configuring commit squashing](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/configuring-commit-squashing-for-pull-requests); [About merge methods on GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github)
- **[CURRENT] Rebase and merge:** "all commits from the topic branch (or head branch) are added onto the base branch individually without a merge commit." "The rebase and merge behavior on GitHub deviates slightly from `git rebase` outside of GitHub. Rebase and merge on GitHub: **Always updates the committer information and creates new commit SHAs**, whereas `git rebase` does not change the committer information when the rebase happens on top of an ancestor commit. **Drops commits that were empty to begin with**, such as those created with `git commit --allow-empty`, whereas `git rebase` keeps originally-empty commits by default." — [Pull request merges](https://docs.github.com/en/pull-requests/reference/pull-request-merges#rebase-and-merge-your-commits)
- **[CURRENT] Rebase limit:** "Merging a pull request using the 'Rebase and merge' option is limited to **100** commits." — [Repository limits](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits#rebase-limits)
- **[CURRENT] Signatures, rebase-and-merge:** "the commits in the head branch are added to the base branch without commit signature verification. When you use this option, GitHub creates a modified commit, using the data and content of the original commit. This means that GitHub didn't truly create this commit, and can't therefore sign it as a generic system user. GitHub doesn't have access to the committer's private signing keys, so it can't sign the commit on the user's behalf. A workaround for this is to rebase and merge locally, and then push the changes to the pull request's base branch." — [About commit signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification#signature-verification-for-rebase-and-merge)
- **[CURRENT] Signatures, merge commit and squash:** "GitHub will automatically use GPG to sign commits you make using the web interface. Commits signed by GitHub will have a verified status. You can verify the signature locally using the public key available at https://github.com/web-flow.gpg." — [About commit signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification); and specifically for squash: "GitHub would sign the final squash commit." — [Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-signed-commits)
- **[CURRENT] Author/email on merge:** for merge and squash you can "select the email address to use as the Git author email address. Only verified email addresses appear"; with email privacy a no-reply address is the default. "The email selector is not available for rebase merges, which do not create a merge commit. For squash merges, the email selector is only shown if you are the pull request author and you have more than one email address associated with your account." Note on the merge page: "Rebase and merge will always update the committer information and create new commit SHAs." — [Merging a pull request](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-a-pull-request)
- **[CURRENT]** Web-created commits use committer `noreply@github.com` (implied by: metadata restrictions on committer email "must also include `noreply@github.com` for web-based merges and other commits created on GitHub.com"). — [Available rules for rulesets (Enterprise Cloud view)](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#metadata-restrictions)
- **[CURRENT]** After merge with head-branch deletion: "GitHub checks for any open pull requests in the same repository that specify the deleted branch as their base branch. GitHub automatically updates any such pull requests, changing their base branch to the merged pull request's base branch." — [Merging a pull request](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-a-pull-request)
- **[CURRENT] Indirect merges:** "A pull request can be marked as merged if its head branch commits become reachable from the base branch outside that pull request... Pull requests merged indirectly are marked as `merged` even if branch protection rules on that pull request were not satisfied." — [Pull request merges](https://docs.github.com/en/pull-requests/reference/pull-request-merges#indirect-merges)
- **[CURRENT]** With a merge queue "you no longer get to choose the merge method, as this is controlled by the queue." — [About merge methods on GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github)

#### Merge queue
- **[PLAN-GATED]** "Pull request merge queues are available in any public repository owned by an organization, or in private repositories owned by organizations using GitHub Enterprise Cloud." (By this wording, repositories owned by personal accounts are not eligible.) — ["Who can use this feature?" box, Managing a merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)
- **[CURRENT] How it works:** "A merge queue creates temporary branches with a special prefix to validate pull request changes... the changes in the pull request are grouped into a `merge_group` with the latest version of the `base_branch` as well as changes from pull requests ahead of it in the queue." First-in-first-out. Third-party CI must build branches prefixed `gh-readonly-queue/{base_branch}`, which "contain a different `sha` from the pull request". A failing or conflicting entry is removed and later entries' temporary branches are recreated without it. "Jumping to the top of the queue" causes "a full rebuild of all in-progress pull requests". — [Managing a merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue#how-merge-queues-work)
- **[CURRENT] `merge_group` event:** "You **must** use the `merge_group` event to trigger your GitHub Actions workflow when a pull request is added to a merge queue... Otherwise, status checks will not be triggered... The merge will fail as the required status check will not be reported. The `merge_group` event is separate from the `pull_request` and `push` events." Only activity type: `checks_requested`. — [Managing a merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue#triggering-merge-group-checks-with-github-actions); [Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#merge_group)
- **[CURRENT] Settings:** Merge method (merge, rebase, squash); Build concurrency (1–100 `merge_group` webhooks); "Only merge non-failing pull requests"; Status check timeout; Merge limits (min/max 1–100 PRs and wait time). — [Managing a merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue#managing-a-merge-queue)
- **[CURRENT] Using it:** button "Merge when ready" → "Confirm merge when ready" (can be clicked before requirements pass); admins may "Merge without waiting for requirements to be met (bypass branch protections)". `gh pr merge` "automatically adds the pull request to the queue if required checks have passed. If required checks have not passed, this command enables auto-merge." "You cannot use GitHub CLI to remove a pull request from a merge queue" or to view a queue. Removal reasons: CI failure for a merge group; timeout; user removal via API/UI; "Branch protection failure that could not automatically be resolved." — [Merging a pull request with a merge queue](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-a-pull-request-with-a-merge-queue)

#### Auto-merge

Must be enabled per repository first. — ["Who can use this feature?" box, Managing auto-merge for pull requests in your repository](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-auto-merge-for-pull-requests-in-your-repository)

#### Linking issues with closing keywords
- **[CURRENT]** Keywords: `close`, `closes`, `closed`, `fix`, `fixes`, `fixed`, `resolve`, `resolves`, `resolved` (optionally with colon/uppercase); syntax `KEYWORD #N`, `KEYWORD OWNER/REPOSITORY#N`; multiple issues need the keyword repeated. #### Limits that affect PR display
- **[CURRENT]** Diff limits: "In a pull request, no total diff may exceed *20,000 lines that you can load* or *1 MB* of raw diff data"; single file: 20,000 loadable lines or 500 KB ("Four hundred lines and 20 KB are automatically loaded for a single file"); "maximum number of files in a single diff is limited to *300*"; 25 renderable files. #### Status checks as they affect merging
- **[CURRENT]** Two kinds: **checks** ("Detailed output, annotations, and messages"; created by GitHub Apps including GitHub Actions) and **commit statuses** (simpler; external services). "GitHub Actions generates checks, not commit statuses." "Anyone with write permissions to a repository can set the state for any status check in the repository." "A job that is skipped will report its status as 'Success'. It will not prevent a pull request from merging, even if it is a required check." Checks data is retained 400 days; "To merge a pull request with checks that are both required and archived, you must rerun the checks." — [Status checks](https://docs.github.com/en/pull-requests/reference/status-checks)
- **[CURRENT]** Required-check troubleshooting facts: "A required status check must have completed successfully in the chosen repository during the past seven days" (to be selectable); "Required checks must pass on the latest commit SHA"; successful states are `success`, `skipped`, `neutral`; "If a check and a commit status have the same name, both must pass"; if the test merge commit has a status, that is what must pass (UI shows "Showing checks for the merge commit"), otherwise the head commit; a workflow skipped by path/branch filtering or commit message leaves required checks "Pending" and blocks merging ("Waiting for status to be reported"), whereas a job skipped by a conditional reports Success; only workflow runs triggered by `push`, `pull_request`, `pull_request_review`, `pull_request_target`, `deployment`, `deployment_status` produce checks that count for a PR (e.g. `workflow_dispatch` runs do not). #### Documented reasons a PR shows unexpected commits or an unexpectedly large diff

### Inferences
- **Git vs GitHub split for teaching:** Git provides commits, refs, merge-base, `git diff A...B`, `--no-ff`, rebase. GitHub adds the PR object, `refs/pull/N/head` and `refs/pull/N/merge`, the test merge commit, reviews, merge queue, auto-merge, closing keywords, and the three merge buttons. "Squash and merge" and "Rebase and merge" are GitHub server-side operations whose results differ from local `git merge --squash`/`git rebase` (new committer, new SHAs, dropped empty commits, GitHub-signed or unsigned results).
- After rebase-and-merge or squash-and-merge, the PR's original commits are *not* ancestors of the base branch; `git branch -d` will refuse the local branch and `git branch --merged` will not list it — a common learner confusion that follows from "creates new commit SHAs".
- Under "Require signed commits", rebase-and-merge is effectively unusable on GitHub (results are unsigned), while squash and merge commits are signed by GitHub's web-flow key — but the PR's own head commits must still be signed because the rule evaluates commits introduced by the test merge.
- A PR opened against the wrong base (e.g. `main` instead of the parent feature branch) will list every commit not reachable from that base — this follows from the three-dot/merge-base definition; GitHub's stacked PRs feature is the first-party answer to dependent-branch workflows.
- Since 19 Feb 2026, tooling that relied on "viewing the PR refreshes `refs/pull/N/merge`" may see merge refs up to 12 hours stale unless a push or base change occurs or the REST GET is called.

### Gaps
- Current docs no longer contain an explicit sentence stating that the squash commit's *author* is the PR author and that other commit authors become `Co-authored-by` trailers; the only remaining hint is the email-selector note quoted above. Treat exact squash authorship as UNVERIFIED against current docs (older docs said squash merges "credit the user who created the pull request as the author of the squashed commit"; I could not retrieve that sentence from the live page).
- The current Pull requests reference page no longer spells out `refs/pull/N/head` and `refs/pull/N/merge` by name; the names are confirmed via the checkout doc (`pull/ID/head`) and the Actions events doc (`refs/pull/PULL_REQUEST_NUMBER/merge`).
- No doc explicitly lists "wrong base branch" as a troubleshooting cause in one place; the findings above are assembled from separate reference pages.
- Whether the classic "Files changed" opt-out still exists on 1 Oct 2026 was not confirmed (it existed on 22 Jan 2026).

## 3. CODEOWNERS

### Takeaway
A CODEOWNERS file lives in `.github/`, the repository root, or `docs/` (searched in that order, first found wins), is read from the PR's *base* branch, must be under 3 MB, uses gitignore-like patterns minus three unsupported features, and resolves ownership by last-matching-pattern; owners must have explicit write access. It only *requests* reviews by itself — enforcement requires "Require review from Code Owners" in a ruleset or branch protection rule, and the newer "Required reviewers" ruleset rule complements rather than replaces it.

### Cited Findings
- **[PLAN-GATED]** "You can define code owners in public repositories with GitHub Free and GitHub Free for organizations, and in public and private repositories with GitHub Pro, GitHub Team, GitHub Enterprise Cloud, and GitHub Enterprise Server." "People with write permissions for the repository can create or edit the CODEOWNERS file and be listed as code owners. People with admin or owner permissions can require that pull requests have to be approved by code owners before they can be merged." — ["Who can use this feature?" box, About code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)
- **[CURRENT] Locations and precedence:** "create a new file called `CODEOWNERS` in the `.github/`, root, or `docs/` directory of the repository, in the branch where you'd like to add the code owners. If `CODEOWNERS` files exist in more than one of those locations, GitHub will search for them in that order and use the first one it finds." — [About code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners#codeowners-file-location)
- **[CURRENT] Per-branch:** "Each CODEOWNERS file assigns the code owners for a single branch in the repository." "For code owners to receive review requests, the CODEOWNERS file must be on the base branch of the pull request." For fork PRs into upstream, the upstream base branch's file is used. — [About code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners#codeowners-and-forks)
- **[CURRENT] Size limit:** "CODEOWNERS files must be under 3 MB in size. A CODEOWNERS file over this limit will not be loaded, which means that code owner information is not shown and the appropriate code owners will not be requested to review changes in a pull request." — [About code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners#codeowners-file-size)
- **[CURRENT] Syntax:** "A CODEOWNERS file uses a pattern that follows most of the same rules used in gitignore files. The pattern is followed by one or more GitHub usernames or team names using the standard `@username` or `@org/team-name` format." Email addresses work "in most cases" but "You cannot use an email address to refer to a managed user account." Inline `#` comments are supported. "CODEOWNERS paths are case sensitive." — [About code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners#codeowners-syntax)
- **[CURRENT] Documented unsupported gitignore syntax (complete list):** "Escaping a pattern starting with `#` using `\` so it is treated as a pattern and not a comment doesn't work"; "Using `!` to negate a pattern doesn't work"; "Using `[ ]` to define a character range doesn't work". — [About code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners#codeowners-syntax)
- **[CURRENT] Last match wins:** "Order is important; the last matching pattern takes the most precedence." Multiple owners for one pattern must be on the same line ("If the code owners are not on the same line, the pattern matches only the last mentioned code owner"). A later pattern with *no* owners (e.g. `/apps/github` after `/apps/ @octocat`) un-assigns ownership for that path. Pattern examples from the docs: `docs/*` matches `docs/getting-started.md` "but not further nested files"; `apps/` matches an `apps` directory anywhere; `/docs/` is anchored to the root; `**/logs` matches at any depth. — [About code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners#example-of-a-codeowners-file)
- **[CURRENT] Write access required:** "The people you choose as code owners must have write permissions for the repository. When the code owner is a team, that team must be visible and it must have write permissions, even if all the individual members of the team already have write permissions directly, through organization membership, or through another team membership." "If you specify a user or team that doesn't exist or has insufficient access, a code owner will not be assigned." — [About code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)
- **[CURRENT] Behavior:** "Code owners are automatically requested for review when someone opens a pull request that modifies code that they own. Code owners are not automatically requested to review draft pull requests." — [About code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners#about-code-owners)
- **[CURRENT] Enforcement with branch protection/rulesets:** enable "Require review from Code Owners"; "an approval from *any* of the owners is sufficient". Hardening advice: "you also need to define an owner for the CODEOWNERS file itself. The most secure method is to define a CODEOWNERS file in the `.github` directory of the repository and define the repository owner as the owner of either the CODEOWNERS file (`/.github/CODEOWNERS @owner_username`) or the whole directory (`/.github/ @owner_username`)." Docs also point to rulesets "as an alternative to branch protection rules". — [About code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners#codeowners-and-branch-protection)
- **[CURRENT] Debugging:** "If any line in your CODEOWNERS file contains invalid syntax, that line will be skipped. When you navigate to the CODEOWNERS file in your repository, you can see any errors highlighted. A list of errors in a repository's CODEOWNERS file is also accessible via the API" (`GET /repos/{owner}/{repo}/codeowners/errors`, "List CODEOWNERS errors"). Hovering the shield icon on a file shows its owner. — [About code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners#codeowners-syntax); [REST API endpoints for repositories](https://docs.github.com/en/rest/repos/repos#list-codeowners-errors)
- **[CHANGED 2026-02-17]** Relationship to the "Required reviewers" ruleset rule: "The required reviewer rule augments CODEOWNERS files but doesn't replace them. CODEOWNERS files remain the best way to manage ownership, support individuals as reviewers, and request reviews even when not required." The ruleset rule supports `!` negation and team-only reviewers with per-team approval counts — things CODEOWNERS cannot do. — [Changelog 2026-02-17](https://github.blog/changelog/2026-02-17-required-reviewer-rule-is-now-generally-available/)
- **[CHANGED 2025-04-29 / 2025-08-08]** Dependabot's `reviewers` configuration option was replaced by code owners. — [Changelog 2025-04-29](https://github.blog/changelog/2025-04-29-dependabot-reviewers-configuration-option-being-replaced-by-code-owners/); [Changelog 2025-08-08](https://github.blog/changelog/2025-08-08-dependabot-reviewers-configuration-option-is-replaced-by-code-owners/)
- **[PREVIEW]** In stacked PRs, CODEOWNERS is "Evaluated from the stack base." — [Stacked pull requests (reference)](https://docs.github.com/en/pull-requests/reference/stacked-pull-requests#branch-protections-and-required-checks)

### Inferences
- Because the file is read from the base branch, a PR that *edits* CODEOWNERS is reviewed under the old rules; and a team with only inherited (not explicit) write access silently fails to be assigned — the two most common "why wasn't my team requested?" causes follow directly from the quoted rules.
- "Secret" teams cannot be code owners ("that team must be visible").
- CODEOWNERS has no way to require approvals from *all* owners or N owners per path; the ruleset "Required reviewers" rule is the documented mechanism for per-team counts.

### Gaps
- The `gh` CLI has no dedicated CODEOWNERS-lint command in the manual; the documented debugging paths are the web UI highlighting and the REST "List CODEOWNERS errors" endpoint (callable via `gh api repos/OWNER/REPO/codeowners/errors`).

## 4. Authentication and authorization (HTTPS/PATs, SSH, credential helpers, Apps, deploy keys, SAML SSO, 2FA, passkeys, and documented error causes)

### Takeaway
GitHub.com has not accepted account passwords for Git operations since 13 August 2021; Git over HTTPS uses a token (fine-grained PATs are GA since 18 Mar 2025 and recommended, but still cannot do everything classic PATs can) usually supplied by `gh` or Git Credential Manager, and Git over SSH uses Ed25519/ECDSA/RSA-SHA2 keys (DSA removed 15 Mar 2022; a further SSH tightening announced 22 Sep 2026 takes effect 14 Oct 2026 – 13 Jan 2027). GitHub Apps with short-lived tokens are the preferred integration identity; SAML SSO adds a per-organization authorization step for classic PATs and SSH keys; unauthorized access to private resources is deliberately reported as "not found".

### Cited Findings

#### Password removal and HTTPS token authentication
- **[DEPRECATED/SUNSET 2021-08-13]** "Beginning August 13, 2021, we will no longer accept account passwords when authenticating Git operations and will require the use of token-based authentication, such as a personal access token (for developers) or an OAuth or GitHub App installation token (for integrators) for all authenticated Git operations on GitHub.com. You may also continue using SSH keys." Brownouts were 30 Jun and 28 Jul 2021. — [GitHub Blog, "Token authentication requirements for Git operations" (15 Dec 2020, updated 7 Feb 2022)](https://github.blog/security/application-security/token-authentication-requirements-for-git-operations/)
- **[CURRENT]** "When Git prompts you for your password, enter your personal access token. Alternatively, you can use a credential helper like Git Credential Manager. Password-based authentication for Git has been removed in favor of more secure authentication methods." — [About remote repositories](https://docs.github.com/en/get-started/git-basics/about-remote-repositories#cloning-with-https-urls)
- **[CURRENT]** "Personal access tokens can only be used for HTTPS Git operations. If your repository uses an SSH remote URL, you will need to switch the remote from SSH to HTTPS." — [Managing your personal access tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#using-a-personal-access-token-on-the-command-line)
- **[CURRENT]** REST API: "Basic authentication with your username and password is not supported." — [Troubleshooting the REST API](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api)

#### Personal access tokens: classic vs fine-grained
- **[CURRENT]** "GitHub currently supports two types of personal access tokens: fine-grained personal access tokens and personal access tokens (classic). GitHub recommends that you use fine-grained personal access tokens instead of personal access tokens (classic) whenever possible." A token "cannot grant additional access capabilities to a user." PATs are "intended to access GitHub resources on behalf of yourself"; for org or long-lived integrations "you should use a GitHub App." — [Managing your personal access tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)
- **[CHANGED 2025-03-18]** Fine-grained PATs GA: "fine-grained PATs are now enabled by default for all organizations on GitHub, unless that organization or enterprise explicitly disabled them during the preview. - **[CURRENT] Fine-grained advantages:** limited to resources owned by a single user or organization; can be limited to specific repositories; granular permissions instead of scopes; org owners can require approval. "There is a limit of 50 fine-grained personal access tokens you can create." — [Managing your personal access tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#fine-grained-personal-access-tokens)
- **[CURRENT] Documented fine-grained limitations (verbatim list of "major gaps"):** "Using fine-grained personal access token to contribute to public repos where the user is not a member"; "...to contribute to repositories where the user is an outside or repository collaborator"; "...to access multiple organizations at once"; "...to access Packages"; "...to call the Checks API"; "...to access Projects owned by a user account." #### SSH
- **[CURRENT]** Recommended key generation: `ssh-keygen -t ed25519 -C "your_email@example.com"`; legacy fallback in docs: `ssh-keygen -t rsa -b 4096`; hardware security keys: `ssh-keygen -t ed25519-sk` (fallback `ecdsa-sk`). RSA keys (`ssh-rsa`) with a `valid_after` before November 2, 2021 may continue to use any signature algorithm. RSA keys generated after that date must use a SHA-2 signature algorithm." — [Generating a new SSH key...](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/generating-a-new-ssh-key-and-adding-it-to-the-ssh-agent#generating-a-new-ssh-key). - **[CHANGED 2026-09-22; effective dates in the future relative to 1 Oct 2026]** "We're removing the ability to use RSA keys using SHA-1 in SSH (i.e., the `ssh-rsa` signature type...)"; "We're removing the key exchange mechanism `diffie-hellman-group-exchange-sha256`"; "All new RSA SSH keys uploaded after October 14, 2026 must be at least 3072 bits in size, both for signing and authentication"; adding post-quantum `mlkem768x25519-sha256` key exchange (not in the U.S. data-residency region). #### GitHub Apps vs OAuth apps
- **[CURRENT]** "In general, GitHub Apps are preferred over OAuth apps." Reasons given: fine-grained permissions instead of broad scopes (an OAuth app needing to read contents "would require the `repo` scope, which would also let the app edit the repository contents and settings"); installer chooses repositories; "GitHub Apps use short lived tokens... Conversely, OAuth app tokens do not expire until the person who authorized the OAuth app revokes the token"; can act independently of a user; "not tied to a user account and do not consume a seat"; rate limits that scale; built-in centralized webhooks. — [Deciding when to build a GitHub App](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/deciding-when-to-build-a-github-app)
- **[CURRENT] Three ways a GitHub App authenticates:** as itself with a JWT; as an installation with an installation access token ("will expire after 1 hour"; can be down-scoped with `repositories`/`repository_ids`); on behalf of a user with a user access token (`ghu_`, "expires after eight hours, and the refresh token expires after six months" when expiring tokens are enabled — an optional feature). — [About authentication with a GitHub App](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/about-authentication-with-a-github-app); [Generating an installation access token](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app); [Refreshing user access tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens)
- **[CURRENT]** Lifespans in one table: classic PAT long-lived; fine-grained PAT "Configurable (up to 1 year, or no expiration)"; OAuth app token long-lived; GitHub App user token 8 hours; installation token 1 hour; refresh token 6 months; `GITHUB_TOKEN` job duration; SSH keys and deploy keys long-lived. — [GitHub credential types reference](https://docs.github.com/en/organizations/managing-programmatic-access-to-your-organization/github-credential-types)
- **[CHANGED 2026-08-14]** OAuth apps can now opt in to expiring access tokens (8 hours) with refresh tokens (6 months); "Short-lived tokens are enabled by default for all new applications." Multiple redirect URIs supported. — [Changelog 2026-08-14](https://github.blog/changelog/2026-08-14-multiple-redirect-uris-and-token-refresh-for-oauth-apps/) (the "OAuth app tokens do not expire" sentence in the decision doc predates this option)
- **[CHANGED 2025-07-14]** PKCE (S256 only) "supported and recommended" for OAuth and GitHub App user authentication; not required. — [Changelog 2025-07-14](https://github.blog/changelog/2025-07-14-pkce-support-for-oauth-and-github-app-authentication/)
- **[CURRENT]** OAuth app token cap: "limit of ten tokens that are issued per user/application/scope combination". New organizations have OAuth app access restrictions enabled by default. — [Token expiration and revocation](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/token-expiration-and-revocation); [About OAuth app access restrictions](https://docs.github.com/en/organizations/managing-oauth-access-to-your-organizations-data/about-oauth-app-access-restrictions)

#### Deploy keys
- **[CURRENT]** "a deploy key... is an SSH key that grants access to a single repository. GitHub attaches the public part of the key directly to your repository instead of a personal account." #### Documented causes of common errors
- **`Permission denied (publickey)`** — "A 'Permission denied' error means that the server rejected your connection." Documented checks: don't use `sudo` with Git (different key set); confirm you connect to the right server/port (`ssh -vT git@github.com`, port 22 unless using SSH-over-443); "All connections, including those for remote URLs, must be made as the 'git' user. If you try to connect with your GitHub username, it will fail"; make sure a key is generated and loaded in `ssh-agent` (`ssh-add -l` "should print out a long string"); verify the public key is attached to your account. — [Error: Permission denied (publickey)](https://docs.github.com/en/authentication/troubleshooting-ssh/error-permission-denied-publickey)
- **`ERROR: Permission to user/repo denied to user/other-repo`** — "the key you are pushing with is attached to another repository as a deploy key". **`...denied to other-user`** — "the key you are pushing with is attached to an account which does not have access to the repository." — [docs](https://docs.github.com/en/authentication/troubleshooting-ssh/error-permission-to-userrepo-denied-to-userother-repo); [docs](https://docs.github.com/en/authentication/troubleshooting-ssh/error-permission-to-userrepo-denied-to-other-user)
- **`remote: Repository not found`** — "it means that the repository does not exist or you do not have permission to access it." Causes listed: typo in the URL; "If you are trying to clone a private repository but do not have permission to view the repository, you will receive this error"; SSH key not attached to the right account (`ssh -T git@github.com` shows which user you are); OAuth app access restricted by the organization; repository truly doesn't exist. — [Troubleshooting cloning errors](https://docs.github.com/en/repositories/creating-and-managing-repositories/troubleshooting-cloning-errors#error-repository-not-found)
- **Why "not found" rather than "forbidden"** — "If you make a request to access a private resource and your request isn't properly authenticated, you will receive a `404 Not Found` response. GitHub uses a `404 Not Found` response instead of a `403 Forbidden` response to avoid confirming the existence of private repositories." — [Troubleshooting the REST API](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api#404-not-found-for-an-existing-resource)
- **HTTPS `The requested URL returned error: 401` / `403`** — "These errors usually indicate you have an old version of Git, or you don't have access to the repository." Fixes listed: check the remote URL; "you must authenticate with a personal access token instead of your password"; authorize a classic PAT for SAML SSO; "make sure you use an account that has access to the repository"; stale cached credentials ("Incorrect or out of date credentials will cause authentication to fail"). — [Troubleshooting cloning errors](https://docs.github.com/en/repositories/creating-and-managing-repositories/troubleshooting-cloning-errors#https-cloning-errors)
- **REST `403 Forbidden`** — returned for insufficient permissions, for primary/secondary rate limits (with `429` as the alternative), and "After detecting several requests with invalid credentials within a short period, the API will temporarily reject all authentication attempts for that user (including ones with valid credentials) with a `403 Forbidden` response." — [Authenticating to the REST API](https://docs.github.com/en/rest/authentication/authenticating-to-the-rest-api); [Troubleshooting the REST API](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api#rate-limit-errors)
- **`fatal: Could not read from remote repository`** — **[GIT]** this is Git's own trailing message after the remote end closes the connection; in GitHub docs it appears verbatim as the last line of other errors, e.g. the SSH key audit error (`ERROR: We're doing an SSH key audit. Reason: unverified due to lack of use ... fatal: could not read from remote repository`). The cause is whatever precedes it (publickey rejection, repository not found, key audit, SSO). — [Error: We're doing an SSH key audit](https://docs.github.com/en/authentication/troubleshooting-ssh/error-were-doing-an-ssh-key-audit)
- **`Host key verification failed`** — "the server to which you're connecting presented a key that doesn't match the keys seen for this server in the past"; compare against GitHub's published fingerprints. — [Error: Host key verification failed](https://docs.github.com/en/authentication/troubleshooting-ssh/error-host-key-verification-failed)
- **`GH006: Protected branch update failed`** — push rejected by a branch protection rule. — [About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)
- **Password-authentication error text** — UNVERIFIED in official docs: I could not find the literal server message in docs.github.com (docs search on 1 Oct 2026 for "Support for password authentication was removed" and "Password authentication is not supported for Git operations" returned no page quoting either). User reports on GitHub's own community forum show the message `remote: Invalid username or token. Password authentication is not supported for Git operations.` — [GitHub Community discussion #171965](https://github.com/orgs/community/discussions/171965); [#181156](https://github.com/orgs/community/discussions/181156). The older wording "Support for password authentication was removed on August 13, 2021" is consistent with the removal date in the [2020 blog post](https://github.blog/security/application-security/token-authentication-requirements-for-git-operations/) but its exact text is not in a GitHub-authored source I could retrieve.

### Inferences
- A learner following pre-2021 tutorials (password prompt) or pre-2022 tutorials (`ssh-keygen -t dsa`, `git://` URLs) will fail; a learner following the *current* docs' legacy fallback `ssh-keygen -t rsa -b 4096` remains compliant with the 3072-bit minimum that starts 14 Oct 2026.
- For a course in Oct 2026: teach Ed25519 keys; warn that RSA keys smaller than 3072 bits cannot be *newly uploaded* after 14 Oct 2026 (existing keys are not stated to be removed) and that very old SSH clients using SHA-1 RSA signatures break on 13 Jan 2027.
- "Repository not found" on a repo that exists almost always means an identity problem (wrong account/credential, missing SSO authorization, fine-grained PAT without that repository selected, or no access) because GitHub hides the existence of private repositories.
- With `gh auth login` over HTTPS, `gh` both stores an OAuth token and (when you answer yes) registers itself as Git's credential helper — the same end state as running `gh auth setup-git` — which is why plain `git push` then works without a PAT prompt.
- Fine-grained PATs are a poor fit for open-source contribution workflows (can't push to repos where you're only an outside contributor/collaborator); `gh`'s own browser OAuth flow or SSH keys avoid that limitation.

### Gaps
- Exact wording of the server-side password-rejection message is not documented officially (see above).
- GitHub's docs do not publish a single list of "supported SSH public key types"; support is inferred from the key-generation instructions (ed25519, ecdsa, rsa, `-sk` variants) and the removal notices. Minimum key size for *existing* RSA keys after 14 Oct 2026 is not stated in the announcement.
- The exact Git-side SAML SSO error text (commonly seen as "ERROR: The 'ORG' organization has enabled or enforced SAML SSO. To access this repository, you must use the HTTPS remote with a personal access token or SSH with an SSH key and passphrase that has been authorized for this organization") is UNVERIFIED: docs search (free and enterprise-cloud versions) on 1 Oct 2026 found no page quoting it; the documented, citable behavior is the REST `403` + `X-GitHub-SSO` header and the requirement to authorize classic PATs and SSH keys.
- No official doc page was found that explains HTTP 403 on `git push` specifically (e.g. write permission missing, token lacking `repo`/`contents:write`); the cloning-errors page covers 401/403 generically.
- I did not verify the SSH-over-HTTPS-port host key behavior beyond the docs page; the docs' sample output shows the Ed25519 fingerprint.

## 5. Repository roles and permissions, organizations, teams, outside collaborators, enterprise accounts, EMU; forks and fork networks

### Takeaway
Organization repositories have five built-in roles (Read < Triage < Write < Maintain < Admin) plus custom repository roles on GitHub Enterprise Cloud; personal-account repositories have only owner and collaborator. Access is the highest of base permission, team grants (inherited down nested teams), and direct grants. A fork is a separate repository that shares one Git object store with its whole network — GitHub documents that commits pushed to any repository in a network can be reachable from the others, even after the fork is deleted.

### Cited Findings

#### Repository roles (organization-owned repositories)
- **[CURRENT]** "From least access to most access, the roles for an organization repository are: **Read**: Recommended for non-code contributors who want to view or discuss your project; **Triage**: ...contributors who need to proactively manage issues, discussions, and pull requests without write access; **Write**: ...contributors who actively push to your project; **Maintain**: ...project managers who need to manage the repository without access to sensitive or destructive actions; **Admin**: ...full access to the project, including sensitive and destructive actions like managing security or deleting a repository." — [Repository roles for an organization](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization)

#### Forks, visibility, syncing, and what a fork network shares
- **[CURRENT]** "Forks are repositories that start as copies of another repository, called the upstream repository. A fork has its own settings and permissions but stays connected to the upstream repository." Each fork has its own branches, issues and pull requests, Actions, tags, labels, wikis. — [Forks (reference)](https://docs.github.com/en/pull-requests/reference/forks)
- **[CURRENT] What can be forked:** any public repository (to your account or an org where you can create repos); a private repository "if... the owner permits forking" — to your personal account or "To an organization on GitHub Team"; "You cannot fork a private repository to an organization using GitHub Free." Internal repositories "support a single level of forking". — [Forks (reference)](https://docs.github.com/en/pull-requests/reference/forks#which-repositories-can-be-forked)
- **[CURRENT] Visibility rules:** "Public repository forks are public, and private repository forks are private. You cannot change the visibility of a fork by itself." Deletion/visibility table: private repo deleted → "Its private forks are also deleted"; public repo deleted → "An active public fork becomes the new upstream repository for the network"; public made private → "Its public forks stay public in a separate network"; private made public → "Private forks stay private but disconnect into separate private networks." "If you remove a person's access to a private repository, any of their forks of that private repository are deleted." — [Forks (reference)](https://docs.github.com/en/pull-requests/reference/forks#what-happens-to-forks-when-a-repository-is-deleted-or-changes-visibility)
- **[CURRENT] Shared Git data and reachability (verbatim):** "A repository network includes the upstream repository, its forks, and forks of those forks. Repositories in the network share Git data"; "If you delete a fork, code contributions from that fork can remain accessible to the repository network"; "Commits pushed to any repository in a network can be accessible from other repositories in that network, including the upstream repository"; "Git data from any repository in a network may be accessed from any repository in the same network, including the upstream repository, even after a fork is deleted"; "Owners of an upstream repository can read all forks in the repository network." — [Forks (reference)](https://docs.github.com/en/pull-requests/reference/forks#important-security-considerations). Also: "a fork and its upstream share the same Git data. This means that all content uploaded to a fork is accessible from the upstream and all other forks of that upstream." — [Pull requests (reference)](https://docs.github.com/en/pull-requests/reference/pull-requests#fork-and-pull-model)
- **[CURRENT] Permissions of forks:** "Private forks inherit the permissions structure of the upstream repository... Only team permissions (not individual permissions) are inherited by private forks." "Public forks do not inherit the permissions structure of the upstream repository." "Allow edits from maintainers" works only for user-owned forks ("You cannot give push permissions to a fork owned by an organization"); if the fork has Actions workflows the option reads "Allow edits and access to secrets by maintainers". — [Forks (reference)](https://docs.github.com/en/pull-requests/reference/forks#permissions-of-forks); [Allowing changes to a pull request branch created from a fork](https://docs.github.com/en/pull-requests/how-tos/work-with-forks/allowing-changes-to-a-pull-request-branch-created-from-a-fork)
- **[CURRENT] Sync fork (web):** "select the **Sync fork** dropdown menu... click **Update branch**. If the changes from the upstream repository cause conflicts, GitHub will prompt you to create a pull request to resolve the conflicts." **CLI:** `gh repo sync owner/cli-fork -b BRANCH-NAME`; "If the changes from the upstream repository cause conflicts, the GitHub CLI can't sync. To overwrite the destination branch, use the `--force` flag." **[GIT]** manual path: `git fetch upstream`, `git checkout main`, `git merge upstream/main`, then push. — [Syncing a fork](https://docs.github.com/en/pull-requests/how-tos/work-with-forks/syncing-a-fork)
- **[CURRENT] `gh repo sync` semantics:** "Sync destination repository from source repository. Syncing uses the default branch of the source repository to update the matching branch on the destination repository so they are equal. A fast forward update will be used except when the `--force` flag is specified, then the two branches will be synced using a hard reset. Without an argument, the local repository is selected as the destination repository. The source repository is the parent of the destination repository by default." Flags: `--branch`, `--force`, `--source`. — [gh repo sync manual](https://cli.github.com/manual/gh_repo_sync)
- **[CURRENT] Detaching:** "Leave fork network" (Settings → General → Danger Zone) only when "The fork is public", "less than 1GB", and has no child forks; "Leaving the fork network is **permanent**". The detached repo loses issues, PRs, wikis, stars, watchers; commits may start counting as contributions. — [Detaching a fork](https://docs.github.com/en/pull-requests/how-tos/work-with-forks/detaching-a-fork)
- **[CURRENT]** "A deleted repository can be restored within 90 days, unless the repository was part of a fork network that is not currently empty." — [Restoring a deleted repository](https://docs.github.com/en/repositories/creating-and-managing-repositories/restoring-a-deleted-repository)
- **[CURRENT]** Persistent commit signature verification records are "scoped to its repository network" (reused when the same commit is pushed to any fork). — [About commit signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification#the-verification-record-is-scoped-to-its-repository-network)
- **[CURRENT]** Push rulesets apply across the entire fork network; branch/tag rulesets are not inherited by forks. — [Forks (reference)](https://docs.github.com/en/pull-requests/reference/forks#push-rulesets-for-forked-repositories)

### Inferences
- Effective access = max(base permission, team role(s) incl. inherited parent-team grants, direct collaborator role, org-owner admin); outside collaborators only get direct grants. (Synthesized from the base-permission and teams docs.)
- The Maintain role cannot edit rulesets or branch protection; the documented "Push to protected branches" for Maintain applies only to classic rules — with rulesets, even admins need to be on the bypass list. This is a common misunderstanding to address when teaching governance.
- Because a fork network shares one object store, "delete the fork" or "delete the branch" is not a data-removal mechanism; a commit pushed to any fork can be addressed by SHA through the upstream URL. This is the documented basis for teaching "treat anything pushed to a public fork network as published".
- Triage is the right role for community helpers: it can label/close/assign and request reviews but cannot push or merge.

### Gaps
- The docs describe reachability across a network but do not specify how long unreferenced commits persist or GC timing.
- "Sync fork" semantics for non-fast-forward cases beyond "create a pull request"/"discard" are not detailed in the current doc text (earlier docs mentioned a "Discard commits" option; not verified in the current page).

### Inferences
- **Exact tag-vs-release difference for teaching:** a tag is Git data (`refs/tags/<name>`, lightweight or annotated, fetched/pushed with Git, can exist with no release); a release is GitHub metadata that points at a tag name and adds title, notes, assets, draft/pre-release/latest state, discussion link, and (optionally) immutability + attestation. Deleting a release leaves the tag unless you ask for tag cleanup (`gh release delete --cleanup-tag`); what happens to a mutable release's record when its tag is deleted with `git push --delete origin v1.0` is not stated in the docs I read (see Gaps). Releases created in the web UI with "Create new tag" produce a tag on the server that the local clone lacks until `git fetch --tags`. (Synthesized from About releases, the release-creation steps and `gh release create` help.)
- A draft release is not tied to an existing Git tag until published, which is why immutable-release guidance says to attach assets while in draft.
- Because Packages requires classic PATs, a learner cannot use a fine-grained PAT for `docker login ghcr.io`; this is a documented exception to "prefer fine-grained tokens".

### Gaps
- Plan/visibility gating for immutable releases is not stated on the concept page (it says enablement is at repository or organization level); I did not find a plan restriction.
- Projects (new) per-plan limits (e.g. insights history) were not researched.
- Whether deleting a tag that backs a *mutable* release converts the release to a draft is not stated in the current docs I read (UNVERIFIED).

## 7. Security features, product packaging and pricing; commit signature verification

### Takeaway
Since 1 April 2025 "GitHub Advanced Security" is sold as two standalone products — **GitHub Secret Protection** ($19 per active committer/month) and **GitHub Code Security** ($30 per active committer/month) — purchasable by GitHub Team and Enterprise; a third standalone product, **GitHub Code Quality** ($10 per active committer/month plus usage), went GA on 20 July 2026. Public repositories get secret scanning, push protection, code scanning (CodeQL + Copilot Autofix) and dependency review free; Dependabot alerts/security updates/version updates, dependency graph, security advisories, SECURITY.md, rulesets and user-level push protection are free on all plans. Commit signature verification supports GPG, SSH and S/MIME with persistent verification records (GA 10 Dec 2024).

This record can't be edited and will persist so that signatures remain verified over time, even if signing keys are rotated, revoked, or if contributors leave the organization"; timestamp via the `verified_at` REST field; "GitHub will not re-verify previously signed commits or retroactively adjust their verification status in response to changes in the key's state." — [About commit signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification#persistent-commit-signature-verification); [Changelog 2024-12-10](https://github.blog/changelog/2024-12-10-persistent-commit-signature-verification-is-generally-available/)
- **[CURRENT] Web-flow commits:** "GitHub will automatically use GPG to sign commits you make using the web interface... You can verify the signature locally using the public key available at https://github.com/web-flow.gpg." Codespaces can optionally GPG-sign. Bots/GitHub Apps: signature verification works only when the request is authenticated as the app and "contains no custom author information, custom committer information, and no custom signature information". — [About commit signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification)
- **[CURRENT]** Rebase-and-merge produces commits "without commit signature verification" (see section 2); Copilot cloud agent signs its commits since 2026-04-03. — [About commit signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification#signature-verification-for-rebase-and-merge); [Changelog 2026-04-03](https://github.blog/changelog/2026-04-03-copilot-cloud-agent-signs-its-commits/)

### Inferences
- For a learner on a personal Free account with a public practice repo: secret scanning, repository push protection, CodeQL default setup, Copilot Autofix, Dependabot (all three flavors), dependency review, advisories and private vulnerability reporting are all usable at no cost; on a private repo only Dependabot, dependency graph, SECURITY.md and user-level push protection (which only guards pushes to *public* repos) remain.
- "Verified" on GitHub proves a signature matched a key registered to an account at verification time; it is not re-evaluated later, so key revocation does not retroactively flip old commits to Unverified (documented), which matters when teaching incident response for leaked signing keys.
- The term "GHAS" is now an umbrella for two SKUs; course material should say "Secret Protection" or "Code Security" when describing what gates a feature.

### Gaps

- The push-protection concept page says repository push protection "Requires GitHub Secret Protection" and "Is disabled by default", while the 2024 changelog says new personal public repos have it on by default and the GHAS table marks it available on public repos without the product; the precise current default for *new organization-owned public repositories* was not verified.
- Whether list prices ($19/$30/$10) carry regional or volume discounts was not researched; Enterprise price is "starting at".

## 8. Removing sensitive data; commit reachability after force push; GitHub's investigate-and-recover tools

### Takeaway
GitHub's official guidance is: rotate/revoke the secret first (that alone may be sufficient); only then consider rewriting history with `git-filter-repo --sensitive-data-removal` (≥ v2.47), force-pushing with `git push --force --mirror`, and opening a GitHub Support ticket so Support can dereference PRs, garbage-collect, and purge cached views — because after a force push the old commits remain accessible in clones and forks, "directly via their SHA-1 hashes in cached views on GitHub", and through read-only `refs/pull/*` refs. For investigation and recovery GitHub provides the repository Activity view (filter by force pushes/branch deletions, "Compare changes"), "Restore branch" on closed PRs, the Events API (`PushEvent` `before`/`head` SHAs), the Git refs REST API, audit logs, and 90-day repository restoration.

### Cited Findings

#### Official removal guidance (current text)
- **[CURRENT] Rotate first:** "if the sensitive data you need to remove is a secret (e.g. password/token/credential), as is often the case, then as a first step you need to revoke and/or rotate that secret. Once the secret is revoked or rotated, it can no longer be used for access, and that may be sufficient to solve your problem. Going through the extra steps to rewrite the history and remove the secret may not be warranted." — [Removing sensitive data from a repository](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)
- **[CURRENT] Documented side effects of rewriting history:** "High risk of recontamination" (a colleague's `git pull` + `git push` from an old clone restores the data); "Risk of losing other developers' work"; "Changed commit hashes" for the offending commits "*and* all commits that came after"; "Branch protection challenges" (force-push protections "will have to be turned off (at least temporarily)"); "Broken diff view for closed pull requests"; "Poor interaction with open pull requests" ("We recommend merging or closing all open pull requests before removing files"); "Lost signatures on commits and tags" (`git-filter-repo` removes them, even for commits predating the sensitive data); "Leading others directly to the sensitive data" (history divergence reveals what was removed). — [Removing sensitive data from a repository](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository#side-effects-of-rewriting-history)
- **[CURRENT] Why force-pushing alone is not enough (verbatim):** "If you only rewrite your history and force push it, the commits with sensitive data may still be accessible elsewhere: In any clones or forks of your repository; Directly via their SHA-1 hashes in cached views on GitHub; Through any pull requests that reference them." "If the commit that introduced the sensitive data exists in any forks, it will continue to be accessible there. You will need to coordinate with the owners of the forks... GitHub cannot provide contact information for these owners." — [Removing sensitive data from a repository](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository#about-sensitive-data-exposure)
- **[CURRENT] The four high-level steps:** "Rewrite the repository locally, using git-filter-repo; Update the repository on GitHub, using your locally rewritten history; Coordinate with colleagues to clean up other clones that exist; Prevent repeats and avoid future sensitive data spills." — [same doc](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository#about-sensitive-data-exposure)
- **[CURRENT] Exact tool steps:** install `git-filter-repo` "at least version 2.47" (needs the `--sensitive-data-removal` flag; e.g. `brew install git-filter-repo`); fresh clone; `git-filter-repo --sensitive-data-removal --invert-paths --path PATH-TO-YOUR-FILE-WITH-SENSITIVE-DATA` (use the full Git path; add extra `--path` for renamed locations) or `git-filter-repo --sensitive-data-removal --replace-text ../passwords.txt`; count affected PRs with `grep -c '^refs/pull/.*/head$' .git/filter-repo/changed-refs`; then `git push --force --mirror origin`. "This command will fail to push any refs starting with `refs/pull/`, since GitHub marks those as read-only." Other failing refs mean branch protection must be temporarily disabled. "Once you move on to the next step, the rewrite becomes irreversible." — [same doc](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository#purging-a-file-from-your-local-repositorys-history-using-git-filter-repo)
- **[CURRENT] Contacting GitHub Support:** provide owner/repo, the number of affected pull requests, the "First Changed Commit(s)" reported by `git-filter-repo`, and any "LFS Objects Orphaned" file. "If you have successfully cleaned up all references other than PRs, and no forks have references to the sensitive data, Support will then: Dereference or delete any affected PRs on GitHub. Run a garbage collection on the server to expunge the sensitive data from storage. Remove cached views. If LFS Objects are involved, delete and/or purge the orphaned LFS objects." "GitHub Support won't remove non-sensitive data, and will only assist in the removal of sensitive data in cases where we determine that the risk can't be mitigated by rotating affected credentials." — [same doc](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository#fully-removing-the-data-from-github)
- **[CURRENT] Aftercare:** "Collaborators must rebase, *not* merge, any branches they created off of your old (tainted) repository history. One merge commit could reintroduce some or all of the tainted history." Prevention list includes `.gitignore`, avoiding `git add .`/`git commit -a`, `git add --interactive`, `git diff --cached`, pre-commit hooks (git-secrets, gitleaks), and enabling push protection. — [same doc](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository#avoiding-accidental-commits-in-the-future)
- **[CURRENT]** Secret scanning docs give the same priority: "rotate the affected credential immediately... While you can also remove secrets from your Git history, this is time-intensive and often unnecessary if you've already revoked the credential." — [Secret scanning](https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning#secret-scanning-alerts-and-remediation)
- **[CURRENT]** Tokens for GitHub itself that land in a public repo or gist are auto-revoked ("If a valid OAuth token, GitHub App token, or personal access token is pushed to a public repository or public gist, the token will be automatically revoked"). — [Token expiration and revocation](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/token-expiration-and-revocation)

#### Documented reachability-by-SHA behavior
- **[CURRENT]** After a rewrite + force push, old commits remain reachable "Directly via their SHA-1 hashes in cached views on GitHub" until Support removes cached views and runs garbage collection. — [Removing sensitive data from a repository](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository#about-sensitive-data-exposure)
- **[CURRENT]** "A commit exists on GitHub but not in your local clone": "If `git show COMMIT-SHA` returns an error locally but the commit is visible on GitHub, your local clone may be out of date or the commit may no longer be referenced by a branch." If "the branch was deleted or force pushed, ask a collaborator who still has the commit locally to push it to a new branch" (`git branch recover-B B`; `git push upstream B:recover-B`). — [Troubleshooting commits](https://docs.github.com/en/pull-requests/how-tos/commit-changes/troubleshooting-commits#a-commit-exists-on-github-but-not-in-your-local-clone)
- **[CURRENT]** Fork networks: "Git data from any repository in a network may be accessed from any repository in the same network, including the upstream repository, even after a fork is deleted." — [Forks (reference)](https://docs.github.com/en/pull-requests/reference/forks#important-security-considerations)
- **[CURRENT]** PR head commits stay available via hidden refs: "Commits in a pull request are available in a repository even before the pull request is merged"; the `refs/pull/` namespace is read-only to users. — [Checking out pull requests locally](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/checking-out-pull-requests-locally)
- **[CURRENT]** With Enterprise metadata restrictions, rejected pushes still store objects: "the commits will be 'retrievable' (you can navigate to them in your repository), but not 'reachable' (they are not connected to the history of a branch or tag)." — [Available rules for rulesets (Enterprise Cloud view)](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#important-considerations-for-metadata-restrictions)

### Inferences
- **Recovery recipe that follows from the documented pieces** (not itself a single documented procedure): find the pre-force-push SHA from the Activity view ("Compare changes" on the force-push entry) or from a `PushEvent`'s `before` field (within 30 days / last 300 events), then create a new branch pointing at it with `POST /repos/{owner}/{repo}/git/refs` (e.g. `gh api repos/OWNER/REPO/git/refs -f ref=refs/heads/recovered -f sha=<SHA>`) — this works as long as GitHub has not garbage-collected the unreferenced commit. GitHub's docs describe each component but do not promise how long dangling commits persist.
- The same persistence that enables recovery is why a force push is *not* a secret-removal mechanism; the two lessons should be taught together.
- `git push --force --mirror` in the official procedure updates every branch and tag; a learner must do it from a fresh clone, as instructed, to avoid pushing stale local refs.
- **Git vs GitHub:** rewriting (`git-filter-repo`), reflogs, and `git push --force` are Git; cached commit views, `refs/pull/*`, fork-network object sharing, Support-run garbage collection, the Activity view, Events API, and audit log are GitHub.

### Gaps
- The current Activity view article does not document a "Restore branch" action inside the Activity view (it documents filtering by branch deletions and "Compare changes" only); the restore capability I could verify is "Restore branch" on a closed pull request. Treat "restore from Activity view" as UNVERIFIED.
- No GitHub doc states a retention period or GC schedule for unreachable commits, or guarantees that `POST /git/refs` succeeds for a dangling SHA; the recovery recipe above is an inference from documented endpoints.
- The Activity view's access requirements (read vs write) are not stated in the fetched article body.
- GitHub server-side reflogs are not exposed to users (not mentioned in docs); nothing found to cite either way.

## 10. Git LFS on GitHub: file-size limits, quotas, billing model, forks and archives, client version

### Takeaway
Regular Git pushes warn above 50 MiB per file and are blocked above 100 MiB (browser uploads: 25 MiB); a single push is capped at 2 GB; repositories should stay well under 5 GB (10 GB on-disk recommended maximum). Git LFS per-file maximums are 2 GB (Free/Pro), 4 GB (Team), 5 GB (Enterprise Cloud). LFS billing is now metered: pre-paid "data packs" were removed, every account gets a free monthly quota (10 GiB storage + 10 GiB bandwidth on Free/Pro; 250 GiB + 250 GiB on Team/Enterprise Cloud), and overage depends on the account's budget. The latest git-lfs client is v3.8.0 (28 Aug 2026).

### Cited Findings
- **[CURRENT] Regular Git file limits:** "If you attempt to add or update a file that is larger than 50 MiB, you will receive a warning from Git. The changes will still successfully push." "GitHub blocks files larger than 100 MiB." "If you add a file to a repository via a browser, the file can be no larger than 25 MiB." — [About large files on GitHub](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github#file-size-limits)
- **[CURRENT] Repository and push size:** "We recommend repositories remain small, ideally less than 1 GB, and less than 5 GB is strongly recommended." Repository-limits page: on-disk size recommended maximum 10 GB; "Push size: This limit is enforced at 2GB"; "Single object size: The recommended maximum limit is 1MB. This is enforced at 100 MB." — [About large files on GitHub](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github#repository-size-limits); [Repository limits](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits)
- **[CURRENT]** Removing an oversized file already committed: unpushed last commit → `git rm --cached GIANT_FILE` then `git commit --amend -CHEAD`; earlier commits → `git filter-repo` (or an interactive rebase under stated conditions). Release assets are the suggested channel for large binaries. — [About large files on GitHub](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github#removing-files-from-a-repositorys-history)
- **[CURRENT] [PLAN-GATED] LFS maximum file size:** GitHub Free 2 GB; GitHub Pro 2 GB; GitHub Team 4 GB; GitHub Enterprise Cloud 5 GB. "If you exceed the per-file limit of 5 GB, the file will be rejected by Git LFS with an error message." — [About Git Large File Storage](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-git-large-file-storage)
- **[CURRENT] How LFS works on GitHub:** "Git LFS handles large files by storing references to the file in the repository, but not the actual file itself"; pointer file has `version https://git-lfs.github.com/spec/v1`, `oid sha256:...`, `size ...`. "Git LFS cannot be used with GitHub Pages sites." "Git LFS cannot be used with template repositories." — [About Git Large File Storage](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-git-large-file-storage)
- **[CHANGED — metered billing] Billing model:** "Previously, Git LFS billing used pre-paid data packs. These have been removed and replaced with metered billing and you only pay for what you actually use." Bandwidth quota resets each billing cycle; storage accrues hourly. "Budget set to $0: You are not charged for overages, but Git LFS usage is blocked for the rest of the calendar month... Budget deleted: There is no spending limit." — [Git Large File Storage billing](https://docs.github.com/en/billing/concepts/product-billing/git-lfs)
- **[CURRENT] [PLAN-GATED] Free quotas (bandwidth / storage):** GitHub Free 10 GiB / 10 GiB; GitHub Pro 10 GiB / 10 GiB; GitHub Free for organizations 10 GiB / 10 GiB; GitHub Team 250 GiB / 250 GiB; GitHub Enterprise Cloud 250 GiB / 250 GiB. — [Git Large File Storage billing](https://docs.github.com/en/billing/concepts/product-billing/git-lfs#free-use-of-git-lfs)
- **[CHANGED 2024-06-03 → 2025] Timeline of the move to metered billing:** new Enterprise accounts created after 2 Jun 2024 got metered LFS ("transitions Git LFS from a pre-paid, quota-based model (data packs) to a post-paid, usage-based model"; "$0.07 per GiB per month" storage and "$0.0875 per GiB" download bandwidth beyond 250 GiB each); new Free orgs from 4 Feb 2025 and new personal Free/Pro accounts from 13 Feb 2025 joined the enhanced billing platform, existing ones "in the coming months"; existing Team organizations "by the end of March 2025"; each notice says "Git Large File Storage will transition from prepaid, quota-based data packs to a usage-based metered billing model... you'll receive credits for any unused data packs." — [Changelog 2024-06-03](https://github.blog/changelog/2024-06-03-new-enterprise-accounts-have-metered-billing-for-git-lfs/); [Changelog 2025-02-19](https://github.blog/changelog/2025-02-19-enhanced-billing-platform-for-free-plan-for-organizations/); [Changelog 2025-02-25](https://github.blog/changelog/2025-02-25-enhanced-billing-platform-is-now-available-for-personal-accounts/); [Changelog 2025-02-24](https://github.blog/changelog/2025-02-24-migration-of-github-team-plan-organizations-to-the-enhanced-billing-platform/)
- **[CURRENT] What counts:** every pushed version of an LFS file counts in full toward the *repository owner's* storage ("If you make a 1 byte change and push the file again, you'll use another 500 MB of storage"); downloads count toward the owner's bandwidth (including GitHub Actions downloads); uploads do not consume bandwidth. Without a payment method: over storage quota → clones get only pointer files and you cannot push new LFS files; over bandwidth quota → "Git LFS support is disabled on your account until the next month." — [Git Large File Storage billing](https://docs.github.com/en/billing/concepts/product-billing/git-lfs)
- **[CURRENT] Forks:** "Bandwidth and storage usage always count against the repository owner's account. Forking and pulling a repository counts against the parent repository's bandwidth usage." "Pushing large files to forks of a repository count against the parent repository's bandwidth and storage quotas... You can push Git LFS objects to public forks if the repository network already has Git LFS objects or you have write access to the root of the repository network." — [Git Large File Storage billing](https://docs.github.com/en/billing/concepts/product-billing/git-lfs#usage-in-forks); [Collaboration with Git Large File Storage](https://docs.github.com/en/repositories/working-with-files/managing-large-files/collaboration-with-git-large-file-storage)
- **[CURRENT] Source archives:** "By default, Git LFS objects are not included in these archives, only the pointer files." Admins can enable Settings → Archives → "Include Git LFS objects in archives"; then "every download of those archives will count towards bandwidth usage". Archives are produced by `git archive`, "generated on request, cached for a while, and then deleted". — [Managing Git LFS objects in archives of your repository](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/managing-git-lfs-objects-in-archives-of-your-repository); [Downloading source code archives](https://docs.github.com/en/repositories/working-with-files/using-files/downloading-source-code-archives)
- **[CURRENT] Collaboration caveats:** collaborators without Git LFS installed "will only fetch the pointer files"; "GitHub does not render some Git LFS objects in pull requests. Only the pointer file is shown". — [Collaboration with Git Large File Storage](https://docs.github.com/en/repositories/working-with-files/managing-large-files/collaboration-with-git-large-file-storage)
- **[CURRENT] Removing LFS objects:** "After you remove files from Git LFS, the Git LFS objects still exist on the remote storage and will continue to count toward your Git LFS storage quota. To remove Git LFS objects from a repository, delete and recreate the repository" (or contact Support to purge). — [Removing files from Git Large File Storage](https://docs.github.com/en/repositories/working-with-files/managing-large-files/removing-files-from-git-large-file-storage)
- **[CURRENT] Client version:** git-lfs v3.8.0, published 28 Aug 2026 ("adds support for zstd-compressed object downloads..."; "built using Go v1.27 and therefore requires macOS version 13 (Ventura) or later"); previous: v3.7.1 (17 Oct 2025), v3.7.0 (27 Jun 2025), v3.6.1 (14 Jan 2025). — [git-lfs/git-lfs releases](https://github.com/git-lfs/git-lfs/releases)
- **[CONFLICT]** GitHub's marketing pricing page still shows "Git Large File Storage — $5 per month for 50 GB bandwidth and 50 GB of storage" (the old data-pack price) — [github.com/pricing](https://github.com/pricing); contradicted by the billing docs' statement that data packs "have been removed and replaced with metered billing" — [Git Large File Storage billing](https://docs.github.com/en/billing/concepts/product-billing/git-lfs). The docs are the authoritative, more specific source.

### Inferences
- The task brief's "100 MB hard block and 50 MB warning" is confirmed, with the nuance that GitHub's docs state the thresholds in MiB (50 MiB / 100 MiB) on the large-files page and "100 MB" on the repository-limits page.
- Rewriting history does not free LFS storage; only deleting the repository (or Support) does — relevant when teaching "I committed a huge file to LFS by mistake".
- A public fork's LFS pushes bill the *upstream owner*, which is why GitHub restricts LFS pushes to forks unless the network already uses LFS or the pusher has write access to the root.

### Gaps
- Current per-GiB overage rates are not printed in the billing doc (it points to the pricing calculator); the $0.07 / $0.0875 figures come from the June 2024 changelog and should be re-checked in the calculator before quoting.
- The date on which *all* legacy accounts completed migration off data packs is not stated; the docs simply say data packs "have been removed".

## 12. API and integration concepts (concept level, with doc links)

### Takeaway
GitHub exposes a date-versioned REST API (header `X-GitHub-Api-Version`; default `2022-11-28`; newest `2026-03-10`) and a GraphQL API, both rate-limited (60 req/h unauthenticated, 5,000 req/h per authenticated user, higher for GitHub Enterprise Cloud apps) with secondary limits; webhooks push events instead of polling; GitHub Apps are the recommended integration identity.

### Cited Findings
- **[CURRENT] REST API versioning:** "The API version name is based on the date when the API version was released." "You should use the `X-GitHub-Api-Version` header." "Requests without the `X-GitHub-Api-Version` header will default to use the `2022-11-28` version." Breaking changes ship only in new versions; additive changes appear in all supported versions; "the previous API version will be supported for at least 24 more months"; unsupported versions return `410 Gone`; `Deprecation` and `Sunset` response headers announce retirement. Supported versions table: `2026-03-10` (end of support not yet scheduled) and `2022-11-28` (end of support March 10, 2028). — [API Versions](https://docs.github.com/en/rest/about-the-rest-api/api-versions)
- **[CHANGED 2026-03-12]** `2026-03-10` is "the first calendar version to include breaking changes" (e.g. removal of the deprecated `rate` property from `GET /rate_limit`). — [Changelog](https://github.blog/changelog/2026-03-12-rest-api-version-2026-03-10-is-now-available/); [Breaking changes](https://docs.github.com/en/rest/about-the-rest-api/breaking-changes)
- **[CURRENT]** GitHub CLI pins REST calls to `2022-11-28` since v2.87.0 ("Pin REST API version to 2022-11-28"). — [cli/cli release v2.87.0](https://github.com/cli/cli/releases/tag/v2.87.0)
- **[CURRENT] REST primary rate limits:** unauthenticated "60 requests per hour" (per IP); authenticated users "5,000 requests per hour" (15,000 for apps owned by a GitHub Enterprise Cloud organization); GitHub App installations 5,000/h minimum, scaling to at most 12,500/h (15,000/h on GHEC orgs); `GITHUB_TOKEN` "1,000 requests per hour per repository" (15,000 for GHEC resources); Git LFS has its own bucket (300/min unauthenticated, 3,000/min authenticated). — [Rate limits for the REST API](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)
- **[CURRENT] Secondary rate limits:** no more than 100 concurrent requests (shared REST + GraphQL); 900 points/minute for REST endpoints and 2,000 points/minute for GraphQL (GET = 1 point, mutating requests = 5); 90 seconds CPU per 60 seconds; "no more than 80 content-generating requests per minute and no more than 500 content-generating requests per hour". Exceeding limits returns `403` or `429`; honor `retry-after` and `x-ratelimit-reset`. — [Rate limits for the REST API](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#about-secondary-rate-limits); [Troubleshooting the REST API](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api#rate-limit-errors)
- **[CURRENT] REST authentication errors:** no/insufficient token → `404 Not Found` or `403 Forbidden`; invalid credentials → `401 Unauthorized`; "Basic authentication with your username and password is not supported"; most list endpoints return 30 items by default (paginate). — [Authenticating to the REST API](https://docs.github.com/en/rest/authentication/authenticating-to-the-rest-api); [Troubleshooting the REST API](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api)
- **[CURRENT] GraphQL API:** strongly typed, introspective, hierarchical; "lets you replace multiple REST requests with a single call"; rate-limited in points (5,000 points/hour per user; 10,000 for GHEC-owned apps/installations; `GITHUB_TOKEN` 1,000 points/hour per repository); node limit 500,000 total nodes per call; requests taking more than 10 seconds are terminated. — [About the GraphQL API](https://docs.github.com/en/graphql/overview/about-the-graphql-api); [Rate limits and query limits for the GraphQL API](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api)
- **[CHANGED 2025]** GraphQL timeouts count against the primary rate limit (21 Jul 2025); per-query resource limits can return partial results (1 Sep 2025); GraphQL Explorer removed from docs (7 Nov 2025). — [Changelog 2025-07-21](https://github.blog/changelog/2025-07-21-including-timeouts-in-primary-rate-limits/); [Changelog 2025-09-01](https://github.blog/changelog/2025-09-01-graphql-api-resource-limits/); [Changelog 2025-11-07](https://github.blog/changelog/2025-11-07-graphql-explorer-removal-from-api-documentation-on-november-7-2025/)
- **[CURRENT] REST vs GraphQL:** "GitHub provides two APIs: a REST API and a GraphQL API... Occasionally, a feature may be supported on one API but not the other... Node IDs let you move between the REST API and GraphQL API." — [Comparing GitHub's REST API and GraphQL API](https://docs.github.com/en/rest/about-the-rest-api/comparing-githubs-rest-api-and-graphql-api)
- **[CURRENT] Webhooks:** "let you subscribe to events happening in a software system and automatically receive a delivery of data to your server whenever those events occur"; created on a repository, organization, GitHub Marketplace account, GitHub Sponsors account, or GitHub App; preferred over polling (less effort, scales better, near real-time); "GitHub webhooks do not currently support IPv6"; GitHub Services (service hooks) are retired. The `push` webhook also fires for branch/tag deletion; "Events will not be created if more than 5000 branches are pushed at once... for tags when more than three tags are pushed at once." — [About webhooks](https://docs.github.com/en/webhooks/about-webhooks); [Webhook events and payloads](https://docs.github.com/en/webhooks/webhook-events-and-payloads#push)
- **[CURRENT] GitHub Apps as the integration model:** "In general, GitHub Apps are preferred over OAuth apps" — fine-grained permissions, repository selection, short-lived tokens, built-in webhooks, not tied to a user seat; check runs/check suites REST API "is only available to GitHub Apps". — [Deciding when to build a GitHub App](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/deciding-when-to-build-a-github-app)
- **[CURRENT] Events API** (polling alternative): ETag/`X-Poll-Interval`, 300 events / 30 days, latency "30s to 6h". — [REST API endpoints for events](https://docs.github.com/en/rest/activity/events)
- **[CHANGED 2026-10-01]** Async merge API (`PUT .../pulls/{n}/merge-async`, poll with GET) is the recommended programmatic merge path. — [Changelog](https://github.blog/changelog/2026-10-01-github-async-merge-api-generally-available/)

### Inferences
- `gh api` is the lowest-friction way to teach both APIs (it handles auth and, since 2.87.0, the version header); `gh api graphql` covers GraphQL.
- For course exercises: unauthenticated `curl` against api.github.com is limited to 60 requests/hour per IP — enough for demos, not for scripts.

### Gaps
- Not researched in depth: webhook delivery retries/signature validation (`X-Hub-Signature-256`), GraphQL schema previews, Octokit SDK versions.

## 13. Organization and enterprise governance features

### Takeaway
Governance at scale on GitHub is built from: custom properties (repository and organization metadata) → rulesets targeted by those properties; roles and teams; required 2FA and (on Enterprise Cloud) SAML SSO, IP allow lists, audit-log streaming, and enterprise policies; plus per-account defaults for community health files via a public `.github` repository, repository templates, and issue/PR templates and issue forms.

### Cited Findings
- **[CURRENT] Repository custom properties:** "structured metadata fields that you can add to repositories... You can use those properties to target repositories with rulesets." Types: "a text string, a single select field, a multi select field, or a true/false boolean" (URL type added 9 Dec 2025). Options: "Allow repository actors to set this property"; "Require this property for all repositories" with a default value; "Require explicit user-specified values" (17 Feb 2026). Name ≤ 75 characters, no spaces. Visibility follows the repository. Managed by organization owners at Settings → Repository → Custom properties. GA since 14 Feb 2024. — [Managing custom properties for repositories in your organization](https://docs.github.com/en/organizations/managing-organization-settings/managing-custom-properties-for-repositories-in-your-organization); [Changelog 2025-12-09](https://github.blog/changelog/2025-12-09-repository-custom-properties-graphql-api-and-url-type/); [Changelog 2026-02-17](https://github.blog/changelog/2026-02-17-custom-properties-and-rule-insights-improvements/); [Changelog 2024-02-14](https://github.blog/changelog/2024-02-14-repository-custom-properties-ga-and-ruleset-improvements/)
- **[PLAN-GATED: Enterprise]** Enterprise custom properties GA (24 Mar 2025); *organization* custom properties (tag organizations, target enterprise rulesets) GA 13 Jan 2026; external custom properties synced from a system of record — public preview 29 Sep 2026. — [Changelog 2025-03-24](https://github.blog/changelog/2025-03-24-enterprise-custom-properties-enterprise-rulesets-and-pull-request-merge-method-rule-are-all-now-generally-available/); [Changelog 2026-01-13](https://github.blog/changelog/2026-01-13-organization-custom-properties-now-generally-available/); [Changelog 2026-09-29](https://github.blog/changelog/2026-09-29-bring-business-context-with-external-custom-properties/)
- **[CURRENT] Required 2FA (organization):** owners "can require all members, outside collaborators, and billing managers in your organization to enable two-factor authentication"; non-compliant members keep membership but lose access; non-compliant outside collaborators are removed. — [Requiring two-factor authentication in your organization](https://docs.github.com/en/organizations/keeping-your-organization-secure/managing-two-factor-authentication-for-your-organization/requiring-two-factor-authentication-in-your-organization)
- **[PLAN-GATED: GitHub Enterprise Cloud] IP allow lists:** "Only organizations that use GitHub Enterprise Cloud can use IP allow lists"; applies to web UI, APIs and Git for user sessions, PATs, OAuth app tokens, SSH keys (incl. deploy keys), GitHub App tokens incl. `GITHUB_TOKEN`; "applies to users with any role or access, including enterprise and organization owners"; with an org allow list "you won't be able to use GitHub Codespaces for repositories owned by the organization". Coverage of EMU user namespaces GA 8 Jun 2026. — [Managing allowed IP addresses for your organization](https://docs.github.com/en/enterprise-cloud@latest/organizations/keeping-your-organization-secure/managing-security-settings-for-your-organization/managing-allowed-ip-addresses-for-your-organization); [Changelog 2026-06-08](https://github.blog/changelog/2026-06-08-ip-allow-list-coverage-for-emu-namespaces-in-general-availability/)
- **[CURRENT] Audit log:** organization audit log covers 180 days, owner-only, searchable with qualifiers (`operation:`, `created:` …), exportable (JSON/CSV); enterprise audit log additionally retains Git events for seven days and supports streaming to external systems (GHEC). — [Reviewing the audit log for your organization](https://docs.github.com/en/organizations/keeping-your-organization-secure/managing-security-settings-for-your-organization/reviewing-the-audit-log-for-your-organization); [Audit log for an enterprise](https://docs.github.com/en/enterprise-cloud@latest/admin/concepts/security-and-compliance/audit-log-for-an-enterprise)
- **[PLAN-GATED: Enterprise] Enterprise policies:** "Each enterprise policy controls the options available for a policy at the organization level" (e.g. enforce a "Base permissions" level for all organizations); "By default, no enterprise policies are enforced." — [Enterprise policies](https://docs.github.com/en/enterprise-cloud@latest/admin/concepts/security-and-compliance/enterprise-policies)
- **[CURRENT] PAT and OAuth governance:** per-token-type PAT restriction, lifetime and approval policies; OAuth app access restrictions on by default for new organizations. — [Setting a personal access token policy for your organization](https://docs.github.com/en/organizations/managing-programmatic-access-to-your-organization/setting-a-personal-access-token-policy-for-your-organization); [About OAuth app access restrictions](https://docs.github.com/en/organizations/managing-oauth-access-to-your-organizations-data/about-oauth-app-access-restrictions)
- **[CURRENT] Repository templates:** "Anyone with admin permissions to a repository can make the repository a template" (Settings → "Template repository"); new repos get "the same directory structure and files as your default branch" and optionally all branches; "Branches created from a template have unrelated histories"; "Your template repository cannot include files stored using Git LFS." — [Creating a template repository](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-template-repository)
- **[CURRENT] Default community health files:** stored in a repository named `.github` that "must be **public**"; used for any repository owned by the account that lacks its own file; lookup order `.github` folder → root → `docs`; supported defaults: *CODE_OF_CONDUCT.md*, *CONTRIBUTING.md*, discussion category forms, *FUNDING.yml*, issue and pull request templates and *config.yml*, *SECURITY.md*, *SUPPORT.md*; "You cannot create a default license file"; a repository's own `.github/ISSUE_TEMPLATE` overrides all default issue templates. — [Creating a default community health file](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/creating-a-default-community-health-file)
- **[CURRENT] Issue and PR templates:** issue templates live on the default branch in `.github/ISSUE_TEMPLATE` (`.md` with `name:`/`about:` front matter); template chooser configured by `.github/ISSUE_TEMPLATE/config.yml`; PR templates can be in the root, `docs`, or `.github` directory, on the default branch. — [About issue and pull request templates](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/about-issue-and-pull-request-templates)
- **[CURRENT] Issue forms:** YAML files in `/.github/ISSUE_TEMPLATE` (top-level keys shown: `name`, `description`, `title`, `labels`, `projects`, `assignees`, `type`, `body`); responses are converted to Markdown; "Issue forms are not supported for pull requests"; the docs still carry the note "Issue forms are currently in public preview and subject to change." — [Syntax for issue forms](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-issue-forms)

### Inferences
- A typical enterprise control chain to teach: define custom properties (e.g. `tier`, `compliance`) → require them on repository creation → target organization/enterprise rulesets with `props.<name>:<value>` filters → roll out in Evaluate mode → inspect Rule Insights → set Active with a narrow bypass list → monitor via audit log.
- For a learner without an organization on a paid plan, the governance features they can practice hands-on are: repository rulesets on public repos, CODEOWNERS, templates/forms, community health files, and (in a free organization) teams, base permissions, required 2FA, repository custom properties (availability on GitHub Free organizations not explicitly confirmed — see Gaps).
