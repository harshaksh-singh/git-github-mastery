# Module 2 lab answers: Working tree, index, and HEAD

Answers to the "Questions" of each lab in the [Module 2 lab manual](../lab-manual/m02-working-tree-index-head.md). Blob and commit IDs are the ones printed in the manual; commits that you made by hand have other IDs, blobs do not. Every statement about behavior was checked on Git 2.55.0 in the lab sandbox.

## Lab 2.1: The three-trees prediction table

1. The first column compares HEAD with the index: `top_k: 5` against `top_k: 8`, so `M`. The second compares the index with the working tree: `8` against `12`, so `M`. `git commit` records the index, so it would have recorded `8`, which is what step 4 then did. The `12` would have stayed in the working tree as an unstaged modification.
2. Step 6 ran `git add` on `top_k: 20`, which wrote the blob `cbda4f9` into the object database. Step 7 removed only the index entry, and the failure scenario's `git restore` only overwrote the working tree file; neither touched the object. `top_k: 12` was written to the working tree in step 3 and never added, so no object ever held it, and `git restore` in step 5 overwrote the only copy. The index, not the working tree, is what feeds the object database.
3. After step 7 the index entry is HEAD's entry again, blob `434fcdb`. `git diff` compares the index with the working tree and `git diff HEAD` compares HEAD with the working tree; with index and HEAD identical, the two comparisons have the same two inputs and print the same hunk. The reverse state is the one in Chapter 5, section 5.4: stage a change, then run `git restore --source=HEAD <path>`. The working tree equals HEAD, so `git diff HEAD` is empty, while `git diff --cached` shows the staged change and `git diff` shows its reverse.
4. A blob ID is the hash of the blob's type, size and bytes, and nothing else: no time, author, path or history enters it. The content `top_k: 20` plus a newline is the same in every sandbox, so its ID is the same. A commit ID covers the commit's tree, parent, author and committer lines with their timestamps, and the message; in the lab shell the clock is real, so your commits differ from the replay.
5. An unreachable loose object is removed when `git gc` runs and the object is older than `gc.pruneExpire`, which the manual gives as two weeks by default (`git help gc`). The lab configuration sets `gc.reflogExpire` and `gc.reflogExpireUnreachable` to `never` and leaves `gc.pruneExpire` alone, so the two-week rule applies in the sandbox as well. Reflogs are irrelevant to this blob anyway: a reflog records movements of refs, and no ref ever pointed at a blob that was only staged.

## Lab 2.2: Partial staging

1. A hunk is a run of changed lines together with the three lines of context that `git diff` shows around them (`-U3` by default), and changes whose unchanged gap fits inside that context fall into one hunk. Between the fix in `is_correct` and the debug line in `accuracy` there are only three unchanged lines, two blank lines and the `def accuracy` line, so Git offered them together. `s` changed nothing in the index: it re-cut the questions. The index is written once, after the last answer, with the hunks that were accepted (git-add manual, "Interactive mode": "After deciding the fate for all hunks, if there is any hunk that was chosen, the index is updated with the selected hunks").
2. `git diff --stat` compares the index with the working tree. After the first commit the index equalled HEAD, blob `9dfbf7e`, and the working tree still held the threshold change (one removed line, one added line) and the debug line (one added line): 2 insertions, 1 deletion, as reported.
3. No. `9dfbf7e` is the HEAD version `e7e92e7` with the accepted hunk applied. Git applied the chosen hunks as a patch to the index version and wrote the result as a new blob. The working tree held `5f28fc9`, with all three edits, the whole time. The commit `e878c0f` therefore recorded content that was never a file on disk until later, which is why the lab tells you to export and test the staged snapshot in such cases (Chapter 5, section 5.5).
4. `-a` first staged every tracked file whose working tree content differed from the index, the equivalent of `git add -u`. That replaced the carefully built index entry, docstring only, with the full working tree content, docstring and debug line, and the commit then recorded the index. New, untracked files would not have been included; `-a` affects tracked files only.
5. It moved `main` from `b62f1b4` back to its parent `8c8c524`; HEAD still named `main`, so HEAD moved with it. The index was rewritten from that commit, which is why both edits showed up as unstaged (` M`). The working tree was not touched. `ORIG_HEAD` and the reflog recorded the move. It was the right tool because the commit existed only in this repository; after a push, moving the branch backwards leaves the commit in every clone that fetched it and makes your next push a non-fast-forward, so you would add a correcting commit on top instead (Chapter 11, Reset, Revert, Restore).
6. No. `git fsck` reports objects that nothing references, and an object exists only for content that was added or committed at some point. The debug lines were never added: the first pass and the recovery both answered `n` for their hunks. `git restore` overwrote the only copy. Lab 2.1's recovery worked because the lost value had been added once.

## Lab 2.3: The `.gitignore` trap and its fix

1. Exit status 1 with no output means that no ignore rule applies to the path as Git sees it, and for a tracked path Git does not consult the rules at all, so the result tells you that `.env` is tracked. `--no-index` answers the question with the index left out: `.gitignore:1:.env` with exit status 0 says the pattern itself is correct and would ignore an untracked `.env`. Together the two results locate the problem in tracking, not in the pattern.
2. `D ` comes from the first comparison, HEAD against the index: HEAD has `.env`, the index no longer does, so a deletion is staged. `!!` comes from the scan for paths without an index entry: `.env` is on disk, it has no entry any more, and the pattern matches it, so it is ignored. The three parts of `git status` are independent, so one path can appear in two of them.
3. The pull fast-forwarded her `main`. To check out the new commit Git removes tracked files that the commit no longer has, and it does so without asking when the file is identical to the version in her index and HEAD, because nothing of hers is lost. Ignore rules play no part: the path was tracked in her HEAD. Had she edited her `.env` before pulling, the merge would have stopped with "Your local changes to the following files would be overwritten by merge" and left her file as it was (checked for these answers in the lab sandbox).
4. First, treat the key as leaked and rotate or revoke it: the commit `aa3b3a3` with the key is in your repository, in Asha's clone, and in a real project on the server. The `git rm --cached` commit achieved three things: the path is no longer tracked, the ignore rule now applies to it, and future edits stay out of commits. It did not remove the file from `aa3b3a3` and `ec7fe5d`, it did not remove it from any clone, and it deleted the file from the working tree of everyone who pulled it. Removing the content from history is a separate operation with its own costs (Chapter 21).
5. `git ls-files --cached --ignored --exclude-standard` lists every tracked path that an ignore rule matches. In a healthy repository it prints nothing, so a CI step can fail when its output is not empty, for example `test -z "$(git ls-files -ci --exclude-standard)"`.
6. With the trailing slash the pattern matches only a directory named `__pycache__`, and everything below it; without the slash it would also match a regular file of that name. The manual: "If there is a separator at the end of the pattern then the pattern will only match directories, otherwise the pattern can match both files and directories." In this project only the directory exists, so the ignored paths would be the same; the slash records the intent.

## Lab 2.4: Unstage three ways and compare the results

1. In the lab, `git reset` printed "Unstaged changes after reset:" with the paths that still differ from the index, while `git restore --staged` printed nothing; the two indexes were identical, down to the blob `1e0b1ad` for `src/retriever.py`. Only one works in a repository without commits: `git restore --staged` fails with "fatal: could not resolve 'HEAD'", `git reset <path>` has a rule for that case and removes the entry. In the other direction, `git restore --staged` needs a pathspec, while `git reset` without one unstages everything.
2. To unstage a path means to make its index entry equal to HEAD's entry again. For a path that HEAD has, that means putting HEAD's blob back. `git rm --cached` deletes the entry instead, so the index now differs from HEAD in the other direction: HEAD has the path and the index does not, which is exactly what a staged deletion is. The two operations coincide only for a path that HEAD lacks, because then "HEAD's entry" is no entry.
3. Before the first commit there is no HEAD, so every staged path is new and HEAD's version of it is "no entry". Deleting the entry is then the only possible meaning of unstaging, and `git restore --staged` cannot even run, so the hint is right. In Experiment C, HEAD had `src/retriever.py`; deleting its entry staged a deletion of a file that the project is supposed to keep.
4. The comparison between HEAD and the index, which is what `git commit` records: HEAD `2a0f42b` had `src/retriever.py` and the index did not. `git commit` without `-a` or a path never looks at the working tree, so the file on disk could not save it; status reported the same file as `??` for the same reason.
5. `A`: HEAD, now the wrong commit `401eb62`, lacks the path and the index has it, so the entry is a staged addition. `M`: the index entry holds `TOP_K = 5` from `HEAD~1` and the working tree file holds `TOP_K = 8`, your edit. The `diff` is empty because `HEAD~2`, the original commit `2a0f42b`, and the repair commit `46134ed` hold the same blob `1e0b1ad` for the path; `git restore --source=HEAD~1 --staged` copied that entry unchanged.
6. If her copy was unmodified, the pull deleted it, and with it the then empty `src/` directory, like Asha's `.env` in Lab 2.3 (checked for these answers in the lab sandbox). When she pulls the repair, the file is checked out again from the repair commit with the content of `1e0b1ad`, `TOP_K = 5`. Had she edited the file before the first pull, that pull would have refused to overwrite her change, and the file would have stayed.
