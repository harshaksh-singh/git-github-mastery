# Module 17 lab answers: The index file, ref storage, and the `.git` directory

Answers to the "Questions" of each lab in the [Module 17 lab manual](../lab-manual/m17-index-refs-gitdir.md). Object IDs are the ones printed in the manual; commits that you created by hand have other IDs. Every statement about behavior was checked on Git 2.55.0 in the lab sandbox.

## Lab 17.1: Read the index as a data structure

1. The `TREE` extension caches, for the top level and for each directory, the ID of the tree object that the entries under that directory would produce, together with the number of entries it covers, so that a commit can reuse those trees instead of hashing every directory again. Adding `src/health.py` changed the contents of `src` and therefore of the top level, and Git marked both nodes invalid (an entry count of -1), which is the 15-byte version of the extension. The commit computed the two trees, wrote them to the object database and recorded them in the extension, which is why it returned to 53 bytes.
2. Stat data describes a working tree file that matches an entry, and during a conflict the file `config.toml` with its markers matches none of the three blobs, so the three stage entries carry zeros; the stages are blobs with a role (1 the common ancestor, 2 ours, 3 theirs), not files. `git add config.toml` writes a single stage 0 entry with the blob of the current working tree content, here `34506a9f`, the same blob stage 3 had, so no new object was written, and it removes the three higher stages after copying their IDs into the `REUC` extension.
3. `git diff-files` compared the cached stat data of the entry with `lstat` of the file; the modification time differed, so it reported the path as possibly modified and printed an all-zero ID for the working tree side, because it had not read the content. `git status` saw the same mismatch, read the file and hashed it, found the blob the entry already named, and wrote the index back with the fresh stat data, which is why the second `git diff-files` found nothing to report.
4. Only the index knows which blob is staged for each path, that is, the proposed next commit, together with the cached stat data and the flag bits; history and refs live elsewhere, which is why `git log` worked. After `rm .git/index && git reset` the index equals the tree of `HEAD`: the staged state of `logging.toml` was lost (the file is untracked again, and its blob `e8b40360` survives only as a dangling object), the stat cache was rebuilt, and nothing else changed. Staged content that differed from both `HEAD` and the working tree would have to be recovered from such dangling blobs, which `git fsck --lost-found` writes out as files.
5. The `ort` merge strategy wrote the tree of the working tree state it produced when it stopped, conflict markers included, and recorded it under `AUTO_MERGE`; that is a tree object in the database like any other. When the merge was committed, `AUTO_MERGE` was removed and the tree became unreachable, so `git fsck` reports it as dangling. It will stay until a garbage collection deletes it, after the two-week grace period by default, or at once with `--prune=now`.
6. `git reset` without a mode is `--mixed`: it moves nothing and rewrites the index to match `HEAD`, and it does not touch any file in the working tree, so the edit to `config.toml` survived and appeared as unstaged. `git reset --hard` would have rewritten the working tree from `HEAD` as well, destroying that edit, and no reflog or object would have brought it back, because content that was never staged was never an object.

## Lab 17.2: The `files` backend versus reftable

1. Backward compatibility. Tools and older Gits recognise a repository by finding `.git/HEAD` with the syntax of a symbolic ref, and the stub keeps that recognition working, so that an old client stops at this directory instead of searching the parent directories for another repository. It then refuses to operate because the configuration declares an extension it does not know, which is the safe outcome. The real `HEAD` is a record in the tables, read with `git symbolic-ref HEAD`.
2. Removed: the `logs/` directory, the loose ref files under `refs/heads` and `refs/tags`, and `packed-refs` where one exists. Added: `reftable/` with `tables.list` and one `.ref` table, the stub file `refs/heads`, and in `config` the lines `repositoryformatversion = 1` and `refstorage = reftable`; `HEAD` was rewritten as the stub. Identical: everything under `objects/`, the index, hooks, `info/`, `description`, `COMMIT_EDITMSG`, and every object ID. With a stash entry, `refs/stash` and its reflog `logs/refs/stash` would also have been removed and migrated into the tables, and `git stash list` would show the entry unchanged, because the stash list is that reflog.
3. The first fetch wrote the new value of `Hotfix` as the loose file `refs/remotes/origin/Hotfix` and then failed to create `refs/remotes/origin/hotfix`, which on a case-insensitive filesystem is the same file. `git rev-parse` resolves a name by opening the file with that name, and the filesystem returned the content of `Hotfix` for both names, so both printed `b97d03d`. `git for-each-ref` enumerates: it lists the directory, which yields the single name `Hotfix`, and reads `packed-refs`, which still holds `hotfix` with its value from before the fetch, `6bf35b1`. Lookup answered from the loose file, enumeration from the directory listing and the packed file.
4. `expected 6bf35b1`: the value fetch believed `origin/hotfix` had, taken from its enumeration of the refs before the update, which found the old line in `packed-refs`. `is at b97d03d`: the value the lock-time lookup of `refs/remotes/origin/hotfix` found, which was the loose file of `Hotfix`. The compare-and-swap that protects ref updates saw a ref whose current value was not what it had just read, and refused.
5. The migration enumerates refs through the `files` backend the same way `for-each-ref` does, so `hotfix` was taken from `packed-refs` with `6bf35b1`, and `Hotfix` from its loose file with `b97d03d`. After the migration both names are distinct records in the tables, and the fetch moved `hotfix` from `6bf35b1` to the server's `23223f8`.
6. The protocol exchanges ref names with object IDs, and objects; how each side stores its refs is a local matter, which is why a `files` clone, a reftable clone and a reftable server interoperate without noticing. The server-side fix is to rename one of the two branches so that no two names differ only in case, for example by pushing `hotfix` under a new name and deleting the old one. It is the better fix for a team because every `files`-format clone on every Mac and Windows machine hits the same failure, and not every client or tool can migrate to reftable yet; the migration fixed one laptop, the rename fixes the repository.

## Lab 17.3: A tour of every special ref and file

1. Pseudorefs: `FETCH_HEAD` and `MERGE_HEAD`. Root refs: `HEAD`, `ORIG_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `REBASE_HEAD`, `AUTO_MERGE`, and `BISECT_EXPECTED_REV`, which the glossary lists among the irregular root refs. Neither: `MERGE_MSG`, `MERGE_MODE`, `COMMIT_EDITMSG`, the `rebase-merge/` directory and the other `BISECT_*` files, which hold text that is not a ref. The test: `git update-ref <name> HEAD` is refused for a pseudoref with `refusing to update pseudoref` and accepted for a root ref; `git for-each-ref --include-root-refs` lists root refs and not pseudorefs; and in a reftable repository the root refs are records in the tables while the two pseudorefs remain files.
2. `git reset --soft` (documented and seen twice), `git merge` and `git rebase` (documented in `git help revisions`), and `git stash push`, which left `ORIG_HEAD` behind on Git 2.55. Each writer overwrites the file, so after several commands `ORIG_HEAD` records only the last of them, and a script cannot tell which; use the reflog of the branch, which keeps every move with its reason. `AUTO_MERGE` at the checkpoint was left by `git stash pop`, which applies the stash through the merge machinery; a clean pop leaves the tree behind on this version, and the next commit removes it.
3. A rebase replays commits one at a time on top of `onto`, and until the last one has been applied the branch must keep its old tip, so that an abort can return to it and so that a failure leaves nothing half-moved; the replayed commits are therefore made on a detached `HEAD`. The state directory `rebase-merge/` records `head-name`, the branch to update at the end, and `onto`, the base, together with the original tip and the todo list; `git rebase --abort` reads them, moves the branch back to its original tip and makes `HEAD` point at the branch again.
4. `refs/bisect/bad` and `refs/bisect/good-*` are refs because the bisection is computed by the revision machinery: `git rev-list --bisect` adds `refs/bisect/bad` to the included commits and the `good-*` refs to the excluded ones (`git help rev-list`), and refs are the form in which that machinery takes commits. The `BISECT_*` files are bookkeeping, the log that `git bisect replay` can re-run, the terms in use, and the original position in `BISECT_START`. `git bisect reset` deletes the refs and the files and checks out the commit recorded in `BISECT_START`, here `main`.
5. The tree was right because `git commit` builds it from the index, and the index held the resolved `config.toml` at stage 0 next to the unchanged files. The parents were wrong because `git commit` takes `HEAD` as the first parent and adds the commits listed in `MERGE_HEAD` as further parents; with the file gone, there was nothing to add, so the commit had one parent. `git branch --no-merged main` then listed `feature/timeouts`, because its tip `0cab12e` is not an ancestor of `main`: the content had arrived, the history had not.
6. `--soft` moves the branch and `HEAD` to the new commit and leaves the index and the working tree alone, which is right because both already match that commit's tree; `--mixed` would have rewritten the index for no reason and `--hard` would have touched files. The faulty single-parent commit stays in the object database, reachable from the reflog of `HEAD` and of `main` and from `ORIG_HEAD`, until reflog expiry and a garbage collection remove it. Had it been pushed, you would not move the branch: you would run `git merge feature/timeouts` again, which creates a merge commit with the missing second parent and no content change, and leave the faulty commit in the history.
