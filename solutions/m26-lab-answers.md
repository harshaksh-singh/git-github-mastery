# Module 26 lab answers: GitHub Actions fundamentals

> **Baseline.** Git 2.55.0 on macOS; GitHub facts as of 1 October 2026. These are answers to the "Questions" of each lab in the [Module 26 lab manual](../lab-manual/m26-actions-fundamentals.md). Write your own answers first. Commit IDs quoted here are those of the replay scripts in `labs/ch20a/`; yours differ. Answers about what GitHub does rest on its documentation, as cited in [Chapter 20A](../textbook/ch20a-actions-fundamentals.md) and the manual: the workflows were not executed on GitHub by the author. Where your run disagrees with an answer, your run is the evidence; note the difference.

## Lab 26.1: Workflow 1, run the tests

1. **Refs and commits.** Push run: `GITHUB_REF` was `refs/heads/main` and `GITHUB_SHA` the commit you pushed, which is in your clone. Pull request run: `GITHUB_REF` was `refs/pull/N/merge` and `GITHUB_SHA` the test merge commit that GitHub created from your head and the current `main`. That commit is not in your clone; `git cat-file -t` on it fails, as in the transcript `ch20a/merge-ref/06-not-in-your-clone`, where the same check on `d04ef31` ends with exit status 128.
2. **The branch filter.** A push to a pull request branch causes two events: `push` (for the branch) and `pull_request` (`synchronize`). Without the filter, workflow 1 would run twice per push, once on the head commit and once on the merge commit, and the pull request would show two results that can disagree. With `branches: [main]`, the `push` trigger covers only what lands on `main`.
3. **Permissions.** With a read and write default, the job token could push commits, create tags and releases, or change issues and pull requests. With the block it can read repository contents and nothing else, because naming one permission sets every unnamed one to `none`. A test job needs none of the rest, and a compromised dependency running inside it gets none of the rest.
4. **Re-running.** No. A re-run reuses the original commit and ref. The first run tested a merge commit whose tree contains the broken test; running it again tests the same tree. The fix is in a new commit, which causes a new `synchronize` event, a new test merge commit and a new run.
5. **Scope of `env`.** At the top of the file, `PYTHONPATH=src` would be set for every step of every job, including the actions. Step level is the narrowest scope that works. For one variable in a four-step file the difference is small; the habit matters when the variable is a credential.

## Lab 26.2: Workflow 2, linting

1. **Why the next step ran, and why the job failed.** Every step has an implicit `if: success()`. The formatting step replaces it with `if: ${{ !cancelled() }}`, which is true after a failure. The job fails because a failed step fails its job unless that step has `continue-on-error: true`; an `if` on a later step changes which steps run, not the job's result.
2. **`outcome` and `conclusion`.** `outcome` is the step's result before `continue-on-error` is applied, `conclusion` the result after. They differ only for a step that failed with `continue-on-error: true`: outcome `failure`, conclusion `success`. The lint step has no `continue-on-error`, so both are `failure`; the summary uses `outcome` because it is the honest one in either case.
3. **`--locked`.** It asserts that `uv.lock` will remain unchanged, so it fails when the lock file does not match `pyproject.toml`. Without it, `uv sync` would resolve again on the runner and install versions nobody reviewed and nobody committed: the pull request would be tested against one set of dependencies and the next run against another.
4. **Why `env`.** An expression inside `run:` is pasted into the script text before the shell starts; a value passed through `env` reaches the shell as data. For `success` or `failure` both are harmless. The course uses one form everywhere so that the safe form is the reflex when the value is a pull request title or a branch name (Chapter 21A).
5. **Machines.** Two, one per job, since each workflow has one job. They shared nothing: not files, not the virtual environment, not variables. Each fetched the same test merge commit on its own. The only common inputs were the event and the repository content.

## Lab 26.3: Workflow 3, build the application

1. **A green wrong answer.** `--always` makes `git describe` fall back to the abbreviated commit ID when it finds no tag, with exit status 0. In the shallow, tagless clone that is the only thing it can print; the replay shows `6fe5455` where the full clone prints `v0.1.0-1-g6fe5455`. In a release workflow, drop `--always`: a failure with "No names found" is better than a release named after a commit.
2. **Tags without history.** No. In `ch20a/shallow-checkout/04-tags-are-not-enough` the tag `v0.1.0` is present and `describe` still fails with "No tags can describe", because the walk from HEAD to the tagged commit `ae299cb` ends at the shallow boundary. `fetch-tags: true` needs enough depth to reach the tag; `fetch-depth: 0` gives both.
3. **The hops.** Shell variable `describe` in the step; a line `describe=...` appended to the file named by `GITHUB_OUTPUT`; the step output `steps.describe.outputs.describe`; the job output `describe` declared under `jobs.build.outputs`; `needs.build.outputs.describe` in the job `report`; the environment variable `DESCRIBE` of its step; the `echo` into the file named by `GITHUB_STEP_SUMMARY`.
4. **Manual runs.** The workflow file must exist on the default branch with a `workflow_dispatch` trigger. The run then uses the file from the ref given with `--ref`, which is why the edited version ran.
5. **The pipeline.** `ls dist | tr '\n' ' '` in the step "List the build outputs". Under the implicit `bash -e`, a failing `ls` would be hidden by a succeeding `tr`, and the output `files` would be an empty string. With `shell: bash` the template adds `-o pipefail` and the step fails. (The plain `ls dist` on the line before it would stop either shell.)

## Lab 26.4: Workflow 4, Python tests with uv and caching

1. **Miss after the merge.** A cache created by a pull request run is scoped to that pull request's merge ref and "can only be restored by re-runs of the pull request", not by the base branch. Scope is checked in addition to the key.
2. **The recovery run.** A miss. `uv.lock` changed, the key depends on it, and caches are immutable per key, so no entry can match. The run saves a new entry when the job succeeds.
3. **`cache-hit: false` on a restore-key match.** The restored content belongs to another key, so it is close but not exact: the step that installs dependencies must still run to add what is missing, and the cache must be saved under the new key. A `true` would let a workflow skip the install on stale content.
4. **Concurrency.** The second run in the same group cancels the first, because `cancel-in-progress` is `true`; only the newest commit's result is of interest. The group is the workflow name plus `github.ref`, and for a pull request run `github.ref` is `refs/pull/N/merge`, so each pull request has its own group and runs on `main` have another.
5. **A 6 GB model in the cache.** The repository's free allowance is 10 GB across all branches, and when it is exceeded the least recently used entries are evicted, which would be the dependency caches. An entry not read for 7 days disappears, so the job must be able to fetch the model anyway. And cache contents are unsigned and readable by anyone who can open a pull request, which is the wrong trust level for an input that decides an evaluation result.

## Lab 26.5: Workflow 5, Java tests with Maven

1. **A required check that never reports.** The check stays in the "Pending" state and blocks merging, indefinitely: no run was created, so nothing will ever report. This is the documented behavior for workflows skipped by path filtering.
2. **The workflow file in its own filter.** A change to the workflow is a change to how the Java module is tested. Without the entry, an edit to the file would merge without ever having run.
3. **Two base directories.** `defaults.run.working-directory` applies to `run` steps only. The upload is a `uses` step; the action resolves `path` from the workspace root.
4. **A skipped step is not a skipped workflow.** A step skipped by `if` does not affect the job's result, and even a whole job skipped by a conditional reports "Success". The check exists and passes. In question 1 no check exists. The two cases are opposites for a required check.
5. **Whole pull request, not last push.** Yes, it would start. For a pull request the filter is evaluated on the three-dot diff of the whole pull request, which still contains the `java-service/` change of the first commit. The replay shows the same from the other side: after the second commit the diff lists both `README.md` and `java-service/pom.xml`.

## Lab 26.6: Workflow 6, build and push a container image

1. **Job-level permission.** Only the job that pushes needs to write packages; a second job added to the file later would otherwise inherit a permission it does not need. A job-level `permissions` block replaces the workflow-level block for that job, which is why `contents: read` is repeated there: unnamed permissions become `none`.
2. **Fork pull requests.** Checkout, Buildx, metadata, build and summary run; login is skipped and `push` is false. Without the `if`, the login step would run with the read-only token that fork runs receive. Whether the login itself then fails is not something the documentation read for this course states; nothing could be pushed with that token either way, and `push` is false for pull requests. The `if` keeps a credential step out of a run that needs no credential.
3. **`latest`.** The `flavor` input, whose default `latest=auto` adds `latest` for semver and tag types. Turn it off (`latest=false`) when pre-release tags should not move `latest`, or when deployments must reference a version or digest and never a moving tag.
4. **Deleting the Git tag.** Nothing happens to the image. The tag ref and its tag object are Git data in the repository. The image `0.2.0` is a version of a package, a GitHub object in the container registry, created by a workflow run that has already finished. Unpublishing it is a separate, deliberate action on the package.
5. **Layer cache scope.** The pull request run can restore layers cached by runs on `main`, because a pull request may read its base branch's caches. The `main` run cannot read what the pull request run cached: that entry is scoped to the merge ref.

## Lab 26.7: Workflow 7, create an artifact and consume it

1. **No waiting.** A download step asks the artifact service once for the name. Nothing in the workflow told GitHub that the jobs are related, so they started together, and at that moment the artifact did not exist. Ordering between jobs exists only through `needs`. Whether the run got that far or was rejected for the dangling `needs.build` reference is what you recorded.
2. **Checkout and artifact.** From the checkout, `scripts/deploy.sh`. From the artifact, the built files. Rebuilding in the deploy job would resolve the build backend again and could produce different bytes from the ones the pipeline produced and inspected; passing the artifact means the deployed files are the built files, with a digest to prove it.
3. **Cache instead of artifact.** A cache is saved only at the end of a successful job and restored by key, with no guarantee that the entry exists or is the one this run produced; another run with the same key could have written it. And cache contents are neither tied to a run nor verified by digest. An artifact belongs to the run and is verified on download.
4. **`warn` instead of `error`.** The upload step would pass with a warning, the build job would be green, and the failure would appear one job later as a download error for a missing artifact, pointing at the wrong job.
5. **Two years.** No. The retention of an artifact is at most the repository's setting, 90 days at most in a public repository, and 7 days in this workflow. A GitHub Release or a package registry is the place; Chapter 15 covers releases.

## Lab 26.8: Workflow 10, matrix testing

1. **The arithmetic.** Two operating systems times three Python versions times one value of `experimental` is 6. `exclude` removes macOS with 3.11: 5. `include` is processed after `exclude`. Its entry sets `python: "3.14"` and `experimental: true`; adding it to an existing combination would overwrite that combination's original `python` and `experimental` values, which `include` never does, so it becomes a new combination: 6.
2. **`fail-fast: true`.** The first failure, on Python 3.11, would have cancelled the jobs still running or queued. You would have seen one red job and several cancelled ones, and you would not know that the code works on 3.12 and later, which is the fact that identifies the cause as a language-version problem.
3. **The aggregate job.** Its name does not depend on the matrix, so the ruleset survives a change of versions, and no check name has to be guessed. Without `always()`, a failed matrix would cause the job to be skipped, and a job skipped by a conditional reports "Success": the required check would pass exactly when the tests failed.
4. **A promise only CI keeps.** Your machine runs one Python version. The file parsed and the tests passed there. Only the 3.11 job showed that the code no longer runs on the oldest version the project declares. (The lint workflow is a second witness: ruff reads `requires-python` and reports the `type` statement as a syntax error for that target; with ruff 0.15.21 it did so on the author's machine.)
5. **One name, six uploads.** Artifacts are immutable per name within a run, so the second upload would fail. Put the matrix values in the name, for example `report-${{ matrix.os }}-py${{ matrix.python }}`, and download them together with `pattern` and `merge-multiple`.
