## Lab 15.1: A submodule that breaks for a teammate

1. **Predictions.** After a commit inside `vendor/textsplit`, `git status --short` in `doc-qa` prints ` M vendor/textsplit`: the checked-out library commit differs from the one in the index. Ravi notices at `git pull`, with `not our ref`, during the automatic fetch in the submodule. The command that could have warned you is `git push origin main`. It did not, because by default a push of the superproject looks at the superproject only: `push.recurseSubmodules` is unset, which behaves like `no`. The gitlink is valid data for the service's repository whether or not anyone can fetch the commit it names.
2. **Three places.** (a) The gitlink: a tree entry with mode `160000` whose ID is a commit of the library. (b) `.gitmodules`, a tracked file that maps the path to a URL. (c) The library's repository in `.git/modules/vendor/textsplit`, with the matching `submodule.<name>.*` entries in `.git/config`. A commit of the superproject records (a) and (b), because both are in its tree. It does not record (c) and it does not contain the library commit, only its ID (section 23.2).
3. **Behind 1.** `git pull` is a fetch followed by a merge. The fetch of the service succeeded, so `origin/main` moved to `08ffafb`. The fetch in the submodule failed, the pull stopped with exit status 1, and the merge did not run, so `main` stayed at `235f4b8`. Nothing in Ravi's clone was damaged. `git merge origin/main` would have fast-forwarded `main` at that moment, and `git status --short` would then have shown ` M vendor/textsplit`: a service commit that records a library commit which Ravi cannot check out. The pull's refusal to go on is the more useful failure.
4. **The option.** In the first part, the fetch in the submodule was done by `git pull`, as part of fetching new superproject commits that change a gitlink, and `git submodule update` found the commit present and only had to check it out. In the recovery, the superproject commits had been fetched by the failed pull, so the second `git pull` had nothing new to fetch and did not look into the submodule. `git submodule update` then found the recorded commit missing and started a fetch itself. A transfer that `git submodule update` starts over the `file` transport is subject to `protocol.file.allow`, whose default `user` refuses it; hence `-c protocol.file.allow=always` for that one command. The restriction dates from Git 2.38.1 and exists because a recursive clone of an untrusted repository must not be able to read local paths of the victim's machine (section 23.4). With HTTPS or SSH remotes the question does not arise.
5. **Where `check` does not help.** First, it is local configuration and not versioned: a teammate, a new clone, or a script without the setting can still push the superproject alone. Second, it trusts your remote-tracking branches: it is satisfied when the library commit is on any remote-tracking branch of the submodule, including a branch that is deleted later, or a branch of the library that is never merged in the form you pushed. One control covers both: CI that makes a fresh recursive clone of every pushed commit and fails when a submodule commit cannot be fetched, combined with a required status check (section 23.12).
6. **Without push permission.** (a) Get the exact commit published: open a pull request to the library from a fork or a branch someone creates for you, and have it merged with a merge commit or a fast-forward. A squash merge or a rebase merge creates a different commit, and the recorded ID stays unreachable. (b) Add a new commit to the service that moves the gitlink back to a library commit that is published, and reverts the code that depends on the unpublished one. (c) Rewrite the service's branch to remove the commit, and force-push. Options (a) and (b) rewrite nothing. (b) is the fastest way to unblock the team; (a) follows through the library's own review; (c) is not justified for a commit that others have fetched.

## Lab 15.2: The same dependency as a subtree

1. **Prediction, and where the blobs are.** `git ls-tree HEAD vendor/` prints mode `040000` and type `tree`, and Ravi runs nothing after `git clone`. In Lab 15.1 the library's blobs are in the library's own object database (`.git/modules/vendor/textsplit` in each clone, `remotes/textsplit.git` on the server), and the service stores a commit ID. In Lab 15.2 the library's blobs are in the service's object database and on the service's remote, reachable from the service's commits, and the service stores no reference to the library's repository at all.
2. **Where the version is recorded.** In the message of the squash commit, as the trailers `git-subtree-dir: vendor/textsplit` and `git-subtree-split: <upstream commit ID>`. `git subtree pull --squash` searches the history for the newest such commit to learn which upstream commit the content corresponds to, and builds the next squash commit as the difference from there. If a rewrite squashes that commit away or changes its message, the next pull no longer finds its starting point, and `split` can no longer connect its synthetic history to upstream's commits. Do not squash-merge, rebase or reword the commits that `git subtree` creates (sections 23.13 and 23.16).
3. **Unrelated histories.** Without `--squash`, the pull asks `git merge` to merge the library's real tip, `2cb6684`, into your branch. Your branch contains `65b9504`, a parentless commit with the library's content, and no commit of the library's own history. So the ancestors of `2cb6684` and the ancestors of your HEAD have no commit in common, there is no merge base, and `git merge` refuses unless `--allow-unrelated-histories` is given. With `--squash`, the command first builds a new squash commit on top of `65b9504` and merges that; its merge base with your branch is `65b9504`.
4. **Existing IDs from a synthetic history.** `git subtree split` walks your history and writes, for each commit that touches the prefix, a new commit whose tree is the content of the prefix. When it meets a squash commit, it does not synthesize anything: it takes the commit named in `git-subtree-split` as the parent to build on. That is upstream's real commit, with its real ancestors, and its objects are in your repository because the earlier `add` and `pull` fetched them. Only commits made in the service get new IDs; here that is the one on top, `84d2435`.
5. **A mixed commit.** `split` reduces the commit to its library part and keeps the whole message, so upstream receives a commit whose message describes a change to `answer.py` that is not in it. Reviewers of the service see a dependency change hidden in a feature commit, and an update of the library may later conflict with an edit nobody knew about. The rule: a commit that touches `vendor/textsplit` touches nothing else, and says in its subject that it changes the vendored copy.
6. **Choices.** (a) Package manager: the library is published with versions, six consumers need a resolver, a lock file and security advisories, and neither Git mechanism provides those. (b) Submodule: the schema stays one repository with its own history and owners, every consumer pins an exact commit ID, and updates are explicit pointer commits; the price is the configuration and CI discipline of sections 23.12 and 23.16. If the three teams turn out to need one atomic change across schema and services, that points to one repository instead. (c) Subtree: the files are in every clone, CI needs no second repository and no extra credentials, local patches are ordinary commits, and `split` can offer them upstream (section 23.14).

## Lab 15.3: Inspect an LFS pointer

1. **Two sizes.** `git cat-file -s` reports 132, the pointer blob. `wc -c` reports 1,200,000, the content in the working tree. `git clone` transfers Git objects, so it transfers the 132 bytes; the 1,200,000 bytes are transferred by LFS, during checkout through the smudge filter when the client is installed, or by `git lfs pull` afterwards.
2. **Two hashes.** The `oid` is the SHA-256 of the file's bytes and nothing else. The blob ID is Git's hash of the pointer blob: the header `blob 132` and a NUL byte, followed by the three lines of pointer text. Identical model bytes give the same `oid` and the same size, therefore the same pointer text, therefore the same blob ID. Git sees an unchanged file, and the LFS store already has an object of that name.
3. **Modified without a change.** With the new `*.wav` line, Git applies the clean filter to `samples/hello.wav` whenever it compares the working tree with the index. The filter returns a pointer of 130 bytes. The index entry is the blob committed before the line existed: 48,000 bytes of audio. The two differ, so the file is reported as modified. The report is correct in Git's terms: `git add` would now store something else than what is committed.
4. **Three commits.** The scope of the migration was the commits of `main` that are on no remote: three. The migration writes the tracking line for `*.wav` into `.gitattributes` in the earliest commit in scope (`git show HEAD~2:.gitattributes` shows both lines), so that commit's tree changed although it adds no WAV file, and it became `a55418e`. A commit ID covers the parent IDs, so both descendants changed as well; the second of them also has a new tree, with a pointer in place of the audio. `c66100a` was outside the scope, and nothing in it or below it changed.
5. **On Ravi's machine.** The program reads 132 bytes of text that begin with `version https://git-lfs.github.com/spec/v1`. A model loader fails with a parse or format error of its own (invalid protobuf, bad magic number, truncated file); nothing in the message mentions Git or LFS. Ask for `git lfs version`, to learn whether the client exists on the machine, and `git lfs ls-files`, where a `-` after the abbreviated oid says that the working tree file holds a pointer (`wc -c` or `head -c 100` on the file shows the same). The fix is `git lfs install` (in the lab: `--local`) and `git lfs pull` (section 22.7).
6. **Two checkers.** `git lfs fsck` checks, for the LFS files of HEAD, that each object exists in `.git/lfs/objects` and that its content hashes to its name, and that pointers are well-formed and that files which the attributes say should be pointers are pointers. `git fsck` checks Git's object database. A pointer blob is a valid blob, so `git fsck` reports nothing for a repository whose LFS store is empty: for Git, nothing is missing.

## Lab 15.4: Migrate an already-committed large file

1. **Predictions.** The four unpushed commits of `main` were rewritten. `c66100a` kept its ID because the default scope excludes commits that are on a remote, and a commit that is not rewritten and whose ancestors are not rewritten keeps its ID. `.git` is not smaller: the three large blobs are still in the object database, held by the reflogs of `main` and HEAD, and the same content now also lies in `.git/lfs/objects`. To make it smaller you would expire the reflogs and collect garbage (`git reflog expire --expire=now --all`, then `git gc --prune=now`), and that removes the way back to the commits from before the migration: the recovery of this lab would no longer be possible. Verify, and push, first (section 22.9).
2. **Ahead 5, behind 1.** Ahead: the commits reachable from `main` and not from `origin/main` are the rewritten root `e6c7da2` and the four rewritten commits above it. Behind: `c66100a` is reachable from `origin/main` and no longer from `main`, because `main` now descends from the copy.
3. **Why the root was rewritten.** `--everything` put it in scope, and it was the earliest commit in scope. The migration writes the `.gitattributes` line into the earliest commit it rewrites, so that every later commit has pointers and the rule that explains them. `git show --stat` of `e6c7da2` shows the added `.gitattributes`. A changed tree gives a changed commit ID, and every descendant follows.
4. **Two reflog entries.** `main@{0}` is the tip after `--everything` (`ca28864`). `main@{1}` is the tip after the first, correct migration (`d1e8e7d`). `main@{2}` is the original tip with the large blobs (`8b13104`). With `main@{2}` you would have undone both migrations on `main`. The last command, which names `experiment/quantized` only, would then have migrated that branch alone: `main` would still carry 3.75 MB of model blobs, the two branches would no longer share their first two commits, and you would have had to run the migration for `main` again.
5. **The same commit twice.** A commit ID is a hash of the tree, the parents, the author and committer with their dates, and the message. The migration keeps author, committer, dates and message, and it derives the tree and the `.gitattributes` content from the input alone. For "Add acoustic model v1" and "Retrain acoustic model on noisy audio (v2)" the second run had the same input as the first: the same original commits on top of the same unrewritten parent `c66100a`. Same content, same ID: `b1b921b` and `53cb32a` were not created a second time, they were found. That is also why your hands-on IDs match the replay in this lab.
6. **Already pushed, five clones.** The plan: announce a freeze and have everyone push or park their work; one person runs `git lfs migrate info` and then `import` with a scope that covers every branch and tag that contains the files; verifies as in this lab; pushes all rewritten refs with `git push --force-with-lease`, which also uploads the LFS objects; then everyone re-clones, or fetches and resets each local branch to its rewritten counterpart, and rebases unfinished work onto the new commits. Open pull requests have to be recreated or rebased. It fails most often after the push: someone merges or pushes from a clone that still has the old history, and the large blobs return to the remote with it. LFS does not coordinate any of this. It does not remove the old blobs from other clones, and whether and when the server discards the old, now unreachable objects is a matter for the hosting platform and not for Git or LFS (section 22.9). It also does not make the past cheaper: every version of the model is now an LFS object that counts against the storage quota (section 22.11).
7. **Neither Git nor LFS.** Training data and model weights that change with every run: DVC with a remote you control, or a model registry that records the Git commit beside each model version. Files above the per-file cap, and data that must be deletable (personal or licensed data): object storage with retention controls, with the URI and a checksum in Git. Binaries built from a tag: release assets or a package registry (section 22.13).
