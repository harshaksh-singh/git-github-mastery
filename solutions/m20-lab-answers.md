# Module 20 lab answers: Authentication and SSH

> **Baseline.** Git 2.55.0, OpenSSH 10.2 and GitHub CLI 2.88.1 on macOS; GitHub facts as of 1 October 2026. These are answers to the "Questions" of each lab in the [Module 20 lab manual](../lab-manual/m20-authentication-ssh.md). Write your own answers first. Nothing here was captured from GitHub: where an answer depends on what you saw in Part B, it says what the documentation leads you to expect.

## Lab 20.1: SSH setup and verification

1. **Which file GitHub received.** The `.pub` file: one line with the key type, the public key and a comment. Someone who has only that file can recognize your key and check signatures made with it. They cannot authenticate as you, because authentication requires a signature that only the private key can produce, and the private key cannot be computed from the public one.
2. **Where `user git` came from.** In Part A, from the line `User git` in the `Host github.com` block. GitHub's own four-line block has no `User` line; there the user comes from the URL or the command line, `git@github.com`, which Git passes to `ssh` unchanged. That is why `ssh -G github.com` without `git@` prints your local user name on such a machine, and `ssh -G git@github.com` prints `git`.
3. **Two identity files, one user.** `IdentityFile` is a list: every directive that applies adds a file, and all are tried in order. `User` holds one value, and for single-valued settings the first value obtained wins. The `Host *` block came first, so its user won, and its key was merely added in front of the right one.
4. **Offline verification of host keys.** You computed fingerprints locally, with `ssh-keygen -l`, from the `known_hosts` lines that GitHub publishes, and compared them with the fingerprints that GitHub publishes on the same documentation page. A fingerprint is a hash of the key, so equal fingerprints mean equal keys. When `ssh` later meets a server whose key matches a stored line, it is the server that holds the matching private key. The anchor of trust is the documentation page, fetched over HTTPS.
5. **Exit status 1.** Not an error: GitHub's page says the command should exit with 1, because GitHub provides no shell. The greeting proves that the key you offered is registered to the named account. It proves nothing about any repository: authorization is decided per request, later.
6. **Agent, keychain, backup.** The agent holds the decrypted private key in memory for the session. The keychain holds the passphrase, so that the key can be loaded again after a restart. A thief with a copy of `~/.ssh` has the encrypted private key, which is useless without the passphrase, plus the public keys, the configuration and `known_hosts`, which reveal which hosts you use.
7. **Why `-F` everywhere.** `ssh` does not consult `$HOME`. It asks the system for the account's home directory, so without `-F` it would have read your real `~/.ssh/config`. Changing `HOME` redirects the shell's `~` and Git's global configuration, not `ssh`.

## Lab 20.2: HTTPS through the GitHub CLI, and the helper behind it

1. **Order of operations.** First successful push with nothing stored: `get` (no answer), a prompt or a browser flow supplies the credential, the server accepts it, `store`. Push with a revoked token: `get` (the stored token is returned), the server answers 401, `erase`, and Git ends with "Authentication failed". The next attempt starts with a `get` that finds nothing.
2. **Configured and still failing.** The helper was asked and had nothing stored: its log shows one `get`. Git then fell back to prompting, which `GIT_TERMINAL_PROMPT=0` forbids. The log proves that the configuration works and that the store was empty; "could not read Username" is about the missing terminal, not about the helper.
3. **No `path=`.** By default Git asks for a credential per protocol and host, so one stored credential serves every repository on `github.com`, and two accounts on the same host collide. `credential.useHttpPath=true` adds the repository path to the request, so that a helper can store one credential per repository, and `credential.https://github.com.username` asks the helper for a specific account.
4. **The second helper.** Git asks helpers in order and stops as soon as it has a username and a password. The first helper supplied both. The evidence is the trace, which shows only `git credential-labstore get`, and the helper log.
5. **Why the empty value.** The helpers that apply to a URL are the general list followed by the URL-specific list. Without the reset, the list for `github.com` would be `labstore`, `workstore`, `workstore`, and `labstore` would still answer first. The empty value discards everything configured before it.
6. **Your machine.** The answer is in the first column of `git config get --show-origin --all ...`. A helper set by the Git installation is in a system-level file; one written by `gh auth setup-git` is in your global file. The lab shell does not see the system file because the lab environment sets `GIT_CONFIG_NOSYSTEM=1`, and it does not see your global file because `GIT_CONFIG_GLOBAL` points elsewhere.
7. **After a 403.** Nothing: the stored credential stays. Git's HTTP code calls `credential_reject` when the server answers 401 to a credential that was sent, and not for 403 or 404 (`http.c` at 2.55.0, linked in Chapter 16, section 16.4). So a credential for the wrong account keeps being sent, and Git never prompts.

## Lab 20.3: Three failures, reproduced and diagnosed

1. **Who wrote the decisive line.** Failure 1: `ssh`, reporting that the server refused authentication; the failing layer is the client credential, because no key was offered. Failure 2: `ssh`, before any authentication; the failing layer is the transport, more precisely the check of the server's identity. Failure 3 with the wrong credential: Git's `Authentication failed`, for the server's 401; the layer is the credential. Failure 3 with your real credential: the server's "not found" line and Git's `repository ... not found`, for a 404; the layer is the server's decision.
2. **What the server has established.** With `Permission denied (publickey)` it has established nothing: no key matched any account. With "Repository not found" it has identified an account, or an anonymous visitor, and decided that this identity cannot see such a repository.
3. **Two statuses.** "Authentication failed" is 401: the credential was rejected, and Git tells the helpers to erase it. "Not found" is 404: the request was understood, and the answer is no; Git neither stores nor erases anything.
4. **Why the stored credential survived.** The command emptied both helper lists and installed an inline helper for that one command. The `erase` that follows a 401 therefore went only to the inline helper, which ignores it. The keychain or `gh` was never asked and never told.
5. **`StrictHostKeyChecking=no`.** It would have accepted the unknown key and connected. That removes the only check that the server is GitHub, so anyone on the network path could impersonate it. The fix for a host key error is to learn why the key differs, and then to install the published key.
6. **The bare trailer.** Ask for the output of the transport on its own, `ssh -vT git@github.com` with the host from `git remote get-url origin`, and for the complete output of the failing command. Git's sentence means only that the other program exited; when `ssh` printed nothing, the cause has to be asked of `ssh` directly.
7. **Is it over?** No. The token is valid until GitHub revokes it. The string may also be in the shell history, in the terminal's scrollback, in backups and file-sync copies of the directory, and in any log or ticket where `git remote -v` was pasted. With a real token the first action is to revoke it; cleaning comes second.

## Lab 20.4: Two identities on one machine

1. **Three identities.** The commit identity, written by Git from `user.email` and checked by nobody. The effective remote URL, rewritten by Git through `insteadOf`. The authentication identity, chosen by `ssh` through the host alias and its `IdentityFile`, and decided by GitHub, which maps the accepted key to an account.
2. **Stored URL and effective URL.** `ssh` receives the host of the effective URL, `github-work`. Keeping the stored URL canonical means that the repository's configuration is the same as everyone else's and survives a change of your personal setup: remove the include and the repository is an ordinary one again.
3. **Consequences of the wrong place.** The next commit records the personal email, permanently, unless the history is rewritten before it is shared. The next push is authenticated with the personal key: GitHub answers that the repository is not found or that the personal user is denied, or, if the personal account happens to have access, accepts the push under the wrong account, which is worse because nothing fails.
4. **A clone made with the alias URL.** It would not match: `hasconfig:remote.*.url:` compares the configured URL as a glob, and `git@github-work:acme-pay/...` does not match a pattern that begins with `git@github.com:`. Add a second `includeIf` for `git@github-work:acme-pay/**`, or adopt the rule that clones always use the canonical URL.
5. **`IdentitiesOnly yes`.** Without it, `ssh` may offer every key the agent holds in addition to the configured file. GitHub accepts the first offered key that belongs to any account, so the connection can be authenticated as the other account, and the repository is then "not found". GitHub's guide gives this reason for the line: with several keys in the agent, it makes `ssh` use the correct one.
6. **Over HTTPS.** One credential per account, selected by `credential.https://github.com.username` inside the include file, or one per repository with `credential.https://github.com.useHttpPath`. `gh auth switch` changes the active account for the host everywhere at once; it does not follow the directory you are in, so two terminals in two repositories would fight over it.
