# Module 0 lab answers: Lab setup and working method

Answers to the "Questions" of each lab in the [Module 0 lab manual](../lab-manual/m00-lab-setup.md). Every statement about behavior was checked on Git 2.55.0 in the lab sandbox; where a statement comes from documentation or from the research report, the source is named.

## Lab 0.1: Verify the toolchain and build the sandbox

1. A script that calls `/usr/bin/git` by its full path; a program started with a shorter `PATH` than your terminal, such as a scheduled job or a graphical tool that was not launched from a shell; and a shell whose startup files put `/usr/bin` in front of the Homebrew directory, as the failure scenario did. The check is `git --version`: the Apple build prints `(Apple Git-155)` after the version, and `which git` names the file that would run.
2. `labs/shell` writes three settings: `user.name`, `user.email` and `init.defaultBranch`. A replay sandbox adds `gc.reflogExpire=never` and `gc.reflogExpireUnreachable=never`, because the replays pin the clock to September 2026: their reflog entries are weeks old on whatever day you run them, and `git gc` or `git reflog expire` would otherwise drop entries older than 90 days (30 days for unreachable commits), which would make a transcript depend on the date (Chapter 1, section 1.7). The lab shell uses the real clock, so the defaults behave as they do in any repository.
3. `GIT_CONFIG_GLOBAL`, which makes Git read and write the named file instead of `~/.gitconfig` and `~/.config/git/config`, and `GIT_CONFIG_NOSYSTEM=1`, which makes Git skip the system-wide configuration file ([git(1)](https://git-scm.com/docs/git), environment variables). With only the first, your personal file would still be untouched, but the system-wide file of whichever Git runs would be read, so a system-level setting could change a transcript.
4. `labs/verify-all.sh` ran `labs/ch00/smoke-test.sh` with its snippet output redirected into a temporary directory under the lab root, then compared that directory with `labs/ch00/out/smoke-test/` using `diff -r`: PASS means every produced snippet is byte-for-byte identical to the stored one. Two causes of FAIL on a healthy machine: a different Git in front of `PATH`, because messages, hints and the version line in the summary differ between releases; and a `GIT_*` variable exported by your shell that changes Git's output, such as `GIT_TRACE=1`, which adds trace lines to everything. A third is a stored snippet that was not rebuilt after its script changed.
5. Status 1 came from Git 2.50.1, which has no `history` command and exits with 1 after printing that the command is unknown. Status 129 is the exit code Git 2.55 uses after printing usage information for `-h`. The research report records that Git 2.56 changed `-h` to exit with 0 ([report](../reports/Git%20and%20GitHub%20mastery%20research.md), section 1), so the same command prints the same usage text and exits with 0 after an upgrade.

## Lab 0.2: Read every file in an empty `.git`

1. `HEAD`, `objects/` and `refs/`. When one of them is missing, every command answers "fatal: not a git repository (or any of the parent directories): .git" with exit status 128, including `git symbolic-ref`, which could otherwise repair HEAD. The rule is the function `is_git_directory` in Git's source: a directory is a repository when it has an `objects/` directory (or `GIT_OBJECT_DIRECTORY` is set), a `refs/` directory, and a `HEAD` that is a valid symbolic ref or holds a valid object name ([setup.c](https://github.com/git/git/blob/v2.55.0/setup.c)). The layout manual states the HEAD part in words: a valid repository must have the HEAD file ([gitrepository-layout](https://git-scm.com/docs/gitrepository-layout)).
2. `config` carries settings that `git init` probed for this filesystem. On this Mac they are `core.ignorecase=true` and `core.precomposeunicode=true`, next to `core.repositoryformatversion`, `core.filemode`, `core.bare` and `core.logallrefupdates`. Without the file Git uses defaults, so the repository is recognised, but `core.ignoreCase` would be false on a case-insensitive volume, which is the trap of [Chapter 4](../textbook/ch04-working-tree.md), section 4.12. In the sandbox, deleting `config` and running `git init` again brought back only the first four settings: the case and Unicode probes run only when a repository is created, not on reinitialisation. That is why the lab moved the file aside instead of deleting it.
3. Because Git never found a repository: with HEAD missing, `is_git_directory` fails for `.git`, the search continues upwards and stops at the lab root, and the command dies before it can touch anything. `git init` would have succeeded, because it creates a missing HEAD: it writes `ref: refs/heads/<init.defaultBranch>`, which is `main` in the lab shell, and prints "Initialized empty Git repository". In a repository that had been on branch `topic`, `git status` would then say "On branch main" and "No commits yet", although the commits still exist on `topic`; nothing is lost, but HEAD points at the wrong branch. Writing the one-line file yourself puts the branch you were on back.
4. It is not an error; the exit status is 0. `git fsck` starts its check from the index, the refs and the reflogs, and an empty repository has none of them: HEAD names an unborn branch. The notice disappears as soon as a ref exists, that is, after the first commit; in Lab 1.1 the same notice appears until `git update-ref` creates the branch, and `git fsck` is silent afterwards.
5. `count` becomes 1, the number of loose objects, and `size` becomes the disk space that the object file occupies, in KiB; in the sandbox it was 4. The other counters stay 0: nothing is packed, nothing is garbage. `git add` writes the blob at once, before any commit exists.
