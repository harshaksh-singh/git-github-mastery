# Module 16 lab answers: The object database, part 1

Answers to the "Questions" of each lab in the [Module 16 lab manual](../lab-manual/m16-object-database.md). Object IDs are the ones printed in the manual; in Lab 16.1 your commit IDs and pack name differ, your blob IDs do not. Every statement about behavior was checked on Git 2.55.0 in the lab sandbox.

## Lab 16.1: Watch loose objects become a pack

1. Three commits, three trees and three blobs. A tree is a listing of entries with their object IDs, so the top-level tree of each commit is a different object: it names `vocab.txt` with a different blob each time. One directory in the working tree becomes as many tree objects as there are distinct versions of its content.
2. First, storage granularity: `size` reports disk space, and a loose object is a file of its own that occupies at least one 4 KiB block on this filesystem, so nine objects cost 36 KiB although the largest compresses to under a kilobyte (the pack listing shows 739 bytes for it). Second, delta compression: in the pack the two older blobs are stored as seven-byte deltas against the newest one, and all objects share one file, so the total is 2 KiB. Neither reason has anything to do with the content changing.
3. The seven is the size of the delta: the uncompressed instructions that rebuild the blob from its base, which `git verify-pack -v` prints in the size column for a deltified object. Their base is the newest blob, `664847f2`, 4,422 bytes, stored whole; both older blobs are at depth 1 against it, so this is two one-step deltas rather than a chain. `git cat-file -s` reports the logical size, 4,400 and 4,411, because Git reconstructs the full object.
4. `git rev-parse HEAD` needs refs only: it reads `HEAD`, follows it to `refs/heads/main`, finds that in `packed-refs`, and prints the ID without touching the object database. `git cat-file -t HEAD` must open the object, and the only way to find an object inside a pack is the `.idx`; with it gone, the object cannot be located and the command fails with `could not get object info`.
5. The index is a function of the pack: `git index-pack` reads every entry, recomputes each ID from the content, records the offsets and CRC32s, sorts the IDs and appends the pack checksum, so the same pack produces the same index to the byte. If the `.pack` had been deleted, the objects themselves would be gone, and no file in `.git` can regenerate an object. You would then get them from another clone or the remote (a fresh clone, or the intact pack copied from a healthy clone), from a backup, or for the current version of each file from the working tree with `git hash-object -w`; loose objects of recent commits would still be present and would not need rescue.

## Lab 16.2: Read a pack listing and find a delta chain

1. The base is `a4e58256`, the blob of `eval/cases.jsonl` in the newest commit, `14fbba9` ("Relax case 150 to two sentences"), the version `HEAD` names. Pro Git explains the direction: the newest version is stored intact "because you're most likely to need faster access to the most recent version of the file", and reading the newest version then costs no delta application. The manual for `git cat-file` adds the caveat that matters for diagnosis: which object is the base "is arbitrary and is subject to change during a repack".
2. A delta is a short program: the sizes of the base and of the result, then instructions that either copy a byte range from the base or insert bytes given in the delta itself. Each version differs from the next by one line, so a delta copies everything before that line, inserts the new line, and copies the rest, which fits in 17 to 22 bytes. `%(objectsize)` reports the logical size because the delta is only a storage form: Git always reconstructs the complete object before it hands it to any command.
3. The damaged byte lies inside the zlib stream of the base, so inflating the base fails, and every one of the five deltas needs the base, so all six versions of the file fail with the same chain of errors. Commits and trees are separate entries with their own compressed data, so `git log` reads them without trouble. `git status` compares the cached stat data of the index with the working tree and the index entry's blob ID with the tree in `HEAD`; it never opens the blob, so it has no reason to complain.
4. Before writing, `git hash-object -w` asks whether an object with that ID already exists, and the pack index says yes: existence is decided by the ID being listed, not by the content being readable. With the pack moved aside the ID is unknown, so the second `-w` writes the loose object. The lesson is that the object store trusts its indexes, which is why a corrupt object has to be removed or shadowed before it can be replaced.
5. A pack is named after the checksum of its content, so the same name means the same bytes: the rebuilt pack contains the same 25 objects in the same order with the same deltas, and the repository is byte for byte what it was before the damage. A different name would not have meant a failed repair; `git pack-objects` could have chosen different deltas or a different order and still stored every object correctly. The proof of correctness is `git fsck` and `git verify-pack`; the identical name is a stronger statement than you can usually expect.
6. In order: another clone or the remote, because every clone has the same objects under the same IDs, so a fresh clone or an intact pack copied from a healthy clone restores everything that was pushed; a backup of the repository; and the content itself from any machine that has that version of the file, written with `git hash-object -w`, which works only for versions you can lay hands on. The risk of running `git gc` or `git repack` first: on this repository, `git gc` aborted with `fatal: packed object ... is corrupt` and `failed to run repack`, leaving a temporary pack behind as garbage, and had it succeeded with pruning enabled, it would have deleted the unreachable objects that might have been your next recovery source. Copy the repository, repair, and only then let maintenance run.
