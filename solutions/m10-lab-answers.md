## Lab 10.1: Backport a fix with `-x`

1. **Author and committer.** The author is Asha Rao, with the date of her original commit. The committer is Lab User, with the time at which the cherry-pick ran. A cherry-pick keeps who wrote the change and records who created this commit object, and when.
2. **Why no conflict.** The base is the parent of "Log rejected prompts", which is Asha's fix on `main`. "Ours" is the release tip, which has the same `if` block (from your backport) and differs from the base in the `MAX_RETRIES` line only. "Theirs" adds one line inside the `if` block. The two sides changed different lines, so the text merges cleanly. Whether `log_event` exists is not a textual question: the function was added by an earlier commit on `main`, in another file, and that commit was not picked. Git merges text. It knows nothing about dependencies.
3. **If it had been pushed.** `git revert <the bad backport>` and push. The revert is a new commit, a fast-forward for everyone who has pulled, and the shared branch is not rewritten.
4. **Two correct ways.** (a) Backport the prerequisite first, `git cherry-pick -x 577852f` ("Add structured event logger"), then the follow-up; the smoke test then passes. (b) Adapt the change: pick it with `-n`, remove the call or replace it with something the release has, commit, and say in the message that it differs from the original. For a maintenance release the first question is whether to backport at all: the follow-up adds logging, it fixes nothing. If it is wanted, (a) brings a new module into a maintenance line and (b) creates a variant; both need review as new code.
5. **Right and misleading.** Right: search for the recorded line, `git log --oneline --grep="cherry picked from commit e2a9939" release/1.4`, which finds the copy. Misleading: `git branch --contains e2a9939` lists only `main`, because the release has a copy under another ID. `git cherry -v release/1.4 main` misleads here as well: it marks the fix with `+`, because the release's `MAX_RETRIES` line lies inside the context of the hunk and the two diffs are not identical (section 10.9).

## Lab 10.2: A cherry-pick conflict

1. **Where stage 1 comes from.** From the parent of the picked commit on `main`. By then an earlier commit, "Move to the v2 generate endpoint", had changed the line. The base of a cherry-pick is the picked commit's parent, not anything from your own branch.
2. **The change.** From `post("/v2/generate", prompt, timeout=TIMEOUT_S)` to the same call with `retries=MAX_RETRIES` added. The commit adds one argument. A correct resolution adds that argument to your line and changes nothing else, so `/v1/` stays.
3. **Why `--theirs` is wrong.** `--theirs` takes the whole file as it is in the picked commit. That snapshot contains everything `main` had done to the file up to that point, the move to v2 included. "Theirs" is a snapshot; the fix is a difference between two snapshots.
4. **With `diff3` or `zdiff3`.** The markers would have a third part, between `|||||||` and `=======`, holding the base line (`/v2/generate` without retries) and labelled `parent of ebcee16`. You would see in the file what the commit changed (base against theirs) and where your branch differs (base against ours). `zdiff3` shows the same and moves lines that both sides share at the edges out of the conflict.
5. **For the reviewer.** `git range-diff main~2..main~1 HEAD~1..HEAD` compares the original and the backport as two one-commit series. It reports the pair with `!` and shows that the removed line differs (`/v2/` in the original, `/v1/` in the backport) while the added line is the same: the backport changed the endpoint. Comparing `git show main~1` with `git show HEAD` by eye gives the same information.

## Lab 10.3: Detect duplicates with `git cherry`

1. **What is compared.** For every commit that `main` has and the release lacks, Git computes a patch ID, a hash of the commit's diff with line numbers ignored, and looks for the same patch ID among the commits that the release has and `main` lacks. `-` means an equivalent exists on the release; `+` means none was found.
2. **Why `+`.** That backport ran into a conflict, because the release still calls `/v1/`, and was resolved by hand. Its diff changes a `/v1/` line; the original's diff changes a `/v2/` line. Different diffs give different patch IDs. Patch comparison recognises exact copies only.
3. **A procedure.** (1) `git cherry -v release/1.4 main` gives the candidates: every line marked `+`. (2) For each candidate, search the release for its recorded line: `git log --oneline --grep="cherry picked from commit <full ID>" release/1.4`. A hit means it was backported in adapted form. (3) For candidates without a hit, check by subject and author as well, in case someone backported without `-x`. (4) What remains is missing; decide which of those are fixes that belong on a maintenance line.
4. **Resolving to the existing content.** The index would equal HEAD, so there is nothing to commit. `git cherry-pick --continue` stops with "The previous cherry-pick is now empty, possibly due to conflict resolution" and offers `git commit --allow-empty` or `git cherry-pick --skip`. The message itself is a hint that the change was already there.
5. **Three dots.** `--cherry-mark` compares the commits of one side with the commits of the other side. Two sides exist only in a symmetric difference, `A...B`: commits reachable from either tip and not from both. With two dots there is one side and nothing to compare it with.
