## Lab 30.1: Push protection, and what a push-time check catches

1. The hook lists the commits to be introduced with `git rev-list`, which prints the newest first, and searches the whole tree of each. The tip `3f376a8` did not add `.env`, but its snapshot contains it, because a commit is a full snapshot and nothing had removed the file. The hook reports the first commit in which it finds the pattern. To find the commit that *introduced* the secret you use `git log -S` or `--diff-filter=A`, as GitHub's instructions do when they ask you to identify the earliest commit.
2. An interactive rebase replaces the commit and all its descendants with new commits. Before the push those commits exist only in your clone, so nobody notices. After the push, others have the old commits: the branch needs a force push, their clones still contain the secret, and a pull followed by a push from one of them brings it back (Lab 31.1). More important, a pushed secret is published. The fix is then revocation at the issuer, and a rewrite only if it is warranted.
3. Any two of: reading `git diff --cached` before the commit (acts before the commit, depends on a person); a scanner with generic or entropy-based rules as a pre-commit hook (before the commit, can be skipped) or in CI (after the push, cannot be skipped); a custom pattern in push protection, which needs GitHub Secret Protection (at the push); secret scanning's generic and AI-detected alerts (after the push: passwords are excluded from push protection, so this produces an alert and not a block); a push ruleset that blocks the file path (at the push).
4. Not necessarily. Deleting the branch removed a ref. The commit became unreachable, and GitHub's documentation says such commits can remain accessible by commit ID in cached views; GitHub publishes no retention period. The value is a dummy, so nothing follows from it here. With a real secret the answer would be: revoke.
5. No. Push protection for users stops pushes of recognized secrets to *public* repositories. A private repository is protected at push time only by push protection for repositories, which requires Secret Protection.

## Lab 30.2: A Dependabot configuration

1. Version updates only. Dependabot alerts and security updates are switched on in the repository's or organization's settings; `dependabot.yml` can customize security updates (grouping, for example) but does not enable them.
2. Dependabot alerts for actions are generated only for actions referenced by semantic version, not by commit SHA, so a SHA-pinned action raises no alert when an advisory is published for it. The `github-actions` ecosystem in `dependabot.yml` keeps the pins current through version updates, which is why the pin carries the version as a comment.
3. The options reference says to use `/` for GitHub Actions: Dependabot then searches `/.github/workflows` and an `action.yml` or `action.yaml` in the root directory.
4. It was removed on 8 August 2025. Reviewers of Dependabot pull requests are now determined by CODEOWNERS.
5. A cooldown delays adoption of a release that was published minutes or hours ago. In the supply-chain incidents of the Phase 0 report, malicious package versions were live for a few hours before they were removed (Nx about four hours, LiteLLM about three), so a project that waits a few days does not install them. This reading is an inference from those cases, not a GitHub statement. The default cooldown does not apply to security updates, where waiting has its own cost.

## Lab 30.3: Scan a full history for planted secrets

1. `git log -S` lists the commits in which the number of occurrences of the string changed. In this repository that is the one commit that introduced it, `0805fd8`; there is no commit that removed it. `git grep` over `git rev-list --all` lists the snapshots that contain it: `0805fd8` and every commit made on top of it on any ref, six in all. The first number says where the secret entered. The second says how much of the history serves it.
2. `--all` means every ref under `refs/`. The commit `94cd897` was replaced by an amend, so no ref reaches it; only the reflog of HEAD and of `main` does, and `--reflog` adds those starting points. Even `--reflog` misses objects that nothing names: commits whose reflog entries have expired but that have not been pruned yet, blobs that were staged with `git add` and never committed, and the contents of a dropped stash. `git fsck --unreachable` and `git fsck --lost-found` list those (Chapter 13). No local command sees other people's clones.
3. No. The branch was pushed, so everyone who can fetch the repository can fetch it, and GitHub's secret scanning covers all branches. "Not merged" describes the project's history, not the exposure. It also has no deletion commit, so the token is present at the tip of that branch.
4. A remote-tracking branch records what your clone saw at its last fetch or push. The commit could have reached the server from another clone, on a branch you have not fetched, or on a branch that was deleted since. An empty answer means "my clone has no evidence that it was pushed". The lab closed the gap by asking the server itself (`git -C ../server.git cat-file -t`), which on GitHub corresponds to fetching the commit by ID or to the secret scanning alert.
5. A library of provider patterns, so that you do not need to know the shape in advance; generic and entropy-based detection; verification of candidates against the issuer, which separates live keys from dead ones; baselines and reports across many repositories; and coverage of places that are not Git objects, such as issues and pull request text. The built-in commands are for establishing scope quickly once you know what you are looking for.
