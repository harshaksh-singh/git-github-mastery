# Module 6 lab answers: Divergence and merge

Answers to the "Questions" of each lab in the [Module 6 lab manual](../lab-manual/m06-merge.md). Commit and blob IDs are the ones printed in the manual; merge commits that you created by hand have other IDs. Every statement about behavior was checked on Git 2.55.0 in the lab sandbox.

## Lab 6.1: Predict fast-forward or three-way

1. If the branch is an ancestor of `main`, the merge prints "Already up to date.". If `main` is an ancestor of the branch and not the other way round, the merge fast-forwards. If neither is an ancestor of the other, the branches have diverged and the merge creates a commit with two parents. When both tests succeed, the two names point to the same commit, because `--is-ancestor` treats a commit as an ancestor of itself. That case is "Already up to date." as well.
2. None. A fast-forward rewrites the ref `refs/heads/main` and updates the index and the working tree from objects that already exist. `git count-objects` prints the same number before and after, and so does `git rev-list --count --all`. The true merge that followed added two objects: the merge commit and its top-level tree. It added no blob, because no file needed a content merge.
3. Nothing in the working tree, nothing in the index, and no branch moved. One file in `.git` was rewritten: `ORIG_HEAD`, with the current tip of `main`. Every `git merge` call does that, even one that refuses or reports "Already up to date.".
4. A fast-forward creates no commit, so there is no single commit whose effect `git revert` could undo; the unwanted commits themselves are now the tip of `main`. The two records are `ORIG_HEAD` and the reflog (of HEAD and of `main`). `ORIG_HEAD` is overwritten first: by the next `git merge` call of any outcome, and by rebase, reset and `git am`. Reflog entries stay for 90 days by default (Chapter 13) and exist only in your clone.
5. `git merge --no-ff wip/streaming`, or the setting `merge.ff=false`, would have created a merge commit that is visible in the graph and can be reverted as one unit. `--ff-only` would not have prevented the accident: the merge was a fast-forward, which is exactly what `--ff-only` allows. The real prevention is process: `main` changes only through reviewed pull requests (Chapters 17 and 18).

## Lab 6.3: Rename against edit

1. Nowhere. The merge commit stores a tree, and that tree has one entry for the file, `evalkit/scoring.py`. A rename is an inference that Git makes when it compares two trees and finds a deleted path and an added path with similar content.
2. The similarity index: 100% for the pure rename, 39% for the move with a rewrite. A deleted path and an added path are paired as a rename only at or above the threshold, which is 50% by default (the default documented for `git diff --find-renames`, and used by the merge). `-X find-renames=<n>` changes it for one merge.
3. Because the two sides know the file under different names. The label after each marker names the commit and the path on that side: `HEAD:evalkit/metrics.py` for ours, `refactor/score-objects:evalkit/scoring.py` for theirs.
4. Your whitespace fix. The staged `evalkit/scoring.py` was Ravi's rewrite, which compares `pred == gold` without `strip()`. After `git rm evalkit/metrics.py` the merge would have completed, the branch would count as merged, and the fix would be gone without any message. Only `git show --remerge-diff` on that merge would show the modify/delete conflict and how it was resolved.
5. As run on Git 2.55, `--follow` listed only the side of the merge on which the rename happened: the rename commit and the two commits before it. Your commit `1c21386` is on the other side, where it changed the file under its old name. `git log --oneline -- evalkit/metrics.py evalkit/scoring.py` lists all five commits. The Git 2.56 release notes announce better handling of non-linear history by `--follow`; that was not run here.

No path was changed by both sides, so no file-level merge ran.
2. That the merge commit is exactly the tree that Git computes on its own. No human changed anything while merging. The defect is therefore not a bad resolution. It is a semantic conflict between two changes that are each correct alone.
3. For the amended merge, `git log -p` shows nothing, so the renumbering cannot be reviewed there, but no commit on the first-parent line of `main` fails the check. If the fix goes into the merge, the merge message must say so.
4. `git commit --amend` wrote a new commit object with another tree and a new committer timestamp, and a commit ID is the hash of the commit's content (Chapter 6). The original commit was not changed or deleted. The reflog recorded it as `HEAD@{1}`, which is where `git reset --keep` found it.
5. Running the check on the merge result before it reaches `main`: CI on the pull request's merge commit, together with a rule that the branch is up to date with `main`, or a merge queue (Chapter 18). Locally, `git merge --no-ff --no-commit`, then the check, then the commit.

## Lab 6.6: Audit merges with `--remerge-diff`

1. `67a4d6c`: no output, so the recorded tree equals the mechanical merge. `c3e4310`: a "remerge CONFLICT" line, the marker lines and both candidates removed, and one added line that applies `strip()` and `lower()`: both intents are kept. `60a4fbe`: a "remerge CONFLICT" line, 0.7 kept and 0.0 dropped, and in addition `retries: 3` replaced by `retries: 2` several lines away from the markers: a change that the conflict does not explain. `859b0e3`: no conflict line at all, and `timeout_s` changed from 30 to 300: content that neither branch contains.
2. The mechanical merge already contained `retries: 3`, merged cleanly from the `main` side. The recorded file has `retries: 2`, the value on their side. So the conflict was not resolved by editing the marked region. The whole file was replaced by their version, for example with `git checkout --theirs config/eval.yaml`, and every non-conflicting change from `main` in that file went with it.
3. History simplification. For a log that is limited to a path, when a merge leaves the path identical to one parent, Git follows only that parent. The merge kept their file exactly, so the `main` side, with Ravi's two commits, was pruned from the walk. `--full-history` turns that pruning off.
4. The remerge diff is defined for merges with exactly two parents; the manual says "Remerge two-parent merge commits". An octopus merge has three or more parents and is made by another strategy. The combined diff relies only on comparing the result with every parent, so it works for any number of parents and shows lines that differ from all of them. The `git merge-tree` reconstruction relies on the fact that an octopus merge is only ever created from branches that merge without conflict, so merging them one after the other reproduces the mechanical result.
5. Integrate through pull requests instead of local merges into `main`: a pull request shows the three-dot diff of the branch, so a line changed inside a merge on that branch is reviewed like any other change. Agree that a merge contains only what is needed to resolve conflicts and that everything else is a separate commit. Before a release, read `git log --merges --remerge-diff --first-parent` for the release range.

## Lab 6.7: Abort and retry with `zdiff3`

1. Their side, because the `raise` line appears only in the lower half of the block. The base section proved that the line was already in the common ancestor. Our side replaced it by `return None`; their side only inserted the `UNSURE` branch above it. The resolution therefore keeps their insertion and our replacement. Taking their half as a whole would have brought the `raise` back and undone our commit.
2. `reset: moving to HEAD`. The abort is `git reset --merge`: HEAD does not move, the index is reset to HEAD, and the `MERGE_*` files are deleted. The cleanly merged prompt change disappeared because it was a staged merge result, and resetting staged paths to HEAD is what the command does.
3. Only the text that is written between the markers in the working tree file, and the label of the base section. The three index stages are the input in both cases. `git restore --conflict=zdiff3 evalkit/judge.py`, or the same option with `git checkout`, rewrites that one file from the stages without aborting.
4. Because it was no longer unstaged. `git reset --merge` keeps a file whose working tree content differs from the index, and it resets every path whose index entry differs from HEAD. `git add -A` moved the prompt edit from the first group into the second, where it cannot be told apart from a merge result.
5. From `git merge`. Before a true merge starts on a working tree with local changes, Git 2.55 runs `git stash create` so that it can restore the tree if the merge strategy fails. That command writes a stash-shaped commit and stores it in no ref, so it is not in `git stash list` and only `git fsck` finds it. Do not rely on it for long: an unreachable object can be pruned once its grace period has passed (two weeks by default, Chapter 13). It also exists only if the tree had local changes when the merge started.
6. With `--autostash` the edit was moved into a stash commit before the merge began, referenced by `MERGE_AUTOSTASH`. The working tree was clean during the merge, so `git add -A` staged only merge results, and the abort reset those and then applied the stash ("Applied autostash."). The hint tells you to run `git stash pop` when you are finished. While the merge is open the stash list is empty, and both `git merge --continue` and `git merge --abort` apply the autostash themselves.
