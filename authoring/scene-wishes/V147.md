# Scene wishes for V147: Workflows 1 to 5, line by line

Spots are given as section heading plus the first six words of the paragraph in `video/scripts/V147-*.md`. Every label is copied from the script (step names of workflow 1 from `workflows/01-tests.yml`, which the script reads). The five files were parse-checked, not executed on GitHub: no picture may look like a captured run. Two library scenes are already placed (`ci` for workflow 1 on a push, CONCEPT; `ci` with `result=failed` for the breaking pull request, LIVE TERMINAL DEMO).

## 1. Four ways a green result is false

- **Spot.** HOOK, "An executive says that, and it".
- **Picture.** A large green tick with the sentence "The pipeline is green, so the tests passed and the change is safe to merge." Four cards arrive under it, and with each the tick loses a quarter of its fill.
- **Steps.**
  1. `skipped`: "The job was skipped by its `if`, and a skipped job reports success."
  2. `pipe`: "The failing command was on the left side of a pipe."
  3. `commit`: "The tests ran on a commit that is no longer what will be merged."
  4. `file`: "The run tested the workflow file from the branch, which the author had edited."
  5. `default`: caption "None of these is exotic. Each is a default."
- **Why not today.** No scene for a claim taken apart.

## 2. One reading order for every file

- **Spot.** INTRODUCTION, "Welcome back to Git and GitHub", and again at the start of each of the five workflows in CONCEPT.
- **Picture.** A file card with five rows that fill in the fixed order: "trigger", "permissions", "job and runner", "checkout", "commands". The same card returns for each workflow with that file's values.
- **Steps (workflow 1).** trigger: "pushes to `main`, and pull requests"; permissions: `contents: read`; job and runner: `ubuntu-24.04`, "a ten-minute limit"; checkout: `persist-credentials: false`; commands: "Python 3.13", "The tests".
- **Steps (workflow 3).** trigger: "pushes to `main`, pushes of tags that match `v*`, and manual runs"; checkout: `fetch-depth: 0`; commands: `git describe --tags --always`.
- **Steps (workflow 5).** trigger: "a path filter": "everything under `java-service`, and the workflow file itself"; job: `defaults.run.working-directory` = `java-service`; commands: `mvn -B verify`.
- **Why not today.** `ci` shows a run, not a file being read, and has no permissions or checkout rows.

## 3. Workflow 2: two checks, both report

- **Spot.** CONCEPT, "Then two checks with IDs: `uv".
- **Picture.** A column of steps in one job.
- **Steps.**
  1. `lint-fails`: `uv run ruff check` gets a red cross.
  2. `still-runs`: `uv run ruff format --check` carries the chip `if: !cancelled()` and runs anyway; caption "formatting is checked even when linting failed".
  3. `job-fails`: the job gets a red cross; caption "a failed step fails the job unless `continue-on-error` is set".
  4. `summary`: the last step "appends a Markdown table to the step summary" with the two step outcomes.
- **Why not today.** `ci` with `result=failed` can only fail the last step and stops there.

## 4. Workflow 3: two machines, two strings

- **Spot.** CONCEPT, "`defaults.run.shell: bash`, so pipelines fail properly."
- **Picture.** Two runner boxes side by side.
- **Steps.**
  1. `build`: job `build`; checkout with `fetch-depth: 0`; a step with the ID `describe` runs `git describe --tags --always`.
  2. `output`: that step "appends to `GITHUB_OUTPUT`"; the job "publishes two outputs".
  3. `report`: a second machine, job `report`, with `needs: build` and "no checkout"; two small string chips travel across.
  4. `only`: caption "the only things that reached the second machine are two strings".
- **Why not today.** `ci` draws one job and one runner.

## 5. Workflow 4: one run per ref, and a cache keyed on the lock file

- **Spot.** CONCEPT, "Same trigger and permissions as workflows", then "The setup step has an ID".
- **Picture.** A lane per ref with runs on it; then a key and a cache shelf.
- **Steps.**
  1. `group`: a group chip built from "the workflow name and `github.ref`"; one run in progress.
  2. `cancel`: a new push arrives on the same lane; the run in progress is cancelled (`cancel-in-progress: true`).
  3. `per-pr`: a second lane labelled `refs/pull/N/merge`; caption "each pull request is its own group".
  4. `key`: `cache-dependency-glob: uv.lock`; "a changed lock file gives a new key and a miss, and any other change gives a hit"; read-out `cache-hit`.
- **Why not today.** No scene for concurrency lanes or a keyed store.

## 6. Workflow 5: a filter that creates no check

- **Spot.** CONCEPT, "This is the file with a", then PRODUCTION EXAMPLE, "The diagnosis is the one you".
- **Picture.** A pull request card, a path filter, and a required-check slot.
- **Steps.**
  1. `java`: a pull request that touches `java-service`; the filter passes; a run starts; a check appears.
  2. `readme`: a pull request with "one Markdown file"; the filter stops it; "No run exists, so no check is reported".
  3. `waits`: the required-check slot keeps an amber dashed ring; "the ruleset waits".
  4. `fix`: "require one aggregate job, and filter inside jobs, not on the workflow".
- **Why not today.** `pr: ... blocked` cannot show a check that is absent because no run was created.
