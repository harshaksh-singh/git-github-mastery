# Module 12 lab answers: Recovery

Answers to the "Questions" of each lab in the [Module 12 lab manual](../lab-manual/m12-recovery.md). Commit and blob IDs are the ones printed in the manual; commits that you created by hand have other IDs. Statements about Git's behavior were checked on Git 2.55.0 in the lab sandbox or come from the manual pages and sources that Chapter 13 cites. Retention periods are quoted from the manual: the lab configuration switches time-based reflog expiry off, so they cannot be observed in the sandbox.

## Lab 12.1: An accidental hard reset

1. `ORIG_HEAD`, `HEAD@{1}` and `main@{1}`. After one more reset none of the three names is still correct. `ORIG_HEAD` is overwritten with the tip that the new reset leaves, and both selectors move down by one position (`HEAD@{2}`, `main@{2}`). The entries are still in the reflogs, and the full ID `495f3a9` never changes, which is why you note the ID and not the selector.
2. The branch puts the lost commits on a ref before anything else moves. A ref does not shift, is not overwritten by the next command, and cannot expire. If the next step goes wrong, as in the failure scenario, the anchor is still where you put it. It also lets you inspect the candidate with `git log` before the working tree is rewritten. The cost is one ref that you delete at the end.
3. A mixed reset moves the branch and rebuilds the index and leaves the files alone. The files had the content of `3106f68` the whole time. After `git reset 'HEAD@{1}'`, HEAD and the index were back at that commit, so all three agreed and there was nothing to report.
4. `ORIG_HEAD` held `495f3a9`, written by the bad `git reset --hard HEAD~3`. The commit made afterwards did not update it, because `git commit` does not write `ORIG_HEAD`. Resetting to it restored the old tip and took the new commit `4d74950` off the branch. In the reflog of `main` the entries are named by their messages: `commit: Add MRR metric` is the one to anchor, whatever its position.
5. All commits are recoverable from the reflog. Of the uncommitted edits to `retriever.py`, any version that was staged with `git add` survives as a dangling blob and is found with `git fsck --lost-found`. Edits that were never staged were never hashed, so no object exists and Git cannot return them (Lab 12.8).

## Lab 12.2: A deleted branch

1. The ref `refs/heads/feature/cross-encoder` and its reflog. The ref can be recreated at any time by pointing a branch at `2f65488`. The reflog cannot: the four entries of step 1 are gone, and the new branch starts a new log with the single line `branch: Created from 2f65488`.
2. `git fsck` counts reflog entries as starting points. After step 2 the three commits were still reachable from the HEAD reflog, because HEAD had been on the branch while they were made. The commits of `exp/hard-negatives` were never checked out. Only the remote-tracking ref and its own reflog named them, and the pruning fetch removed both, so nothing reached them and the tip was reported as dangling.
3. A `checkout` entry records the commit HEAD arrived at, here the tip of `main` at that time. The entry below it records the last commit HEAD pointed at while it was on the branch. That is the branch tip unless the branch was moved later without being checked out, for example with `git branch -f feature/cross-encoder <commit>`, `git update-ref`, or a fetch or push that writes into the local branch. Those movements are in the branch's own reflog only, which is deleted with the branch.
4. They were protected by the grace period alone: `gc.pruneExpire`, two weeks by default, measured against the modification time of the objects, which were written when you fetched them. Nothing ends the period by itself. A garbage collection or an automatic maintenance run that finds the objects older than the cut-off deletes them. If the fetch was more than two weeks ago, the next collection may delete them at once.
5. Yes, while her clone existed. She made the commits with the branch checked out, so her HEAD reflog had them, and `git branch -D` printed the tip ID. `git branch exp/hard-negatives <id>` would have restored the branch, for 30 days and until maintenance by default, because the entries were not reachable from any ref. With her clone gone and the server branch deleted, only another clone that had fetched the branch could do it, which is what this lab did. On GitHub the platform adds its own instruments (Chapter 13, section 13.15).

## Lab 12.3: A deleted commit

1. `git reset` (reflog message `reset: moving to <target>`), `git rebase` (one line `rebase (finish): refs/heads/<branch> onto <commit>` in the branch reflog, and `rebase (start)`, `rebase (pick)` and `rebase (finish)` lines in the HEAD reflog), and `git commit --amend` (`commit (amend): <subject>`).
2. A commit ID is a hash over the commit's tree, parents, author, committer and message. The first commit in the todo list kept its parent and everything else, so Git reused the existing commit instead of recreating it. The two commits after the deleted line had to be created on a different parent, and a different parent, with a new committer time, gives a new ID.
3. A commit, `a7061c1`, had been made after the rebase. A reset to the tip from before the rebase would have removed it from the branch, and would have exchanged the rebuilt commits for their old versions for no gain. The cherry-pick added the one missing change and left everything else as it was. Adding is the lower-risk move.
4. The patch ID is computed from the diff of a commit. If the rebased version of a commit has a different diff, `git cherry` cannot pair the two and prints `+`. That happens when a conflict was resolved during the rebase, when the commit was changed with `edit`, or when it was combined with another one by `squash` or `fixup`.
5. A soft reset moves the branch and nothing else. The index and the working tree kept the tree of the amended commit, which is the tree of the old tip plus the typo fix. With the branch back on the old tip, the difference between HEAD and the index was exactly the typo fix, and that is what `git status` showed as staged.

## Lab 12.4: A wrong rebase

1. `git rebase main` replays every commit that is reachable from the branch and not from `main`. For a branch that was cut from `release/1.4`, that set contains the two hotfix commits and also `dc1ff44`, the commit that only the release branch has. Git has no notion of which commits "belong" to a branch (Chapter 7, section 7.9). The replayed copy is `7213db9`; the original is still on `release/1.4`.
2. `hotfix/judge-timeout@{2}`, the entry `commit: Retry judge on timeout` with the ID `eb1f140`. Entry 0 is the commit that was made after the rebase, entry 1 is the `rebase (finish)` line, whose ID is the tip after the rebase, and entry 2 is the value before it. If nothing had been committed since the rebase, the same commit would have been `@{1}`.
3. `--onto rescue/pre-rebase` is the new base on which the commits are recreated. `HEAD~1` is the upstream: every commit reachable from it is left out. The third argument, which is not written, is the branch to rebase and defaults to the current branch. Together: the commits in `HEAD~1..HEAD`, one commit, are replayed onto `rescue/pre-rebase`, and `hotfix/judge-timeout` is moved to the result.
4. `ORIG_HEAD` is correct for exactly one purpose: undoing the reset, merge, rebase or `git am` that wrote it, before another such command runs. In this lab the last command was `git reset --hard`, which wrote the tip it had left, the one that includes the latency commit. In Lab 12.9 the last command was a cherry-pick, which does not write the slot, so it still held a value from an old merge on another branch.
5. The server then holds the wrongly rebased branch, and the repaired branch does not descend from it. Publishing the repair needs `git push --force-with-lease --force-if-includes` (Chapter 12, section 12.8). Before that, tell everyone who may have fetched the rebased version, because their copies will diverge and work based on it must be transplanted in the same way. A pull request against `release/1.4` shows three commits again after the push.

## Lab 12.5: A bad merge

1. `HEAD~1` is the first parent of the tip. After a true merge the tip is the merge commit and its first parent is the previous tip of the branch you were on, so resetting to it removes the merge commit and everything it brought in. After a fast-forward there is no merge commit. The tip is the last commit of the merged branch, and its first parent is the commit before it on that branch, so the reset removes one commit, however many the merge added.
2. `df44d03`. The first reset left `deec1c6` and stored that. The second reset, `git reset --hard ORIG_HEAD`, moved from `df44d03` back to `deec1c6` and stored the commit it left, `df44d03`. Each reset overwrites the slot with the position it moves away from.
3. `--keep` updates the files that differ between the two commits and refuses to run if one of those files has an uncommitted change; changes in other files are carried along. `--hard` overwrites everything. With an uncommitted edit to `system.txt`, which differs between the two commits, `--keep` stops and tells you, while `--hard` destroys the edit without a word. With an uncommitted edit to `loader.py`, which does not differ, `--keep` preserves it and `--hard` destroys it.
4. `git revert`, and for a fast-forward that means reverting the three commits, for example `git revert --no-edit 0529d31..deec1c6`, followed by an ordinary push. For a merge commit it is `git revert -m 1 <merge>`. The later problem is the re-merge: when the experiment is finished and merged again, Git considers the reverted commits already merged and brings in only what was added since, so the team must revert the revert first (Chapter 11, section 11.9).
5. `merge.ff=false`, or `--no-ff` on the command line, forces a merge commit even when a fast-forward is possible. With a merge commit, `HEAD~1` is the previous tip of `main`, and the recipe would have been correct. `merge.ff=only` would not have helped: this merge was a fast-forward.

## Lab 12.6: Commits on the wrong branch

1. It is defined by state, not by counting: "what `main` has and the server does not". It is right for one misplaced commit and for seven, and it does not depend on which branch is checked out. `HEAD~2..HEAD` is right only if you counted correctly and are on `main`.
2. `git branch feature/pdf-tables`, which creates the branch at the current commit with both commits on it, and `git reset --keep origin/main`, which moves `main` back. No commit has to be copied, because the new ref names the commits where they are.
3. Each `-` says that a commit reachable from the old tip of `main` has an equivalent on `feature/pdf-tables`: a commit with the same change, by patch ID. The content of the original is therefore preserved on the feature branch, and the original can be abandoned.
4. The reflog, layer 2: `main@{1}` and the matching entries of the HEAD reflog. With default settings those entries fall under the 30-day rule, because the commits are not reachable from the tip of `main` or of any other ref. After that, the next maintenance run removes the entries, and the objects are deleted by a collection once they are older than the grace period.
5. Others may have fetched the commits. Moving a shared branch backwards requires a force push and leaves every clone that already has the commits ahead of the server, from where an ordinary push brings them back. Copy the commits to the feature branch with `git cherry-pick`, undo them on `main` with `git revert`, and push normally.

## Lab 12.7: Lost work in detached HEAD

1. A branch reflog records changes of that branch's ref. In detached HEAD no branch is current, and a commit updates HEAD itself. Only the HEAD reflog has an entry.
2. The default starting points of `git fsck` include every reflog, and the HEAD reflog reaches both lines. The silence tells you that the commits were on layer 2: protected until their reflog entries expire, which is 30 days by default for commits that no ref reaches, and in no danger from a collection before that.
3. Its message names a full 40-digit commit ID where a branch name would be: `checkout: moving from 266d3b2a96a6... to main`. HEAD had no branch to leave, so Git recorded the commit.
4. `git fsck` reports dangling objects, which are tips: unreachable objects that no other object refers to. `266d3b2` refers to its parent `ba8c3d9`, so the parent is unreachable and not dangling. Three commits were lost, on two lines, and each line has one tip.
5. A cherry-pick applies the change between a commit and its parent. `266d3b2` modifies `validate.py`, a file that its parent `ba8c3d9` created and that does not exist on `main`. Git cannot apply a modification to a file that is absent on your side and reports a modify/delete conflict. You could have seen it with `git log --oneline v1.2.0..hotfix/1.2.1`, which lists two commits, or by comparing `git show --stat 266d3b2` with the files on `main`.

## Lab 12.8: Overwritten changes and a cleared stash

1. `sweep.yaml` was staged twice. The first `git add` wrote `0697c1f`, the second wrote `e199091` and replaced the index entry, which left the first blob without a reference even before the reset. Every `git add` is a checkpoint: the content at that moment is in the object database and can be found until a collection prunes it.
2. A blob stores content and nothing else. File names are stored in trees and in index entries. No commit was made, so no tree has the name, and the reset removed the index entry. `git fsck --lost-found` can only name the file after the blob's ID.
3. `git clean -f`. Git would have had no object for it: an untracked file is never hashed. `git stash -u` would have been the way to put it into the object database first.
4. The default message of a stash entry is `WIP on <branch>: <id> <subject>`, which contains "WIP". An entry made with `git stash push -m` is named `On <branch>: <message>` and does not match the filter. `--merges` works because a stash entry is a commit with two or three parents, while the commits that amends, rebases and resets leave behind have one. An abandoned real merge commit would also be listed.
5. `git stash store` appends a line to the reflog of `refs/stash` and points the ref at the commit, so the entry stored last is `stash@{0}`. In the original list the "lora" entry was the newest. Storing the older entry `a0cbbaf` first and `0b0c40d` second reproduces that order. The position is decided by the order of the reflog lines, not by the dates of the commits.

## Lab 12.9: A wrong cherry-pick

1. The HEAD reflog and the reflog of `release/2.1`, each with the line `cherry-pick: Add per-tenant quotas`. It did not write `.git/ORIG_HEAD`.
2. The fast-forward merge of `feature/quotas` into `main`, which the setup script performed before you entered the sandbox. `git merge` stored the previous tip of `main`, `f028350`. Nothing that ran afterwards writes the slot: not the switch to `release/2.1`, not the commit on it, not the cherry-pick.
3. `git log --oneline` shows three commits and they are the history of `main`; "Pin dependencies for 2.1" is missing. `requirements.txt` is missing from the working tree. The tip has the ID `f028350`, the same ID as the commit on `main`, where a backport would have a new ID and a `(cherry picked from commit ...)` line. The reflog of the branch has the line `reset: moving to ORIG_HEAD` directly above the wrong pick.
4. It records which commit of `main` the backport came from. A reviewer can compare that ID with the fix that was requested, and would have caught this mistake: the line named `cad5d75`, the quota feature. Later, anyone who audits the release can map each backport to its source.
5. `git revert <the wrong pick>`, then `git cherry-pick -x main~1`, then an ordinary push. The release branch then shows three commits on top of "Pin dependencies for 2.1": the wrong pick, its revert, and the fix. Nothing is rewritten, and the commit that was deployed still exists under its ID.

## Lab 12.10: Broken remote-tracking state, and a corrupt index

1. `git status` compares two local refs, `refs/heads/main` and `refs/remotes/origin/main`, and uses no network. Someone had set the second to the value of the first. `git push` contacts the server and compares with the server's real `main`, which had a commit you did not have.
2. That the ref was written by plumbing, `git update-ref` without `-m`, and not by a transfer. A fetch writes `fetch: fast-forward` or `fetch: forced-update`, a pull writes `pull: ...`, and a push writes `update by push`.
3. The failed fetch had already received the pack with the server's new commit `e275388` when it stopped at the unreadable ref. No ref had been updated, so nothing reached the commit and it was dangling. The successful fetch set `origin/main` to that commit, which made it reachable.
4. Remote-tracking refs are rebuilt from the server: `git fetch` writes them from the refs the server advertises. Nothing of value is lost, apart from the old reflog entries if you delete those too. The index is rebuilt from the tree of HEAD by `git reset`. What is lost is the staging state: which changes had been staged, and any staged content that differed from the file on disk, which survives only as a dangling blob.
5. Moving the file keeps the evidence and keeps the step reversible. `git reset` writes only the index. `git reset --hard` would also overwrite the working tree with HEAD, and the working tree held the only copy of both edits.

## Lab 12.11: A force push, seen from the local side

1. The `+` at the start of the line and the words `(forced update)`; the three dots in `d8a3934...882b940` say the same. The default fetch refspec is `+refs/heads/*:refs/remotes/origin/*`, and the leading `+` permits updates that are not fast-forwards (Chapter 12, section 12.4). A remote-tracking ref has to follow the server wherever it goes.
2. The previous value of your ref `refs/remotes/origin/main`: what your clone believed the server's `main` to be before this fetch, `d8a3934`. It is a line in your local file `logs/refs/remotes/origin/main`. The server is a bare repository without `core.logAllRefUpdates`, so it keeps no reflog, and reflogs are never transferred between repositories.
3. `git push --force-with-lease=main:882b940 origin d8a3934:main`. It sets the server's branch back to the old tip and removes the forced commit from it, and the explicit lease makes it fail if anyone has pushed in the meantime. Choose it when the forced commit must not stay on the branch, for example when the force push replaced or rewrote history, and agree with its author first, who then re-applies the change on top.
4. A rebase would recreate `2a2bf94` and `d8a3934` on top of `882b940` with new IDs. Asha's clone still has the original `2a2bf94`. After her next merge the same change would be in the history twice (Chapter 9, section 9.15), and every record that quotes the old IDs would point at commits that are no longer on the branch. The merge kept the IDs that already existed elsewhere.
5. None of the local ones. Her reflog of `origin/main` begins with the clone, at the forced value, and her `main` never held the lost commits. For her the only sources are other people's clones and the host's own records. After the repair an ordinary fetch gives her everything.

## Lab 12.12: Prove the point of no return

1. `git branch rescue/ttl 833b96f`, or any other command that points a ref at the commit. You needed the ID. If you had not noted it, `git fsck` printed it as a dangling commit.
2. The commit `833b96f`, its tree, the blob of `ttl.yaml`, and the blob `3d7644e`, the staged file that the reset had thrown away.
3. That `ORIG_HEAD` is not a starting point for garbage collection: an object that only `ORIG_HEAD` names is deleted. It also shows that nothing validates or tidies the file. A name in `ORIG_HEAD` is a convenience for the next command, not a protection.
4. A fetch transfers what is needed to complete the commits you ask for, and it decides that by comparing commits. Both repositories had the same commits, so there was nothing to send. `git pack-objects` was given the ID of the object itself and wrote a pack that contains it, and `git unpack-objects` stored it as a loose object. Because an ID is computed from content, the teammate's object is identical to the one that was deleted.
5. A bundle, like a clone or a fetch, carries the objects that are reachable from the refs it lists. The commit was reachable from `refs/heads/main` when the bundle was written. The staged blob was reachable from the index only, and the index is not a ref.
6. Two events. First, the reflog entries that name the commit must be removed, which the default configuration allows once they are 30 days old, because the commit is not reachable from the tip of any ref; that happens when a collection or the automatic maintenance next runs. Second, a collection must find the objects unreachable and older than `gc.pruneExpire`, two weeks by modification time; for objects that have not been touched since they were written, that can be the same run. So: not earlier than about 30 days, and only when maintenance runs after that.
