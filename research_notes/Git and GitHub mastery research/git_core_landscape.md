# Git core landscape as of 1 October 2026 (Git the tool, not the GitHub platform)

Research date: 2026-10-01. Conventions used throughout these notes:

- Labels: **[STABLE FUNDAMENTAL]** (unchanged for many years, safe to teach as bedrock), **[CURRENT BEHAVIOR]** (true in Git 2.55/2.56 today), **[VERSION-SPECIFIC]** (tied to a named version), **[DEPRECATED/OUTDATED]** (older practice or removed/discouraged feature). **UNVERIFIED** marks anything not confirmed from an authoritative source.
- Man-page facts were read from the AsciiDoc sources at the release tags `v2.56.0` and `v2.55.0` of the official repository (github.com/git/git). Rendered equivalents live at `https://git-scm.com/docs/<page>` (spot-checked: git-switch and BreakingChanges render the same text). Release-note facts were read from `Documentation/RelNotes/*.adoc` on `master`.
- "(=2.55)" means the cited documentation file is byte-identical at v2.55.0 and v2.56.0, so the statement holds on the learner's machine. "2.56-only" means it is absent in 2.55.0.
- "Local check" means reproduced on the learner's machine (Homebrew `git version 2.55.0`, macOS 26.5.2) on 2026-10-01 with `GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_NOSYSTEM=1` so that only built-in defaults applied. Local checks are supplementary; the URL beside them is the documentary source.
- "Introduced in X (tag check)" means the feature's documentation is present at tag vX.0 and absent at the preceding feature-release tag.
- lore.kernel.org and LWN's mail archive were behind bot protection during this research; mailing-list messages were read through the public mirror ratatoskr.run, so Message-IDs are mostly missing.

## 1. Latest stable release, release cadence, headline changes 2.45 → 2.56, and versions shipped by platforms

### Takeaway
The latest stable Git on 1 Oct 2026 is **2.56.0, released 28 Sep 2026**; the learner's **2.55.0 (29 Jun 2026) is exactly one feature release behind and has no newer 2.55.x maintenance release**, so it is current for everything except a handful of 2.56-only additions (`git add --resolved`, `git history drop`, `git refs create/delete/update/rename`, `git branch --delete-merged`, `git replay --linearize`, `git bisect --reset-when-found`). Platform-bundled Gits lag far behind (Apple 2.50.1, Ubuntu 24.04 2.43.0, Debian 13 2.47.3), which matters for any lesson using post-2024 syntax.

**Cadence and version naming**
- [STABLE FUNDAMENTAL] "One release cycle for a feature release is expected to last for eight to ten weeks. A few "release candidate" releases are expected to be tagged about a week apart before the final release". — [howto/maintain-git.adoc @v2.56.0](https://github.com/git/git/blob/v2.56.0/Documentation/howto/maintain-git.adoc)
- [CURRENT BEHAVIOR] The maintainer wrote on 2026-09-06: "our typical development cycle lasts between 8 and 12 weeks". The twelve releases above are 9 to about 13.5 weeks apart. — [mailing-list mirror, "What will come after Git 2.56?"](https://ratatoskr.run/git/2026/09/17520163/t); [kernel.org listing](https://mirrors.edge.kernel.org/pub/software/scm/git/)
- [STABLE FUNDAMENTAL] Feature releases are named with two numbers (e.g. "2.53") and tagged with a trailing ".0" ("v2.53.0"); maintenance releases increment the third number (e.g. "2.47.1"). — [MaintNotes on the todo branch](https://github.com/git/git/blob/todo/MaintNotes)

**Headline changes per feature release (official release notes; blog posts listed as secondary reading)**
- [VERSION-SPECIFIC] **2.45**: reftable integrated as a ref backend ("With "git init --ref-format=reftable" ..."); "Work to support a repository that work with both SHA-1 and SHA-256 hash algorithms has started"; `git reflog list`; `git cherry-pick --empty` with "a soft deprecation of `--keep-redundant-commits`"; `git config --comment=<message>`; `git pack-refs --auto`; `core.commentChar` may be multi-byte. — [RelNotes 2.45.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.45.0.adoc); secondary: [GitHub highlights 2.45](https://github.blog/open-source/git/highlights-from-git-2-45/)
- [VERSION-SPECIFIC] **2.46**: "The operation mode options (like "--get") the "git config" command uses have been deprecated and replaced with subcommands (like "git config get")"; "A new command has been added to migrate a repository that uses the files backend for its ref storage to use the reftable backend, with limitations" (`git refs migrate`); credential-helper protocol extended beyond username/password; global `--no-advice`; "The "--heads" option of "ls-remote" and "show-ref" has been deprecated; "--branches" replaces "--heads""; symbolic-ref updates inside ref transactions. — [RelNotes 2.46.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.46.0.adoc); secondary: [GitHub highlights 2.46](https://github.blog/open-source/git/highlights-from-git-2-46/)
- [VERSION-SPECIFIC] **2.47**: ""git pack-redundant" has been marked for removal in Git 3.0"; default object hash and ref backend "can be configured in the user's global and system wide configuration" (`init.defaultObjectFormat`, `init.defaultRefFormat`); `git for-each-ref` atom `%(is-base:<commit>)`; "Incremental updates of multi-pack index files is getting worked on"; `git mergetool` learned VSCode. — [RelNotes 2.47.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.47.0.adoc); secondary: [GitHub highlights 2.47](https://github.blog/open-source/git/highlights-from-git-2-47/)
- [VERSION-SPECIFIC] **2.48**: "Describe the policy to introduce breaking changes" (the BreakingChanges document); `git fetch` creates a missing `refs/remotes/<remote>/HEAD` and honors `remote.<remote>.followRemoteHEAD`; `git range-diff --diff-merges`; worktree linkage can "Use relative paths" plus "a new repository extension to prevent older Git versions from mis-interpreting worktrees created with relative paths"; `git rebase --rebase-merges` "now uses branch names as labels when able". — [RelNotes 2.48.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.48.0.adoc); secondary: [GitHub highlights 2.48](https://github.blog/open-source/git/highlights-from-git-2-48/)
- [VERSION-SPECIFIC] **2.49**: ""git backfill" is introduced to help bulk-download necessary files beforehand" for blobless clones; `git pack-objects`/`git repack` "learned an option to use an alternative path-hash function" (`--name-hash-version`); `git clone` can "make a shallow clone for a single commit that is not necessarily be at the tip of any branch" (`--revision`); `git gc --expire-to`; `help.autocorrect = 1` now means run the correction immediately; "Foreign language interface for Rust into our code base has been added"; "All the documentation .txt files have been renamed to .adoc". — [RelNotes 2.49.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.49.0.adoc); secondary: [GitHub highlights 2.49](https://github.blog/open-source/git/highlights-from-git-2-49/)
- [VERSION-SPECIFIC] **2.50**: "Remove remnants of the recursive merge strategy backend, which was superseded by the ort merge strategy"; ""git reflog" learns "drop" subcommand"; ""git maintenance" learns a new task to expire reflog entries" and gc clean-up tasks became maintenance tasks; `git repack --combine-cruft-below-size`; "Incrementally updating multi-pack index files"; `git cat-file --batch` accepts `--filter=`; "A post-processing filter for "diff --raw" output has been introduced" (`git diff-pairs`); `git merge-tree` can check for a clean merge without writing a result. — [RelNotes 2.50.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.50.0.adoc); secondary: [GitHub highlights 2.50](https://github.blog/open-source/git/highlights-from-git-2-50/)
- [VERSION-SPECIFIC] **2.51**: ""git switch" and "git restore" are declared to be no longer experimental"; `git whatchanged`: "Plan to deprecate and remove it"; stash import/export ("An interchange format for stash entries is defined"); "The reftable ref backend has matured enough; Git 3.0 will make it the default format"; "Flipping the default hash function to SHA-256 at Git 3.0 boundary is planned"; `git merge/pull --compact-summary`; `pull.autoStash`; `git for-each-ref --start-after`; `git pack-objects --path-walk`. — [RelNotes 2.51.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.51.0.adoc); secondary: [GitHub highlights 2.51](https://github.blog/open-source/git/highlights-from-git-2-51/)

### Inferences
- Because no 2.52.x–2.55.x maintenance release was ever tagged, "latest patch level" is not a concern for the learner: 2.55.0 is the only 2.55 there is. Upgrading with `brew upgrade git` would move straight to 2.56.0.
- A course written against 2.55/2.56 will break on stock platform Gits in specific, predictable places: `git config set/get/list` needs ≥ 2.46 (Ubuntu 24.04's 2.43 lacks it); reftable needs ≥ 2.45; `git backfill` ≥ 2.49; `git last-modified`/`git repo` ≥ 2.52; `git history` ≥ 2.54. Apple's 2.50.1 still labels `git switch`/`git restore` as experimental (label removed in 2.51). Lessons should state the minimum version beside each newer command.
- The observed cadence (roughly four to five feature releases a year, 9–13 weeks apart) is slightly slower than the "eight to ten weeks" in the maintainer how-to; the maintainer's own 2026 wording ("8 and 12 weeks") is the better description.

### Gaps
- No GitHub "Highlights from Git 2.53" post was found (the expected URL returns HTTP 404); GitLab posts for 2.50 and 2.51 are also missing at the usual URL pattern. Only the official release notes were used for those versions.
- Which Xcode releases bundle Apple Git-155 was not verified; only the learner's own Command Line Tools (26.6) and Apple's source tags were checked.
- Quotes from the 2.56.0 announcement were read via LWN's copy, not lore.kernel.org (bot-protected).

## 2. Git 3.0: status and timeline

### Takeaway
**Git 3.0 has not been released and the official BreakingChanges document still says "There is no planned release date for this breaking version yet."** What is new as of late September 2026 is the maintainer's statement that the next release will be numbered **2.98** (end of 2026), followed by **2.99**, "in preparation for Git 3.0"; calendar months for 2.99/3.0 (spring 2027) come only from secondary reports.

### Cited Findings

**Status**
- [CURRENT BEHAVIOR] "The following subsections document upcoming breaking changes for Git 3.0. There is no planned release date for this breaking version yet." The file is byte-identical at v2.55.0, v2.56.0 and on `master` on 2026-10-01; the same sentence is still present on the unreleased integration branches `next` and `seen`. — [BreakingChanges.adoc @v2.56.0](https://github.com/git/git/blob/v2.56.0/Documentation/BreakingChanges.adoc); rendered: [git-scm.com/docs/BreakingChanges](https://git-scm.com/docs/BreakingChanges)
- [STABLE FUNDAMENTAL] Previous breaking releases were "Git 1.6.0, released in August 2008" and "Git 2.0, released in May 2014"; "The release cadence of breaking versions is typically measured in multiple years." — [BreakingChanges.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/BreakingChanges.adoc)
- [CURRENT BEHAVIOR] Breaking changes are guarded by a compile-time switch `WITH_BREAKING_CHANGES`; "When built with it, the resulting Git binary together with its documentation would behave as if these breaking changes slated for the next big version boundary are already in effect." — [BreakingChanges.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/BreakingChanges.adoc)
- [VERSION-SPECIFIC] Maintainer, 2026-09-28, "What's cooking in git.git (Sep 2026, #10)": "Git 2.56 has been tagged. As usual, we will slow down for a week and fix any brown paper bag bugs if needed, and then open the tree for the next cycle. As discussed at the Git Contributors' Summit, the version will be Git 2.98, scheduled near the end of this year, to be followed by Git 2.99 that will come after that to solidify the codebase in preparation for Git 3.0." — [mailing-list mirror](https://ratatoskr.run/git/2026/09/17654892)
- [VERSION-SPECIFIC] The question was opened by the maintainer on 2026-09-06 with four options: "(1) Git 3.0 ... (2) Git 2.99 ... (3) Git 2.98 (or 2.97): we admit that we are not ready for even (2) and chicken out, leaving us breathing room for a few more preparatory releases before the big one. (4) Git 2.57: doing business as usual", adding "this is not a popularity contest, nor is it even a democracy." — [mailing-list mirror](https://ratatoskr.run/git/2026/09/17520163/t)
- [VERSION-SPECIFIC] The Contributor's Summit was announced for Friday 18 September 2026 in Lisbon, alongside Git Merge (the maintainer's 28 September message refers back to it as having taken place). — [mailing-list mirror, "[ANNOUNCE] Git Contributor's Summit 2026"](https://ratatoskr.run/git/2026/09/17533167/t)
- [VERSION-SPECIFIC] Secondary reports of dates: LWN (update appended to an 18 Sep 2026 article): "Update: at Kernel Recipes, Steinhardt described the plan that had been agreed to regarding releases. The December 2026 release will be called 2.98, as a signal that the 3.0 transition is coming. The 2.99 release will follow in April 2027; that will be a long-term-support release. Git 3.0 will also be released at the same time, and will be the base for all subsequent releases." GitLab's 2.56 post gives a schedule table (2.56 "September 2026 (this release)", 2.98 "December 2026", "2.99 and 3.0" "Spring 2027") and says: "The plan is to jump straight from 2.56 to 2.98; this significant jump serves as an indication to both downstream maintainers and consumers that a big change is coming. After that, both 2.99 and 3.0 will be shipped together, the only difference being that Git 3.0 will have the breaking changes feature flag flipped", and "The 2.99 release will be an LTS release so that platforms without a Rust toolchain continue to get updates." — [LWN "Looking forward to Git 2.56 — and 3.0"](https://lwn.net/Articles/1094575/); [GitLab "What's new in Git 2.56.0"](https://about.gitlab.com/blog/whats-new-in-git-2-56-0/)
- [VERSION-SPECIFIC] Official LTS wording: "The Git project will declare the last version before Git 3.0 to be a long-term support release. This long-term release will receive important bug fixes for at least four release cycles and security fixes for six release cycles." — [BreakingChanges.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/BreakingChanges.adoc)

**Planned changes of defaults (BreakingChanges "Changes")**
- [VERSION-SPECIFIC] "The default hash function for new repositories will be changed from "sha1" to "sha256"." Requirement: "that the ecosystem is ready to support the "sha256" object format. This includes popular Git libraries, applications and forges." And: "There is no plan to deprecate the "sha1" object format at this point in time." — [BreakingChanges.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/BreakingChanges.adoc)
- [VERSION-SPECIFIC] "The default storage format for references in newly created repositories will be changed from "files" to "reftable"." Prerequisite: "alternative implementations of Git like JGit, libgit2 and Gitoxide need to support it." — [BreakingChanges.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/BreakingChanges.adoc)
- [VERSION-SPECIFIC] "In new repositories, the default branch name will be `main`. ## 3. SHA-1 versus SHA-256 object formats

### Takeaway
SHA-1 (hardened by collision detection since 2.13) is still the default in 2.56; SHA-256 repositories are a supported, non-experimental format since 2.42 but **cannot interoperate with SHA-1 repositories**, and hosting support remains the bottleneck: GitHub has no publicly available SHA-256 support as of 1 Oct 2026 (a private beta is reported), GitLab's is labelled experimental, Forgejo supports it.

### Cited Findings
- [CURRENT BEHAVIOR] `git init --object-format=<format>`: "Specify the given object `<format>` (hash algorithm) for the repository. The valid values are `sha1` and (if enabled) `sha256`. `sha1` is the default." (=2.55) — [git-init.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-init.adoc)
- [CURRENT BEHAVIOR] Disclaimer included in that man page: "Note: At present, there is no interoperability between SHA-256 repositories and SHA-1 repositories. Historically, we warned that SHA-256 repositories may later need backward incompatible changes when we introduce such interoperability features. Today, we only expect compatible changes. Furthermore, if such changes prove to be necessary, it can be expected that SHA-256 repositories created with today's Git will be usable by future versions of Git without data loss." (=2.55) — [object-format-disclaimer.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/object-format-disclaimer.adoc)
- [CURRENT BEHAVIOR] Local check (2.55.0): `git init --object-format=sha256` writes `extensions.objectformat=sha256` and `core.repositoryformatversion=1`; `git rev-parse --show-object-format` prints `sha256`; commit and tree IDs are 64 hex digits. Documentary source: `extensions.objectFormat` — "Specify the hash algorithm to use. The acceptable values are `sha1` and `sha256`. If not specified, `sha1` is assumed ... Trying to change it after initialization will not work and will produce hard-to-diagnose issues." — [config/extensions.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/extensions.adoc)
- [CURRENT BEHAVIOR] The default can be set with `init.defaultObjectFormat` (introduced in 2.47, tag check) or the `GIT_DEFAULT_HASH` environment variable; `GIT_DEFAULT_HASH` "is ignored when cloning and the setting of the remote repository is always used. The default is "sha1"." — [config/init.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/init.adoc); [git.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git.adoc)
- [VERSION-SPECIFIC] History: 2.29 — "The recent addition of SHA-256 support is marked as experimental in the documentation" and "there is no interoperability between SHA-1 and SHA-256 repositories yet"; 2.42 — "Tone down the warning on SHA-256 repositories being an experimental curiosity ... at this point, we do not plan to make breaking changes to SHA-256 repositories". — [RelNotes 2.29.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.29.0.adoc); [RelNotes 2.42.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.42.0.adoc)
- [VERSION-SPECIFIC] Interoperability work is in progress, not usable: 2.45 "Work to support a repository that work with both SHA-1 and SHA-256 hash algorithms has started"; 2.52 "The beginning of SHA1-SHA256 interoperability work"; 2.54 "The code to maintain mapping between object names in multiple hash functions is being added, written in Rust." The extension `compatObjectFormat` carries the warning: "the functionality enabled by this extension is incomplete and subject to change. It currently exists only to allow development and testing of the underlying feature and is not designed to be enabled by end users." — [RelNotes 2.45.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.45.0.adoc); [RelNotes 2.52.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.52.0.adoc); [RelNotes 2.54.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.54.0.adoc); [config/extensions.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/extensions.adoc)
- [VERSION-SPECIFIC] **SHA-1DC**: Git 2.13 — "The "detect attempt to create collisions" variant of SHA-1 implementation by Marc Stevens (CWI) and Dan Shumow (Microsoft) has been integrated and made the default." The transition document says: "Git v2.13.0 and later subsequently moved to a hardened SHA-1 implementation by default, which isn't vulnerable to the SHAttered attack, but SHA-1 is still weak." — [RelNotes 2.13.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.13.0.adoc); [technical/hash-function-transition.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/technical/hash-function-transition.adoc)
- [CURRENT BEHAVIOR] Build default: "If don't enable any of the *_SHA1 settings in this section, Git will default to its built-in sha1collisiondetection library, which is a collision-detecting sha1 This is slower, but may detect attempted collision attacks." Local check: `git version --build-options` on the learner's 2.55.0 prints `SHA-1: SHA1_DC`, `SHA-256: SHA256_BLK`, `default-hash: sha1`, `default-ref-format: files`. — [Makefile @v2.56.0](https://github.com/git/git/blob/v2.56.0/Makefile)
- [STABLE FUNDAMENTAL] Why move: the BreakingChanges list of SHA-1 attacks — "The SHAppening (2015) ... SHAttered (2017). Generation of two valid PDF files with 2^63 operations ... Birthday-Near-Collision (2019) ... Shambles (2020)" — and "it is only a matter of time before SHA-1 will be considered broken completely." — [BreakingChanges.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/BreakingChanges.adoc)
- [STABLE FUNDAMENTAL] On-disk formats are parameterised by hash: "In a repository using the traditional SHA-1, pack checksums, index checksums, and object IDs (object names) mentioned below are all computed using SHA-1. Similarly, in SHA-256 repositories, these values are computed using SHA-256." — [gitformat-pack.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/gitformat-pack.adoc)
- [CURRENT BEHAVIOR] **Forgejo**: "Git repositories using SHA-256 are supported" since v7.0 (23 April 2024), with the caveat "As of Forgejo 7.0.2 some features are still unreliable when using SHA-256." — [Forgejo v7.0 release post](https://forgejo.org/2024-04-release-v7-0/)
- [CURRENT BEHAVIOR] **GitLab**: SHA-256 project creation announced 19 Aug 2024 under "Experimental settings", described as "experimental and should only be used to create test projects". GitLab's 28 Sep 2026 post says "GitLab has been supporting SHA-256 since a year ago". — [GitLab blog, Aug 2024](https://about.gitlab.com/blog/gitlab-now-supports-sha256-repositories/); [GitLab "What's new in Git 2.56.0"](https://about.gitlab.com/blog/whats-new-in-git-2-56-0/)
- [CURRENT BEHAVIOR] **GitHub**: no public SHA-256 repository support was found as of 2026-10-01. GitLab's 2.56 post states "GitHub has announced a private beta at Git Merge with general availability following in a few months." The long-running GitHub community discussion contains no staff announcement; a community comment dated 2026-09-21 quotes a slide from brian m. carlson's talk repository (`bk2204/talk-rust-in-git`, linked with a 64-hex-digit commit ID): "This is a SHA-256 repository / SHA-256 now in private preview / SHA-256 repository creation not yet publicly available, but it's coming". Another commenter in the same thread notes that GitHub "doesn't allow natively creating sha256 repos yet". On the Git list (2026-09-07) contributors called GitHub "the biggest question mark". LWN (18 Sep 2026): "GitLab has had support since 2024, and Forgejo has support as well. The elephant that is still missing from this room, though, is GitHub". — [GitLab "What's new in Git 2.56.0"](https://about.gitlab.com/blog/whats-new-in-git-2-56-0/); [GitHub community discussion 12490](https://github.com/orgs/community/discussions/12490); [mailing-list mirror](https://ratatoskr.run/git/2026/09/17520163/t); [LWN article](https://lwn.net/Articles/1094575/)

### Inferences
- Teach SHA-256 as "real, stable on disk, but an island": a SHA-256 repository can only exchange objects with other SHA-256 repositories, and cloning always adopts the remote's format. For a course built around GitHub remotes, every exercise repository must stay SHA-1 until GitHub's support is publicly available.
- "Git uses SHA-1" needs the qualifier "collision-detecting SHA-1 (SHA-1DC) by default since 2.13" and "40-hex object IDs are a property of SHA-1 repositories, not of Git"; tools and regexes that assume 40 hex digits will break on SHA-256 repositories.

### Gaps
- No official GitHub blog, changelog or docs page announcing SHA-256 support was found; the "private beta/preview" is known only from GitLab's blog and a community comment quoting a GitHub employee's conference slide. Status: reported, **UNVERIFIED from GitHub's own channels**; public creation of SHA-256 repositories on GitHub was not available as of 2026-10-01 according to those same sources.
- GitLab's current documentation page for SHA-256 projects was not located; whether the feature left "experimental" status by October 2026 is **UNVERIFIED**.
- The exact error shown when pushing a SHA-256 repository to a SHA-1-only host was not reproduced.

## 4. The reftable backend

### Takeaway
reftable is a binary, block-structured ref (and reflog) store available since 2.45, opt-in today via `git init --ref-format=reftable`, `init.defaultRefFormat`, or `git refs migrate`, and slated to become the default for new repositories in 3.0. In a reftable repository `.git/refs/` and `packed-refs` no longer hold refs, so "look at the file under `.git/refs/heads/`" stops being true.

### Cited Findings
- [VERSION-SPECIFIC] Introduced in 2.45: "Integrate the reftable code into the refs framework as a backend. With "git init --ref-format=reftable", hopefully it would be a lot more efficient to manage a repository with many references." — [RelNotes 2.45.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.45.0.adoc)
- [CURRENT BEHAVIOR] Valid ref formats: "`files`;; for loose files with packed-refs. This is the default. `reftable`;; for the reftable format." (the default flips when built with breaking changes) (=2.55). — [ref-storage-format.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/ref-storage-format.adoc); [git-init.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-init.adoc)
- [CURRENT BEHAVIOR] Defaults for new repositories can be set with `init.defaultRefFormat` (2.47, tag check) or `GIT_DEFAULT_REF_FORMAT` ("The default is "files"."); `git clone` also accepts `--ref-format=<ref-format>`. — [config/init.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/init.adoc); [git.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git.adoc); [git-clone.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-clone.adoc)
- [CURRENT BEHAVIOR] Existing repositories: `git refs migrate --ref-format=<format> [--no-reflog] [--dry-run]` — "Migrate ref store between different formats." Known limitations: "It is not possible to migrate repositories that have worktrees" and "There is no way to block concurrent writes to the repository during an ongoing migration ... If your repository is registered for scheduled maintenance, it is recommended to unregister it first". (2.46 for the command; `--no-reflog` in 2.49.) — [git-refs.adoc @v2.55.0](https://github.com/git/git/blob/v2.55.0/Documentation/git-refs.adoc); [RelNotes 2.46.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.46.0.adoc); [RelNotes 2.49.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.49.0.adoc)
- [CURRENT BEHAVIOR] On-disk layout: "A collection of reftable files are stored in the `$GIT_DIR/reftable/` directory"; "The stack ordering file is `$GIT_DIR/reftable/tables.list`"; "Log-only files use the `.log` extension, while ref-only and mixed ref and log files use `.ref`". For backward compatibility "a reftable-enabled repository must contain the following dummy files: `.git/HEAD`, a regular file containing `ref: refs/heads/.invalid`. `.git/refs/`, a directory. `.git/refs/heads`, a regular file". — [technical/reftable.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/technical/reftable.adoc)
- [CURRENT BEHAVIOR] Local check (2.55.0): `git init --ref-format=reftable` produced `.git/HEAD` containing `ref: refs/heads/.invalid`, a regular file `.git/refs/heads` containing "this repository uses the reftable format", `.git/reftable/tables.list` plus one `.ref` table, and config `extensions.refstorage=reftable` with `core.repositoryformatversion=1`. Documentary source: — [config/extensions.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/extensions.adoc)
- [STABLE FUNDAMENTAL] Compatibility rule: "If a version-1 repository specifies any `extensions.*` keys that the running git has not implemented, the operation MUST NOT proceed." — [technical/repository-version.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/technical/repository-version.adoc)
- [STABLE FUNDAMENTAL] Why it exists (design document): "The existing packed-refs format takes up a lot of space (e.g. 62M), and does not scale with additional references. Lookup of a single reference requires linearly scanning the file"; "Atomic pushes modifying multiple references require copying the entire packed-refs file"; objectives include "Near constant time lookup for any single reference", "Support atomic push with `O(size_of_update)` operations" and "Combine reflog storage with ref storage for small transactions." — [technical/reftable.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/technical/reftable.adoc)
- [CURRENT BEHAVIOR] Why it will be the default (BreakingChanges): the "files" format cannot "store two references that only differ in casing on case-insensitive filesystems ... common on Windows and macOS"; macOS Unicode normalisation causes similar clashes; deleting refs "requires Git to rewrite the complete "packed-refs" file"; multi-ref writes "are not atomic with the "files" backend"; reftable "uses geometric compaction after every write" and "a binary format with prefix compression". — [BreakingChanges.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/BreakingChanges.adoc)
- [VERSION-SPECIFIC] 2.51: "The reftable ref backend has matured enough; Git 3.0 will make it the default format in a newly created repositories by default." 2.56: the reftable code "has been hardened against corrupted tables". — [RelNotes 2.51.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.51.0.adoc); [RelNotes 2.56.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.56.0.adoc)
- [CURRENT BEHAVIOR] `git repo info` reports `references.format` (local check on 2.55.0 printed `references.format=files` and `object.format=sha1`). — [git-repo.adoc @v2.55.0](https://github.com/git/git/blob/v2.55.0/Documentation/git-repo.adoc)

### Inferences
- Any lesson that inspects `.git/refs/heads/<branch>` or `packed-refs` by hand must say "in a `files`-format repository". The format-independent way to read refs is plumbing (`git for-each-ref`, `git rev-parse`, `git symbolic-ref`, `git refs list`), and that is what should be taught as the habit.
- Scripts that test for a repository by reading `.git/HEAD` still find a syntactically valid file under reftable, but its content (`refs/heads/.invalid`) is a stub; reading HEAD must go through `git symbolic-ref HEAD` or `git rev-parse`.
- Third-party tools built on libgit2/JGit may not open a reftable repository until their own support ships (see section 2), so reftable is best demonstrated in a throw-away repository.

### Gaps
- Whether GitHub/GitLab server-side storage uses reftable is out of scope and was not researched. The ref format is local and is not transmitted over the wire, so it does not affect pushes (inference from the design; no single doc sentence was found stating this outright).
- The unreleased `next` branch documents an additional variable `init.defaultRefStorageFormat`; it is in no release as of 2026-10-01, so only `init.defaultRefFormat` should be taught (it works on 2.55.0: local check with `git -c init.defaultRefFormat=reftable init` produced `references.format=reftable`). — [config/init.adoc on next](https://github.com/git/git/blob/next/Documentation/config/init.adoc)

## 5. `git switch`, `git restore` and the status of `git checkout`

### Takeaway
`git switch` and `git restore` (introduced in 2.23) lost their "EXPERIMENTAL" label in **Git 2.51**; their current man pages contain no such wording. `git checkout` is **not deprecated** and the project has recorded a decision to keep all three commands.

### Cited Findings
- [VERSION-SPECIFIC] Introduced in 2.23: "Two new commands "git switch" and "git restore" are introduced to split "checking out a branch to work on advancing its history" and "checking out paths out of the index and/or a tree-ish to work on advancing the current history" out of the single "git checkout" command." — [RelNotes 2.23.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.23.0.adoc)
- [VERSION-SPECIFIC] 2.51: ""git switch" and "git restore" are declared to be no longer experimental." Tag check: the sentence "THIS COMMAND IS EXPERIMENTAL. THE BEHAVIOR MAY CHANGE." is present in git-switch/git-restore at v2.50.0 and absent at v2.51.0. — [RelNotes 2.51.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.51.0.adoc); [git-switch.adoc @v2.50.0](https://github.com/git/git/blob/v2.50.0/Documentation/git-switch.adoc)
- [CURRENT BEHAVIOR] Current wording, git-switch DESCRIPTION (=2.55): "Switch to a specified branch. The working tree and the index are updated to match the branch. All new commits will be added to the tip of this branch." and "Switching branches does not require a clean index and working tree (i.e. no differences compared to `HEAD`). The operation is aborted however if the operation leads to loss of local changes, unless told otherwise with `--discard-changes` or `--merge`." — [git-switch.adoc @v2.56.0](https://github.com/git/git/blob/v2.56.0/Documentation/git-switch.adoc); rendered: [git-scm.com/docs/git-switch](https://git-scm.com/docs/git-switch)
- [CURRENT BEHAVIOR] Current wording, git-restore DESCRIPTION (=2.55): "Restore specified paths in the working tree with some contents from a restore source. If a path is tracked but does not exist in the restore source, it will be removed to match the source." and "By default, if `--staged` is given, the contents are restored from `HEAD`, otherwise from the index. Use `--source` to restore from a different commit." — [git-restore.adoc @v2.56.0](https://github.com/git/git/blob/v2.56.0/Documentation/git-restore.adoc)
- [CURRENT BEHAVIOR] git-checkout man page (=2.55) has no deprecation notice; it now opens with "`git checkout` has two main modes: 1. **Switch branches**, with `git checkout <branch>` 2. **Restore a different version of a file**, for example with `git checkout <commit> <filename>` or `git checkout <filename>`". — [git-checkout.adoc @v2.56.0](https://github.com/git/git/blob/v2.56.0/Documentation/git-checkout.adoc)
- [CURRENT BEHAVIOR] Project decision, under "Superseded features that will not be deprecated": "Because the use of git-checkout(1) is still widespread, and it is not expected that this will change anytime soon, all three commands will stay. This decision may get revisited in case we ever figure out that there are almost no users of any of the commands anymore." — [BreakingChanges.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/BreakingChanges.adoc)
- [VERSION-SPECIFIC] 2.55 changed `git checkout -m <branch>`: it "gave only one chance to resolve conflicts. The command was taught to create a stash to save the local changes." — [RelNotes 2.55.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.55.0.adoc)

### Inferences
- Teach `switch`/`restore` as the primary, stable interface (on ≥ 2.51) and `checkout` as a still-supported command the learner must be able to read in other people's scripts. Saying "checkout is deprecated" is wrong.
- On Apple's bundled 2.50.1 the man pages still carry the experimental banner; the commands behave the same, only the label differs.

### Gaps
- None for this question.

### Inferences
- The modern "safe force push" recipe that the documentation itself supports is `git push --force-with-lease --force-if-includes` (or the explicit `--force-with-lease=<ref>:<expected-oid>` form). Bare `--force-with-lease` gives a false sense of safety wherever something runs a plain `git fetch` in the background (the man page's own example is a cron job; editor auto-fetch features are the usual modern case). Git's own scheduled `prefetch` maintenance task is not such a case: it writes to `refs/prefetch/` "to avoid disrupting the remote-tracking branches" ([git-maintenance.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-maintenance.adoc)).
- "`git pull` = fetch + merge" is no longer a complete description: for diverged histories an unconfigured Git ≥ 2.33.1 refuses, so a course should have the learner choose `pull.rebase`/`pull.ff` deliberately in lesson one.
- `-s recursive` and `-X` options written for recursive in old scripts keep working because `recursive` is an alias of `ort`; nothing needs to be rewritten, but the name should not be taught as a separate algorithm.

### Gaps
- The git-pull man page calls `--ff-only` "the default", while the code path prints a distinct error ("Need to specify how to reconcile divergent branches") rather than the `--ff-only` failure. The observable effect (refusal when diverged) is the same; the exact error text differs from an explicit `--ff-only`.
- The version that introduced `rebase.rebaseMerges` was not verified.

## 8. Defaults that govern recoverability

### Takeaway
The believed defaults are confirmed: reflog entries expire after **90 days** (30 days if unreachable from the current tip), unreachable objects are pruned after a **2-week** grace period, and auto-gc thresholds are **6700 loose objects / 50 packs**. Two facts are frequently missed: **deleting a branch deletes its reflog**, and **bare repositories do not keep reflogs by default**.

### Cited Findings
- [STABLE FUNDAMENTAL] `gc.reflogExpire`: "'git reflog expire' removes reflog entries older than this time; defaults to 90 days. The value "now" expires all entries immediately, and "never" suppresses expiration altogether." A per-pattern form `gc.<pattern>.reflogExpire` exists (e.g. "refs/stash"). — [config/gc.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/gc.adoc)
- [STABLE FUNDAMENTAL] `gc.reflogExpireUnreachable`: "removes reflog entries older than this time and are not reachable from the current tip; defaults to 30 days ... These types of entries are generally created as a result of using `git commit --amend` or `git rebase` and are the commits prior to the amend or rebase occurring." — [config/gc.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/gc.adoc)
- [STABLE FUNDAMENTAL] `gc.pruneExpire`: "When 'git gc' is run, it will call 'prune --expire 2.weeks.ago' (and 'repack --cruft --cruft-expiration 2.weeks.ago' if using cruft packs via `gc.cruftPacks` or `--cruft`). Override the grace period with this config variable. The value "now" may be used to disable this grace period and always prune unreachable objects immediately, or "never" may be used to suppress pruning." — [config/gc.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/gc.adoc)
- [STABLE FUNDAMENTAL] `gc.auto`: "When there are approximately more than this many loose objects in the repository, `git gc --auto` will pack them ... The default value is 6700. Setting this to 0 disables not only automatic packing based on the number of loose objects, but also any other heuristic `git gc --auto` will otherwise use". `gc.autoPackLimit`: "more than this many packs that are not marked with `*.keep` file ... The default value is 50." `gc.autoDetach`: "Default is true." — [config/gc.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/gc.adoc)
- [STABLE FUNDAMENTAL] Other retention defaults: `gc.worktreePruneExpire` 3 months; `gc.rerereResolved` 60 days; `gc.rerereUnresolved` 15 days; `gc.logExpiry` "1.day". — [config/gc.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/gc.adoc)
- [CURRENT BEHAVIOR] What keeps objects alive: "'git gc' tries very hard not to delete objects that are referenced anywhere in your repository. In particular, it will keep not only objects referenced by your current set of branches and tags, but also objects referenced by the index, remote-tracking branches, reflogs (which may reference commits in branches that were later amended or rewound), and anything else in the refs/* namespace. Note that a note (of the kind created by 'git notes') attached to an object does not contribute in keeping the object alive." — [git-gc.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-gc.adoc)
- [CURRENT BEHAVIOR] `git gc --prune=<date>`: "Prune loose objects older than date (default is 2 weeks ago, overridable by the config variable `gc.pruneExpire`). --prune=now prunes loose objects regardless of their age and increases the risk of corruption if another process is writing to the repository concurrently ... --prune is on by default." — [git-gc.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-gc.adoc)
- [CURRENT BEHAVIOR] `git reflog expire`: "The "expire" subcommand prunes older reflog entries. Entries older than `expire` time, or entries older than `expire-unreachable` time and not reachable from the current tip, are removed from the reflog." `--all`: "Process the reflogs of all references." `--expire=<time>` ... "`--expire=all` prunes entries regardless of their age; `--expire=never` turns off pruning of reachable entries". The official checklist for shrinking a repository spells the destructive pair as "Expire all reflogs with `git reflog expire --expire=now --all`" then "Garbage collect all unreferenced objects with `git gc --prune=now`". — [git-reflog.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-reflog.adoc); [git-filter-branch.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-filter-branch.adoc)
- [CURRENT BEHAVIOR] Other reflog subcommands: `delete` "deletes single entries from the reflog, but not the reflog itself"; `drop` (2.50) "completely removes the reflog for the specified references"; `list` (2.45); `exists`; `write`. — [git-reflog.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-reflog.adoc)
- [STABLE FUNDAMENTAL] **Deleting a branch deletes its reflog**: "With a `-d` or `-D` option, `<branch-name>` will be deleted. You may specify more than one branch for deletion. If the branch currently has a reflog then the reflog will also be deleted." Local check on 2.55.0: `.git/logs/refs/heads/tmpb` disappears after `git branch -D tmpb`. (Renaming moves the reflog; copying copies it.) — [git-branch.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-branch.adoc)
- [STABLE FUNDAMENTAL] **Bare repositories**: `core.logAllRefUpdates` — "Enable the reflog ... If this configuration variable is set to `true`, missing "`$GIT_DIR/logs/<ref>`" file is automatically created for branch heads (i.e. under `refs/heads/`), remote refs (i.e. under `refs/remotes/`), note refs (i.e. under `refs/notes/`), and the symbolic ref `HEAD`. If it is set to `always`, then a missing reflog is automatically created for any ref under `refs/`." and "This value is true by default in a repository that has a working directory associated with it, and false by default in a bare repository." Local check: a fresh `git init --bare` repository has no `logs` directory after receiving pushes. — [config/core.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/core.adoc)
- [STABLE FUNDAMENTAL] Reflogs are local: "Reflogs only log changes made in your local repository. They are not shared with remotes." and "Git may delete objects that aren't "reachable" from any reference or reflog ... when the reflog entry expires it may become unreachable and get deleted. Reachable objects will never be deleted." — [gitdatamodel.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/gitdatamodel.adoc)
- [STABLE FUNDAMENTAL] Stashes live in a reflog: "The latest stash you created is stored in `refs/stash`; older stashes are found in the reflog of this reference". The expiry code special-cases it — source comment "If unconfigured, make stash never expire" — so stash entries are exempt from the 90/30-day defaults unless an explicit expiry is given (which `git reflog expire --expire=now --all` does). Dropped stashes are different: "If you mistakenly drop or clear stash entries, they cannot be recovered through the normal safety mechanisms", though the man page shows a `git fsck --unreachable` recipe to find them while the objects still exist. — [git-stash.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-stash.adoc); [reflog.c @v2.55.0, lines 117–126](https://github.com/git/git/blob/v2.55.0/reflog.c#L117-L126)
- [CURRENT BEHAVIOR] With the 2.54+ default (geometric) maintenance strategy the same expiry values are used: the traced 2.55.0 run invoked `git reflog expire --all` and `git repack -d -l --cruft --cruft-expiration=2.weeks.ago`; unreachable objects go into a cruft pack and "Objects that are already part of a cruft pack will be expired." — [config/maintenance.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/maintenance.adoc)

### Inferences
- Practical recovery window on a default non-bare repository: a commit orphaned by `reset`, `amend` or `rebase` stays reachable through reflogs for at least 30 days, then survives up to 2 more weeks as an unreachable object once maintenance actually runs. Commits on a **deleted branch** lose that branch's reflog immediately but usually remain reachable through the `HEAD` reflog if they were ever checked out; commits never checked out locally (for example a branch created with `git branch name <oid>` and deleted) are protected only by the 2-week object grace period.
- On a server (bare) repository there is no reflog by default, so a force-push leaves no built-in record of the old tip; recovery there depends on the host's own features or on `core.logAllRefUpdates` having been enabled.
- `git reflog expire --expire=now --all && git gc --prune=now` is the documented way to make deletion immediate; it is also the documented way to lose the safety net, so it belongs in a "destructive commands" lesson.

### Gaps
- Pro Git says auto-gc needs "around 7,000 loose objects"; the configuration reference says 6700. The config reference is authoritative. — [Pro Git, Maintenance and Data Recovery](https://git-scm.com/book/en/v2/Git-Internals-Maintenance-and-Data-Recovery)
- git-gc(1) still says porcelain commands "run `git gc` automatically", which no longer matches the 2.54+ default maintenance strategy; whether `gc.auto=0` still suppresses all automatic maintenance under the geometric strategy was not verified (`maintenance.auto=false` is the documented switch).
- The "stash never expires by default" rule was confirmed from source code, not from a man page; no man-page sentence stating it was found.

## 9. History-rewriting tools

### Takeaway
`git filter-branch` still ships but its own man page opens with a warning not to use it and points to **git filter-repo**, a separate Python tool (latest release v2.47.0, December 2024) that is not part of core Git. BFG Repo-Cleaner is still published (v1.15.0, January 2025) but is narrower. Core Git's newer `git replay` and `git history` cover targeted rewrites and are experimental.

### Cited Findings
- [DEPRECATED/OUTDATED] The official warning, verbatim: "'git filter-branch' has a plethora of pitfalls that can produce non-obvious manglings of the intended history rewrite (and can leave you with little time to investigate such problems since it has such abysmal performance). These safety and performance issues cannot be backward compatibly fixed and as such, its use is not recommended. Please use an alternative history filtering tool such as git filter-repo. If you still need to use 'git filter-branch', please carefully read SAFETY (and PERFORMANCE) to learn about the land mines of filter-branch, and then vigilantly avoid as many of the hazards listed there as reasonably possible." (=2.55) — [git-filter-branch.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-filter-branch.adoc)
- [VERSION-SPECIFIC] The discouragement began in 2.24: ""filter-branch" is showing its age and alternatives are available. From this release, we started to discourage its use and hint people about filter-repo." Local check on 2.55.0, the runtime banner reads: "WARNING: git-filter-branch has a glut of gotchas generating mangled history rewrites. Hit Ctrl-C before proceeding to abort, then use an alternative filtering tool such as 'git filter-repo' (https://github.com/newren/git-filter-repo/) instead ... to squelch this warning, set FILTER_BRANCH_SQUELCH_WARNING=1." — [RelNotes 2.24.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.24.0.adoc)
- [CURRENT BEHAVIOR] `git filter-branch` is not on the Git 3.0 removal list (the list names grafts, pack-redundant, branches/remotes directories, name-rev --stdin, whatchanged, commentString=auto, preferSymlinkRefs). — [BreakingChanges.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/BreakingChanges.adoc)

Prerequisites: "git >= 2.36.0" and "python3 >= 3.6". ### Inferences
- For "remove a secret/large file from all history", teach filter-repo and mention that it must be installed separately (for example via a package manager) and needs Python 3; for "fix one old commit", teach interactive rebase and show `git history` as the experimental newcomer.
- Pro Git's data-recovery chapter still demonstrates `git filter-branch --index-filter`; that example is outdated relative to the man page's warning. — [Pro Git, Maintenance and Data Recovery](https://git-scm.com/book/en/v2/Git-Internals-Maintenance-and-Data-Recovery)

### Gaps
- Whether filter-repo fully supports SHA-256 or reftable repositories was not researched.
- Package-manager versions of filter-repo (Homebrew, apt) were not checked.

## 10. Commit and tag signing in Git itself

### Takeaway
Git signs with one of three backends chosen by `gpg.format`: `openpgp` (default), `x509` (since 2.19) or `ssh` (since 2.34). SSH signing needs `user.signingKey` and, for verification, `gpg.ssh.allowedSignersFile`.

### Cited Findings
- [CURRENT BEHAVIOR] `gpg.format`: "Specifies which key format to use when signing with `--gpg-sign`. Default is "openpgp". Other possible values are "x509", "ssh"." `gpg.<format>.program`: "The default value for `gpg.x509.program` is "gpgsm" and `gpg.ssh.program` is "ssh-keygen"." — [config/gpg.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/gpg.adoc)
- [VERSION-SPECIFIC] X.509 arrived in 2.19 ("gpg.format that can be set to "openpgp" or "x509" ... to allow x.509 certs with CMS via "gpgsm""); SSH in 2.34 ("In addition to GnuPG, ssh public crypto can be used for object and push-cert signing. Note that this feature cannot be used with ssh-keygen from OpenSSH 8.7, whose support for it is broken. Avoid using it unless you update to OpenSSH 8.8."). — [RelNotes 2.19.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.19.0.adoc); [RelNotes 2.34.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.34.0.adoc)
- [CURRENT BEHAVIOR] `user.signingKey`: "This option is passed unchanged to gpg's --local-user parameter ... If gpg.format is set to `ssh` this can contain the path to either your private ssh key or the public key when ssh-agent is used. Alternatively it can contain a public key prefixed with `key::` directly (e.g.: "key::ssh-rsa XXXXXX identifier") ... If not set Git will call gpg.ssh.defaultKeyCommand (e.g.: "ssh-add -L") and try to use the first key available." — [config/user.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/user.adoc)
- [CURRENT BEHAVIOR] `gpg.ssh.allowedSignersFile` (2.34, tag check): "A file containing ssh public keys which you are willing to trust. The file consists of one or more lines of principals followed by an ssh public key. e.g.: `user1@example.com,user2@example.com ssh-rsa AAAAX1...` ... SSH has no concept of trust levels like gpg does ... the trust level of a signature verification is set to `fully` when the public key is present in the allowedSignersFile. Otherwise the trust level is `undefined` and git verify-commit/tag will fail." It supports `valid-after`/`valid-before` lifetimes ("Since OpensSSH 8.8") and SSH CA keys; `gpg.ssh.revocationFile` lists revoked keys. — [config/gpg.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/gpg.adoc)
- [CURRENT BEHAVIOR] `commit.gpgSign`: "A boolean to specify whether all commits should be GPG signed." `tag.gpgSign`: "A boolean to specify whether all tags should be GPG signed ... this option doesn't affect tag signing behavior enabled by `-u <keyid>` or `--local-user=<keyid>` options." `push.gpgSign` accepts a boolean or `if-asked`. `gpg.minTrustLevel` sets the minimum trust for verification. — [config/commit.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/commit.adoc); [config/tag.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/tag.adoc); [config/push.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/push.adoc); [config/gpg.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/gpg.adoc)
- [CURRENT BEHAVIOR] Command options: `git commit -S[<key-id>]` / `--gpg-sign[=<key-id>]` / `--no-gpg-sign` ("The `<key-id>` is optional and defaults to the committer identity; if specified, it must be stuck to the option without a space"); `git tag -s` ("Make a cryptographically signed tag, using the default signing key. The signing backend used depends on the `gpg.format` configuration variable") and `git tag -u <key-id>`. — [git-commit.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-commit.adoc); [git-tag.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-tag.adoc)
- [STABLE FUNDAMENTAL] Where signatures live: "Git uses cryptographic signatures in various places, currently objects (tags, commits, mergetags) and transactions (pushes)"; tag signatures are appended to the tag object; markers are `-----BEGIN PGP SIGNATURE-----`, `-----BEGIN SSH SIGNATURE-----`, `-----BEGIN SIGNED MESSAGE-----` (X.509). — [gitformat-signature.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/gitformat-signature.adoc)
- [VERSION-SPECIFIC] 2.54 display fix: "A signature on a commit that was GPG signed a long time ago ought to be still valid after the key that was used to sign it has expired, but we showed them in alarming red." — [RelNotes 2.54.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.54.0.adoc)

### Inferences
- Minimal SSH-signing setup that follows the documentation: `git config set --global gpg.format ssh`, `user.signingKey <path to public key or key::...>`, `commit.gpgSign true`, plus an allowed-signers file referenced by `gpg.ssh.allowedSignersFile` so that `git log --show-signature`/`git verify-commit` can report trusted signatures locally. Hosting-side "Verified" badges are a separate, platform-specific check outside this scope.
- The option name `--gpg-sign` and config names `commit.gpgSign` are historical; they apply to all three backends.

### Gaps
- The minimum OpenSSH version recommended today (beyond the 8.8 note in the 2.34 release notes) was not re-verified.
- Exact wording of `git verify-commit`/`git verify-tag` man pages was not extracted.

## 11. Security: advisories 2024–2026, `safe.directory`, `protocol.file.allow`, and why untrusted repositories are risky

### Takeaway
Core Git had coordinated security releases in May 2024, January 2025 and July 2025; **no core-Git advisory or maintenance release was published in 2026 up to 1 October**, though Git for Windows published several Windows-specific advisories in 2026. The recurring theme is recursive clones of untrusted repositories (submodules, symlinks, hooks, bundle URIs); the standing defences are `safe.directory` ownership checks (2022), `protocol.file.allow=user` (2022) and, from 2.55, masking of terminal control sequences from remotes.

### Cited Findings

**The general rule (git(1) SECURITY section)**
- [STABLE FUNDAMENTAL] "Some configuration options and hook files may cause Git to run arbitrary shell commands. - Windows learners need Git for Windows ≥ 2.53.0(3) for the NTLM-leak fixes, and should avoid enabling `transfer.bundleURI` unless needed.

## 12. Hooks

### Takeaway
githooks(5) documents 28 hooks; six run on the receiving side of a push. Hooks live in `$GIT_DIR/hooks` unless `core.hooksPath` redirects them, and since **2.54** hooks can also be declared in configuration (`hook.<name>.command` / `hook.<name>.event`), with optional parallel execution since **2.55**.

### Cited Findings
- [STABLE FUNDAMENTAL] "Hooks are programs you can place in a hooks directory to trigger actions at certain points in git's execution. Hooks that don't have the executable bit set are ignored. By default the hooks directory is `$GIT_DIR/hooks`, but that can be changed via the `core.hooksPath` configuration variable". Working directory: "either $GIT_DIR in a bare repository or the root of the working tree in a non-bare repository", except push-triggered hooks "which are always executed in $GIT_DIR." (=2.55) — [githooks.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/githooks.adoc)
- [CURRENT BEHAVIOR] Full list in man-page order: `applypatch-msg`, `pre-applypatch`, `post-applypatch`, `pre-commit`, `pre-merge-commit`, `prepare-commit-msg`, `commit-msg`, `post-commit`, `pre-rebase`, `post-checkout`, `post-merge`, `pre-push`, `pre-receive`, `update`, `proc-receive`, `post-receive`, `post-update`, `reference-transaction`, `push-to-checkout`, `pre-auto-gc`, `post-rewrite`, `sendemail-validate`, `fsmonitor-watchman`, `p4-changelist`, `p4-prepare-changelist`, `p4-post-changelist`, `p4-pre-submit`, `post-index-change`. — [githooks.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/githooks.adoc)
- [STABLE FUNDAMENTAL] Server-side (each described as "invoked by git-receive-pack(1)"): `pre-receive`, `update`, `proc-receive`, `post-receive`, `post-update`, `push-to-checkout`. `reference-transaction` "is invoked by any Git command that performs reference updates" (so it fires on both sides). Everything else is client-side: commit workflow (`pre-commit`, `pre-merge-commit`, `prepare-commit-msg`, `commit-msg`, `post-commit`), email workflow via `git am` (`applypatch-msg`, `pre-applypatch`, `post-applypatch`), and `pre-rebase`, `post-rewrite`, `post-checkout` (also run by `git switch`), `post-merge`, `pre-push`, `pre-auto-gc`, `sendemail-validate`, `fsmonitor-watchman`, `post-index-change`, and the four `git-p4` hooks. — [githooks.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/githooks.adoc)
- [STABLE FUNDAMENTAL] Pro Git's client/server split agrees for the classic hooks and adds: "It's important to note that client-side hooks are **not** copied when you clone a repository." Bypass: `pre-commit` and `commit-msg` "can be bypassed with the `--no-verify` option". — [Pro Git, Git Hooks](https://git-scm.com/book/en/v2/Customizing-Git-Git-Hooks); [githooks.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/githooks.adoc)
- [CURRENT BEHAVIOR] `core.hooksPath`: "By default Git will look for your hooks in the `$GIT_DIR/hooks` directory. Set this to different path, e.g. `/etc/git/hooks` ... The path can be either absolute or relative. A relative path is taken as relative to the directory where the hooks are run ... You can also disable all hooks entirely by setting `core.hooksPath` to `/dev/null`. This is usually only advisable for expert users and on a per-command basis". — [config/core.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/core.adoc)
- [VERSION-SPECIFIC] `git hook` (man page first at v2.36.0): `git hook run [--allow-unknown-hook-name] [--ignore-missing] [--to-stdin=<path>] [(-j|--jobs) <n>] <hook-name> [-- <hook-args>]` and `git hook list [--allow-unknown-hook-name] [-z] [--show-scope] <hook-name>` — "A command interface for running Git hooks ... for use by other scripted Git commands." (=2.55) — [git-hook.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-hook.adoc)
- [VERSION-SPECIFIC] **Config-based hooks are released** (2.54: "Hook commands are now allowed to be defined (possibly centrally) in the configuration files, and run multiple of them for the same hook event"). Syntax: `[hook "linter"] event = pre-commit` / `command = ~/bin/linter --cpp20`; "Commands are run in the order Git encounters their associated `hook.<friendly-name>.event` configs during the configuration parse"; with `git hook run`, "The default `<hook-name>` from the hookdir is run last." Keys: `hook.<friendly-name>.command`, `.event` (multi-valued; "An empty value resets the list of events"), `.enabled` ("Defaults to `true`"), `hook.<event>.enabled`. The man page's own recipe: `git config set hook.<some-name>.command <path-to-script>` and `git config set --append hook.<some-name>.event <hook-event>`. — [git-hook.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-hook.adoc); [config/hook.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/hook.adoc); [RelNotes 2.54.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.54.0.adoc)
- [VERSION-SPECIFIC] Parallel hooks (2.55): `hook.jobs` ("If unspecified, defaults to 1 (serial execution)"), `hook.<event>.jobs`, `hook.<friendly-name>.parallel` ("Defaults to `false`"). "Some hooks always run sequentially ... `applypatch-msg`, `pre-commit`, `prepare-commit-msg`, `commit-msg`, `post-commit`, `post-checkout`, and `push-to-checkout`." — [config/hook.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/hook.adoc); [RelNotes 2.55.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.55.0.adoc)
- [CURRENT BEHAVIOR] The experimental `git history` "does not execute any githooks(5) at the current point in time." — [git-history.adoc @v2.55.0](https://github.com/git/git/blob/v2.55.0/Documentation/git-history.adoc)

### Inferences
- Config-based hooks solve the long-standing "hooks are not versioned or shared" complaint only partly: configuration is still not cloned, so a project cannot push hooks onto contributors; what changes is that one script can be registered once in global or system config and apply to many repositories, alongside the traditional hook file.
- Because hook configuration can sit in system/global config, "why did a hook run?" debugging should now include `git hook list --show-scope <event>` (available on 2.55).

### Gaps
- No release-note line was found for the original introduction of `git hook` in 2.36; the version comes from the presence of the man page at the v2.36.0 tag.
- Interaction of config-based hooks with `core.hooksPath=/dev/null` was not tested.

## 13. Things older tutorials still teach that are now deprecated, changed, or no longer best practice

### Takeaway
Twenty-one common tutorial habits or claims are outdated; most still "work", which is why they persist. For each: older behavior → current behavior → version → recommended approach.

### Cited Findings
- [DEPRECATED/OUTDATED] **`git checkout` for everything.** Older: one command for switching branches and restoring files. Current: `git switch` and `git restore` exist since 2.23 and are non-experimental since 2.51; `checkout` remains supported and is explicitly not slated for removal. Recommended: teach `git switch <branch>`, `git switch -c <new>`, `git restore <path>`, `git restore --staged <path>`; teach `checkout` for reading. — [RelNotes 2.23.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.23.0.adoc); [RelNotes 2.51.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.51.0.adoc); [BreakingChanges.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/BreakingChanges.adoc)
- [DEPRECATED/OUTDATED] **`git stash save "msg"`.** Current: "deprecated in favour of 'git stash push'" (push since 2.13, save deprecated 2.16); `save` cannot take a pathspec. Recommended: `git stash push -m "msg" [-- <pathspec>]`. — [git-stash.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-stash.adoc); [RelNotes 2.16.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.16.0.adoc)
- [DEPRECATED/OUTDATED] **Relying on `git pull` to merge silently.** Older (before 2.27): diverged histories were merged without comment. 2.27–2.33.0: merged with a warning. Since 2.33.1/2.34.0: "fatal: Need to specify how to reconcile divergent branches." Recommended: set `pull.rebase` (true/false) or `pull.ff only` explicitly, or pass `--rebase`/`--no-rebase`/`--ff-only`. — [builtin/pull.c @v2.56.0](https://github.com/git/git/blob/v2.56.0/builtin/pull.c#L1150); [RelNotes 2.27.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.27.0.adoc); [RelNotes 2.34.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.34.0.adoc)
- [DEPRECATED/OUTDATED] **Assuming `master` is the default branch.** Current: configurable since 2.28 (`init.defaultBranch`, `git init -b`); an unconfigured Git 2.x still creates `master` and prints a hint that this "will change to "main" in Git 3.0". Recommended: never hard-code; set `init.defaultBranch` and discover a remote's default with `refs/remotes/origin/HEAD`. — [git-init.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-init.adoc); [RelNotes 2.52.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.52.0.adoc)
- [DEPRECATED/OUTDATED] **`git filter-branch`.** Current: "its use is not recommended" (discouraged since 2.24). Recommended: git filter-repo for whole-history rewrites. — [git-filter-branch.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-filter-branch.adoc); [RelNotes 2.24.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.24.0.adoc)
- [DEPRECATED/OUTDATED] **`git whatchanged`.** Current: "`git whatchanged` has been deprecated and is scheduled for removal in a future version of Git, as it is merely `git log` with different defaults" (warning in the man page since 2.51). Local check on 2.55.0: it refuses to run without `--i-still-use-this` and suggests `git log <opts> --raw --no-merges`. Recommended: `git log --raw --no-merges`. — [git-whatchanged.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-whatchanged.adoc); [RelNotes 2.51.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.51.0.adoc)
- [DEPRECATED/OUTDATED] **`git rebase -p` / `--preserve-merges` and `pull.rebase=preserve`.** Deprecated 2.22, removed 2.34. Recommended: `git rebase --rebase-merges` (`-r`) and `pull.rebase=merges`. Local check: "fatal: --preserve-merges was replaced by --rebase-merges ... `pull.rebase` configuration may also be set to 'preserve', which is no longer supported; use 'merges' instead". — [RelNotes 2.22.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.22.0.adoc); [RelNotes 2.34.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.34.0.adoc); [git-rebase.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-rebase.adoc)
- [DEPRECATED/OUTDATED] **Pre-2.0 `git add` semantics.** Older: `git add -u`/`-A` without a pathspec only covered the current directory, and `git add <path>` ignored removals. Since 2.0: "When "git add -u" and "git add -A" are run inside a subdirectory without specifying which paths to add on the command line, they operate on the entire tree" and ""git add `<path>`" is the same as "git add -A `<path>`" now, so that "git add dir/" will notice paths you removed from the directory and record the removal." Recommended: say `git add -u .` to limit to the current directory; `--ignore-removal` exists for the old behaviour. — [RelNotes 2.0.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.0.0.adoc); [git-add.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-add.adoc)
- [DEPRECATED/OUTDATED] **`push.default=matching` behaviour / "git push pushes all branches".** Since 2.0 the default is `simple`. — [config/push.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/push.adoc)
- [DEPRECATED/OUTDATED] **`git gc --aggressive` as routine clean-up.** Current doc: "It's probably not worth it to use this option on a given repository without running tailored performance benchmarks on it. It takes a lot more time, and the resulting space/delta optimization may or may not be worth it. Not using this at all is the right trade-off for most users and their repositories." And manual `git gc` "should only be needed when adding objects to a repository without regularly running such porcelain commands, to do a one-off repository optimization". Recommended: let automatic maintenance run; use `git maintenance start` for background upkeep on large repositories. — [git-gc.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-gc.adoc); [git-maintenance.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-maintenance.adoc)
- [DEPRECATED/OUTDATED] **"Set `core.autocrlf` and you are done."** Current docs: `core.autocrlf` is a per-user convenience ("If you simply want to have CRLF line endings in your working directory regardless of the repository you are working with ... This does not force normalization of text files"), whereas "If you want to ensure that text files that any contributor introduces to the repository have their line endings normalized, you can set the `text` attribute to "auto" for _all_ files" (`* text=auto` in `.gitattributes`). The FAQ recommends "that text files be stored in UTF-8 without a byte-order mark (BOM) with LF (Unix-style) endings" and shows a `.gitattributes` with `* text=auto`, `*.sh text eol=lf`, `*.bat text eol=crlf`. `core.autocrlf` is not deprecated. Recommended: commit a `.gitattributes`; use `git add --renormalize .` when introducing it. — [gitattributes.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/gitattributes.adoc); [gitfaq.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/gitfaq.adoc)
- [DEPRECATED/OUTDATED] **`git config --get`, `--add`, `--unset`, `-l`, `git config <name> <value>`.** Since 2.46 these "modes have been deprecated in favor of subcommands": `git config get|set|unset|list|rename-section|remove-section|edit`. Old forms still function. Caution: the new syntax fails on Git < 2.46 (Ubuntu 24.04's 2.43). — [git-config.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-config.adoc)
- [DEPRECATED/OUTDATED] **`git merge -s recursive` as "the" algorithm.** `ort` is the default since 2.34 and `recursive` is "now a synonym for `ort`" since 2.50. — [merge-strategies.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/merge-strategies.adoc)
- [DEPRECATED/OUTDATED] **`git push --force` after a rebase.** Current docs give `--force-with-lease` (1.8.5) and `--force-if-includes` (2.30) and warn that bare `--force` "can cause the remote repository to lose commits". — [git-push.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-push.adoc)
- [DEPRECATED/OUTDATED] **`--heads` for `git ls-remote` / `git show-ref`.** "The "--heads" option of "ls-remote" and "show-ref" has been deprecated; "--branches" replaces "--heads"" (2.46). — [RelNotes 2.46.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.46.0.adoc)
- [DEPRECATED/OUTDATED] **`git cherry-pick --keep-redundant-commits`.** Soft-deprecated in 2.45 in favour of `--empty=(drop|keep|stop)`. — [RelNotes 2.45.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.45.0.adoc)
- [DEPRECATED/OUTDATED] **Grafts (`.git/info/grafts`), `.git/branches/`, `.git/remotes/`, `git pack-redundant`, `core.commentChar=auto`.** All scheduled for removal in 3.0; use `git replace`, config-based remotes, `git gc`/`git repack`. — [BreakingChanges.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/BreakingChanges.adoc)
- [DEPRECATED/OUTDATED] **"GPG is the only way to sign."** SSH signing since 2.34, X.509 since 2.19. — [config/gpg.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/gpg.adoc)
- [DEPRECATED/OUTDATED] **"Refs are files under `.git/refs`, object IDs are 40 hex characters."** True only for `files`-format, SHA-1 repositories; reftable (2.45) and SHA-256 (2.29) break both assumptions and both become defaults for new repositories in 3.0. — [BreakingChanges.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/BreakingChanges.adoc); [technical/reftable.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/technical/reftable.adoc)
- [DEPRECATED/OUTDATED] **"Git runs `git gc --auto` after commands."** Since 2.54 the default automatic maintenance uses the geometric strategy (commit-graph, geometric repack, pack-refs, rerere-gc, reflog-expire, worktree-prune) rather than the `gc` task. — [config/maintenance.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/config/maintenance.adoc); [RelNotes 2.54.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.54.0.adoc)
- [DEPRECATED/OUTDATED] **"ORIG_HEAD, CHERRY_PICK_HEAD and friends are pseudo-refs."** Current glossary restricts "pseudoref" to `FETCH_HEAD` and `MERGE_HEAD`; the others are ordinary refs in the root of the ref hierarchy (see section 14). — [glossary-content.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/glossary-content.adoc)

### Inferences
- The highest-value corrections for a professional audience are the ones that change outcomes rather than spelling: divergent `git pull`, `add -A/-u` scope, force-push safety, branch-deletion reflog loss, and line-ending normalisation via attributes.
- Because almost every deprecated form still executes, a course should present "old form → new form" pairs so the learner can read legacy scripts while writing the modern form.

### Gaps
- When `gc.aggressiveDepth` changed to its current default (50) was not verified.
- The removal/rename history of `git branch --set-upstream` (versus `--set-upstream-to`) was not researched.

## 14. Internals facts confirmed against official documentation

### Takeaway
The classic model holds and now has an official plain-language reference, gitdatamodel(7) (2.53): four object types addressed by a hash of "type size NUL content", trees with five entry types, an index with stat data and stage numbers, refs plus reflogs. Two refinements matter for accuracy: "pseudoref" now officially means only `FETCH_HEAD` and `MERGE_HEAD`, and `A..B`/`A...B` mean different things to `git log` and `git diff`.

### Cited Findings

**Objects**
- [STABLE FUNDAMENTAL] "Git's core operations use 4 kinds of data: 1. Objects: commits, trees, blobs, and tag objects 2. References: branches, tags, remote-tracking branches, etc 3. The index, also known as the staging area 4. Reflogs: logs of changes to references". "Git objects never change after they're created, and every object has an ID"; an ID "is a cryptographic hash of its type and contents." — [gitdatamodel.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/gitdatamodel.adoc)
- [STABLE FUNDAMENTAL] Loose object format: "Each loose object contains a prefix, followed immediately by the data of the object. The prefix contains `<type> <size>\0`. `<type>` is one of `blob`, `tree`, `commit`, or `tag` and `size` is the size of the data (without the prefix) as a decimal integer expressed in ASCII. The entire contents, prefix and data concatenated, is then compressed with zlib and the compressed data is stored in the file. The object ID of the object is the SHA-1 or SHA-256 (as appropriate) hash of the uncompressed data." Example: "a blob containing the contents `abc` would have the uncompressed data of `blob 3\0abc`." — [gitformat-loose.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/gitformat-loose.adoc)
- [STABLE FUNDAMENTAL] Location: "The file for the loose object is stored under the `objects` directory, with the first two hex characters of the object ID being the directory and the remaining characters being the file name." Layout doc: "objects/[0-9a-f][0-9a-f]:: A newly created object is stored in its own file. The objects are splayed over 256 subdirectories using the first two characters of the sha1 object name". — [gitformat-loose.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/gitformat-loose.adoc); [gitrepository-layout.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/gitrepository-layout.adoc)
- [STABLE FUNDAMENTAL] Pro Git agrees: "Git is a content-addressable filesystem ... at the core of Git is a simple key-value data store"; "Git concatenates the header and the original content and then calculates the SHA-1 checksum of that new content"; "All Git objects are stored the same way, just with different types". — [Pro Git, Git Objects](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)
- [STABLE FUNDAMENTAL] **Tree entries**: a tree "lists, for each item in the tree: 1. The filename ... 2. The file type, which must be one of these five types: regular file, executable file, symbolic link, directory, gitlink (for use with submodules) 3. The object ID with the contents of the file, directory, or gitlink." Modes as displayed: "`100644` is "regular file", `100755` is "executable file", `120000` is "symbolic link", `040000` is "directory", and `160000` is "gitlink""; object type shown is "`blob` for files and symlinks, `tree` for directories, and `commit` for gitlinks." — [gitdatamodel.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/gitdatamodel.adoc)
- [STABLE FUNDAMENTAL] The same five modes in fast-import's grammar: "Git only supports the following modes: `100644` or `644`: A normal (not-executable) file ... `100755` or `755`: A normal, but executable, file. `120000`: A symlink ... `160000`: A gitlink, SHA-1 of the object refers to a commit in another repository ... They are used to implement submodules. `040000`: A subdirectory." — [git-fast-import.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-fast-import.adoc)
- [STABLE FUNDAMENTAL] The Git User's Manual adds ordering and the rename point: "a tree object contains a list of entries, each with a mode, object type, SHA-1 name, and name, sorted by name. It represents the contents of a single directory tree"; "Note that the files all have mode 644 or 755: Git actually only pays attention to the executable bit"; and for commits, "a commit does not itself contain any information about what actually changed; all changes are calculated by comparing the contents of the tree referred to by this commit with the trees associated with its parents. In particular, Git does not attempt to record file renames explicitly". (=2.55) — [user-manual.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/user-manual.adoc)
- [STABLE FUNDAMENTAL] **Commit object**: "A commit contains these required fields (though there are other optional fields): 1. The full directory structure of all the files in that version of the repository and each file's contents, stored as the tree ID of the commit's top-level directory 2. Its parent commit ID(s). The first commit in a repository has 0 parents, regular commits have 1 parent, merge commits have 2 or more parents 3. An author and the time the commit was authored 4. A committer and the time the commit was committed 5. A commit message". Also: "Git does not store the diff for a commit: when you ask Git to show the commit with git-show(1), it calculates the diff from its parent on the fly." — [gitdatamodel.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/gitdatamodel.adoc)
- [STABLE FUNDAMENTAL] **Annotated tag object**: "Tag objects contain these required fields (though there are other optional fields): 1. The ID of the object it references 2. The type of the object it references 3. The tagger and tag date 4. A tag message, similar to a commit message", stored as `object <id>` / `type commit` / `tag v1.0.0` / `tagger ...` / blank line / message. Lightweight tags "reference a commit, blob, or tree ID directly". — [gitdatamodel.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/gitdatamodel.adoc)
- [STABLE FUNDAMENTAL] **Blob**: "A blob object contains a file's contents ... if you have a commit that changes 2 files in a repository with 1000 files, that commit will create 2 new blobs, and use the previous blob ID for the other 998 files." — [gitdatamodel.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/gitdatamodel.adoc)

**Packs**
- [STABLE FUNDAMENTAL] "The Git pack format is how Git stores most of its primary repository data. Over the lifetime of a repository, loose objects (if any) and smaller packs are consolidated into larger pack(s)." Pack header: 4-byte signature `PACK`, version ("Git currently accepts version number 2 or 3 but generates version 2 only"), object count; then entries; then a checksum trailer. Object types: OBJ_COMMIT (1), OBJ_TREE (2), OBJ_BLOB (3), OBJ_TAG (4), OBJ_OFS_DELTA (6), OBJ_REF_DELTA (7). — [gitformat-pack.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/gitformat-pack.adoc)
- [STABLE FUNDAMENTAL] Delta compression: "Conceptually there are only four object types: commit, tree, tag and blob. However to save space, an object could be stored as a "delta" of another "base" object ... ref-delta directly encodes base object name. If the base object is in the same pack, ofs-delta encodes the offset of the base object in the pack instead." Thin packs: "Ref-delta can also refer to an object outside the pack (i.e. the so-called "thin pack"). When stored on disk however, the pack should be self contained". — [gitformat-pack.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/gitformat-pack.adoc)
- [STABLE FUNDAMENTAL] `.idx` (version 2): magic `\377tOc`, version 2, "A 256-entry fan-out table", "A table of sorted object names", "A table of 4-byte CRC32 values of the packed object data", 4-byte offsets, and an 8-byte offset table for large packs; "Version 2 pack-*.idx files support packs larger than 4 GiB". Related files in `objects/pack/`: `pack-*.rev`, `pack-*.mtimes`, `multi-pack-index`. — [gitformat-pack.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/gitformat-pack.adoc)
- [STABLE FUNDAMENTAL] Pro Git's explanation of delta direction: "the second version of the file is the one that is stored intact, whereas the original version is stored as a delta — this is because you're most likely to need faster access to the most recent version of the file." — [Pro Git, Packfiles](https://git-scm.com/book/en/v2/Git-Internals-Packfiles)

**The index**
- [STABLE FUNDAMENTAL] "The index, also known as the "staging area", is a list of files and the contents of each file, stored as a blob ... Unlike a tree, the index is a flat list of files. When you commit, Git converts the list of files in the index to a directory tree". "Each index entry has 4 fields": file type (regular, executable, symbolic link, gitlink), blob ID (or commit ID for a submodule), "The stage number, either 0, 1, 2, or 3. This is normally 0, but if there's a merge conflict there can be multiple versions of the same filename in the index", and the file path. Inspect with `git ls-files --stage`. — [gitdatamodel.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/gitdatamodel.adoc)
- [STABLE FUNDAMENTAL] On-disk format: signature `DIRC`, versions 2, 3 and 4; each entry carries stat(2) data (ctime, mtime, dev, ino, uid, gid, file size), a mode, the object name, and flags including "1-bit assume-valid flag", "2-bit stage (during merge)", and in version 3+ "1-bit skip-worktree flag (used by sparse checkout)" and "1-bit intent-to-add flag (used by "git add -N")". Glossary: the index is "A collection of files with stat information, whose contents are stored as objects." — [gitformat-index.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/gitformat-index.adoc); [glossary-content.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/glossary-content.adoc)
- [STABLE FUNDAMENTAL] Stage meaning: "During a merge, stage 1 is the common ancestor, stage 2 is the target branch's version (typically the current branch), and stage 3 is the version from the branch which is being merged." (syntax `:<n>:<path>`). — [revisions.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/revisions.adoc)
- [STABLE FUNDAMENTAL] Intent-to-add: `git add -N` — "Record only the fact that the path will be added later. An entry for the path is placed in the index with no content." — [git-add.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-add.adoc)

**References**
- [STABLE FUNDAMENTAL] "References can either refer to: 1. An object ID, usually a commit ID 2. Another reference. This is called a "symbolic reference"". Branches `refs/heads/<name>`, tags `refs/tags/<name>`, remote-tracking branches `refs/remotes/<remote>/<branch>` ("It's how Git stores the last-known state of a branch in a remote repository. `git fetch` updates remote-tracking branches"). — [gitdatamodel.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/gitdatamodel.adoc)
- [STABLE FUNDAMENTAL] HEAD: "`HEAD` can either be: 1. A symbolic reference to your current branch, for example `ref: refs/heads/main` ... 2. A direct reference to a commit ID. In this case there is no current branch. This is called "detached HEAD state"". Symbolic refs: "A symbolic ref is a regular file that stores a string that begins with `ref: refs/`." (files backend). — [gitdatamodel.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/gitdatamodel.adoc); [git-symbolic-ref.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-symbolic-ref.adoc)
- [STABLE FUNDAMENTAL] packed-refs (files backend): "This command is used to solve the storage and performance problem by storing the refs in a single file, `$GIT_DIR/packed-refs`. - [CURRENT BEHAVIOR] Special names, per gitrevisions: `HEAD` "names the commit on which you based the changes in the working tree"; `FETCH_HEAD` "records the branch which you fetched from a remote repository with your last `git fetch` invocation"; `ORIG_HEAD` "is created by commands that move your `HEAD` in a drastic way (`git am`, `git merge`, `git rebase`, `git reset`), to record the position of the `HEAD` before their operation"; `MERGE_HEAD` "records the commit(s) which you are merging into your branch when you run `git merge`"; `REBASE_HEAD` "during a rebase, records the commit at which the operation is currently stopped, either because of conflicts or an `edit` command in an interactive rebase"; `REVERT_HEAD`; `CHERRY_PICK_HEAD` "records the commit which you are cherry-picking"; `BISECT_HEAD`; `AUTO_MERGE` "records a tree object corresponding to the state the 'ort' merge strategy wrote to the working tree when a merge operation resulted in conflicts." — [revisions.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/revisions.adoc)

**`A..B` and `A...B`**
- [STABLE FUNDAMENTAL] For history-walking commands (`git log`): "The '..' (two-dot) Range Notation:: ... you can ask for commits that are reachable from r2 excluding those that are reachable from r1 by '^r1 r2' and it can be written as 'r1..r2'." "The '...' (three-dot) Symmetric Difference Notation:: ... 'r1...r2' is called symmetric difference of 'r1' and 'r2' and is defined as 'r1 r2 --not $(git merge-base --all r1 r2)'. It is the set of commits that are reachable from either one of 'r1' (left side) or 'r2' (right side) but not from both." Omitted ends default to HEAD. — [revisions.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/revisions.adoc)
- [STABLE FUNDAMENTAL] For `git diff`: "`git diff [<options>] <commit>..<commit>` ... This is synonymous to the earlier form (without the `..`) for viewing the changes between two arbitrary `<commit>`." "`git diff [<options>] <commit>...<commit>` ... This form is to view the changes on the branch containing and up to the second `<commit>`, starting at a common ancestor of both `<commit>`. `git diff A...B` is equivalent to `git diff $(git merge-base A B) B`." And explicitly: "`diff` is about comparing two _endpoints_, not ranges, and the range notations (`<commit>..<commit>` and `<commit>...<commit>`) do not mean a range as defined in the "SPECIFYING RANGES" section in gitrevisions(7)." — [git-diff.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/git-diff.adoc)
- [STABLE FUNDAMENTAL] A related trap: "writing two "two-dot range notation" next to each other, e.g. `$ git log A..B C..D` does *not* specify two revision ranges for most commands. Instead it will name a single connected set of commits". — [revisions.adoc](https://github.com/git/git/blob/v2.56.0/Documentation/revisions.adoc)

### Inferences
- The dot notations invert intuition between the two commands: `git log A..B` = "commits on B not on A" while `git diff A..B` = "endpoint diff A versus B"; `git log A...B` = "commits on either side but not both" while `git diff A...B` = "what B did since it forked from A" (the pull-request view). A single side-by-side table is the clearest teaching device.
- gitdatamodel(7) is new enough (2.53) that most existing courses do not cite it; it is the best official one-page reference for learners and is present on the learner's 2.55 (`git help datamodel`).
- Statements such as "a branch is a 41-byte file" should be taught as "in the files backend"; the format-independent truth is "a branch is a ref that names a commit".

### Gaps
- The binary layout of a tree object (commonly described as `<mode> SP <name> NUL <raw object id>` per entry) was not found stated in any man page read for these notes; the fields (mode, type, object ID, name) and the sort order are documented, but the byte-level tree encoding is **UNVERIFIED** here against official text. Demonstrate it with `git cat-file -p <tree>` / `git ls-tree` rather than asserting the raw bytes.
- Optional commit headers beyond the five required fields (`encoding`, `gpgsig`, `mergetag`) are mentioned only indirectly via gitformat-signature; a consolidated official list was not extracted.
