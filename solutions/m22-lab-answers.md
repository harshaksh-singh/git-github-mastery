# Module 22 lab answers: Merge methods and releases on GitHub

> **Baseline.** Git 2.55.0 on macOS; GitHub facts as of 1 October 2026. These are answers to the "Questions" of each lab in the [Module 22 lab manual](../lab-manual/m22-merge-methods-releases.md). Write your own answers first. Commit IDs quoted here are those of the replay scripts. Answers about Part B rest on GitHub's documentation, cited in the manual and in [Chapter 17](../textbook/ch17-pull-requests.md); two of them are deliberately left for you to answer from your own repository, because the documentation does not.

## Lab 22.1: The three merge methods compared

1. **Same tree, different histories.** A merge method does not decide what the code is after the merge. All three compute the same merged content, tree `beff5a6`. The method decides which commit objects carry that content: their number, their parents, their IDs, their committers and their signatures. Every later difference (blame, bisect, revert, `git branch -d`) comes from the commits, not from the content.
2. **Ancestry.** Only in the merge-commit copy (exit status 0). Two commands that differ because of it: `git branch -d`, which is satisfied only when the branch is merged in the sense of reachability, and `git log main..feature/priority-routing`, which is empty there and lists three commits in the other two copies. `git branch --merged` and a later pull request from the same branch behave differently for the same reason.
3. **Warning versus refusal.** `git branch -d` requires the branch to be merged into its upstream, or into `HEAD` when it has no upstream. In the rebase copy the upstream `origin/feature/priority-routing` still existed and pointed at the same commit, so the branch was "merged" into it; Git deleted it and warned that it was not merged into `HEAD`. In the squash copy Asha had deleted the branch on the server and your `pull --prune` had removed the remote-tracking branch, so Git compared with `HEAD` and refused.
4. **`git cherry` in the squash copy.** `+` for all three commits. `git cherry` compares patches commit by commit. After a rebase each commit has a twin on `main` with the same patch. After a squash, `main` has one commit whose patch is the sum of the three, which equals none of them. Chapter 17, section 17.9 shows the transcript.
5. **Signatures and committers.** Expected from the documentation: the merge commit and the squash commit have a `gpgsig` header, because GitHub signs commits it creates in the web flow, and the rebased commits have none, because rebase and merge adds commits "without commit signature verification". Compare the committers you read with `git log --format=fuller`. Consequence: on a branch that requires signed commits, "Rebase and merge" cannot be used, and for the other two methods the commits on the head branch must still be signed, because the rule evaluates the commits that the test merge introduces.
6. **The author of the squash commit.** No answer is given here on purpose. The live documentation does not state it, and the Phase 0 report marks it unverified. Your `git log --format=fuller -1 origin/base/squash` and the body of that commit message are the evidence; note the author, the committer and any trailers.
7. **Undoing.** Merge commit: one command, `git revert -m 1 <merge>`, and you must know which parent is the mainline (and remember to revert the revert before merging the branch again). Squash: one command, `git revert <commit>`. Rebase: one revert per commit or a range, `git revert <first>^..<last>`, and you must know where the pull request began and ended, which nothing in the history marks.

## Lab 22.2: A release from an annotated tag

1. **Two lines.** The first is the ID of the tag object that `refs/tags/v0.1.0` points at (`4f7a52d`). The second, with the suffix `^{}`, is the object the tag object points at after peeling, the commit `9a383e5`. A lightweight tag would have one line: the commit.
2. **`git describe` and the lightweight tag.** By default `git describe` uses annotated tags only. `v0.2.0` was a plain ref to a commit, so it was ignored, and the nearest annotated tag was `v0.1.0`, one commit back: `v0.1.0-1-gbab2607`. With `--tags` it considered the lightweight tag and printed `v0.2.0`.
3. **Git data and GitHub data.** Git data: the tag ref, the tag object, and the commit and tree behind it. GitHub data: the release title, the notes, the assets, and the draft, pre-release and latest flags. A fresh clone contains the tags and nothing of the release.
4. **`--verify-tag`.** From a release created for a tag name that does not exist, in which case the platform creates the tag itself from the tip of the default branch: a tag you did not make, on a commit you did not choose, without a tagger or a message.
5. **Deleting and re-creating a published tag.** It is acceptable here because both versions name the same commit and almost nobody can have fetched the wrong one in the minutes between; the danger of a moved tag is that people who already have it keep the old meaning without any warning. In a real project you would announce it, or prefer a new version number. On GitHub, a tag ruleset that restricts updates and deletions forbids it, and so does an immutable release, which locks the tag of a published release.
6. **The type of the platform-made tag.** Read it with `git cat-file -t v0.2.0`. The lab expects `commit`, a lightweight tag, as in the local imitation; the help text of `gh release create` says only that a tag "will automatically get created". If you saw `tag`, GitHub created an annotated tag, and `git cat-file -p v0.2.0` shows its tagger. Either way, record it: this is one of the places where the course defers to your observation.
