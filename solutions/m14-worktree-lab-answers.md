## Lab 14.1: A hotfix in a second worktree while a rebase is in progress

1. **Shared or per worktree.** Per worktree: HEAD, the index, and the directory `rebase-merge`. Shared: the branch `main`, like every ref under `refs/`, and the object database. The command that settles it for any path is `git rev-parse --git-path <path>`, run in each worktree: a path that resolves into `.git/worktrees/<name>/` is private, a path that resolves into the repository's `.git/` is shared. The lab's last two commands did this for `rebase-merge` (section 25.3).
2. **Detached, and still in use.** A rebase detaches HEAD at the new base and replays the commits there; it moves the branch ref only when it finishes, which is why the last line of the rebase said "updated refs/heads/feature/rerank". Until then HEAD names a commit, and `git worktree list` reports what HEAD says. The rebase state records which branch it will move, and Git counts a branch that is being rebased in a worktree as in use by that worktree. A second checkout of `feature/rerank` would let you commit on a branch that the rebase is about to overwrite, so `git worktree add` refuses it with the "already used by worktree" error of section 25.4.
3. **The stale claim.** The claim was in `.git/worktrees/rag-api-hotfix/HEAD`, which still contained `ref: refs/heads/hotfix/empty-question`. `rm -rf` deleted the working tree, which lies outside the repository; it could not touch the entry inside `.git`. Git noticed only that the `gitdir` file of the entry points to a place that no longer exists, and marked the entry `prunable`. An entry that exists still protects its branch.
4. **A commit on a detached HEAD in a removed worktree.** The commit object is in the shared object database, and no ref reaches it. The only thing that named it was the worktree's own HEAD and its reflog, and both were deleted with `.git/worktrees/<name>/`. Look for it from the main worktree with `git fsck --lost-found`, which lists it as a dangling commit, then inspect it with `git show <id>` and give it a name with `git branch rescue/<name> <id>`. Do this before a garbage collection prunes unreachable objects. Prevention: create a branch before you remove a detached worktree (section 25.8).
5. **Where the fix ends up.** The fix reaches `main` when `hotfix/empty-question` is merged, and `feature/rerank` does not need to contain it for that: when the feature is merged later, the merge combines both lines, and the fix, which the feature never touched, stays. If the feature needs the fix now, wait for the hotfix to be merged and then rebase the feature onto the new `main` (or merge `main` into it, if the branch is shared). A cherry-pick of `63fb99e` onto the feature also works and is the worse choice: it creates a second commit with the same change, which a later rebase has to recognise and drop and which shows up twice in a merge-based history.
6. **Not there, and shared.** The second worktree had no ignored files: no virtual environment, no `.env`, no build output. Ignored files belong to no commit, so a checkout cannot produce them, and each worktree needs its own setup step. It also had no untracked files of the first worktree and none of its uncommitted changes. Shared, and surprising: the stash. `refs/stash` lies under `refs/`, so there is one stash list for all worktrees, and a `git stash pop` in one worktree can apply an entry that was made for another task in another directory (section 25.7). The configuration file is shared as well, unless `extensions.worktreeConfig` is on.
