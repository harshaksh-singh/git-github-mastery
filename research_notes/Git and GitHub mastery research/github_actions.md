# GitHub Actions (CI/CD on GitHub) and its security model — state as of 1 October 2026

> **How to read these notes.** Everything below was observed on **2026-10-01 (UTC)** from primary sources (docs.github.com, github.blog/changelog, the GitHub REST API for each action repository's releases, action READMEs at their release tags, vendor post-mortems, CISA). Each finding carries a status label: **[CURRENT]** = documented behavior today; **[CHANGED yyyy-mm-dd]** = behavior that changed recently (date of the change/announcement); **[PLAN-GATED]** = depends on GitHub plan; **[DEPRECATED]** = retired or on a retirement path; **[UNVERIFIED]** = could not be confirmed from an authoritative source (what was tried is stated). Action release tags and dates were read with `gh api repos/<owner>/<repo>/releases` on 2026-10-01.

## 1. Workflow syntax, current state (events, filters, jobs, expressions/contexts, permissions, concurrency, matrix, outputs, reusable workflows, action types, 2025–2026 additions)

### Takeaway
The core model (events → jobs → steps, contexts/expressions, `permissions`, `concurrency`, matrix, reusable workflows) is unchanged, but 2025–2026 added real syntax: YAML anchors (Sep 2025), the `case()` function (Jan 2026), cron `timezone` and `environment.deployment: false` (Mar 2026), service-container `entrypoint`/`command` (Apr 2026), `concurrency.queue: max` (May 2026), step-level `background`/`wait`/`wait-all`/`cancel`/`parallel` (Jun 2026), the `$/` self-repository reference (Jul 2026), and `cache-mode` plus the `vulnerability-alerts` permission and `job.workflow_*` context (Sep 2026). `set-output`/`save-state` are deprecated but still functional; use `$GITHUB_OUTPUT`/`$GITHUB_STATE`.

### Cited Findings

#### Files, events and triggers
- [CURRENT] Workflow files are YAML with `.yml` or `.yaml` extension and "You must store workflow files in the `.github/workflows` directory of your repository." Subdirectories of `workflows` are not supported for reusable workflows. — [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax); [Reuse workflows](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows)
- [CURRENT] `on` accepts a single event (`on: push`), a list (`on: [push, fork]`), or a map with activity `types` and filters. With multiple configured events "You must append a colon (`:`) to all events, including events without configuration." If multiple triggering events occur at once, multiple runs start. — [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)
- [CURRENT] Events documented on 2026-10-01 (page headings): `branch_protection_rule`, `check_run`, `check_suite`, `create`, `delete`, `deployment`, `deployment_status`, `discussion`, `discussion_comment`, `fork`, `gollum`, `image_version`, `issue_comment`, `issues`, `label`, `merge_group`, `milestone`, `page_build`, `public`, `pull_request`, `pull_request_comment` (use `issue_comment`), `pull_request_review`, `pull_request_review_comment`, `pull_request_target`, `push`, `registry_package`, `release`, `repository_dispatch`, `schedule`, `status`, `watch`, `workflow_call`, `workflow_dispatch`, `workflow_run`. "Not all webhook events trigger workflows." — [Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)
- [CURRENT] `push`: `GITHUB_SHA` = "Tip commit pushed to the ref", `GITHUB_REF` = updated ref. Runs for commit or tag pushes, "This includes workflows that are not merged into the default branch." Limits: "Events will not be created if more than 5,000 branches are pushed at once. Events will not be created for tags when more than three tags are pushed at once." — [Events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#push)
- [CURRENT] `pull_request`: default activity types are `opened`, `synchronize`, `reopened` (others such as `labeled`, `closed`, `ready_for_review`, `enqueued`, `dequeued` need `types:`). `GITHUB_REF` = `refs/pull/PULL_REQUEST_NUMBER/merge`, `GITHUB_SHA` = "Last merge commit on the `GITHUB_REF` branch". "Workflows will not run on `pull_request` activity if the pull request has a merge conflict." To run on merge, use `types: [closed]` with `if: github.event.pull_request.merged == true`. — [Events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request)
- [CURRENT] `pull_request_target`: same activity types, but `GITHUB_SHA` = "Last commit on default branch" and `GITHUB_REF` = "Default branch". "This event runs in the context of the default branch of the base repository, rather than in the context of the merge commit, as the `pull_request` event does." It runs even if the PR has a merge conflict. "Avoid using this event if you need to build or run code from the pull request." — [Events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request_target)
- [CHANGED 2025-12-08] `pull_request_target` now *always* takes the workflow file and checkout commit from the repository's default branch "regardless of the pull request's base branch"; `GITHUB_REF` resolves to the default branch and `GITHUB_SHA` to its latest commit. Previously any base branch could supply the (possibly outdated, vulnerable) workflow. Environment branch protection rules for PR events now evaluate against the execution ref (`refs/pull/number/merge` for `pull_request`; default branch for `pull_request_target`). Announced 2025-11-07. — [Changelog 2025-11-07](https://github.blog/changelog/2025-11-07-actions-pull_request_target-and-environment-branch-protections-changes/)
- [CURRENT] `workflow_dispatch`: "This event will only trigger a workflow run if the workflow file exists on the default branch." Input types: "`boolean`, `choice`, `number`, `environment` or `string`". "The maximum number of top-level properties for `inputs` is 25" and "The maximum payload for `inputs` is 65,535 characters." Values are read from the `inputs` context (booleans preserved) or `github.event.inputs` (strings). — [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onworkflow_dispatch); [Events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch)
- [CHANGED 2025-12-04] `workflow_dispatch` input limit raised from 10 to 25. — [Changelog 2025-12-04](https://github.blog/changelog/2025-12-04-actions-workflow-dispatch-workflows-now-support-25-inputs/)
- [CHANGED 2026-02-19] The workflow dispatch REST endpoint accepts an optional `return_run_details` boolean and then returns 200 with workflow run ID/URLs instead of 204; GitHub CLI ≥ 2.87.0 `gh workflow run` prints the created run URL. — [Changelog 2026-02-19](https://github.blog/changelog/2026-02-19-workflow-dispatch-api-now-returns-run-ids/)
- [CURRENT] `workflow_call` marks a workflow as reusable; the called workflow receives the caller's event payload, `GITHUB_SHA` and `GITHUB_REF`. Input `type` is required and must be `boolean`, `number`, or `string`; defaults are `false`, `0`, `""`. Passing an input or secret not declared by the called workflow is an error. — [Events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_call); [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onworkflow_callinputs)
- [CURRENT] `workflow_run`: activity types `completed`, `requested`, `in_progress`; runs with `GITHUB_SHA`/`GITHUB_REF` of the default branch; "This event will only trigger a workflow run if the workflow file exists on the default branch"; "You can't use `workflow_run` to chain together more than three levels of workflows"; and "The workflow started by the `workflow_run` event is able to access secrets and write tokens, even if the previous workflow was not." Filter on `github.event.workflow_run.conclusion`; `branches`/`branches-ignore` refer to the triggering workflow's branch. — [Events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run)
- [CURRENT] `schedule`: POSIX cron (5 fields); "By default, scheduled workflows run in UTC"; "Scheduled workflows run on the latest commit on the default branch. The shortest interval you can run scheduled workflows is once every 5 minutes." Runs "can be delayed during periods of high loads… High load times include the start of every hour. If the load is sufficiently high enough, some queued jobs may be dropped." "In a public repository, scheduled workflows are automatically disabled when no repository activity has occurred in 60 days." `@daily`-style shortcuts are not supported. — [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onschedule); [Events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)
- [CHANGED 2026-03-19] Cron schedules accept an IANA `timezone` field next to `cron` (e.g. `timezone: "America/New_York"`); in DST spring-forward gaps the run advances to the next valid time. — [Changelog 2026-03-19](https://github.blog/changelog/2026-03-19-github-actions-late-march-2026-updates/); [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onschedule)
- [CURRENT] `merge_group`: only activity type `checks_requested`; `GITHUB_SHA`/`GITHUB_REF` are the merge group's. Workflows that provide required checks must add `merge_group` "Otherwise, status checks will not be triggered when you add a pull request to a merge queue." Supports `branches`/`branches-ignore`. — [Events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#merge_group)
- [CURRENT] `release`: types `published`, `unpublished`, `created`, `edited`, `deleted`, `prereleased`, `released`; `GITHUB_REF` = `refs/tags/<tag_name>`. Draft releases do not trigger `created`/`edited`/`deleted`; "If you want a workflow to run when stable *and* pre-releases publish, subscribe to `published`". — [Events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#release)
- [CURRENT] `issue_comment`: types `created`, `edited`, `deleted`; fires for comments on issues *and* pull requests; runs with the default branch's SHA/ref and only if the workflow file is on the default branch. Distinguish with `if: ${{ github.event.issue.pull_request }}`. — [Events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#issue_comment)
- [CURRENT] Events caused by the repository `GITHUB_TOKEN` do not create new workflow runs, except `workflow_dispatch` and `repository_dispatch`, and (new) `pull_request` `opened`/`synchronize`/`reopened`, which create runs in an approval-required state. "Commits pushed by a GitHub Actions workflow that uses the `GITHUB_TOKEN` do not trigger a GitHub Pages build." — [GITHUB_TOKEN concept](https://docs.github.com/en/actions/concepts/security/github_token)
- [CHANGED 2026-06-11] "Pull requests created by the github-actions[bot] are now able to run your CI/CD workflows with user approval" (previously they ran no workflows at all). — [Changelog 2026-06-11](https://github.blog/changelog/2026-06-11-bot-created-pull-requests-can-run-workflows-if-approved/)
- [CURRENT] Skip instructions: `[skip ci]`, `[ci skip]`, `[no ci]`, `[skip actions]`, `[actions skip]` in the commit message (or a `skip-checks: true` trailer) skip `push`/`pull_request` workflows only; they do not affect `pull_request_target`. — [Skipping workflow runs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/skip-workflow-runs)

#### Filters (branches, tags, paths)
- [CURRENT] `push` supports `branches`, `branches-ignore`, `tags`, `tags-ignore`; `pull_request`/`pull_request_target` support `branches`/`branches-ignore` (matching the *base* branch); `push`/`pull_request`/`pull_request_target` support `paths`/`paths-ignore`. "You cannot use both the `branches` and `branches-ignore` filters for the same event" (same for paths); use `!` negation inside the positive filter, and order matters. If both branch and path filters are defined, "the workflow will only run when both filters are satisfied." "Path filters are not evaluated for pushes of tags." — [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onpushpull_requestpull_request_targetpathspaths-ignore)
- [CURRENT] Path diffs: three-dot diff for pull requests, two-dot for pushes. Limits: "If a push contains more than 1,000 commits, the workflow will **always** run"; "If generating the diff times out, the workflow will **always** run"; if the diff has more than 3,000 files and the match is not within the first 3,000, "the workflow will **not** run." — [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#git-diff-comparisons)
- [CURRENT] Glob cheat sheet: `*` (no `/`), `**`, `?`, `+`, `[]`, leading `!`. Patterns starting with `*`, `[`, or `!` must be quoted in YAML. — [Workflow syntax, filter pattern cheat sheet](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#filter-pattern-cheat-sheet)

#### Jobs, steps, `runs-on`, `needs`, `if`
- [CURRENT] `runs-on` may be a string, a variable, an array (the runner must match *all* labels, e.g. `[self-hosted, linux, x64, gpu]`), or a mapping with `group` and/or `labels`. Expressions need quotes (`"${{ inputs.chosen-os }}"`). — [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idruns-on)
- [CURRENT] Runner groups: `runs-on: { group: build-runners }` or `group` + `labels` (runner must satisfy both). "Runner groups can only have larger runners or self-hosted runners as members." (Since 2026-06-25, macOS runners can be added to runner groups and standard labels such as `ubuntu-latest` can be disabled org-wide — Team/Enterprise.) — [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#choosing-runners-in-a-group); [Changelog 2026-06-25](https://github.blog/changelog/2026-06-25-more-control-over-your-github-hosted-runners/)
- [CURRENT] `needs`: "If a job fails or is skipped, all jobs that need it are skipped unless the jobs use a conditional expression that causes the job to continue." Use `if: ${{ always() }}` (or `!cancelled()`) to run regardless. — [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idneeds)
- [CURRENT] `if`: `${{ }}` is optional in `if`, except when the expression starts with `!`. "The `jobs.<job_id>.if` condition is evaluated before `jobs.<job_id>.strategy.matrix` is applied." A skipped job is "marked as *skipped*". — [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idif)
- [CHANGED 2026-01-29] `if:` conditions with text outside `${{ }}` (which makes the whole value an always-truthy string) are now caught by editor validation and produce a run annotation; skipped-job logs now show the original and expanded expression (download the job log archive, open `JOB-NAME/system.txt`, look for `Evaluating`/`Expanded`/`Result`). — [Changelog 2026-01-29](https://github.blog/changelog/2026-01-29-github-actions-smarter-editing-clearer-debugging-and-a-new-case-function/); [Troubleshooting workflows](https://docs.github.com/en/actions/how-tos/troubleshoot-workflows)
- [CURRENT] `steps[*].run` runs "command-line programs that do not exceed 21,000 characters"; each `run` is a new process/shell. `steps[*].uses` selects an action by `{owner}/{repo}@{ref}`, `{owner}/{repo}/{path}@{ref}`, `$/path` (same repo, running commit), `./path` (checked-out workspace), or `docker://image:tag`. — [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idstepsrun)
- [CURRENT] `continue-on-error` (step or job) lets the job/run pass when that step/job fails. `jobs.<job_id>.timeout-minutes` default is 360; step `timeout-minutes` max 360, positive integers only. "The `GITHUB_TOKEN` expires when a job finishes or after a maximum of 24 hours." — [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idtimeout-minutes)

#### Expressions and contexts
- [CURRENT] Contexts: `github`, `env`, `vars`, `job`, `jobs` (reusable workflows only), `steps`, `runner`, `secrets`, `strategy`, `matrix`, `needs`, `inputs`. Dereferencing a nonexistent property yields an empty string. — [Contexts reference](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts)
- [CURRENT] Context availability is per key. Examples: workflow-level `concurrency` and `run-name` allow only `github, inputs, vars`; `jobs.<job_id>.if` allows `github, needs, vars, inputs`; `jobs.<job_id>.steps.if` allows `github, needs, strategy, matrix, job, runner, env, vars, steps, inputs` — i.e. `secrets` cannot be used directly in an `if`; `jobs.<job_id>.runs-on` allows `github, needs, strategy, matrix, vars, inputs`; `hashFiles` only in step keys. — [Contexts reference, context availability](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#context-availability)
- [CURRENT] Useful `github` properties: `github.event` (full webhook payload), `github.event_name`, `github.ref` / `ref_name` (`<pr_number>/merge` for unmerged PRs) / `ref_type` / `ref_protected`, `github.sha`, `github.head_ref` and `github.base_ref` (only on `pull_request`/`pull_request_target`), `github.actor` vs `github.triggering_actor` ("Any workflow re-runs will use the privileges of `github.actor`"), `github.run_id`, `github.run_number`, `github.run_attempt`, `github.workflow`, `github.workflow_ref`, `github.workflow_sha`, `github.token`, `github.workspace`. `runner.os` (`Linux`/`Windows`/`macOS`), `runner.arch` (`X86`/`X64`/`ARM`/`ARM64`), `runner.temp`, `runner.debug`, `runner.environment` (`github-hosted`/`self-hosted`). `job.status`, `job.services.<id>.ports`, `job.check_run_id`. — [Contexts reference](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#github-context)
- [CHANGED 2025-09-18 / 2026-09-03] `job.check_run_id` added (2025-09-18). `job.workflow_ref`, `job.workflow_sha`, `job.workflow_repository`, `job.workflow_file_path` added (2026-09-03): they identify the workflow file that *defines* the job, so they differ from `github.workflow_ref` only inside reusable workflows; not available on GHES. — [Changelog 2025-09-18](https://github.blog/changelog/2025-09-18-actions-yaml-anchors-and-non-public-workflow-templates/); [Changelog 2026-09-03](https://github.blog/changelog/2026-09-03-github-actions-early-september-2026-updates/)
- [CURRENT] Result fields: `needs.<job_id>.result` is `success`, `failure`, `cancelled`, or `skipped`; `steps.<step_id>.outcome` is the result before `continue-on-error` is applied and `steps.<step_id>.conclusion` the result after ("When a `continue-on-error` step fails, the `outcome` is `failure`, but the final `conclusion` is `success`"). — [Contexts reference](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#needs-context)
- [CURRENT] `secrets` context "is not available for composite actions due to security reasons"; pass secrets to composite actions as inputs. — [Contexts reference](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#secrets-context)
- [CURRENT] Expression facts: literals `boolean`, `null`, `number`, `string` (single quotes inside `${{ }}`; double quotes are an error); operators `( ) [ ] . ! < <= > >= == != && ||`; "GitHub ignores case when comparing strings"; loose equality coerces to number; falsy values are `false`, `0`, `-0`, `""`, `''`, `null`. Functions: `contains`, `startsWith`, `endsWith`, `format`, `join`, `toJSON`, `fromJSON`, `hashFiles`, `case`; status functions `success()` (implicit default), `always()`, `cancelled()`, `failure()`. Docs warn against `always()` for critical tasks and recommend `if: ${{ !cancelled() }}`. Object filter syntax `array.*.prop`. — [Expressions](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions)
- [CHANGED 2026-01-29] New `case( pred1, val1, pred2, val2, ..., default )` function (true if/else-if/else; replaces the `&&`/`||` ternary hack). — [Changelog 2026-01-29](https://github.blog/changelog/2026-01-29-github-actions-smarter-editing-clearer-debugging-and-a-new-case-function/); [Expressions](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions#case)
- [CURRENT] Default environment variables include `CI` ("Always set to `true`"), `GITHUB_ACTIONS`, `GITHUB_REF`, `GITHUB_SHA`, `GITHUB_HEAD_REF`/`GITHUB_BASE_REF` (PR events only), `GITHUB_WORKSPACE`, `RUNNER_OS`, `RUNNER_ARCH`, `RUNNER_DEBUG`. — [Variables reference](https://docs.github.com/en/actions/reference/workflows-and-actions/variables)

#### `permissions`
- [CURRENT] `permissions` can be set at workflow level or per job. Scopes listed on 2026-10-01: `actions`, `artifact-metadata`, `attestations`, `checks`, `code-quality`, `contents`, `deployments`, `discussions`, `id-token` (`write|none`), `issues`, `packages`, `pages`, `pull-requests`, `security-events`, `statuses`, `vulnerability-alerts` (`read|none`). Values `read|write|none`; "`write` includes `read`"; shorthand `permissions: read-all`, `permissions: write-all`, `permissions: {}`. "If you specify the access for any of these permissions, all of those that are not specified are set to `none`." — [Workflow syntax, permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)
- [CHANGED 2026-09-03] New `vulnerability-alerts` permission gives read-only access to Dependabot alerts (`read`/`none` only; auto-included as `read` under `read-all`/`write-all`). — [Changelog 2026-09-03](https://github.blog/changelog/2026-09-03-github-actions-early-september-2026-updates/)
- [CURRENT] For fork PRs "You can use the `permissions` key to add and remove read permissions for forked repositories, but typically you can't grant write access" (exception: the private-repo setting "Send write tokens to workflows from pull requests"). Dependabot-triggered runs "run as if they are from a forked repository, and therefore use a read-only `GITHUB_TOKEN`. These workflow runs cannot access any secrets." — [Workflow syntax, permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)

#### `concurrency`
- [CURRENT] `concurrency` (workflow or job level) allows at most one running job/workflow per group. Group expressions may use only `github`, `inputs`, `vars` (job level additionally `needs`, `strategy`, `matrix`). Default: a newly queued run is `pending` and "any existing `pending` job or workflow in the same concurrency group will be canceled". `cancel-in-progress: true` (or an expression) also cancels the running one. "The concurrency group name is case insensitive." Ordering is FIFO but "not guaranteed". Typical group: `${{ github.workflow }}-${{ github.ref }}`; fallback idiom `${{ github.head_ref || github.run_id }}`. — [Workflow syntax, concurrency](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency)
- [CHANGED 2026-05-07] New `queue` property: `single` (default: one pending, replaced by newer) or `max` (up to 100 pending jobs/runs per group, processed sequentially; extra runs canceled). "The combination of `queue: max` and `cancel-in-progress: true` is not allowed and will result in a workflow validation error." — [Changelog 2026-05-07](https://github.blog/changelog/2026-05-07-github-actions-concurrency-groups-now-allow-larger-queues/); [Workflow syntax, concurrency](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency)
- [CURRENT] Reusable-workflow gotcha: a called workflow sees the caller's name in `github.workflow`, so using the same `concurrency.group` with `cancel-in-progress: true` in caller and callee cancels the caller. — [Reusing workflow configurations](https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations)

#### `strategy.matrix`
- [CURRENT] "A matrix will generate a maximum of 256 jobs per workflow run." Variable names are case-insensitive. `include` adds keys to matching combinations or creates new combinations ("original matrix values will not be overwritten, but added matrix values can be overwritten"); a matrix may consist only of `include`. `exclude` removes combinations by partial match and "All `include` combinations are processed after `exclude`." `fail-fast` defaults to `true` (cancels in-progress and queued matrix jobs when one fails). `max-parallel` caps concurrency (default: maximize). Job-level `continue-on-error: ${{ matrix.experimental }}` lets specific legs fail. Matrix job outputs are merged, last writer wins ("Actions does not guarantee the order that matrix jobs will run in"). — [Workflow syntax, strategy](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idstrategymatrix)

#### `defaults.run`, shells
- [CURRENT] `defaults.run.shell` and `defaults.run.working-directory` at workflow or job level. Shell templates: unspecified on Linux/macOS → `bash -e {0}`; explicit `shell: bash` → `bash --noprofile --norc -eo pipefail {0}`; Windows default `pwsh`; also `sh`, `cmd`, `powershell`, `python`, or a custom `command {0}` template. Note: `-o pipefail` is only applied when `shell: bash` is written explicitly. Inside a job `container`, "The default shell for `run` steps inside a container is `sh` instead of `bash`." — [Workflow syntax, shell](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idstepsshell)

#### `container` and `services`
- [CURRENT] Job containers, service containers and Docker container actions require a Linux runner ("If you are using GitHub-hosted runners, you must use an Ubuntu runner"). Service hostnames equal the service key when the job itself runs in a container; otherwise map ports and use `localhost` (dynamic ports via `${{ job.services.<name>.ports['6379'] }}`). An empty-string `image` disables a service (conditional services). `options` does not support `--network`. `credentials` (`username`/`password`) for private registries. — [Workflow syntax, services](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idservices)

#### Outputs, `GITHUB_OUTPUT`, `GITHUB_ENV`, `GITHUB_STEP_SUMMARY`, deprecated commands
- [CURRENT] Step output: `echo "{name}={value}" >> "$GITHUB_OUTPUT"` (step needs an `id`); job output maps `outputs: { x: ${{ steps.id.outputs.x }} }`; downstream jobs read `needs.<job>.outputs.x`. "Outputs can be a maximum of 1 MB per job. The total of all outputs in a workflow run can be a maximum of 50 MB." Outputs that look like secrets are skipped ("Skip output … since it may contain secret"). — [Workflow commands](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands#setting-an-output-parameter); [Workflow syntax, outputs](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idoutputs)
- [CURRENT] `GITHUB_ENV`: `echo "NAME=value" >> "$GITHUB_ENV"`; "The step that creates or updates the environment variable does not have access to the new value, but all subsequent steps in a job will have access." Cannot override `GITHUB_*`/`RUNNER_*`; "`GITHUB_ENV` cannot be used to set the `NODE_OPTIONS` environment variable." Multiline values use `{name}<<{delimiter}` heredoc syntax. `GITHUB_PATH` prepends to `PATH` for later steps. `GITHUB_STATE` passes values to an action's `pre`/`post` (as `STATE_*`). — [Workflow commands](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands#environment-files)
- [CURRENT] `GITHUB_STEP_SUMMARY`: append GitHub-flavored Markdown; per-step file; "each step is restricted to a maximum size of 1MiB… A maximum of 20 job summaries from steps are displayed per job." — [Workflow commands](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands#adding-a-job-summary)
- [CURRENT] New environment files documented in 2026: `GITHUB_ARTIFACTS` (declare files or OCI digests as "workflow artifacts"; max 500 per job) and read-only `GITHUB_ARTIFACTS_LIST`; also exposed as `github.artifacts`/`github.artifacts_list`. — [Workflow commands](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands#declaring-workflow-artifacts)
- [DEPRECATED] `::set-output` and `::save-state` stdout commands: deprecated 2022-10-11 (runner 2.298.2 warns); the planned 2023-05-31 disablement was postponed on 2023-07-24 ("Workflows using `save-state` or `set-output` … will continue to work as expected, however, a warning will appear"). The current workflow-commands docs page no longer documents them at all. Other masking/annotation commands (`::add-mask::`, `::error`, `::warning`, `::notice`, `::group::`, `::debug::`) remain current. — [Changelog 2022-10-11](https://github.blog/changelog/2022-10-11-github-actions-deprecating-save-state-and-set-output-commands/); [Changelog 2023-07-24](https://github.blog/changelog/2023-07-24-github-actions-update-on-save-state-and-set-output-commands/); [actions/runner ActionCommandManager.cs @ v2.337.0](https://github.com/actions/runner/blob/v2.337.0/src/Runner.Worker/ActionCommandManager.cs); [Workflow commands](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands)

#### Reusable workflows
- [CURRENT] Call with `jobs.<job_id>.uses`: `$/.github/workflows/{file}` (same repo, recommended; not on GHES), `{owner}/{repo}/.github/workflows/{file}@{ref}`, or `./.github/workflows/{file}`. "You cannot use contexts or expressions in this keyword." Only these job keys are allowed on a calling job: `name`, `uses`, `with`, `secrets` (incl. `secrets: inherit`), `strategy`, `needs`, `if`, `concurrency`, `permissions`, `cache-mode`. — [Workflow syntax, jobs.uses](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_iduses); [Reusing workflow configurations](https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations)
- [CHANGED 2025-11-06] Limits: "You can connect up to ten levels of workflows" (top-level caller plus up to nine reusable levels) and "call a maximum of 50 unique reusable workflows from a single workflow file" (previously 4 levels and 20 workflows). Loops are not permitted. — [Changelog 2025-11-06](https://github.blog/changelog/2025-11-06-new-releases-for-github-actions-november-2025/); [Reusing workflow configurations](https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations#limitations-of-reusable-workflows)
- [CURRENT] `secrets: inherit` passes "all the calling workflow's secrets… namely organization, repository, and environment secrets", within the same organization or enterprise. Secrets pass only one level (A→B→C needs re-passing). "Environment secrets cannot be passed from the caller workflow as `on.workflow_call` does not support the `environment` keyword." Caller workflow-level `env` is not propagated; use outputs/`vars`. `GITHUB_TOKEN` permissions "can be only downgraded (not elevated) by the called workflow". Outputs: `on.workflow_call.outputs.<id>.value: ${{ jobs.<job>.outputs.<name> }}` → caller reads `needs.<job>.outputs.<id>`. Billing and GitHub-hosted runner assignment always use the caller's context. — [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idsecretsinherit); [Reuse workflows](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows); [Reusing workflow configurations](https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations)
- [CURRENT] Re-run semantics: re-running *all* jobs re-resolves a non-SHA reusable-workflow ref; re-running failed/specific jobs uses "the same commit SHA of the first attempt". — [Reusing workflow configurations](https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations#behavior-of-reusable-workflows-when-re-running-jobs)

#### Composite vs JavaScript vs Docker container actions
- [CURRENT] Three action types, defined by `action.yml`/`action.yaml` `runs.using`: JavaScript (`node24`; docs also still list `node20`), composite (`using: 'composite'` with `runs.steps`; each `run` step requires `shell`), Docker container (`using: 'docker'`, Linux runners only, slower "Because of the latency to build and retrieve the container"). ### Inferences
- Because `secrets` is not an allowed context for `if`, the standard way to make a step conditional on a secret being present is to map it into `env:` and test `env.X != ''` (GitHub's own syntax page shows this "Using secrets" example pattern under `steps[*].if`).
- The combination of YAML anchors, `$/` references and `parallel:` reduces much of the boilerplate that older courses solved with composite actions; however these features are github.com-only or runner-version-gated (`$/` needs runner ≥ 2.336.0 and is absent on GHES), so examples for mixed fleets should say so.
- A course example that needs pipe failures to fail a step should write `shell: bash` explicitly (or set `defaults.run.shell: bash`), since the implicit default omits `-o pipefail`.

### Gaps
- YAML merge keys (`<<:`) are not mentioned in the anchors documentation; whether they are accepted was not verified (tried: docs page "Reusing workflow configurations" and the 2025-09-18 changelog — neither mentions merge keys). Treat as UNVERIFIED and avoid in examples.
- The workflow-level dependency lock (`dependencies:` section) announced in GitHub's 2026 security roadmap (2026-03-26) does **not** appear in the workflow syntax reference or the Actions changelog as of 2026-10-01; do not present it as available syntax. — [Roadmap post](https://github.blog/news-insights/product-news/whats-coming-to-our-github-actions-2026-security-roadmap/)
- The `permissions` list above is exactly what the docs page shows today; a `models` scope (seen in 2025 material) is not on the page as of 2026-10-01 — not investigated further.

## 2. GitHub-hosted runners (labels, `-latest` mappings, image retirements, arm64, larger and GPU runners, specs) and self-hosted runners (security warning, groups, ARC, ephemeral/JIT, minimum version)

### Takeaway
On 1 October 2026: `ubuntu-latest` = Ubuntu 24.04 (migration to Ubuntu 26.04 is scheduled for 19 Oct – 19 Nov 2026), `windows-latest` = Windows Server 2025 with Visual Studio 2026 (since June 2026), `macos-latest` = macOS 26 on arm64 (since June–July 2026). `ubuntu-20.04`, `windows-2019` and `macos-13` are gone; `ubuntu-22.04` entered deprecation on 17 Sep 2026 (retirement 17 Apr 2027) and `macos-14` retires 2 Nov 2026. Self-hosted runners must be ≥ 2.329.0 to register and must take every runner update within 30 days (enforced on github.com from 29 Sep 2026); GitHub still says self-hosted runners "should almost never be used for public repositories".

#### Self-hosted runners
- [CURRENT] Security warning (verbatim): "self-hosted runners should almost never be used for public repositories on GitHub, because any user can open pull requests against the repository and compromise the environment. GitHub-hosted runners are "ephemeral and clean isolated virtual machines"; self-hosted runners "can be persistently compromised by untrusted code in a workflow." — [Secure use reference, hardening for self-hosted runners](https://docs.github.com/en/actions/reference/security/secure-use#hardening-for-self-hosted-runners)

- [CURRENT] Ephemeral and JIT runners: "GitHub recommends implementing autoscaling with ephemeral self-hosted runners; autoscaling with persistent self-hosted runners is not recommended." `./config.sh --url … --token … --ephemeral` registers a runner that is de-registered after one job. ### Inferences
- A course written today should say "`ubuntu-latest` is Ubuntu 24.04 now and becomes Ubuntu 26.04 during Oct 19 – Nov 19, 2026", and recommend pinning an explicit image label for reproducibility; all three `-latest` labels moved (or will move) in 2026.
- Because public-repo standard runners have 4 vCPU/16 GB and private-repo ones 2 vCPU/8 GB, a build that fits in an open-source repo can run out of memory or time after the same repository is made private (or in a private fork) — a concrete "passes there, fails here" cause.
- The minimum-version enforcement mostly bites container-image-based fleets (ARC with `disableUpdate`, golden AMIs) rather than auto-updating runners.

## 3. JavaScript action runtime transitions (Node 16 → Node 20 → Node 24)

### Takeaway
Node 24 is the only JavaScript action runtime on github.com runners as of 23 September 2026: runners defaulted to Node 24 on 16 June 2026 and Node 20 was removed on 23 September 2026 (the `ACTIONS_ALLOW_USE_UNSECURE_NODE_VERSION` opt-out no longer works). Every action major that predates its Node 24 release line must be upgraded; the Node 24 majors require runner ≥ 2.327.1.

### Cited Findings
- [DEPRECATED] Node 12 → Node 16: all actions ran on Node 16 instead of Node 12 from mid-2023; Node 12 removed from the runner (changelogs 2023-05-04, 2023-06-13, 2023-07-17). — [Changelog 2023-06-13](https://github.blog/changelog/2023-06-13-github-actions-all-actions-will-run-on-node16-instead-of-node12-by-default/)
- [DEPRECATED] Node 16 → Node 20: announced 2023-09-22 (warnings from 2023-10-23); "we will start enforcing the use of Node20 rather than Node16 on the 3rd of June [2024]"; "Node16 will reach end of life in the Actions runner on November 12, 2024." — [Changelog 2023-09-22](https://github.blog/changelog/2023-09-22-github-actions-transitioning-from-node-16-to-node-20/); [Changelog 2024-03-07](https://github.blog/changelog/2024-03-07-github-actions-all-actions-will-run-on-node20-instead-of-node16-by-default/); [Changelog 2024-09-25](https://github.blog/changelog/2024-09-25-end-of-life-for-actions-node16/)
- [CHANGED 2025-09-19 → 2026-06-16 → 2026-09-23] Node 20 → Node 24: deprecation announced 2025-09-19 (runner v2.328.0 supports both; `FORCE_JAVASCRIPT_ACTIONS_TO_NODE24=true` to test early). "Beginning on June 16th, 2026, runners will begin using Node24 by default"; opt-out `ACTIONS_ALLOW_USE_UNSECURE_NODE_VERSION=true` "will only work until we upgrade the runner and remove Node20 on September 23rd, 2026." — [Changelog 2025-09-19](https://github.blog/changelog/2025-09-19-deprecation-of-node-20-on-github-actions-runners/)
- [CURRENT] "Node 20 is no longer available on GitHub Actions runners. Runners now use Node 24 for JavaScript actions. The temporary `ACTIONS_ALLOW_USE_UNSECURE_NODE_VERSION` opt-out is no longer available." "Node 24 is incompatible with macOS 13.4 and earlier, and it doesn't officially support ARM32." Applies to github.com and GitHub with Data Residency. — [Changelog 2026-09-23](https://github.blog/changelog/2026-09-23-node-20-is-no-longer-available-in-github-actions/)
- [CURRENT] Action authors: set `runs.using: 'node24'`. The Node 24 majors of first-party actions state "requires a minimum Actions Runner version of 2.327.1" (e.g. checkout v5, setup-node v5, cache v5, upload-artifact v6). — [Metadata syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/metadata-syntax#runs-for-javascript-actions); [actions/checkout v5.0.0 release](https://github.com/actions/checkout/releases/tag/v5.0.0)
- [CURRENT] Runner behavior for older declarations (runner v2.337.0 source, released 2026-08-26): `action.yml` may still declare `node12`, `node16`, `node20` or `node24`; `node12`/`node16` are remapped to `node20` ("we want to execute all JS actions using node20"), and a `node20` action is executed on Node 24 when the service's `UseNode24ByDefault`/`RequireNode24` flags are set (`DetermineActionsNodeVersion` returns node24 unconditionally when `requireNode24` is true; the code records the action as "upgraded from node20 to node24"). In other words, old majors are run on Node 24 rather than rejected. — [actions/runner HandlerFactory.cs @ v2.337.0](https://github.com/actions/runner/blob/v2.337.0/src/Runner.Worker/Handlers/HandlerFactory.cs); [actions/runner NodeUtil.cs @ v2.337.0](https://github.com/actions/runner/blob/v2.337.0/src/Runner.Common/Util/NodeUtil.cs)
- [CURRENT] GHES note: GHES 3.18 and older cannot run Node 24 actions; GHES 3.19 supports Node 24 actions; GHES 3.20 ships CodeQL Action v4. — [Changelog 2025-10-28](https://github.blog/changelog/2025-10-28-upcoming-deprecation-of-codeql-action-v3/)

### Inferences
- Node-20-era majors (e.g. `actions/checkout@v4`, `actions/setup-node@v4`, `actions/cache@v4`, `actions/upload-artifact@v4`, `docker/build-push-action@v6`, `softprops/action-gh-release@v2`) declare `node20`; combining the 2026-09-23 changelog ("Runners now use Node 24 for JavaScript actions") with the runner source above, such actions still start but execute on Node 24, so they work only if their bundled code happens to be Node 24-compatible. That is an untested configuration for old majors (softprops calls v2.6.2 "no longer maintained or supported"), so teach "use the Node 24 majors".
- The docs metadata page still listing `node20` as a valid `runs.using` value is documentation lag, not evidence that Node 20 still exists on github.com runners.

### Gaps
- Partly verified only from source: the forced-Node-24 behavior is read from the runner v2.337.0 code and depends on server-side feature flags (`RequireNode24`) that cannot be observed from outside; no doc page states what annotation users see for `node20`/`node16` actions after 2026-09-23, and no runner release newer than v2.337.0 (which still bundles Node 20 code paths) was published as of 2026-10-01.

## 5. What `actions/checkout` does by default

### Takeaway
By default checkout fetches exactly one commit (`fetch-depth: 1`) for the ref/SHA that triggered the run, without tags (`fetch-tags: false`), leaves the repo in detached HEAD for pull requests, and persists the job token for later git commands (`persist-credentials: true` — the default did **not** change; v6 only changed where the credential is stored). On `pull_request` events the default ref is the PR merge ref `refs/pull/N/merge` (a test merge of head into base), not the head commit. v7 additionally refuses to check out fork PR code under `pull_request_target`/`workflow_run`.

### Inferences
- Tools that need history or tags (`git describe`, changelog generators, semantic-release, `git diff origin/main...`, SonarQube blame, setuptools-scm, GitVersion) fail or mis-version under the default shallow, tagless clone; the fix is `fetch-depth: 0` (all history and tags) or `fetch-tags: true` with enough depth.
- Because the PR job builds a merge commit of head + current base, a PR can fail CI after someone else merges to the base branch even though the PR's own commits did not change (re-runs pick up a newer base only when the merge ref is recomputed) — and `git log -1`/`GITHUB_SHA` show a commit that does not exist in the contributor's local clone.
- `persist-credentials: true` leaves a usable token on disk for every later step (including third-party actions and, classically, uploaded artifacts — zizmor's `artipacked` audit); GitHub Security Lab's pwn-request article recommends `persist-credentials: false` when the token is not needed.

### Gaps
- The README text does not state "tags are not fetched" in prose; the claim rests on `fetch-tags` default `false` in `action.yml` and on "Only a single commit is fetched by default".

## 6. Caching and artifacts (limits, eviction, scope/isolation, retention, attestations)

### Takeaway
Cache: 10 GB per repository remains the free default, but since 20 Nov 2025 admins can raise the limit (pay-as-you-go, $0.07/GB-month) and set retention; entries unused for 7 days are evicted, and over-limit eviction is least-recently-used (checked hourly since Nov 2025). Cache scope is per ref: runs can read caches from their own branch, the default branch and (for PRs) the base branch — never siblings — and since 26 June 2026 untrusted triggers get a read-only token for the default-branch cache. Artifacts and logs default to 90 days retention (max 90 public / 400 private), and from 1 Oct 2026 the same retention setting also deletes checks, workflow runs and statuses. Attestations are created with `actions/attest@v4` and verified with `gh attestation verify`.

### Cited Findings

#### Cache size, eviction, rate limits
- [CURRENT] "GitHub will remove any cache entries that have not been accessed in over 7 days. There is no limit on the number of caches you can store, but the total size of all caches in a repository is limited. By default, the limit is 10 GB per repository, but this limit can be increased by enterprise owners, organization owners, or repository administrators. Any usage beyond 10 GB is billed to your account." When full, "the cache eviction policy will create space by deleting the caches in order of last access date, from oldest to most recent." — [Dependency caching reference, usage limits](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#usage-limits-and-eviction-policy)
- [CHANGED 2025-11-20] "Repositories can go beyond the previous 10 GB per-repository cache cap using a pay-as-you-go model. User-owned repos can configure up to 10 TB. - [CHANGED 2026-01-16] Rate limits: 200 cache uploads/minute/repository (plus documented 1,500 downloads/minute and 400 deletes/minute). — [Changelog 2026-01-16](https://github.blog/changelog/2026-01-16-rate-limiting-for-actions-cache-entries/); [Actions limits](https://docs.github.com/en/actions/reference/limits)

#### Cache scope and access restrictions (security-relevant)
- [CURRENT] "Workflow runs can restore caches created in either the current branch or the default branch (usually `main`). If a workflow run is triggered for a pull request, it can also restore caches created in the base branch, including base branches of forked repositories." "Workflow runs cannot restore caches created for child branches or sibling branches" nor for different tag names. — [Dependency caching reference, restrictions](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#restrictions-for-accessing-a-cache)
- [CURRENT] "When a cache is created by a workflow run triggered on a pull request, the cache is created for the merge ref (`refs/pull/.../merge`). Because of this, the cache will have a limited scope and can only be restored by re-runs of the pull request. It cannot be restored by the base branch or other pull requests targeting that base branch." — [Dependency caching reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#restrictions-for-accessing-a-cache)
- [CURRENT] Confidentiality: "Anyone with read access can create a pull request on a repository and access the contents of a cache. Additionally, forks of a repository can create pull requests on the base branch and access caches on the base branch." "Cache contents are not signed or verified". — [Dependency caching reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)
- [CHANGED 2026-06-26] **Read-only cache for untrusted triggers.** "GitHub Actions now issues read-only cache tokens to the default branch for workflow events that can be triggered without write permissions". Only `push`, `workflow_dispatch`, `repository_dispatch`, `delete`, `registry_package`, `page_build`, `schedule` can create/overwrite caches in the default branch's scope; other events resolving to the default branch (e.g. `pull_request_target`, `issue_comment`, `workflow_run`) can restore but not save (save logs a warning; job continues). `pull_request` is unaffected (merge-ref scope). — [Changelog 2026-06-26](https://github.blog/changelog/2026-06-26-read-only-actions-cache-for-untrusted-triggers/); [Dependency caching reference, low-trust triggers](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#cache-access-for-low-trust-workflow-triggers)
- [CHANGED 2026-09-10] `cache-mode` lets a workflow/job declare `read`, `write`, `write-only`, or `none`; declaring `write`/`write-only` on a low-trust trigger overrides the secure default and adds a warning annotation. The runner exposes `ACTIONS_CACHE_MODE`. — [Changelog 2026-09-10](https://github.blog/changelog/2026-09-10-control-github-actions-cache-access-with-cache-mode/); [Dependency caching reference, cache-mode](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#controlling-cache-access-with-cache-mode)
- [CURRENT] Setup actions with built-in caching: setup-node (npm/yarn/pnpm), setup-python (pip/pipenv/poetry), setup-java (Gradle/Maven), setup-go (`go.sum`/build cache), setup-ruby, setup-dotnet. — [Dependency caching reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#setup--actions-for-specific-package-managers)

#### Artifacts: retention, limits, validation
- [CURRENT] "By default, checks, workflow runs, commit statuses, and the artifacts and log files generated by workflows are retained for 90 days before they are automatically deleted." - [CURRENT] Generate with `actions/attest@v4` and permissions `id-token: write`, `contents: read`, `attestations: write` (+ `packages: write` for images, `artifact-metadata: write` for linked-artifact storage records). Binary: `subject-path`; image: `subject-name` (no tag) + `subject-digest` + `push-to-registry: true`; SBOM: add `sbom-path`. — [Using artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)
- [CURRENT] Verify: `gh attestation verify PATH/TO/ARTIFACT -R ORG/REPO`; images `gh attestation verify oci://ghcr.io/ORG/IMAGE:tag -R ORG/REPO`; SBOM needs `--predicate-type https://spdx.dev/Document/v2.3`. CLI help: default predicate `https://slsa.dev/provenance/v1`; requires `--owner` or `--repo`; `--signer-workflow`/`--signer-repo` when a reusable workflow signed. — [Using artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations#verifying-artifact-attestations-with-the-github-cli); [gh attestation verify manual](https://cli.github.com/manual/gh_attestation_verify)
- [CURRENT] "Artifact attestations by itself provides SLSA v1.0 Build Level 2"; building in a shared reusable workflow can meet Build Level 3. Public repos use the Sigstore Public Good Instance (public transparency log); private repos use GitHub's Sigstore instance (no transparency log). "artifact attestations are *not* a guarantee that an artifact is secure." GA since 2024-06-25. — [Artifact attestations concept](https://docs.github.com/en/actions/concepts/security/artifact-attestations); [Changelog 2024-06-25](https://github.blog/changelog/2024-06-25-artifact-attestations-is-generally-available/)

### Inferences
- "Stale cache" bugs follow directly from immutability plus prefix `restore-keys`: a broad restore key keeps restoring an old cache that is then extended and re-saved under a new key; include a lockfile hash in `key` and bump a manual prefix (`v2-`) to invalidate.
- The 2026 cache changes (read-only tokens, `cache-mode`, setup-uv/setup-node defaults) are direct responses to cache-poisoning incidents (TanStack, May 2026); a release/publish job should either not restore caches at all or restore only caches written by trusted `push` runs.
- Attestation provenance proves *which workflow built* an artifact, not that the workflow's inputs were clean: in the TanStack incident the malicious versions were published by the genuine release workflow's OIDC identity (secondary reports add that they carried valid provenance attestations; the post-mortem itself does not use that wording).

## 7. Environments (protection rules, secrets/variables, plan availability)

### Takeaway
Environments gate jobs with required reviewers (up to 6, optional prevent-self-review), wait timers (up to 30 days), deployment branch/tag rules, admin-bypass control and custom (GitHub App) protection rules, and scope secrets/variables to the job. For private repositories the strong gates (required reviewers, wait timers, custom rules) remain Enterprise-only; branch/tag restrictions and environment secrets/variables are available from Pro/Team. Docs and a May 2025 changelog disagree on whether Free-plan private repos can use environments at all.

- A teachable staging→production pattern that works on all plans for public repos (and on Enterprise for private ones): `deploy-staging` job with `environment: staging`, then `deploy-production` with `needs: deploy-staging` and `environment: production` protected by required reviewers + "Selected branches: main" + prevent self-review. ## 8. Security model, from official docs and GitHub Security Lab

### Takeaway
The model is: a short-lived per-job `GITHUB_TOKEN` (read-only by default for new repos/orgs since Feb 2023; always read-only and secret-less for fork `pull_request` runs), least-privilege `permissions:`, untrusted event data kept out of `run:` scripts via intermediate environment variables, third-party actions pinned to full commit SHAs, and OIDC instead of stored cloud keys. 2025–2026 turned much of this guidance into platform enforcement: SHA-pinning and blocklist policy (Aug 2025), `pull_request_target` pinned to the default branch (Dec 2025), allowed-actions policy on all plans (Feb 2026), immutable OIDC subjects (Apr–Jul 2026), `actions/checkout` v7 refusing fork-PR checkouts in privileged triggers (Jun–Jul 2026), read-only cache for untrusted triggers (Jun 2026), workflow execution protections GA with a default policy that will block `pull_request_target` in public repos from 2 Nov 2026 (Sep 2026), and automatic holds on suspicious workflow runs (Jul 2026).

### Cited Findings

#### `GITHUB_TOKEN`: nature, defaults, least privilege
- [CURRENT] "At the start of each workflow job, GitHub automatically creates a unique `GITHUB_TOKEN` secret"; it is "a GitHub App installation access token" whose "permissions are limited to the repository that contains your workflow"; it "expires when the job finishes or after its effective maximum lifetime" (6 hours on GitHub-hosted runners; refreshable up to 24 hours on self-hosted). — [GITHUB_TOKEN concept](https://docs.github.com/en/actions/concepts/security/github_token)
- [CURRENT] "An action can access the `GITHUB_TOKEN` through the `github.token` context even if the workflow does not explicitly pass the `GITHUB_TOKEN` to the action." — [Use GITHUB_TOKEN for authentication in workflows](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token)
- [CHANGED 2023-02-02] Default became read-only for *new* enterprises, organizations and personal-account repositories: "This change will not impact any existing enterprises, organizations or repositories." Repositories in an org inherit the org setting. — [Changelog 2023-02-02](https://github.blog/changelog/2023-02-02-github-actions-updating-the-default-github_token-permissions-to-read-only/)
- [CURRENT] Setting "Workflow permissions": permissive = "read and write access for all permissions"; restricted = "just read access for the `contents` and `packages` permissions". "By default, when you create a new repository in your personal account, `GITHUB_TOKEN` only has read access for the `contents` and `packages` scopes"; same default for a new organization; a restrictive org/enterprise default disables the permissive option below it. Separately, "Allow GitHub Actions to create and approve pull requests" is off by default for new personal repositories. "Anyone with write access to a repository can modify the permissions granted to the `GITHUB_TOKEN`… by editing the `permissions` key in the workflow file." — [Managing GitHub Actions settings for a repository](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository#setting-the-permissions-of-the-github_token-for-your-repository); [Org settings](https://docs.github.com/en/organizations/managing-organization-settings/disabling-or-limiting-github-actions-for-your-organization#setting-the-permissions-of-the-github_token-for-your-organization)
- [CURRENT] Least privilege guidance: "It's good security practice to set the default permission for the `GITHUB_TOKEN` to read access only for repository contents. The permissions can then be increased, as required, for individual jobs within the workflow file." Also: "Any user with write access to your repository has read access to all secrets configured in your repository." — [Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use#use-secrets-for-sensitive-information)
- [CURRENT] Exception to remember: "When a workflow is triggered by the `pull_request_target` event, the `GITHUB_TOKEN` is granted read/write repository permission, even when it is triggered from a public fork." — [Workflow syntax, permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)
- [CHANGED 2025-03-31] A workflow's `GITHUB_TOKEN` can no longer modify the conclusion/status of Actions-created check runs. — [Changelog 2025-02-12](https://github.blog/changelog/2025-02-12-notice-of-upcoming-deprecations-and-breaking-changes-for-github-actions/)

#### Fork pull requests
- [CURRENT] "With the exception of `GITHUB_TOKEN`, secrets are not passed to the runner when a workflow is triggered from a forked repository. The `GITHUB_TOKEN` has read-only permissions in pull requests from forked repositories." Dependabot PRs are treated the same way. — [Events, pull_request](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflows-in-forked-repositories)
- [CURRENT] Approval for public forks: "By default, all first-time contributors require approval to run workflows." Options: "Require approval for first-time contributors who are new to GitHub", "Require approval for first-time contributors", "Require approval for all external contributors". Warning: a user "that has had any commit or pull request merged into the repository will not require approval. A malicious user could meet this requirement by getting a simple typo… accepted". Pending approvals expire after 30 days. — [Managing GitHub Actions settings for a repository](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository#controlling-changes-from-forks-to-workflows-in-public-repositories); [Approving workflow runs from forks](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/approve-runs-from-forks)
- [CURRENT] "Workflows triggered by `pull_request_target` events are run in the context of the base branch. Since the base branch is considered trusted, workflows triggered by these events will always run, regardless of approval settings." — [Managing GitHub Actions settings for a repository](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository#controlling-changes-from-forks-to-workflows-in-public-repositories)
- [CURRENT] Private-repository forks: policies "Run workflows from fork pull requests" (read-only token, no secrets), "Send write tokens to workflows from pull requests", "Send secrets to workflows from pull requests", "Require approval for fork pull request workflows". — [Managing GitHub Actions settings for a repository](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository#enabling-workflows-for-forks-of-private-repositories)
- [CURRENT] Copilot- and bot-authored changes are treated like outside contributions: Copilot-authored events need approval (public preview 2025-04-15; optional skip setting added 2026-03-13); `github-actions[bot]` PRs need approval (2026-06-11). — [Changelog 2025-04-15](https://github.blog/changelog/2025-04-15-upcoming-breaking-changes-and-releases-for-github-actions/); [Changelog 2026-03-13](https://github.blog/changelog/2026-03-13-optionally-skip-approval-for-copilot-coding-agent-actions-workflows/); [Changelog 2026-06-11](https://github.blog/changelog/2026-06-11-bot-created-pull-requests-can-run-workflows-if-approved/)

#### `pull_request_target` and `workflow_run` ("pwn requests")
- [CURRENT] Official definition of the risk: `pull_request_target` workflows "run with elevated trust: the job receives the base repository's `GITHUB_TOKEN` and access to repository and organization secrets." It is safe by default because "the workflow, and any subsequent `actions/checkout` call that does not specify a `ref`, is taken from the base repository's default branch". "You introduce risk when a workflow author overrides this default to run the fork's code." "The checkout step alone does not execute untrusted code… The vulnerability is completed by the *next* step that runs code checked out into the current working directory" (`make test`, `npm install`, build scripts, config files). "This pattern is known as a 'pwn request' and has been the root cause of multiple supply-chain compromises." Vulnerable shapes: `ref: ${{ github.event.pull_request.head.sha }}`, `ref: refs/pull/${{ github.event.pull_request.number }}/merge`, `repository: ${{ github.event.pull_request.head.repo.full_name }}`, or fetching PR code with `git fetch`/`gh pr checkout`/artifacts and running it. "Pwn requests are also not unique to `pull_request_target`… an `issue_comment` or `workflow_run` workflow that fetches and runs a fork's pull request code is vulnerable in the same way." — [Securely using pull_request_target](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)
- [CURRENT] Good practices: "Avoid using the `pull_request_target` workflow trigger if it's not necessary. For privilege separation between workflows, `workflow_run` is a better trigger." "Workflows that use these triggers must not explicitly check out untrusted code… Workflows triggered on `workflow_run` should treat artifacts uploaded from other workflows with caution." — [Secure use reference, untrusted code checkout](https://docs.github.com/en/actions/reference/security/secure-use#mitigating-the-risks-of-untrusted-code-checkout)
- [CURRENT] GitHub Security Lab (Jaroslav Lobačevski, 2021-08-03): "Combining `pull_request_target` workflow trigger with an explicit checkout of an untrusted PR is a dangerous practice that may lead to repository compromise." Safe design: an unprivileged `pull_request` workflow builds/tests and uploads results as artifacts; a privileged `workflow_run` workflow downloads them and comments/labels, treating artifact contents as untrusted data. Label-gating "is still prone to a race condition in which the attacker may push new changes after the workflow was approved (labeled), but has not started yet." — [Keeping your GitHub Actions and workflows secure Part 1: Preventing pwn requests](https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/)
- [CHANGED 2025-12-08] `pull_request_target` workflow source/ref always the default branch (closes "outdated vulnerable workflow on another branch" attacks); environment branch rules evaluate on the execution ref. — [Changelog 2025-11-07](https://github.blog/changelog/2025-11-07-actions-pull_request_target-and-environment-branch-protections-changes/)
- [CHANGED 2026-06-18 / 2026-07-20] `actions/checkout` v7 (and back-ported v2–v6 lines) refuses fork-PR head/merge checkouts in `pull_request_target` and PR-originated `workflow_run` unless `allow-unsafe-pr-checkout: true`. "The flag is intentionally named to be easy to spot in code review and static analysis." — [Changelog 2026-06-18](https://github.blog/changelog/2026-06-18-safer-pull_request_target-defaults-for-github-actions-checkout/)

#### Script injection
- [CURRENT] "Attackers can add their own malicious content to the `github` context, which should be treated as potentially untrusted input. These contexts typically end with `body`, `default_branch`, `email`, `head_ref`, `label`, `message`, `name`, `page_name`, `ref`, and `title`." Branch names are attacker-controlled too (`zzz";echo${IFS}"hello";#` is a valid branch name). Mechanism: "the `run` command executes within a temporary shell script on the runner. Before the shell script is run, the expressions inside `${{ }}` are evaluated and then substituted with the resulting values". Docs example: `title="${{ github.event.pull_request.title }}"` exploited with PR title `a"; ls $GITHUB_WORKSPACE"`. — [Script injections](https://docs.github.com/en/actions/concepts/security/script-injections)
- [CURRENT] Documented mitigations: (1) "Use an action instead of an inline script" (pass the value via `with:`); (2) "Use an intermediate environment variable": `env: TITLE: ${{ github.event.pull_request.title }}` then use `"$TITLE"` in the script — "the value of the `${{ github.event.pull_request.title }}` expression is stored in memory and used as a variable, and doesn't interact with the script generation process"; quote shell variables. — [Secure use reference, script injection](https://docs.github.com/en/actions/reference/security/secure-use#good-practices-for-mitigating-script-injection-attacks)

#### Secrets handling
- [CURRENT] Secrets are encrypted client-side with Libsodium sealed boxes; "GitHub Actions can only read a secret if you explicitly include the secret in a workflow." Levels: organization (with repository access policy), repository, environment (optionally gated by required reviewers). — [Secrets concept](https://docs.github.com/en/actions/concepts/security/secrets)
- [CURRENT] Masking: registered secrets are redacted from logs, but "Because there are multiple ways a secret value can be transformed, this redaction is not guaranteed"; "Never use structured data as a secret" (JSON/XML/YAML blobs defeat exact-match redaction); register derived values with `::add-mask::VALUE`; "If an unredacted secret is sent to a workflow run log, you should delete the log and rotate the secret." GitHub also auto-redacts some recognizable token formats (Azure keys, JWTs, npm tokens, GitHub tokens…). — [Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use#use-secrets-for-sensitive-information); [Secrets reference](https://docs.github.com/en/actions/reference/security/secrets#automatically-redacted-secrets)
- [CURRENT] Naming/limits: alphanumeric + `_`, not starting with `GITHUB_` or a digit, case-insensitive; 1,000 org / 100 repo / 100 environment secrets; 48 KB each (larger → encrypt a file with `gpg` and store the passphrase). Not passed to fork-triggered or Dependabot-triggered workflows; not passed automatically to reusable workflows; cannot be referenced in `if:`; avoid passing on command lines (visible via `ps`). — [Secrets reference](https://docs.github.com/en/actions/reference/security/secrets); [Using secrets in GitHub Actions](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets)
- [CURRENT] Docs recommend GitHub App installation tokens over PATs when `GITHUB_TOKEN` is insufficient ("a GitHub App is not tied to a user"). — [Secrets concept](https://docs.github.com/en/actions/concepts/security/secrets#limiting-credential-permissions)

#### Cache poisoning and artifact poisoning
- [CURRENT] Cache poisoning definition (docs): events that outsiders can trigger "run in the context of the default branch… could be used to write a malicious cache that a later, more privileged workflow restores and trusts." Mitigations now built in: read-only default-branch cache tokens for low-trust triggers (2026-06-26), `cache-mode` (2026-09-10); guidance: "Save caches from trusted triggers", don't store secrets in caches, treat caches as unsigned/unverified. — [Dependency caching reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#cache-access-for-low-trust-workflow-triggers)
- [CURRENT] Artifact poisoning: "A `workflow_run` workflow should treat artifacts uploaded by other workflows as untrusted data, since their contents can come from a fork." Security Lab: "Incoming data from artifacts is potentially untrusted. When used in a safe manner, like reading PR numbers or reading a code coverage text to comment on the PR, it is safe to use such untrusted data in the privileged workflow context." — [Securely using pull_request_target](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target); [Security Lab: preventing pwn requests](https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/)
- [CURRENT] Job isolation caveat: "The individual jobs in a workflow can interact with (and compromise) other jobs" on the same runner environment (shared directories, Docker socket), which is why a single compromised action is so damaging. — [Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use#using-third-party-actions)

#### Roadmap (announced, not shipped unless noted)
- [CURRENT as roadmap, 2026-03-26] GitHub's "2026 security roadmap" for Actions (citing tj-actions/changed-files, Nx and trivy-action): workflow-level dependency locking (`dependencies:` with commit SHAs for direct and transitive actions), policy-driven execution via rulesets (shipped: workflow execution protections), scoped secrets and explicit trust for reusable-workflow secret inheritance, Actions Data Stream telemetry, and a native Layer-7 egress firewall for GitHub-hosted runners. — [What's coming to our GitHub Actions 2026 security roadmap](https://github.blog/news-insights/product-news/whats-coming-to-our-github-actions-2026-security-roadmap/)

### Inferences
- A defensible "secure by default" workflow template for 2026: top-level `permissions: contents: read` (or `{}`), per-job additions; `pull_request` (not `pull_request_target`) for CI; actions pinned to full SHAs with `# vX.Y.Z` comments and Dependabot `github-actions` updates (now with a cooldown); untrusted `${{ github.event.* }}` values only via `env:`; OIDC + environment-scoped trust for deploys; `persist-credentials: false` where the job does not push; explicit `cache-mode: read`/`none` in release jobs.
- SHA pinning protects against moved tags (tj-actions, trivy-action, actions-cool) but not against a malicious commit you pin deliberately, nor against transitive unpinned actions inside composite actions; this is the gap the announced dependency lock is meant to close.
- From 2 November 2026, public repositories that rely on `pull_request_target` (labelers, welcome bots, coverage commenters) must explicitly allow it in an Actions event policy or migrate; course material should present `pull_request_target` as opt-in and discouraged.

## 9. Real incidents usable as case studies (root cause, impact, lesson)

### Takeaway
The same three weaknesses recur: (1) mutable action tags re-pointed after a maintainer credential is stolen (tj-actions/reviewdog 2025, trivy-action and actions-cool 2026); (2) "pwn requests"/script injection in `pull_request_target` workflows that hand an attacker a write token or publish credential (SpotBugs → reviewdog → tj-actions chain, Nx, hackerbot-claw/Trivy, TanStack); (3) stolen maintainer or CI tokens used to push secret-dumping workflows or self-propagating packages (GhostAction, Shai-Hulud). The 2026 TanStack compromise is the richest teaching case: no credential was stolen — a fork PR poisoned the shared Actions cache, a trusted release job restored it, and malware lifted the job's OIDC token from runner memory to publish through the project's own legitimate trusted-publisher identity.

### Cited Findings

#### tj-actions/changed-files (March 2025, CVE-2025-30066) and reviewdog/action-setup (CVE-2025-30154)
- [Authoritative advisory] CISA alert (released 2025-03-18; updated 2025-03-19 and 2025-03-26): `tj-actions/changed-files` and `reviewdog/action-setup@v1` were compromised; secrets exposed included "access keys, GitHub Personal Access Tokens (PATs), npm tokens, and private RSA keys"; affected windows: tj-actions 2025-03-12 00:00 UTC to 2025-03-15 12:00 UTC, reviewdog/action-setup 2025-03-11 18:42–20:31 UTC; patched in tj-actions/changed-files v46.0.1; both CVEs added to the Known Exploited Vulnerabilities catalog. Other reviewdog actions affected via the dependency: action-shellcheck, action-composite-template, action-staticcheck, action-ast-grep, action-typos. — [CISA alert](https://www.cisa.gov/news-events/alerts/2025/03/18/supply-chain-compromise-third-party-tj-actionschanged-files-cve-2025-30066-and-reviewdogaction)
- [Root cause/impact] GitHub Advisory GHSA-mrrh-fwg8-r2c3 (published 2025-03-15, CVSS 8.6): "Attackers retroactively modified multiple version tags to reference a malicious commit" (`0e58ed8671d6b60d0890c21b07f8835ace038e67`); the script "extracted secrets from the Runner Worker process memory and printed them in GitHub Actions logs, making them publicly accessible"; affected ≤ 45.0.7, patched 46.0.1; "over 23,000 repositories" used the action. — [GHSA-mrrh-fwg8-r2c3](https://github.com/advisories/GHSA-mrrh-fwg8-r2c3)
- [Attack chain] Unit 42 (published 2025-03-20, updated 2025-04-02): a SpotBugs maintainer added a PAT to a workflow (2024-11-28); on 2024-12-06 an attacker's PR exploited a `pull_request_target` workflow in `spotbugs/sonar-findbugs` and exfiltrated the PAT; on 2025-03-11 the PAT was used to push a malicious workflow to `spotbugs/spotbugs`, leaking a reviewdog maintainer's PAT; the `v1` tag of `reviewdog/action-setup` was overridden the same day; that compromise is believed to have exposed the `tj-actions` bot PAT (CISA: "potentially enabled by"); the initial target was Coinbase (`coinbase/agentkit` ran the malicious version at 2025-03-14 15:10 UTC and leaked a write token); at 16:57 UTC the attacker "pushed new git tags to override its existing tags, making them all point to the malicious commit". — [Unit 42 analysis](https://unit42.paloaltonetworks.com/github-actions-supply-chain-attack/)
- [Detail] Wiz: the bot PAT (`@tj-actions-bot`) was compromised; secrets appeared in logs as "a double-encoded base64 string"; "Pin all GitHub Actions to specific commit hashes instead of version tags"; deleting a workflow run removes its logs. Detection came from StepSecurity Harden-Runner's network-egress anomaly. — [Wiz blog](https://www.wiz.io/blog/github-action-tj-actions-changed-files-supply-chain-attack-cve-2025-30066); [StepSecurity](https://www.stepsecurity.io/blog/harden-runner-detection-tj-actions-changed-files-action-is-compromised)
- [Lesson] Tags (including "major version" tags) are mutable pointers; only workflows pinned to a full commit SHA were unaffected. Public-repo logs are world-readable, so "printing" secrets equals leaking them. Long-lived PATs stored as secrets are the lateral-movement currency; `pull_request_target` on an upstream dependency's repo was the first domino. (Lesson derived from the sources above; pinning guidance: [Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use#using-third-party-actions); [Unit 42](https://unit42.paloaltonetworks.com/github-actions-supply-chain-attack/))

#### Nx "s1ngularity" (26–27 August 2025, GHSA-cxm3-wv7p-598c)
- [Post-mortem, published 2025-09-05] Three weaknesses converged: (1) the PR-title validation workflow used `pull_request_target` and echoed the unsanitized PR title into a shell (script injection); (2) "Overpermissive Workflow Tokens" — the repository still had GitHub's legacy "Read and write permissions" default ("GitHub changed this default to 'Read permissions' for new repositories in February 2023, but existing repositories weren't automatically updated"); (3) the publish workflow had `workflow_dispatch`, so the stolen read/write token could trigger it via the API from an attacker-modified branch to exfiltrate the npm token. Malicious versions of 8 packages (`nx` ×5 versions, `@nx/devkit`, `@nx/js`, `@nx/workspace`, `@nx/node` ×2, `@nx/eslint`, `@nx/key`, `@nx/enterprise-cloud` ×1) were live about 4 hours; the postinstall script "scanned user systems for sensitive data, attempted to use local AI tools (like Claude and Gemini), and uploaded the results to a public GitHub repo via the GitHub CLI." Remediation: npm Trusted Publishing (OIDC) instead of tokens; manual 2FA approval for publishing; "Disable pipeline runs for all external contributors, not just first-time contributors"; provenance checks. — [Nx post-mortem](https://nx.dev/blog/s1ngularity-postmortem); [GHSA-cxm3-wv7p-598c](https://github.com/nrwl/nx/security/advisories/GHSA-cxm3-wv7p-598c)
- [Lesson] One injectable `run:` line in a privileged trigger plus a write-capable default token is enough to reach a publish credential. Mitigations map 1:1 to the docs: intermediate env var, `pull_request` instead of `pull_request_target`, read-only default token, OIDC trusted publishing, environment approvals on publish jobs. (Derived from [Nx post-mortem](https://nx.dev/blog/s1ngularity-postmortem) and [Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use#good-practices-for-mitigating-script-injection-attacks))

#### "Shai-Hulud" npm worm (September 2025) and "Shai-Hulud 2.0" (November 2025) — where they touched GitHub Actions/tokens
- [Authoritative] CISA alert (2025-09-23): a self-replicating worm compromised "over 500 packages"; it scanned for "GitHub Personal Access Tokens (PATs) and application programming interface (API) keys for cloud services", uploaded credentials "to a public repository named `Shai-Hulud`", and used the developer's npm token to inject itself into their other packages. Recommendations include rotating credentials, phishing-resistant MFA, pinning to versions released before 2025-09-16, branch protection and secret scanning. — [CISA alert](https://www.cisa.gov/news-events/alerts/2025/09/23/widespread-supply-chain-compromise-impacting-npm-ecosystem)
- [GitHub response, 2025-09-22] GitHub removed "500+ compromised packages" and announced npm changes: publishing limited to local publish with mandatory 2FA, granular tokens "with a limited lifetime of seven days", or trusted publishing; deprecating legacy classic tokens and TOTP 2FA. — [GitHub blog: Our plan for a more secure npm supply chain](https://github.blog/security/supply-chain-security/our-plan-for-a-more-secure-npm-supply-chain/)
- [Actions angle, Wiz 2025-09-16] With stolen GitHub tokens the malware "pushes a new GitHub Actions workflow to all accessible repositories" (on a `shai-hulud` branch) that exfiltrates repository secrets to a webhook.site URL — and "secrets will still be exposed in the workflow log"; it also migrated private org repositories to public personal repositories with a `-migration` suffix. Wiz links initial access to tokens stolen in the Nx/s1ngularity incident. — [Wiz: Shai-Hulud](https://www.wiz.io/blog/shai-hulud-npm-supply-chain-attack)
- [Shai-Hulud 2.0, Wiz 2025-11-24] ~700 malicious package versions (Zapier, ENS Domains, PostHog, Postman, AsyncAPI); payload ran at `preinstall`; "registers the infected machine as a self hosted runner named 'SHA1HULUD'" and adds `.github/workflows/discussion.yaml` "that contains an injection vulnerability and runs specifically on self-hosted runners" (a persistent backdoor triggered by opening a discussion); a `formatter_123456789.yml` workflow dumped secrets; 25,000+ repositories created across ~500 users. — [Wiz: Shai-Hulud 2.0](https://www.wiz.io/blog/shai-hulud-2-0-ongoing-supply-chain-attack)
- [Lesson] A GitHub token with `workflow`/contents write is equivalent to all Actions secrets of every repository it can reach (push a workflow that prints `secrets`). Controls: short-lived tokens/OIDC, restrict who can trigger workflows (execution protections), restrict repository-level self-hosted runner registration, review audit logs for new workflows/runners, GitHub's 2026 automatic hold on suspicious workflow runs. (Derived from [Wiz: Shai-Hulud](https://www.wiz.io/blog/shai-hulud-npm-supply-chain-attack), [Wiz: Shai-Hulud 2.0](https://www.wiz.io/blog/shai-hulud-2-0-ongoing-supply-chain-attack) and [Changelog 2026-07-28](https://github.blog/changelog/2026-07-28-github-actions-holds-potentially-malicious-workflows-for-approval/))

#### GhostAction (September 2025)
- [GitGuardian, published 2025-09-05] Attackers with access to maintainer accounts pushed commits titled "Add Github Actions Security workflow" containing a workflow that posted secrets to an attacker server (`curl -s -X POST -d 'PYPI_API_TOKEN=${{ secrets.PYPI_API_TOKEN }}' …`); first seen in the FastUUID project (malicious commit 2025-09-02); totals: 327 GitHub users, 817 repositories, 3,325 secrets (DockerHub, GitHub, npm tokens most common). GitGuardian opened issues in affected repos and notified GitHub, npm and PyPI. — [GitGuardian: GhostAction campaign](https://blog.gitguardian.com/ghostaction-campaign-3-325-secrets-stolen/)
- [Lesson] Any account with write access can read every repository secret by adding a workflow; protect with branch/ruleset protection on `.github/workflows` (CODEOWNERS), environment-scoped secrets with required reviewers, OIDC/trusted publishing instead of long-lived registry tokens, and 2FA on maintainer accounts. (Derived from [GitGuardian](https://blog.gitguardian.com/ghostaction-campaign-3-325-secrets-stolen/) and the statement "Any user with write access to your repository has read access to all secrets configured in your repository" in the [Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use#use-secrets-for-sensitive-information))

- [Aqua incident notice / advisory GHSA-69fq-xp46-6x23, CVE-2026-33634, published 2026-03-21, CVSS 9.4] "a threat actor used a compromised credential to publish malicious trivy (v0.69.4), trivy-action, and setup-trivy releases. (Derived from [Aqua discussion #10425](https://github.com/aquasecurity/trivy/discussions/10425), [Wiz](https://www.wiz.io/blog/trivy-compromised-teampcp-supply-chain-attack) and [StepSecurity](https://www.stepsecurity.io/blog/hackerbot-claw-github-actions-exploitation))

#### 2026: TanStack npm compromise (11 May 2026, GHSA-g7cv-rxg3-hmpx) — pwn request + cache poisoning + OIDC token theft
- [TanStack post-mortem, 2026-05-11, all-clear 2026-05-15] "An attacker compromised 42 @tanstack packages across 84 malicious versions by chaining three vulnerabilities": (1) `bundle-size.yml` "ran `pull_request_target` for fork PRs and, inside that trigger context, checked out the fork's PR-merge ref and ran a build"; the author had tried a trust split with `permissions: contents: read`, but "cache writes use a runner-internal token, not the workflow `GITHUB_TOKEN`… Setting `permissions: contents: read` does not block cache mutation." (2) The fork's code wrote a poisoned pnpm store under the exact key the release workflow computes (`Linux-pnpm-store-${hashFiles('**/pnpm-lock.yaml')}`), saved for scope `refs/heads/main`; "When `release.yml` next ran on a push to main, its Setup Tools step restored the poisoned entry—entirely as designed." (3) `release.yml` had `id-token: write` for npm trusted publishing; the malware located `Runner.Worker`, read `/proc/<pid>/mem`, extracted the OIDC token and published directly to npm — "it does not come from the workflow's defined Publish Packages step, which was skipped because tests failed." "No npm tokens were stolen and the npm publish workflow itself was not compromised." The fork PR needed no approval: "no first-time-contributor approval required because `pull_request_target` bypasses that gate" (the `pull_request` workflow stayed blocked pending approval). Timeline: PR opened 2026-05-11 ~10:49 UTC, cache saved 11:29, malicious publishes 19:20 and 19:26, external report (StepSecurity researcher) 19:46, all versions deprecated by 21:03, tarballs removed by 23:55. The memory-dump script was the same one used in the tj-actions attack. The payload harvested cloud/GitHub/npm/SSH credentials and "Self-propagates: enumerates other packages the victim maintains… and republishes them with the same injection" (secondary reporting calls this worm "Mini Shai-Hulud"; the post-mortem does not use the name). The vulnerable workflow used `actions/checkout@v6.0.2` under `pull_request_target`. — [TanStack post-mortem](https://tanstack.com/blog/npm-supply-chain-compromise-postmortem)
- [TanStack's own lessons] "`pull_request_target` workflows had not been audited despite being a long-known dangerous pattern"; "Floating refs (`@v6.0.2`, `@main`) on third-party actions create standing supply-chain risk"; "OIDC trusted-publisher binding has no per-publish review. Once configured, any code path in the workflow can mint a publish-capable token"; no internal publish monitoring; npm unpublish was unavailable for packages with dependents. Fixes: purge caches, restructure the workflow, add `repository_owner` guards, pin third-party actions to SHAs. — [TanStack post-mortem](https://tanstack.com/blog/npm-supply-chain-compromise-postmortem)
- [Platform response] In the following weeks GitHub shipped checkout v7 fork-PR refusal (2026-06-18), read-only cache tokens for untrusted triggers (2026-06-26), workflow execution protections (2026-06-18 preview → 2026-09-17 GA) and `cache-mode` (2026-09-10). — [Changelog 2026-06-18](https://github.blog/changelog/2026-06-18-safer-pull_request_target-defaults-for-github-actions-checkout/); [Changelog 2026-06-26](https://github.blog/changelog/2026-06-26-read-only-actions-cache-for-untrusted-triggers/)

#### 2026: actions-cool tag hijack (May 2026) — secondary reporting
- [The Hacker News, 2026-05-19, citing StepSecurity and Socket] In `actions-cool/issues-helper` "Every existing tag in the repository has been moved to point to an imposter commit that does not appear in the action's normal commit history" (also 15 tags of `actions-cool/maintain-one-comment`); the code downloaded the Bun runtime, read `Runner.Worker` memory for credentials and sent them to an attacker domain; linked to the "Mini Shai-Hulud" cluster; "Only workflows pinned to a known-good full commit SHA are unaffected." — [The Hacker News](https://thehackernews.com/2026/05/github-actions-supply-chain-attack.html)

#### Codecov Bash Uploader (2021) — history only
- [Codecov security update, disclosed 2021-04-15] From 2021-01-31 to 2021-04-01 an attacker modified the Bash Uploader script after extracting a credential through "an error in Codecov's Docker image creation process"; the altered script sent `git remote -v` and the CI environment (`env`) to a third-party server, exposing "any credentials, tokens, or keys that our customers were passing through their CI runner". Affected: Bash Uploader, Codecov GitHub Action, CircleCI Orb, Bitrise Step. Detected when a customer's `shasum` check of the script did not match. — [Codecov security update](https://about.codecov.io/security-update/)
- [Lesson] `curl | bash` of a mutable script in CI is the same risk class as a mutable action tag; verify checksums/pin by digest and minimize the secrets present in the job environment. (Derived from the [Codecov security update](https://about.codecov.io/security-update/))

### Inferences
- Technique reuse across incidents: dumping `Runner.Worker` process memory to harvest secrets/OIDC tokens (tj-actions 2025 → Trivy, TanStack, actions-cool 2026). Masked logs and "we never print secrets" are irrelevant once attacker code runs in the job; the only robust controls are preventing untrusted code execution in privileged jobs and limiting which secrets/tokens the job holds.
- Each official mitigation shipped in 2025–2026 lines up with an incident: SHA-pinning policy and blocklists (after tj-actions), default-branch-only `pull_request_target` (after Nx-style stale-branch workflows), checkout v7 + read-only caches + `cache-mode` (after TanStack), execution protections and suspicious-workflow holds (after GhostAction/Shai-Hulud-style pushed workflows), immutable OIDC subjects (name-recycling risk).
- For teaching, pair incidents with lessons: tj-actions → pin SHAs; Nx → script injection + token defaults; TanStack → cache poisoning and "OIDC ≠ safe if untrusted code runs in the job"; GhostAction/Shai-Hulud → write access = secret access; Trivy → incident response and atomic rotation; Codecov → unpinned remote scripts.

### Gaps
- Date-window conflict for tj-actions: CISA says 2025-03-12 00:00 UTC–2025-03-15 12:00 UTC; the GitHub advisory says "active between March 14 and March 15, 2025"; Unit 42's timeline places the mass tag override at 2025-03-14 16:57 UTC (earlier activity was targeted at Coinbase). Use CISA's window for "audit these runs" guidance.
- The number of repositories that actually leaked secrets in the tj-actions incident is not given by CISA/GHSA (Wiz: "dozens of repositories" observed; a "218 repositories" figure appears only in secondary reporting and was not verified).
- The actions-cool incident rests on secondary reporting (The Hacker News); the primary StepSecurity/Socket write-ups were not fetched. A September 2026 report that GitHub re-enabled previously compromised action repositories (SC World brief) was seen only in search results and is UNVERIFIED.
- No GitHub-authored post-mortem for the TanStack incident was found; the GitHub changelog posts do not name it. The causal link between the incident and the June 2026 platform changes is an inference from timing and content.
- "Mini Shai-Hulud" (May 2026) details beyond TanStack's own post-mortem were not verified against a primary source.

## 11. Debugging CI: documented tools and well-documented causes of "passes locally, fails on GitHub Actions"

### Takeaway
Official tools: step/runner debug logging (`ACTIONS_STEP_DEBUG`, `ACTIONS_RUNNER_DEBUG`, or "Enable debug logging" on a re-run), expanded job-condition logs (2026), re-running failed jobs only, and the GitHub CLI (`gh run view --log-failed`, `gh run rerun --failed --debug`, `gh run watch`). `act` (third-party) runs workflows locally in Docker but ignores concurrency, permissions, environments, OIDC and more. Most local-vs-CI differences trace to documented defaults: shallow tagless clone, the PR merge ref, Linux case-sensitive filesystem, implicit shell flags, missing secrets on fork/Dependabot PRs, moving `-latest` images and tool versions, immutable caches, and runner size limits.

### Cited Findings

#### Tools

#### Documented causes of local-vs-CI differences
- [CURRENT] **Shallow clone, no tags**: checkout fetches a single commit; `fetch-tags` default `false`; "Set `fetch-depth: 0` to fetch all history for all branches and tags." — [checkout README](https://github.com/actions/checkout/blob/v7.0.1/README.md)
- [CURRENT] **PR merge ref, detached HEAD**: on `pull_request`, CI tests "the merged result, not just the head branch alone" (`refs/pull/N/merge`), in "detached HEAD mode"; base-branch changes are therefore included, and `pull_request` workflows do not run at all while the PR has a merge conflict. — [Events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#how-the-merge-branch-affects-your-workflow); [checkout README](https://github.com/actions/checkout/blob/v7.0.1/README.md)
- [CURRENT] **Missing secrets and read-only token on fork and Dependabot PRs**: secrets are not passed; an unset secret evaluates to an empty string (no error). — [Using secrets in GitHub Actions](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets); [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions-for-workflow-runs-triggered-by-dependabot)
- [CURRENT] **Shell differences**: implicit Linux/macOS shell is `bash -e {0}` (no `pipefail`); explicit `shell: bash` adds `--noprofile --norc -eo pipefail`; commands run in non-login shells; Windows default is PowerShell Core; inside job containers the default is `sh`; `cmd` has no fail-fast. — [Workflow syntax, shell](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idstepsshell)
- [CURRENT] **Different tool versions / moving images**: images are rebuilt weekly; `-latest` labels migrate (all three moved or are moving in 2026); e.g. Node 20 was removed from images and default `node` became 22 in May 2026. Pin with `setup-*` actions and explicit image labels. — [runner-images README](https://github.com/actions/runner-images/blob/main/README.md); [runner-images #14029](https://github.com/actions/runner-images/issues/14029)
- [CURRENT] **Path/branch filters and skipped required checks**: a workflow skipped by path/branch filter or `[skip ci]` leaves required checks "Pending" and blocks merging; >3,000 changed files or >1,000 commits change filter behavior. — [Skipping workflow runs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/skip-workflow-runs); [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#git-diff-comparisons)
- [CURRENT] **Concurrency cancellation**: with a shared group, a newer run cancels the pending one (and the running one with `cancel-in-progress: true`); group names are case-insensitive and shared across workflows unless `github.workflow` is included. — [Workflow syntax, concurrency](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency)
- [CURRENT] **Stale or missing caches**: caches are immutable per key; `restore-keys` prefix matches restore "the most recent cache"; PR caches are scoped to the merge ref; caches unused for 7 days are evicted; since June 2026 low-trust triggers cannot save default-branch caches. — [Dependency caching reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)
- [CURRENT] **Resource limits**: private-repo standard runners have 2 vCPU/8 GB RAM/14 GB SSD (public 4/16/14); macOS arm64 3 vCPU/7 GB; jobs stop at 6 hours (GitHub-hosted) or the `timeout-minutes` (default 360); `ubuntu-slim` stops at 15 minutes. — [GitHub-hosted runners reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners); [Actions limits](https://docs.github.com/en/actions/reference/limits)
- [CURRENT] **Environment differences**: `CI=true` is always set (many tools change behavior, e.g. treat warnings as errors or disable prompts); steps don't share shell state — only `GITHUB_ENV`/`GITHUB_PATH`/outputs persist between steps; each job starts on a fresh VM, so files must move via artifacts or caches. — [Variables reference](https://docs.github.com/en/actions/reference/workflows-and-actions/variables); [Workflow commands](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands#setting-an-environment-variable); [Workflow syntax, runs-on](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#choosing-github-hosted-runners)
- [CURRENT] **Events that never fire**: pushes/PRs made with `GITHUB_TOKEN` don't trigger `push` workflows (PRs now trigger approval-required runs); `schedule`, `workflow_dispatch`, `issue_comment`, `workflow_run` only use the workflow file on the default branch; scheduled runs are delayed or dropped under load and are disabled after 60 days of inactivity in public repos. — [GITHUB_TOKEN concept](https://docs.github.com/en/actions/concepts/security/github_token); [Events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule); [Troubleshooting workflows](https://docs.github.com/en/actions/how-tos/troubleshoot-workflows#triggering-event-conditions)
- [CURRENT] **Case sensitivity (Git-level source)**: Git documents case-insensitive filesystems "like APFS, HFS+, FAT, NTFS" and sets `core.ignoreCase` when it detects one; Linux runners use case-sensitive filesystems, so `import './Foo'` vs `foo.js` works on a Mac/Windows laptop and fails on `ubuntu-*`. — [git-config: core.ignoreCase](https://git-scm.com/docs/git-config#Documentation/git-config.txt-coreignoreCase)
- [CURRENT] **Line endings (Git-level source)**: `core.autocrlf true` (the Windows recommendation) converts LF to CRLF on checkout; a committed `.gitattributes` (`* text=auto`, `*.sh text eol=lf`) "overrides the `core.autocrlf` setting for all repository contributors." — [Configuring Git to handle line endings](https://docs.github.com/en/get-started/git-basics/configuring-git-to-handle-line-endings)
- [CURRENT] **Time zone**: cron schedules are UTC unless `timezone` is set (2026). — [Workflow syntax, on.schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onschedule)

### Inferences
- A practical triage order for "passes locally, fails in CI": (1) read `gh run view --log-failed`; (2) identify which commit CI built (`GITHUB_SHA` is the merge commit on PRs) and rebase/merge the base branch locally to reproduce; (3) compare tool versions printed by `setup-*` steps with local ones; (4) check whether the run came from a fork/Dependabot (no secrets); (5) look for cache restores with broad `restore-keys`; (6) re-run failed jobs with debug logging; (7) reproduce in the same container image or with `act`, remembering `act`'s gaps.
- Flaky tests that only fail in CI often relate to the smaller private-repo runners (2 vCPU/8 GB) and parallel test timing — a resource-limit effect rather than a logic bug.

### Gaps
- UNVERIFIED from official Actions docs: the *runner VM's* system time zone/locale (commonly UTC and `C.UTF-8`/`en_US.UTF-8`) — only the cron default (UTC) is documented on the pages fetched; tried the hosted-runners reference and variables reference.
- UNVERIFIED from official Actions docs: that Windows hosted runners check out with CRLF by default (i.e. Git for Windows `core.autocrlf=true` on the image). The Git/GitHub line-ending docs explain the mechanism; a search of `actions/runner-images` and `actions/checkout` code for `autocrlf` returned nothing in this session. Recommend teaching `.gitattributes` as the fix regardless.
- Case-sensitivity of the hosted runners' filesystems is not stated in the GitHub pages fetched (only the Git documentation was verified); macOS runners being case-insensitive by default was not verified.
- The runner release notes for v2.337.0 mention an interactive debugger ("DAP debugger", "debugger Dev Tunnel"), but no changelog or docs page describing a user-facing step debugger was found — do not teach it as available. — [actions/runner v2.337.0](https://github.com/actions/runner/releases/tag/v2.337.0)

## 12. Deployment patterns from official docs

### Takeaway
GitHub's documented deployment toolkit is: environments (approvals, branch rules, scoped secrets) + `concurrency` to serialize deploys + OIDC for cloud credentials + reusable workflows for shared deploy logic + `workflow_dispatch` inputs for manual promotion. Official examples cover GHCR publishing with `GITHUB_TOKEN` and `packages: write`, GitHub Pages via `configure-pages` → `upload-pages-artifact` → `deploy-pages`, and release creation with the GitHub CLI or actions (release-please, action-gh-release).

### Cited Findings
- [CURRENT] "GitHub Actions gives you fine-grained control over deployments with environments, concurrency groups, and protection rules." Common triggers: `push` to `main`, `pull_request`, `workflow_dispatch`. A job referencing an environment "won't start until all of the environment's protection rules pass" and cannot read its secrets before that. — [Deploying with GitHub Actions](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/control-deployments)
- [CURRENT] Concurrency for deploys: `concurrency: production` (one running + one pending; older pending canceled) or `queue: max` to keep up to 100 queued in order; "`concurrency` and `environment` are not connected". — [Deploying with GitHub Actions](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/control-deployments#using-concurrency); [Workflow syntax, concurrency](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#example-queueing-multiple-pending-runs)
- [CURRENT] Approvals: jobs waiting on required reviewers show "Waiting"; "If a job is not approved within 30 days, it will automatically fail." Reviewers click **Review deployments** → **Approve and deploy** / **Reject** (rejection fails the workflow); admins may bypass unless disabled. — [Deploying with GitHub Actions](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/control-deployments#using-required-reviews-in-workflows); [Reviewing deployments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/review-deployments)
- [CURRENT] Each environment job creates a deployment object and status (`environment`, `environment_url` from `environment.url`); `deployment: false` suppresses it. — [Managing environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments#how-environments-relate-to-deployments)
- [CURRENT] Manual promotion: `workflow_dispatch` inputs of type `choice` or `environment` (both are documented input types) read via `inputs.<name>`; the job's `environment.name` may be an expression (allowed contexts: `github`, `inputs`, `vars`, `needs`, `strategy`, `matrix`). — [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onworkflow_dispatchinputsinput_idtype); [Workflow syntax, environment](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idenvironment)
- [CURRENT] Reusable deploy workflow: matrix over targets calling a reusable workflow (`strategy.matrix.target: [dev, stage, prod]` with `uses: …/deployment.yml@main` and `with: target: ${{ matrix.target }}`); environment secrets must be consumed by declaring `environment` inside the called workflow's job (they cannot be passed from the caller). — [Reuse workflows](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows#using-a-matrix-strategy-with-a-reusable-workflow)
- [CURRENT] **GHCR with `GITHUB_TOKEN`**: official workflow sets job `permissions: contents: read, packages: write, attestations: write, id-token: write`; `docker/login-action` with `registry: ghcr.io`, `username: ${{ github.actor }}`, `password: ${{ secrets.GITHUB_TOKEN }}`; `docker/metadata-action` for tags/labels; `docker/build-push-action` with `push: true`; then `actions/attest@v4` with `subject-name`, `subject-digest: ${{ steps.push.outputs.digest }}`, `push-to-registry: true`. Docs: "we highly recommend you update your workflow to use the `GITHUB_TOKEN`" instead of a PAT; "The easiest way to connect a repository to a container package is to publish the package from a workflow using `${{secrets.GITHUB_TOKEN}}`"; add the `org.opencontainers.image.source` label. (The docs example pins old docker action SHAs; current majors are login v4, metadata v6, build-push v7.) — [Publishing Docker images](https://docs.github.com/en/actions/tutorials/publish-packages/publish-docker-images#publishing-images-to-github-packages); [Working with the Container registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)
- [CURRENT] Docker's own guidance: `build-push-action` uses the Git context by default ("you don't need to use the `actions/checkout` action"), but then "any file mutation in the steps that precede the build step will be ignored"; use `context: .` with checkout for path context. Cache options: inline, registry, or `type=gha` (`cache-from: type=gha`, `cache-to: type=gha,mode=max`); some events have read-only cache access. `setup-qemu-action` for emulated multi-platform builds; `setup-buildx-action` creates a BuildKit builder. — [build-push-action README](https://github.com/docker/build-push-action/blob/v7.4.0/README.md); [Docker docs: GitHub Actions cache](https://docs.docker.com/build/ci/github-actions/cache/); [Docker docs: GitHub Actions](https://docs.docker.com/build/ci/github-actions/)
- [CURRENT] **GitHub Pages**: build job runs `actions/configure-pages` and `actions/upload-pages-artifact` (artifact = gzip of a single tar, < 10 GB, no symlinks); deploy job needs `permissions: pages: write, id-token: write`, `needs: build`, `environment: { name: github-pages, url: ${{ steps.deployment.outputs.page_url }} }`, and `actions/deploy-pages` (`id: deployment`). Docs examples still show configure-pages@v5 / upload-pages-artifact@v4 / deploy-pages@v4; latest are v6.0.0 / v5.0.0 / v5.0.1. — [Using custom workflows with GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)
- [CURRENT] **Release automation with the CLI**: "GitHub CLI is preinstalled on all GitHub-hosted runners. For each step that uses GitHub CLI, you must set an environment variable called `GH_TOKEN`" (e.g. `GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}`), with `contents: write` to create a release. `gh release create <tag> [files…]` creates the tag if missing (`--verify-tag` to require it), `--generate-notes`, `--draft`, `--target`, `--notes-from-tag`, `--fail-on-no-commits`; with immutable releases the CLI creates a draft, uploads assets, then publishes. — [Using GitHub CLI in workflows](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-github-cli); [gh release create](https://cli.github.com/manual/gh_release_create); [Workflow syntax, permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)
- [CURRENT] **Release automation tools (concept level)**: `googleapis/release-please-action` — "Automate releases with Conventional Commit Messages": the README workflow runs on pushes to `main` with `permissions: contents: write, issues: write, pull-requests: write` and "release-please will start creating Release PRs for you"; its example passes a PAT secret as `token` (latest release v5.0.0; README examples at that tag still say `@v4`). `softprops/action-gh-release@v3` — creates a release and uploads `files` on tag pushes; `generate_release_notes`, `make_latest`; defaults to `github.token`. — [release-please-action README](https://github.com/googleapis/release-please-action/blob/v5.0.0/README.md); [action-gh-release README](https://github.com/softprops/action-gh-release/blob/v3.0.3/README.md)
- [CURRENT] Immutable release best practice: "Create the release as a draft. Attach all associated assets to the draft release. Publish the draft release." — [Immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases)
- [CURRENT] Cloud deploys: use OIDC (section 8) and add environment protection rules when the trust policy's `sub` is `repo:ORG/REPO:environment:NAME`. — [OIDC in AWS](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws)

### Inferences
- "Build once, promote the same artifact" maps cleanly onto documented pieces: a build job publishes an image by digest (and attestation); `deploy-staging` and `deploy-production` jobs (`needs:` chain, separate environments, OIDC roles scoped per environment) deploy that digest; production adds required reviewers (Enterprise for private repos) and `concurrency: { group: production, queue: max }`.
- Because events created with `GITHUB_TOKEN` do not trigger `push`/`release` workflows, release pipelines that chain workflows (release created → publish workflow) need either a GitHub App/PAT token for the creating step or a single workflow with jobs chained by `needs`.

### Gaps
- semantic-release was not verified from its own documentation in this session (treat as concept-level only: conventional-commit-driven versioning that runs in CI and needs full history/tags and a token with `contents: write`).
- No single official "staging → production promotion" tutorial page was found; the pattern is assembled from the environments, concurrency and reusable-workflow references above.

## 13. Required status checks and Actions (skipped jobs, path filters, merge queue, required workflows via rulesets)

### Takeaway
Three rules explain most "stuck PR" confusion: a workflow that never starts (path/branch filter or `[skip ci]`) leaves its required check "Pending" forever; a job skipped by an `if:` conditional reports success and satisfies the requirement; and merge queues only get checks from workflows that also trigger on `merge_group`. Organization/enterprise rulesets can require whole workflows ("Require workflows to pass before merging"), which ignore the workflow's own filters.

### Cited Findings
- [CURRENT] "If a workflow is skipped due to path filtering, branch filtering or a commit message… then checks associated with that workflow will remain in a 'Pending' state. A pull request that requires those checks to be successful will be blocked from merging." — [Skipping workflow runs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/skip-workflow-runs)
- [CURRENT] Troubleshooting table: workflow skipped by path/branch filter or commit message → "Associated checks stay in a 'Pending' state and block merging" → "Avoid requiring workflows that can be skipped."; job skipped by a conditional → "The job reports 'Success'"; job that depends on a failed job → "The dependent job is skipped and may not block merging" → "Use `always()` with `needs` for required checks that depend on other jobs." A PR blocked this way shows "Waiting for status to be reported." — [Troubleshooting required status checks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks#handling-skipped-but-required-checks)
- [CURRENT] "Successful check statuses are `success`, `skipped`, and `neutral`." "Required checks must pass on the latest commit SHA." "A required status check must have completed successfully in the chosen repository during the past seven days" to be selectable. "If a check and a commit status have the same name, both must pass". — [Troubleshooting required status checks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks)
- [CURRENT] Only checks from runs triggered by `push`, `pull_request`, `pull_request_review`, `pull_request_target`, `deployment`, `deployment_status` are evaluated for a pull request; e.g. checks from a `workflow_dispatch` run on the head branch "do not satisfy a required status check in a branch ruleset." — [Troubleshooting required status checks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks#checks-from-some-workflow-jobs-are-not-evaluated)
- [CURRENT] Head commit vs test merge commit: if the test merge commit has a status, that is what must pass ("Showing checks for the merge commit"); otherwise the head commit. — [Troubleshooting required status checks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks#conflicts-between-head-commit-and-test-merge-commit)
- [CURRENT] Strict vs loose: "Require branches to be up to date before merging" (strict, the default) forces the head branch to contain the latest base before merging; a required check can be restricted to an expected GitHub App source. — [Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-status-checks-to-pass-before-merging)
- [CURRENT] **Merge queue**: "You **must** use the `merge_group` event to trigger your GitHub Actions workflow when a pull request is added to a merge queue." Minimal trigger: `on: { pull_request:, merge_group: }`. The queue builds temporary branches (`gh-readonly-queue/{base_branch}/…` for third-party CI) containing the base, earlier queued PRs and the PR; settings include merge method, build concurrency (1–100), "Only merge non-failing pull requests", status check timeout, and merge limits. A merge queue cannot be enabled with wildcard branch-name patterns. — [Managing a merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue); [Events, merge_group](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#merge_group)
- [CURRENT][PLAN-GATED] **Required workflows via rulesets** ("Require workflows to pass before merging"): "Ruleset workflows can be configured at the organization or enterprise level"; the workflow file lives in a source repository whose visibility bounds where it can run (public → any repo; internal → internal/private; private → private); supported triggers are `pull_request`, `pull_request_target`, `merge_group`; "Any filters you specify for the supported events are ignored - for example, `branches`, `branches-ignore`, `paths`, `types`"; the rule blocks direct pushes, so apply it only to branches changed exclusively via PRs; "Evaluate" mode is available. History: organization-wide "required workflows" (beta Jan 2023) moved into repository rules (announced 2023-08-02; GA 2023-10-11; `pull_request_target` support 2023-10-26). — [Available rules for rulesets (GHEC)](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-workflows-to-pass-before-merging); [Changelog 2023-10-11](https://github.blog/changelog/2023-10-11-requiring-workflows-with-repository-rules-is-generally-available/); [Changelog 2023-08-02](https://github.blog/changelog/2023-08-02-github-actions-required-workflows-will-move-to-repository-rules/)

### Inferences
- The robust pattern for path-conditional CI with required checks: do not put `paths:` on the workflow; always start the workflow, detect changed paths in a first job, guard the heavy jobs with `if:`, and require a final aggregate job (`if: ${{ always() }}`/`!cancelled()` with `needs:` on all others, failing when any needed job's `result` is `failure` or `cancelled`). Skipped-by-`if` jobs count as success; never-started workflows do not report.
- Matrix jobs create one check per combination with the matrix values in the name, so requiring individual matrix checks is brittle; requiring a single aggregate job avoids renames when the matrix changes (inference from the "check name must match" rule; not stated verbatim in the docs fetched).
- With a merge queue, the same required check name must be produced by both the `pull_request` and the `merge_group` runs; jobs that are meaningless in the queue can be skipped with `if: github.event_name != 'merge_group'` and still satisfy the requirement because skipped = success.
