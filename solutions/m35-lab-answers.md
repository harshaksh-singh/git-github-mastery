# Module 35 lab answers: The diagnosis method

Answers to the "Questions" of each lab in the [Module 35 lab manual](../lab-manual/m35-diagnosis-method.md). Commit IDs are the ones printed in the manual; commits that you created by hand have other IDs. Statements about Git's behavior were checked on Git 2.55.0 in the lab sandbox or come from the manual pages that [Chapter 29](../textbook/ch29-production-troubleshooting.md) cites.

## Lab 35.1: The ten-command diagnosis on three repositories

1. The first line of `git status`: `HEAD detached from v0.2.0`. A detached HEAD means that commits made now belong to no branch, so "not on `main`" follows before any history is read. `git branch -vv` (the star on `(HEAD detached from v0.2.0)` and `main` at `b7b08aa`), the graph (only `HEAD` beside `720369a`) and the reflog (`checkout: moving from main to v0.2.0` followed by two `commit` entries) confirm it and add the sequence of events. `git log --oneline main..HEAD` and `git branch -a --contains HEAD` are the tests of the hypothesis, not its source.
2. The remote-tracking ref `refs/remotes/origin/main` moved from `0880c4c` to `92aea83`, as the fetch output `0880c4c..92aea83  main -> origin/main` says, and new objects arrived. The local branch `main`, HEAD, the index and the working tree did not change: `main` is still `58a42a9`, the staged docstring is still staged, `.env` is still modified. Only the comparison changed, because `git status` compares the branch with the remote-tracking ref and never asks the server.
3. `git check-ignore` reports the rule that causes a path to be ignored, and by default it looks only at paths that are not tracked. `.env` in `batch-infer` is in the index, so ignore rules are not applied to it and there is nothing to report; exit status 1 means "no path is ignored". With `--no-index` the command skips the index check and shows that the pattern would match. `router/cache_keys.py` in `prompt-router` is untracked, so the rule `*_keys.py` from `.git/info/exclude` applies and is printed with its file and line.
4. Any two of these. It does not tell you what the server holds: `git ls-remote origin`, or `git fetch` followed by `git status -sb`; with no upstream, as here, `git status` does not even print a comparison (`git branch -vv` shows the missing brackets). It does not list ignored files: `git status --ignored` or `git check-ignore -v <path>`. It does not tell you whether the commit contains what you think: `git show --stat HEAD`, `git ls-tree -r --name-only HEAD`. It does not show stashes or other worktrees: `git stash list`, `git worktree list`. It does not show who the author is: `git log -1 --format='%an <%ae>'`.
5. `git switch main` destroyed nothing: every object is still in the object database, the working tree was clean, and the HEAD reflog recorded the move, which is how the recovery found the commits. In that sense the label 🟢 is correct. The situation was unsafe because the only name for the two commits was HEAD itself. Moving HEAD removed the last name, so the commits became reachable through the reflog alone, where they expire (after 30 days by default for entries no longer reachable from the tip, although the lab configuration switches expiry off). The risk came from the state, not from the command, and the state was readable in the first line of `git status`. Anchoring with `git branch` before moving would have cost one second.
6. In `annotator`, `git diff`, `git diff --cached` and the configuration listing showed nothing unusual, and `git remote -v` printed nothing, which is itself a finding: no server holds a copy. In `batch-infer`, `git remote -v` and the configuration were unremarkable, while both diffs carried findings. In `prompt-router`, both diffs were empty, while the configuration listing, which was irrelevant in the first repository, held the wrong `user.email`. The set of "skippable" commands is different for every repository and is known only afterwards. That is the argument for running all of them every time: the command you would skip is chosen by the hypothesis you already believe.

## Lab 35.2: Five operations in progress, read from `.git` alone

1. Rebase and bisect. A rebase builds a new line of commits and must leave the branch untouched until the last pick succeeds, so that `--abort` can return to the original; it therefore works on a detached HEAD and moves the branch ref once, at the end. A bisect checks out arbitrary commits of the history for testing and must not move any branch to them. Merge, cherry-pick and revert each add commits on top of the current branch, one at a time, and every one of those commits is meant to be on the branch as soon as it exists. They need no detached HEAD; their undo information is `ORIG_HEAD` for a merge and `sequencer/head` for a sequence.
2. A line leaves `sequencer/todo` when its commit has been created, not when Git starts to apply it. The first line of the todo list is therefore the pick in progress, the one `CHERRY_PICK_HEAD` names. `git cherry-pick --continue` commits it, removes the line, and goes on with the next one. For a rebase the bookkeeping is split differently: the stopped pick is already in `rebase-merge/done`, and `git-rebase-todo` holds only what follows.
3. No. `ORIG_HEAD` records where the branch was before the last `git merge`, `git rebase` or `git reset`, and `FETCH_HEAD` records what the last `git fetch` brought. Both are left behind by finished commands. An operation in progress shows as `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `REBASE_HEAD` with a `rebase-merge` or `rebase-apply` directory, a `sequencer` directory, or `BISECT_*` files.
4. Any two of: `.git/HEAD` holds a raw commit ID instead of `ref: refs/heads/...`; the files `BISECT_LOG`, `BISECT_START` and `BISECT_TERMS` exist in `.git`; refs exist under `refs/bisect/` (`git for-each-ref refs/bisect` or `ls .git/refs/bisect`); `git branch` marks the current position as "(no branch, bisect started on feature/strict-guard)"; the reflog has checkout entries to commits nobody chose by name.
5. A commit is a tree plus parents. The tree answers "what is the content"; the parents answer "what has been integrated". With one parent, Git's history says that `feature/strict-guard` was never merged: `git branch --no-merged` still lists it, `git branch -d feature/strict-guard` refuses, `git log main..feature/strict-guard` still lists its three commits, and the merge base of the two branches stays where it was. The next `git merge feature/strict-guard` therefore merges all of the branch again from the old base and can conflict with the copy of its own changes. `git log --graph`, `git log --first-parent` and `git bisect` also see a different history.
6. Both remove the state files and leave the index and the working tree as they are: half-merged content, conflict stages and staged files from the other branch. `git merge --quit` is the supported way to do that, for the rare case in which you want to keep the working tree and continue by other means; `rm` does the same without Git's bookkeeping. Neither restores anything. The command that undoes a merge in progress is `git merge --abort`, which needs `MERGE_HEAD` to exist and resets the index and the working tree to the state before the merge. After the files have been deleted, the route back is the one of the lab: commit or reset deliberately, then merge again.

## Lab 35.3: Preserve evidence, then fix

1. Lost with no way back: the hand-made resolution of `guard.yaml`. It existed only in the working tree, was never staged, and was therefore never written as an object; the abort overwrote the file. Recoverable: the first pick, `5c011a9`. It is a commit, the HEAD reflog and the reflog of `release/1.4` both list it, and without any anchor it would have stayed available until reflog expiry and garbage collection. The conflict itself is also reproducible: starting the cherry-pick again produces the same three stages.
2. Yes, at that moment. The bundle listed `refs/heads/release/1.4` and `HEAD` at `5c011a9`, the same commit as `refs/heads/rescue/backport-partial`. A bundle made with `--all` contains every ref and HEAD with everything they reach, and the branch itself still pointed at the first pick. The rescue branch matters for what comes next: after an abort, `release/1.4` points at `329817a`, and a bundle made then, without the rescue branch, would not contain `5c011a9`, because only a reflog would still name it and bundles do not carry reflogs. The order "anchor, then bundle" makes the bundle independent of when it is made.
3. `git merge --ff-only` succeeds only when the branch can move forward to the target without creating a merge: the target must be a descendant of the current tip. It adds; it cannot take a commit off the branch; and it refuses if a local change is in the way. `git reset --hard` moves the branch to any commit, in any direction, and overwrites the index and the working tree without asking. Here both would have produced the same branch tip, but the first one proves on the way that nothing is being discarded, and the second one would have destroyed anything uncommitted. Choose the command that fails when your assumption is wrong.
4. `git cherry` compares patch IDs, and a backported commit whose conflict was resolved has a different diff, so it is reported with a plus sign. Before concluding that a commit is missing: look for the record that `-x` wrote, with `git log --oneline --grep='cherry picked from commit' release/1.4`, which here lists all three backported commits; compare the content directly, for example `git show release/1.4:guard.yaml`; and compare the two versions of the commit with `git range-diff` or `git show`. A minus sign is proof of presence. A plus sign is only the absence of that proof.
5. Not finish it on a guess. The resolution decides what a release branch ships. Without a note, establish both intents from the repository: `git show CHERRY_PICK_HEAD` for what the picked commit meant to change, `git log --oneline release/1.4 -- guard.yaml` and `git show` for why the release line has its own value, and `git diff` for what the colleague's edit takes from each side. Then confirm with the colleague or with the owner of the release branch before `git add`. The state was already preserved, so waiting costs nothing; a wrong threshold in a release costs an incident ([Chapter 8](../textbook/ch08-merge.md), section 8.15).
6. Evidence must stay exactly as it was found, so that it can answer later questions and serve as the source for recovery. A rehearsal changes the repository it runs in: after the abort, the rehearsal copy no longer contained the resolved file, and the recovery had to take it from somewhere. If the rehearsal had run in the only copy, the resolution would have been gone from every place. Two copies cost a few seconds and keep the roles apart: one is read, the other is changed.
