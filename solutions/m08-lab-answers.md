# Module 8 lab answers: Undo

Answers to the "Questions" of each lab in the [Module 8 lab manual](../lab-manual/m08-undo.md). Commit and blob IDs are the ones printed in the manual; commits that you created by hand have other IDs. Statements about Git's behavior were checked on Git 2.55.0 in the lab sandbox or come from the manual pages that Chapter 11 cites.

## Lab 8.1: The reset prediction table

1. The first `M` compares the index with HEAD, the second compares the working tree with the index. After the soft reset the first one compares v4 (index) with v2 (the new HEAD), where it compared v4 with v3 before. The second one still compares v5 with v4. The letters stayed the same and the comparison behind the first letter changed: `git commit` would now record v4 directly on top of v2.
2. `--keep` succeeds when `prompt.txt` has no local change at all (index and file both v3). It then does exactly what `--hard` does. In a larger repository it also succeeds when the local changes are in files that the dropped commit did not touch, and it carries them across. `--merge` succeeds when the change to `prompt.txt` is completely staged (index and file both v4, no further edit). It then resets the index and the file to v2, and v4 survives only as a dangling blob. This is the row "working B, index B, HEAD C, target D" in the tables of the git-reset manual.
3. The second `git reset --hard HEAD~1` wrote it. Every reset stores the tip it is leaving, and that reset left `60c3e2e` (v2). v3, commit `978507c`, was at `HEAD@{3}` in the transcript: below the reset to `ORIG_HEAD` and the two resets to `HEAD~1`.
4. A blob stores content only. The file name and the mode belong to the index entry or tree entry that points at the blob, and the reset replaced the index entry. v5 was written to the file and never passed to `git add`, so Git never computed a blob for it. The object database holds what was staged or committed, and nothing else.
5. By the text of the entry, not by its number. `git reflog` prints the action that created each entry, so look for the line `commit: Refuse when unsure (v3)` and use the commit ID at the start of that line: `git reset --hard 978507c`. An ID does not shift when further entries are added, while `HEAD@{3}` means a different entry after every command that moves HEAD. `git reflog show main` is often shorter to read, because it lists only the moves of that branch.

## Lab 8.2: Revert a pushed commit

1. Base: `store.yaml` in `6820622`, the commit being reverted (batch size 512). Ours: `store.yaml` in HEAD, `dbd9949` (also 512, because Asha did not touch the file). Theirs: `store.yaml` in `c98d2c1`, the parent of the reverted commit (128). Ours equals the base and theirs differs, so the result is theirs: 128. Asha's commit changed only `client.py`. For that file the base and "theirs" are identical, so there is nothing to apply and her version stays. No line was changed by both sides.
2. After the fetch half of the pull, her `main` and `origin/main` would each have had a commit that the other lacks (`ahead 1, behind 1`). With no pull configuration, Git 2.55 then stops with "fatal: Need to specify how to reconcile divergent branches." (Chapter 12). The revert has reached her clone at that point, because the fetch already moved `origin/main`. It reaches her branch as soon as she integrates with `git pull --rebase` or `git pull --no-rebase`. Either way it arrives as an ordinary commit.
3. It would have set `refs/heads/main` in `server.git` to `c98d2c1`. The three commits above it (the bad one, Asha's retry commit and your revert) would have been on no branch on the server, and a bare repository keeps no reflog by default, so the server could not have undone it. Asha's clone would still have had all three: after a fetch, her status would say `ahead 3`. Her next plain `git push` would have been a fast-forward for the server and would have put all three commits back, the bad one included.
4. It proves that `origin/main`, as your clone recorded it at the last fetch, contains the commit. The commit was therefore on the server's `main` at that moment, and anyone may have fetched it. It cannot prove that a commit is private when the list is empty: the remote-tracking branch may be stale, the commit may have been pushed to a remote or a ref that this clone does not track, and nothing in Git records who has fetched what.
5. The working tree was clean, and the branch was strictly behind its upstream, so every commit it could reach was also reachable from `origin/main`. Nothing existed only in the place that was overwritten. The same command destroys work when the tree has uncommitted changes to tracked files, and it takes local commits off the branch when the branch is ahead of its upstream (those stay in the reflog).

## Lab 8.3: Revert a merge, then re-merge

1. The merge base is `cb65ab5`, the tip of `feature/dedup`. The first merge made that commit an ancestor of `main`, and the revert did not change the graph. A branch whose tip is an ancestor of HEAD has, for Git, nothing left to merge.
2. Base (`cb65ab5`): `dedup.py` exists. Ours (`main` at the revert): the file does not exist, because the revert deleted it. Theirs (the branch with its fix): the file exists, unchanged since the base. Only our side changed the path, by deleting it, so the result is the deletion. There is no conflict, because their side did nothing to the file.
3. Its diff is the inverse of the revert's diff, which is the content change of the original merge relative to its first parent: `dedup.py` is created and `pipeline.py` gets its import and call back (2 files changed, 5 insertions, 1 deletion). It has one parent, the revert commit. It is an ordinary commit, and the graph shows no second line into it.
4. The first command of step 5, the revert of the revert. A branch rebuilt with `git rebase --no-ff` consists of new commits that are not ancestors of `main`. The merge base is then the commit where the branch started, and the merge alone brings the whole feature. Reverting the revert first would put the old copy of the feature back, and the merge would have to combine it with the rebuilt copy. Where the two copies are identical that merges cleanly. Where a rebuilt commit differs from its old version, the merge stops with a conflict (an add/add conflict when the file was created by the branch). The how-to "revert-a-faulty-merge" gives the same warning.
5. `--merged` answers a question about the graph: is the tip of the branch an ancestor of `main`? That was already true while the content of the branch was reverted. Whether a feature is live is a question about content. Check the files (`ls`, `git grep`), run the tests, or search the history for the pair: `git log --oneline --grep='^Revert' main` and `--grep='^Reapply'`.

## Lab 8.4: Restore variants

1. `git restore rubric.yaml`: from the index to the working tree. `git restore --staged rubric.yaml`: from HEAD to the index. `git restore --staged --worktree rubric.yaml`: from HEAD to both. `git restore --source=HEAD~2 rubric.yaml`: from that commit to the working tree. `git restore --source=HEAD~2 --staged --worktree rubric.yaml`: from that commit to both.
2. It is a blob that nothing refers to: HEAD has 0.80, the index now has 0.80, and the file has 0.90. `git fsck --lost-found` prints `dangling blob 9296c5c...`, and `git cat-file -p 9296c5c` prints `pass_mark: 0.85`. To stage it again without touching the file: `git update-index --cacheinfo 100644,9296c5cb4fcfb26a0b5c3563e5f62d55ba82d55b,rubric.yaml`. To get it as a file, redirect the output of `git cat-file -p` into a new file. The blob lasts until garbage collection removes unreachable objects, two weeks by default.
3. The first `M` compares the index (0.85) with HEAD (0.80). The second compares the file (0.60) with the index (0.85). The command wrote the file only, so the staged 0.85 is still there, between two other versions.
4. The pathspec `.` named every tracked path. By default restore works in "no overlay" mode: a tracked path that does not exist in the source is removed, so that the destination matches the source. The first commit contained only `rubric.yaml`. With `--overlay`, restore never removes files: `cases.jsonl` and `judge.txt` stay, and so does the unstaged edit to `judge.txt`, because a path that the source lacks is not touched at all.
5. The sentence existed only in the working tree file. It was never staged, so no blob holds it, and the restore overwrote the only copy. Any of these before the mistake would have created an object: `git add judge.txt`, `git stash`, or a commit. After `git add`, the version would have been found by `git fsck --lost-found` even if the index entry were lost later.

## Lab 8.5: Clean safely

1. `git clean -n -d -X` and `git clean -n -d -x`. `.env` matches a pattern in `.gitignore`. Without `-x` or `-X`, clean considers only untracked paths that are not ignored. `-X` selects exactly the ignored paths. `-x` stops using the ignore rules, so ignored and merely untracked paths are treated alike.
2. A second `-f`: `git clean -n -d -f -f` lists `third_party/` for removal. The manual says that Git refuses to modify untracked nested repositories unless a second `-f` is given. A nested repository is more than files. It has its own history, possibly with commits that exist nowhere else, and deleting the directory deletes that whole repository.
3. `-e` adds a pattern to the ignore rules for this run. A pattern that begins with `!` re-includes what an earlier pattern excluded, so for this run `.env` and `checkpoints/` are not ignored. `-X` removes only ignored paths, so it leaves them alone and removes the rest: `__pycache__/`, `data/` and `run.log`.
4. The status is short because the files were deleted, not because they are safe. `git fsck` is silent because there are no unreferenced objects, and that means Git never stored any of these files. In section 11.5 a silent `fsck` after a hard reset would be equally bad news. The two commands confirm that nothing remains to recover from.
5. In a CI job whose workspace contains nothing but the checkout, `git clean -f -d -x` is acceptable, because nothing in it is irreplaceable. On a laptop, use `-X` after a dry run, with `-e '!<pattern>'` for what must stay, or name the paths. What avoids cleaning altogether is building from a fresh clone or from a separate worktree (Chapter 25), where no local files exist in the first place.

## Lab 8.6: Stash and a pop conflict

1. In three commits that only `refs/stash` reached. The unstaged change to `limits.yaml` was in the tree of the stash commit itself, which records all tracked files as they were on disk. The staged change to `router.py` was in that tree too, and separately in the tree of the second parent, the commit named `index on main: ...`. `notes.md` was in the tree of the third parent, `untracked files on main: ...`, a commit without a parent of its own. On disk and in the index nothing was left: both were reset to HEAD, and `notes.md` was deleted.
2. `Updated upstream` is the file as it was in your working tree when the pop started, which is the hotfix version with 30. `Stashed changes` is the file in the stash commit, with 120 and the `per_tenant` line. Git merged three versions of `limits.yaml`: the base from the commit the entry was made on (60), ours from the current files (30), and theirs from the stash commit (120 and `per_tenant: true`). `git ls-files -s limits.yaml` shows them as stages 1, 2 and 3 while the conflict lasts.
3. Because the pop is a merge and it stopped at a conflict. A merge writes every cleanly merged path into the index, and a pop that completes removes that staging again unless `--index` was given. A pop that stops leaves it in place. The staged `router.py` is a by-product of the stopped merge, not a memory of what you had staged: a file that was unstaged when it was stashed comes back staged in the same situation.
4. `git reset --hard` destroyed the files of the merge in progress: the staged `router.py` and the half-merged `limits.yaml`. Nothing was lost by that, because the stash entry still held all of it. `git stash drop` then deleted the only ref to the entry. From then on the work was in unreachable objects only, which garbage collection deletes after its grace period. The loss became real with the drop, and final only with a later prune.
5. A stash commit has two parents, or three with `-u`: the commit that was HEAD, the index commit and the untracked-files commit. Any commit with more than one parent is a merge to `git log --merges`, and the two helper commits are not, so the filter isolates the entries. The recipe finds nothing when the objects have been pruned, and it lists nothing useful when the entry is still reachable from somewhere. The manual's version of the recipe ends with `--grep=WIP`, which matches only entries with the default message `WIP on <branch>`. An entry created with `-m "wip: per-tenant limits"` does not match, which is why the lab used the recipe without that filter.

## Lab 8.7: Scenario cards

1. Card 1: `git reset --hard @{u}`, which takes the three commits off the branch and their changes out of the working tree (the commits stay in the reflog). Card 2: `git reset --hard HEAD~2` followed by a forced push, which also removes the good `max_tokens` commit and rewrites shared history. Card 3: `git rm outputs/predictions.jsonl` without `--cached`, which deletes the file from disk, or a second commit that removes the file, which leaves it in the first commit forever once pushed. Card 4: `git revert` of the last two commits, which also undoes the changes to `tools.yaml` and `README.md`, or `git reset --hard HEAD~2`, which rewrites history as well. Card 5: `git reset --hard ORIG_HEAD`, which destroys the edit to `notes.md`. Card 6: `git clean -f -d -x`, which deletes `.env`, or `git reset --hard` alone, which leaves the untracked files in place.
2. It can keep more than one commit. An interactive rebase can squash some commits and leave others separate, reorder them, reword single messages and drop one commit, and it keeps the authorship and dates of the commits it does not change (Chapter 9). `git reset --soft @{u}` produces exactly one staged change that you commit as one commit.
3. The three versions of `gen.yaml` were: base, the file in the bad commit (temperature 1.5, `max_tokens` 512); ours, the file in HEAD (1.5 and 1024); theirs, the file in the parent of the bad commit (0.2 and 512). Line 1 differs only on their side, line 4 only on our side, and the two lines between them are unchanged, so the two changes do not overlap. `Auto-merging` reports that a content merge of the file was needed. It is not a warning.
4. From your reflogs: it is `HEAD@{1}` and `main@{1}` right after the amend. Nothing else refers to it, and after the reflog entry expires (30 days by default for a commit the branch no longer reaches) garbage collection can delete it. It matters when the file holds something that must not spread: as long as the old commit exists you can reset to it or push it by mistake, and anyone with access to your `.git` directory can read it. Here the commit was never pushed, so the server never had it.
5. If every commit that changed `prompts/system.txt` since the first commit had changed nothing else. `git revert` undoes whole commits. Here each of the two commits also changed another file, so reverting them would have undone the tool list and the README as well. Commits that each do one thing (Chapter 6) are what make `git revert` usable at the level of one intention.
6. The merge wrote `ORIG_HEAD`, and after it you only edited a file. No command that writes `ORIG_HEAD` had run. Any of these would have replaced the value: `git reset` in any mode, `git stash push`, another `git merge` or `git pull`, `git rebase`, `git am`. After one of them, the commit before the merge is still in the reflog as the entry below the `merge feature/cache` line.
