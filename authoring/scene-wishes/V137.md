# Scene wishes for V137: Signatures: what is signed, by which program, and SSH signing end to end

No library scene was placed in this pass. `hash` could show "one more header, another ID", but the script has no pair of IDs for the same commit with and without a signature, and `objects` needs blob IDs the script does not print. The commit graph cannot carry a result letter per commit, which is the point of the demo. All labels below are copied from the script. The demos `signed-header` and `ssh-signing` are volatile: keys, signatures and IDs differ on every run, so every picture should say "on this run".

## 1. CONCEPT, "**Precisely.** Git computes the object without", the quiz and its answer; DIAGRAM, "Two layers. The bracket marks the"

**Picture.** The commit object as a card of lines, built in the order Git works, to replace the still drawing of the DIAGRAM section.

1. `object`: the card "the commit object, as stored" with the lines `tree <tree ID>`, `parent <parent ID>`, `author name <email> date`, `committer name <email> date`, and `message`.
2. `payload`: a bracket over all of them, label "signed bytes: the object WITHOUT gpgsig"; the bracketed lines travel as one block to a box "signing program".
3. `sign`: the box returns a block `-----BEGIN SSH SIGNATURE-----` ... `-----END SSH SIGNATURE-----`.
4. `embed`: the block slides into the card between the committer line and the message as `gpgsig`, with the note "(continuation lines start with a space)".
5. `hash`: an outer box closes around the whole card: "the whole object, signature included, is hashed -> commit ID".
6. Quiz state ("Quick quiz. You sign a commit"): the card without `gpgsig` beside the card with it, both ID chips showing question marks; answer: the two chips differ ("a new commit, with a new ID").

Demo step 1 ("Between the committer line and the") can reuse state 4 with the transcript's real lines: `tree 5dca3a6e589a5d9b648e2563ac9c17bee742e961`, `parent 150744516440fbc2cc4197e81141ce63d5fa7cb2`, `author Lab User <you@example.com> 1788755880 +0530`, `committer Lab User <you@example.com> 1788755880 +0530`, message "Describe the project".

A second form for tags (demo, "A signed tag. `git tag` is"): the tag object lines `object 9d471046051e8d578b339ee37eb466c71e16b6ec`, `type commit`, `tag v1.0.0`, `tagger Lab User <you@example.com> 1788757380 +0530`, message "inference-gateway 1.0.0", and the signature block after the message, not as a header.

## 3. CONCEPT, "With `openpgp`, the default, the program", "With `x509`, available since Git 2.19," and "With `ssh`, available since Git 2.34,"

**Picture.** Git in the middle with a dial `gpg.format`; three programs around it. One arm lights up per paragraph.

| `gpg.format` | program | key chosen by | trust decided by |
|---|---|---|---|
| `openpgp` (the default) | `gpg` | `user.signingKey`, or else the committer identity | "your GnuPG keyring and its trust levels" |
| `x509` (since Git 2.19) | `gpgsm` | the same way | "the certificate chain" |
| `ssh` (since Git 2.34) | `ssh-keygen` | `user.signingKey`, or `gpg.ssh.defaultKeyCommand` | `gpg.ssh.allowedSignersFile` |

Caption that stays: "Git does no cryptography". In the demo (step 2) the same picture with the program replaced by the stand-in `show-args` and the arguments from the transcripts on the arm: `--status-fd=2 -bsau Lab User <you@example.com>` for OpenPGP and X.509, `-Y sign -n git -f ... signing_key.pub <file with the payload>` for SSH; for SSH with no key the arm shows a cross and "either user.signingkey or gpg.ssh.defaultKeyCommand needs to be configured".

## 4. CONCEPT, "**Signing and verifying need different things.**"; demo, "An error, exit status 1," and "One line in a text file:"

**Picture.** Two halves. Left "signing needs one key": a key and a commit card, a signature appears. Right "verifying needs a statement of whom you trust": the signature goes to a list.

1. `sign`: left half, key → `gpgsig` on the card.
2. `no-list`: right half with an empty, dashed frame labelled `gpg.ssh.allowedSignersFile` "not set"; result chip `N`, "No signature"; note "Git doesn't start `ssh-keygen` at all".
3. `list`: the frame becomes a file with one line in three parts, each part labelled: principal `you@example.com`, option `namespaces="git"`, "public key" (`ssh-ed25519 ...`).
4. `verify`: the key on the signature is matched to the line; result chip `G`, text `Good "git" signature for you@example.com`; caption "Nothing in the repository changed."

## 5. CONCEPT, "**The result letters.** For scripts, the"

**Picture.** Four letter chips arriving one per sentence, each with its meaning; four more greyed.

- `G`: "a good signature: the key is in the allowed-signers file and valid at the signature's time" (green tick).
- `B`: "a bad signature: the object was altered after signing, or the key is listed in the revocation file" (red cross).
- `U`: "a good signature with unknown validity" (amber question mark).
- `N`: "no signature", and "also printed, with an error, when no allowed-signers file is configured".
- Greyed: `X`, `Y`, `R`, `E` ("The SSH demos of the chapter don't produce them").

## 8. PRODUCTION EXAMPLE, "Then the first key rotation. An"

**Picture.** The allowed-signers file with one line per engineer.

1. One file per engineer with one line each: own commits `G`, everyone else's not verified.
2. One shared file "in the repository", "one line per engineer": all `G`.
3. Rotation done wrong: a line is replaced, the engineer's old commits turn from `G` to `U`.
4. Rotation done right: "rotation adds, never replaces. Both keys stay listed."
