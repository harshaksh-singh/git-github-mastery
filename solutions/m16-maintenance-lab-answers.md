# Module 16 lab answers: The object database, part 2 (maintenance)

Answers to the "Questions" of Labs 16.3 and 16.4 in the [Module 16 maintenance lab manual](../lab-manual/m16-maintenance.md). Object IDs and counts are the ones printed in the manual. Every statement about behavior was checked on Git 2.55.0 in the lab sandbox, or is quoted from the local manual pages.

## Lab 16.3: Trace what a maintenance run does

1. `git pack-refs --all --prune` deletes loose ref files after writing their values into `packed-refs`; no ref and no object is lost. `git reflog expire --all` deletes reflog entries older than `gc.reflogExpire` (90 days) or, for entries not reachable from the current tip, `gc.reflogExpireUnreachable` (30 days); in the lab both are `never`, so nothing was removed, but in a normal repository this is the step that removes the names by which lost commits are found (Chapter 13). `git repack -d -l ...` deletes loose objects and packs that it has made redundant; in the all-into-one form with `--cruft --cruft-expiration=2.weeks.ago` it also drops unreachable objects older than two weeks and puts younger ones into a cruft pack. `git commit-graph write --split --reachable` deletes only superseded commit-graph layers. `git worktree prune --expire 3.months.ago` deletes administrative records of linked working trees whose directories have been gone for three months. `git rerere gc` deletes recorded conflict resolutions past their age limits (Chapter 14C).
2. Git computes the geometric split over the existing packs. If at least one existing pack can stay as it is, it runs `git repack --geometric=2`, which rolls up only the small packs and the loose objects. If every pack would have to be rolled up, or there is no pack, as in the first run, it runs the all-into-one form. The difference for unreachable objects is the one the manual states: a cruft pack is generated only "when the geometric repacking strategy would decide to do an all-into-one repack". A geometric run packs loose objects whether they are reachable or not and never looks inside the packs it leaves alone, so unreachable objects in them stay where they are.
3. It is not a problem. Three packs with a multi-pack-index over them cost one lookup per object, and 507, 15, 5 is a valid geometric progression (each is at least twice the next). With 20 more loose objects the next run merges nothing: the existing packs are in progression, so the loose objects become a fourth pack and the result is 507, 20, 15, 5. That sequence breaks the rule, and the run after it merges the three small packs with whatever is new. Checked in the sandbox: after one more commit the packs were 507 and 45. The pack of 507 is never rewritten in any of these runs.
4. Automatic maintenance starts after many commands, often several times a minute, and two of them must not repack the same object database at once. Skipping quietly when the lock is held is the right answer to "another run is already doing it". For a scheduled job the same behavior hides a permanent fault: a stale lock makes every run exit 0 without doing anything, so monitoring by exit status reports health for as long as the lock exists. Monitor the state instead (`git count-objects -v`, the age of the newest pack, `git maintenance is-needed --auto`), and run the job with `--no-quiet` so that the warning reaches a log.
5. The cron job and scheduled maintenance can run at the same time, because `git gc` does not take `maintenance.lock`. Two processes then rewrite packs and delete "redundant" files concurrently. The manual's advice follows from that: use `git maintenance run --task=gc`, which takes the lock, or let one mechanism own the repository.
6. Every `git commit`. Each ends by starting `git maintenance run --auto --quiet --detach`. You can see it with `GIT_TRACE=1 git commit ...` (a `run_command` line), predict its effect with `git maintenance is-needed --auto`, and observe the result with `git count-objects -v` a moment later. In the starting state of this lab the first commit would have repacked all 507 loose objects in the background, which is why the setup script switches `maintenance.auto` off.

## Lab 16.4: Write and verify a commit-graph

1. First, the shape of history: for each commit its root tree, the positions of its parents, its commit date and a generation number that is larger than that of any ancestor. Walks that only need the shape (`git merge-base`, `git branch --contains`, `git tag --contains`, `git log --graph`, `git rev-list --count`) read these fixed-size records instead of decompressing commit objects, and generation numbers let them stop early. Second, with `--changed-paths`, a Bloom filter per commit over the paths that differ from its first parent, which path-limited walks (`git log -- <path>`, `git blame`) consult before comparing trees.
2. `definitely_not` counts commits whose filter proved that the path did not change, so no trees were compared. `maybe` counts commits whose filter could not rule it out, so Git compared the trees. `false_positive` counts those "maybe" commits for which the comparison then showed no change. A Bloom filter stores a few hash bits per path in a small bit array: if a path's bits are not all set, the path is certainly absent, but bits set by other paths can coincide, so "all bits set" proves nothing. That asymmetry is what keeps the answers correct: a filter can only make Git skip work that would have found nothing.
3. No. A commit that is not in the file is read from the object database in the ordinary way; the file adds speed for the commits it knows and is not consulted as a list of what exists. It is updated by the next `git commit-graph write`, by the `commit-graph` maintenance task (in automatic runs once about 100 reachable commits are missing from it), by `git gc`, and after fetches if `fetch.writeCommitGraph` is set.
4. The damaged byte is in the record of one commit, `00eae68`, the fifth commit of the history. `git rev-list --count HEAD` walks every commit, reaches that record, reads a parent position of 227 in a list of 96 and dies. `git log -3` reads three records near the tip and never touches the damaged one. For the same reason `git log --oneline` printed 88 lines before it died, which is the dangerous case: a script that discards standard error sees a short history, not an error.
5. `git fsck` verifies the commit-graph as one of its checks, by running the same verification as `git commit-graph verify`, and reports failure if that fails; its exit status describes the repository as a whole, derived files included. The proof that the objects were intact is the same command with the file bypassed, `git -c core.commitGraph=false fsck`, which exited 0, together with `git -c core.commitGraph=false rev-list --count HEAD` printing 94.
6. Derived, and safe to delete and rebuild: the commit-graph (`objects/info/commit-graph` and `objects/info/commit-graphs/`), the multi-pack-index, pack indexes (`.idx`, rebuilt with `git index-pack`, Lab 16.1), reverse indexes (`.rev`) and bitmaps (`.bitmap`). Never delete packs (`.pack`) or loose objects: they are the data. The marker and metadata files beside packs (`.promisor`, `.keep`, `.mtimes`) are not derived either; they record facts that cannot be recomputed from the pack.
