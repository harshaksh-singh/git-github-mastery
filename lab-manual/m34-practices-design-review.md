## What this lab is

This is the assessment that closes Level 8. It is a design review, not a command drill. You are given a company and its repository. You measure the repository, design the company's branching model, governance, CI and security policy, write the design down, and defend it against objections.

There is **no model answer** in this file, and none in the answer file either: a design is judged against the rubric below, and two different designs can both pass. The answer file contains the answers to the "Questions" about the evidence, followed by notes for the assessor. Do not read the assessor notes before you have submitted your design.

## The brief

**Kestrel Lending** builds credit-risk scoring software. Thirty-eight engineers work in four teams: scoring platform (Java and Python services), modelling (Python, notebooks, training and evaluation pipelines), integrations (a client SDK), and infrastructure. Six contractors work on integrations.

**What it ships.**

- A **hosted scoring API**, one live version, which the company wants to deploy several times a week. Today it deploys about once a month.
- An **on-premises edition** installed at two banks. Each bank runs a pinned minor version and takes patch releases only. The contract obliges Kestrel to support the current and the previous minor version.
- **Models.** A risk model is retrained roughly every quarter. Kestrel's auditors require that, for any score produced in the last five years, the company can name the model version, the code that trained it and the data it was trained on, and can show who approved the change that put it into production.

**How it works today.** One private repository on GitHub, `riskscore`, which the setup script generates in reduced form. Branches `main`, `develop`, release branches, and feature branches of very different ages. Releases are tags. There are no rulesets. CI runs unit tests on pushes to `main`. Evaluation of a retrained model is run by hand on a shared GPU workstation that the modelling team also registered as a self-hosted Actions runner. The LLM that writes explanation texts is called through a provider API; its key is a repository secret. Developers use a pre-commit configuration that "everybody has installed". An AI coding agent has recently been allowed to open pull requests.

**What went wrong last quarter**, as reported to you:

1. A fix that shipped to one bank in a patch release was missing from the next minor release.
2. A quoted model metric could not be reproduced from the commit recorded with it.
3. A security scan found an environment file in the repository's history.
4. A new joiner's first clone "took forever".

**Constraints.** The organization is on the GitHub Team plan and will consider Enterprise Cloud if you show which control needs it. The banks will not change how they take releases. Head count does not change. You have one quarter to migrate, and the hosted API must keep shipping during the migration.

### Commands

Measure before you design. These commands only read.

```bash
# 1. Branches: age, distance from main, and what Git considers unmerged
git for-each-ref --sort=committerdate --format='%(committerdate:short) %(ahead-behind:main) %(refname:short)' refs/heads

# 3. Fix direction: is anything on a release branch missing from main?
git log --format="%h %ad %an: %s" --date=short --cherry-pick --right-only --no-merges main...release/2.0
git log --format="%h %ad %an: %s" --date=short --cherry-pick --right-only --no-merges main...release/2.1

# 4. Integration rhythm
git rev-list --count --merges main
git rev-list --count --no-merges main
git log --format="%ad %s" --date=short --first-parent main
git rev-list --count main..develop
git log -1 --format="%ad" --date=short "$(git merge-base main develop)"

# 5. What is in history that should not be
git rev-list --objects --all | git cat-file --batch-check='%(objecttype) %(objectsize) %(rest)' | awk '$1 == "blob"' | sort -k2 -n -r | head -3
git log --all --format="%h %ad %s" --date=short --diff-filter=A -- .env models
git ls-files

# 6. People, messages, signatures
git shortlog -sn --all --no-merges
git log --all --no-merges --format=%s | awk "length(\$0) < 12" | sort | uniq -c
git log --format="%G?" main | sort | uniq -c
```

In the ahead-behind column the first number counts commits on the branch that `main` lacks, the second commits on `main` that the branch lacks. `%G?` prints one letter per commit for its signature status; `N` means no signature.

### What happened internally

Nothing changed: every command read refs and objects. What each one computes, so that you know what it can and cannot prove:

- **Step 1.** `%(ahead-behind:main)` counts the commits in `branch..main` and `main..branch`. It counts commits, not content. `git branch --no-merged` lists branches whose tip is not an ancestor of `main`.
- **Step 2.** `%(*objectname)` dereferences an annotated tag to the commit it names. `--simplify-by-decoration` keeps only commits that a ref names, plus what is needed to connect them, which turns a history into a map of its branches and tags.
- **Step 3.** `--cherry-pick --right-only A...B` lists commits on B's side that have no patch-equivalent commit on A's side ([Chapter 27](../textbook/ch27-open-source-team-workflows.md), section 27.10).
- **Step 4.** `--first-parent main` follows only the first parent of each merge: the sequence of states `main` itself went through.
- **Step 5.** `git rev-list --objects --all` lists every object reachable from any ref with the path it was first seen under; `cat-file --batch-check` adds type and size. This finds blobs that no current commit contains. `--diff-filter=A` lists the commits that added a path.
- **Step 6.** `git shortlog -sn` counts commits per author name as recorded in the commits, which is an assertion and not a verified identity.

These are facts about a repository. Whether a fact is a problem depends on the company in the brief; deciding that is your work.

### Failure scenario

A measurement that misleads. You list the unmerged branches, see `feature/calibration` among them, last touched in early June, and write in your review that it is abandoned work to be deleted or rescued.

```bash

git merge-base --is-ancestor feature/calibration main; echo "exit status: $?"
git cherry -v main feature/calibration
git log --oneline -1 --format="%h %ad %s" --date=short main -- score/calibrate.py
```

### Recovery

The three checks compare commits. Compare content: ask Git what tree a merge of the branch into `main` would produce, and compare it with the tree `main` already has.

```bash
git merge-tree --write-tree main feature/calibration
git rev-parse "main^{tree}"
```

<!-- snippet: ch27/lab-34-1-design-review-evidence/08-content-check -->
```text
# Recovery: the checks above compare commits. Compare content instead.
$ git merge-tree --write-tree main feature/calibration
9daa8833bf087fbcd038397d10033760c1a6f87a
$ git rev-parse "main^{tree}"
9daa8833bf087fbcd038397d10033760c1a6f87a
# Merging the branch would produce exactly the tree main already has: nothing is left to merge.
```
<!-- /snippet -->

`git merge-tree --write-tree` performs the merge in memory and prints the ID of the resulting tree; it changes no ref, no index and no file.

### Questions

These are about the evidence. Answer them before you design; the answers are in the [answer file](../solutions/m34-lab-answers.md).

1. Which measurement corresponds to each of the four things that "went wrong last quarter"? For which of the four does the repository give you proof, and for which only a lead?
2. `develop` is six commits ahead of `main` and two behind. What do the two numbers, together with the date of the merge base, tell you about how this team integrates? What do they not tell you?
3. The step 3 check printed one commit for `release/2.0` and nothing for `release/2.1`. State exactly what each result proves. Then give one way in which the empty result could be wrong.
4. Step 5 shows a 2,097,152-byte blob at a path that `git ls-files` does not list. Where is it, who has a copy, and what does `.gitignore` do about it?
5. `git log --format="%G?" main` printed `N` ten times. What does that establish about who wrote those commits? What would a `G` establish, and what would it still not establish?
6. `feature/calibration` passed the content test and `feature/big-refactor` did not. Why does the same squash-merge habit that explains the first make the second harder to finish?
7. Name three questions in the brief that no Git command can answer, and say where you would look instead.

## The deliverable

Write a design document of at most four pages, plus the evidence table. It must contain these seven parts, in this order.

1. **Evidence.** The table from the checkpoint, corrected after the failure scenario.
2. **Branching and release model.** Which long-lived refs exist, who may move each and how; how the hosted API, the on-premises edition and model releases each get from a commit to a customer; the direction in which fixes travel and the check that proves it; what a version number promises. Include one commit-graph diagram of a release and a hotfix under your model.
3. **Governance.** Rules for each protected ref pattern; review requirements and code ownership; who can bypass, and how a bypass is seen afterwards; what you require of contractors and of the AI agent.
4. **CI design.** What runs on a pull request, on `main`, on a release branch and on a tag; which checks are required; how model evaluation runs, on what hardware and with which credentials; what happens to a pull request from outside the trusted group.
5. **Security policy.** What may not enter the repository and the layer that stops it; how the existing history problems are handled, in order; credentials for CI, for the LLM provider and for the runner; signing.
6. **Reproducibility of model releases.** What is recorded for each released model, where, and how the five-year requirement is met.
7. **Migration.** The order of changes over one quarter, what can be rolled back, how you will know each step worked, and what you are deliberately not doing.

For every control, state the layer that enforces it: a convention, a local hook, a CI check, a GitHub rule, or a contractual or human process. For every factual claim about GitHub (a feature, a plan requirement, a default), cite the chapter of this book or the documentation page. If you do not know whether a plan includes a feature, say so and say how you would find out.

## Grading rubric

One hundred points. Pass: 70 or more, with no automatic failure.

| Part | Points | Full marks | Half marks | No marks |
|---|---|---|---|---|
| Evidence | 15 | at least eight measurements, each tied to a statement of the brief; limits of each stated; the squash trap corrected and explained | measurements present, loosely tied to conclusions; limits missing | assertions about the repository without commands, or numbers that the repository does not produce |
| Branching and release model | 20 | model derived from the number of live versions and the release rhythm of each product; every long-lived ref justified; fix direction stated with a testable invariant; diagram correct | a named model applied without derivation; fix direction stated but not testable | a strategy declared best in general; release branches or their absence not justified; no fix direction |
| Governance | 15 | rules per ref pattern, each with its enforcing layer and its bypass path; ownership for workflows, lock files, prompts and model pointers; agents and contractors covered | rules listed without bypass or audit; ownership partial | "we will ask people to"; controls with no enforcing layer |
| CI design | 15 | checks tied to events and refs; required checks named; evaluation separated from untrusted code; runner risk addressed; cost and non-determinism of evaluations handled | a pipeline list without trust boundaries | secrets reachable by untrusted code; evaluation on the shared workstation left as is |
| Security policy | 15 | history problems handled in the right order with rotation first; prevention at push time and in CI; least-privilege credentials; an honest statement of what signing proves | cleanup without rotation, or prevention by local hooks only, but the gap is acknowledged | ignore rules or deletion commits presented as remediation |
| Reproducibility | 10 | commit, dirty state, data and model identifiers, lock file, image digest and resolved configuration recorded; storage and retention for five years addressed, including the data store | commit and data version only | "the commit ID identifies the model" |
| Migration | 10 | ordered steps, each reversible or explicitly not; the hosted API keeps shipping; measurable success criteria; explicit non-goals | a target state without a path | a big-bang switch |

**Automatic failure**, whatever the points:

- claiming that research proves one branching strategy is best, or citing a number for it;
- a policy whose only enforcement is a local hook or a convention, presented as a control;
- treating a commit that deletes a secret, a force push, or making a repository private as removal of the secret;
- inventing a GitHub feature, default or plan requirement, or a Git command or option;
- a design that cannot produce a patch release for a bank containing only fixes.

**The defence.** After you submit, the assessor raises objections, one at a time, from five directions: a developer who finds the model too heavy; a release manager with an urgent fix for one bank; a security reviewer; an auditor; and the CTO asking about cost and about evidence. For each objection you may defend the design, amend it, or concede; a reasoned amendment scores as well as a successful defence. What costs points is changing the design without saying what the change breaks, or defending a control you cannot say how to enforce. The defence is scored inside the seven parts above: it can raise or lower a part by up to a third of its points.

## How to run the review

Work alone and write the document before any discussion. Then ask for the review in strict interview mode: the assessor asks, you answer, and no hints are given before your attempt. Record the objections you could not answer; they are your revision list for Level 9.
