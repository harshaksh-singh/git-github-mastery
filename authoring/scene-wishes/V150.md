# Scene wishes for V150: Concurrency groups, reusable workflows, composite actions and container actions

Spots are given as section heading plus the first six words of the paragraph in `video/scripts/V150-*.md`. Every label is copied from the script. GitHub Actions behaviour is described from the documentation only: no picture may look like a captured run. No library scene was placed in this pass: nothing in today's library draws runs on a timeline, a group shared by several refs, or one workflow calling another, and the demo's transcripts print no commit IDs for a `graph`.

## 1. One group, three runs (the central picture)

- **Spot.** HOOK, "The release manager looks at the"; CONCEPT, "The default behavior: when a run" and "B, two. The first is in"; DIAGRAM, "Try it now, on paper. Thirty" (it replaces the ASCII drawing); INTERVIEW QUESTION.
- **Picture.** A time axis with one lane named `production`. Three merges on `main` at 10:00, 10:02 and 10:04, each starting a run.
- **Steps (default).**
  1. `run-1`: run 1 as a long bar, "in progress".
  2. `run-2`: run 2 arrives: "pending".
  3. `run-3`: run 3 is queued; run 2 gets a cross: "cancelled when run 3 is queued"; run 3 is "pending".
  4. `finish`: run 1 ends; run 3 becomes "in progress". Counter: "two deployments, not three".
- **Steps (variation `cancel-in-progress: true`).** Run 1 is cancelled when run 2 arrives, and run 2 when run 3 arrives; "only run 3 finishes".
- **Steps (variation `queue: max`).** "nothing is cancelled, and the three run one after another"; note "up to 100 pending runs".
- **Why not today.** No timeline scene; cancellation needs a red cross on a bar (a cross, not a warning triangle: nothing is destroyed).

## 2. The same story as a railway

- **Spot.** MENTAL MODEL, "**Analogy for concurrency,** from the textbook.", then "Now run the three merges from".
- **Picture.** "A single-track railway section with one waiting siding."
- **Steps.**
  1. `track`: one train on the track ("Merge one is on the track").
  2. `siding`: a second train in the siding ("Merge two waits in the siding").
  3. `third`: a third train arrives; the second "is sent away"; the third "takes the siding".
  4. `cancel`: with `cancel-in-progress: true`, "the arriving train also removes the one on the track".
  5. `yard`: with `queue: max`, the siding becomes "a yard for up to 100 trains" (where the analogy breaks).
- **Why not today.** No analogy scene of this kind.

## 3. Two patterns: a track per ref, or one track for everything

- **Spot.** CONCEPT, "The first includes the workflow name"; LIVE TERMINAL DEMO, Step 1, "It's cancelled. A group named `ci`".
- **Picture.** Lanes labelled with group names.
- **Steps.**
  1. `ci-shared`: one lane `ci`; runs for `refs/heads/docs/rollback-steps`, `refs/heads/feature/safety-stock` and `refs/heads/main` all land on it; a run on `feature/safety-stock` is cancelled by a push to `docs/rollback-steps`.

## 4. Three kinds of reuse, by what they replace

- **Spot.** CONCEPT, "A reusable workflow replaces one or", "A composite action replaces several steps", "A Docker container action replaces one".
- **Picture.** One workflow drawn as nested boxes: workflow, jobs, steps. A coloured block covers what each mechanism replaces.
- **Steps.**
  1. `reusable`: a block over "one or more whole jobs"; notes `on: workflow_call`, "`uses` at job level", "chooses its own runners", "can name an environment", "In the log it shows as separate jobs".
  2. `composite`: a block over "several steps inside a job"; notes `runs.using: "composite"`, "`uses` at step level", "runs on the caller's runner", "cannot name an environment", "In the log it is one step".
  3. `container`: a block over "one step"; notes `runs.using: "docker"`, "needs a Linux runner", "slower".
- **Why not today.** The comparison table shows the facts; no scene shows the nesting.

  6. `narrow`: the token's permissions shrink as they cross: "Permissions only narrow".
