# Module 7 lab answers: Remotes, fetch, pull, and push

> **Baseline.** Git 2.55.0 on macOS. These are answers to the "Questions" of each lab in the [Module 7 lab manual](../lab-manual/m07-remotes.md). Write your own answers first. Commit IDs quoted here are those of the replay scripts; commits that you made by hand have other IDs.

## Lab 7.1: A bare server and two clones

1. **`origin/HEAD` missing after the first push.** `refs/remotes/origin/HEAD` records which branch the server's `HEAD` names. Your clone was made while the server had no branch, so there was no remote-tracking branch for it to point at. The clone did learn the name `main` from the server's unborn `HEAD` and used it for the upstream configuration, but it created no ref. A push writes the remote-tracking ref for the branch it pushed and nothing else. Asha cloned after `main` existed, so her clone got `origin/main` and `origin/HEAD` together. Yours was created in step 8 by `git fetch`, which creates a missing `refs/remotes/<remote>/HEAD` (Git 2.48 or later).
2. **Who created `origin/main`.** `git push`. When the server reported the update of `refs/heads/main` as successful, your Git set `refs/remotes/origin/main` to the commit it had sent. It is safe because nothing is guessed: the server has confirmed that its branch has that value. Chapter 12, section 12.7 shows the reflog entry `update by push`.
3. **"Up to date" while the server was ahead.** The message was not wrong, and it was not about the server. `git status` compared `refs/heads/main` with `refs/remotes/origin/main`, two refs in your clone that both named your first commit. It opened no connection. The sentence describes the state at your last contact with the server, which was your own push.
4. **`origin/HEAD` disappeared from `show-ref`.** It is a symbolic ref whose content is `ref: refs/remotes/origin/main`. When you deleted its target it was left dangling: the symbolic ref still existed, but it resolved to no object, and `git show-ref` lists only refs that resolve. The fetch re-created `origin/main`, and the unchanged symbolic ref resolved again. That is why it came back without any command creating it.
5. **No `refs/remotes/` on the server.** Remote-tracking refs are a clone's record of another repository. They are written by fetching through a refspec that maps into `refs/remotes/<name>/` and by pushing to a configured remote. The bare server has no remote and never fetches or pushes; other repositories come to it. Its branches under `refs/heads/` are the originals that everybody's `origin/*` refs record.
6. **Asha's name.** From `user.name` and `user.email` in the configuration of her clone, written by the two `git config set` commands; a repository's own configuration takes precedence over the global file. Without them the commit would carry the global identity of the lab shell, `Lab User`, and the log in step 9 would show two commits by the same person.

## Lab 7.2: A rejected push, merge and rebase

1. **Two messages, one situation.** At the first attempt your repository did not contain the commit that the server's `main` named, so your Git could not test whether the update was a fast-forward: `(fetch first)`. After `git fetch` the commit was in your object database, the test ran, and it failed: `(non-fast-forward)`. The server was in the same state both times. The difference was in your clone.
2. **Two names for a merge.** `git merge origin/main` was given a remote-tracking branch of yours, so the message is `Merge remote-tracking branch 'origin/main'`. `git pull` does not merge `origin/main`. It merges the line of `FETCH_HEAD` that is marked for merging, and that line describes itself as `branch 'main' of <URL>`. The commits merged are the same; the description of where they came from differs.
3. **Who changed a commit ID.** Ravi. The rebase replaced his commit `7dca6cc` (`Add eval harness entry point`) with a new commit that has a different parent and therefore a different ID. Your merge changed no existing commit: it added one merge commit on top of your commit and Asha's, and both kept their IDs.
4. **What the forced push made unreachable.** Three commits: `2ce93f5` (your `Add dev requirements`), `b90ac08` (your merge) and `8421e1c` (Ravi's rebased commit). They still existed in Ravi's clone, all three, reachable from his `main`; in your clone, the first two, reachable from your `main`; and on the server, all three, as objects that no ref reached and no reflog recorded. Asha's clone never had them.
5. **What `git pull --rebase` would have done.** The replay tries it on a copy of Ravi's clone; the transcript follows this answer. It fetched the forced update and then reported a successful rebase that replayed nothing. `main` ended at Asha's commit, and Ravi's commit, your commit and your merge were on no branch of his any more. The cause is the fork point (section 12.8): Ravi had pushed `8421e1c`, so the reflog of his `origin/main` contained it, and Git treated everything up to that commit as history that the upstream once had and then removed. Only commits after the fork point are replayed, and there were none. The commits would still have been in his reflog, but the one clone that could repair the server would have dropped them without an error, and the next push would have had nothing to send.

6. **Why no `--force` was needed.** The server's `main` was at Asha's commit `de0a845`. Ravi's merge commit has two parents, his previous tip and `de0a845`. The server's current commit is therefore an ancestor of the pushed commit, which is the whole of the fast-forward rule. That the push also carried commits the server had lost does not matter to the rule.

## Lab 7.3: The diverged pull error

1. **After the failed pull.** `refs/remotes/origin/main` moved, `FETCH_HEAD` was rewritten and Asha's commit arrived in your object database: the fetch half of the pull ran. Your branch `main`, the index and the working tree did not change: the integration half never started.
2. **Two fatal messages.** With neither `pull.rebase` nor `pull.ff` set and no flag given: `fatal: Need to specify how to reconcile divergent branches.`, after a long hint. With `pull.ff=only`, or `--ff-only`: `fatal: Not possible to fast-forward, aborting.` The first means "you have not said how"; the second means "you said fast-forward only, and that is impossible here".
3. **`ORIG_HEAD`.** A merge stores the tip that the branch had before the merge in `ORIG_HEAD`. `git reset --hard ORIG_HEAD` moved `main` back to that commit and made the index and the working tree match it; the merge commit was left to the reflog. Uncommitted edits to tracked files would have been overwritten with no way back, which is why the lab points out that the working tree was clean ([Chapter 11](../textbook/ch11-reset-revert-restore.md)).
4. **The old commit after a rebase pull.** It is not gone. The rebase created a new commit with the same change and message and a new parent. The original is still in the object database and in the reflogs: `git reflog` lists the entries of the pull (`pull --rebase (start)`, `(pick)`, `(finish)`) and, below them, the old tip; `main@{1}` names it. It stays until the reflog entry expires (by default 90 days, or 30 days for commits not reachable from the branch tip) and the object is pruned after a further two-week grace period ([gc configuration](https://github.com/git/git/blob/v2.56.0/Documentation/config/gc.adoc)).
5. **Precedence.** `pull.ff` and `pull.rebase` are different keys, so "local overrides global" does not apply: the global `pull.ff=only` and the local `pull.rebase=true` were both in force, and with both set Git 2.55 honors `ff=only` (the row `pull.rebase=true pull.ff=only` in section 12.6). A flag on the command line beats all configuration. That is how Asha's `git pull --rebase` went through, although the global setting applied to her as well: every clone in a lab reads the same global file of the lab shell.
6. **A deploy host.** `pull.ff=only`, or always `git pull --ff-only`. A deploy host must never create commits. A merge pull would build a merge commit that exists nowhere else, and a rebase pull would re-create commits. With fast-forward only the host either moves to exactly what the server has, or stops, and a stop means someone committed on the host, which is the real incident.

## Lab 7.4: `--force-with-lease`

1. **Who rejected.** Your Git. It compared the value of `refs/heads/feature/prompt-cache` that the server advertised (Asha's `00e201d`) with your `refs/remotes/origin/feature/prompt-cache` (`914980c`). They differed, so it printed `! [rejected] ... (stale info)` and sent no update. A refusal by the server would read `! [remote rejected]`.
2. **What the fetch changed.** `refs/remotes/origin/feature/prompt-cache` moved from `914980c` to `00e201d`. The bare lease means "the server's ref must equal my remote-tracking ref". After a fetch that is true by construction, whatever the server holds. Any fetch renews the lease, whether or not you look at what arrived.
3. **Two conditions.** `--force-if-includes` requires that the tip of the remote-tracking ref is reachable from some entry in the reflog of your local branch, that is, that your branch once contained it. Your branch never contained Asha's commit: `(remote ref updated since checkout)`. The explicit form `--force-with-lease=feature/prompt-cache:backup/prompt-cache` requires that the server's ref equals the commit that `backup/prompt-cache` names, `914980c`. The server had `00e201d`: `(stale info)`. The explicit form never consults the remote-tracking ref.
4. **Where Asha's commit still existed.** In Asha's clone, as the tip of her local branch. In your clone, on no branch, but named by the reflog of your remote-tracking ref as `origin/feature/prompt-cache@{1}`, because the fetch in step 4 had brought it. On the server, as an object that no ref reached; a bare server keeps no reflog.
5. **Asha's `git pull --rebase`.** A rebase pull replays only the commits after the fork point, which Git finds in the reflog of the remote-tracking ref. Asha had pushed `00e201d`, so that reflog contained her own tip, the fork point was her tip, and nothing was replayed: her branch was set to the fetched history, which already contained your cherry-picked copy of her test. Here that is the right result, because both of her old commits exist upstream in rewritten form. The same mechanism costs a commit when the upstream was replaced and the commit was not carried over: section 12.8, and question 5 of Lab 7.2.
6. **Before step 1.** Ask whether anyone has the branch checked out. A typo in a commit message is not worth rewriting a commit that a teammate builds on; it can be corrected when the branch is squashed for merging, or left. If a rewrite is necessary, agree on the moment: Asha pushes or sets her work aside, you rewrite and push with an explicit lease on the old tip, and she moves her work onto the new branch. The marker branch `backup/prompt-cache` was the one good habit in the story.

## Lab 7.5: Upstream and a triangular fork

1. **Two settings.** `remote.pushDefault=origin` chooses the remote for a push that names none: your fork, whatever the upstream remote of the branch is. `push.default=current` chooses the destination: a branch with the same name as the local one. The upstream, `upstream/main`, is used for `git pull` and for the comparison in `git status`.
2. **`main`.** Both `@{upstream}` and `@{push}` resolve to `origin/main`. `main` was created by cloning the fork, so its upstream is `main` on `origin`, and a push from `main` goes to `origin` under the same name. With one repository on both sides the triangle collapses.
3. **Rejected on your own fork.** The rule compares commits, not people. `origin/feature/streaming` named the commit from before the rebase (`c6f5b32`). The rebase re-created it with a new parent (`e86f478`), and the old commit is not an ancestor of the new one.
4. **Why a forced push here.** The branch in your fork is used by you alone, and the commit being replaced is your own earlier version. The danger described in section 12.8 is overwriting commits that someone else added. The lease still guards against the case you forgot: a push from your other machine, or, on GitHub, a maintainer who was allowed to edit your pull request branch.
5. **`upstream/feature/streaming`.** `git push upstream feature/streaming` created it: a successful push to a configured remote records the pushed branch in that remote's namespace. `git push upstream --delete feature/streaming` removed it together with the branch on the server.
6. **`DISABLED`.** `git remote set-url --push upstream DISABLED` sets `remote.upstream.pushurl`. A push to `upstream` uses that value as the address. It is not a URL, so Git takes it for a path, finds no repository there, and stops with `'DISABLED' does not appear to be a git repository` before anything is sent; fetching still uses `remote.upstream.url`. Limits: it is local configuration and protects only this clone; it does not stop a push that names the repository by URL or path; and it is a convention, not access control. The real control belongs on the server: permissions and branch rules ([Chapter 18](../textbook/ch18-branch-protection.md)).

## Lab 7.6: Prune and "gone" branches

1. **The blocked fetch.** The server has a branch `release/1.0`. Your clone still had `refs/remotes/origin/release`, left over from the deleted branch `release`. One ref name cannot be the prefix of another, so `origin/release/1.0` could not be created: `unable to update local ref`. `--prune` first deleted the remote-tracking refs whose branches are gone from the server, `origin/release` among them, and that freed the name.
2. **What pruning touched.** No local branch was deleted or moved; all three deletions were under `refs/remotes/origin/`. `git branch -vv` then showed `[origin/feature/reranker: gone]` and `[origin/spike/hybrid-search: gone]`, and the `for-each-ref` format `%(upstream:track)` printed `[gone]` for the same two.
3. **What `-d` checks.** The manual: the branch "must be fully merged in its upstream branch, or in HEAD if no upstream was set". Both upstreams no longer existed, and the outcome matches a test against `HEAD`, which was `main` after the fast-forward. `feature/reranker` is contained in `main` through the merge commit, so it was deleted. `spike/hybrid-search` holds a commit that `main` lacks, so `-d` refused.
4. **Commit `ba1b11e` after `-D`.** In the reflog of `HEAD`, in the entry written when the branch was checked out (`checkout: moving from feature/eval-harness to spike/hybrid-search`). The branch's own reflog was deleted with the branch. `git branch spike/hybrid-search ba1b11e` brings the branch back; the deletion message printed the ID as well (`was ba1b11e`). The entry lasts until it expires from the reflog, by default after 30 days for a commit that is not reachable from the current tip (see answer 4 of Lab 7.3).
5. **Why the push re-created the branch.** The local branch still had its upstream settings: `branch.feature/eval-harness.remote=origin` and `merge=refs/heads/feature/eval-harness`. Under `push.default=simple`, a bare push sends the current branch to the branch of the same name on that remote. Whether that branch exists at the moment is not part of the rule; if it does not, the push creates it. `git status` only reports. "The upstream is gone" is information, and nothing in `git push` consults it.
6. **`fetch.prune` with `push.autoSetupRemote`.** With `push.autoSetupRemote=true`, a branch without an upstream is pushed under its own name and given an upstream, so even after `--unset-upstream` a bare `git push` would have re-created the branch. Pruning tidies remote-tracking refs and marks upstreams as gone. It does not remove the local branches that can resurrect the remote ones, and `autoSetupRemote` removes the last refusal. The reliable habit is to delete local branches whose upstream is gone, with `git branch -d`, or after reading `git log main..<branch>`, with `-D`. Where a name must never come back, the server has to forbid it; on GitHub a ruleset can restrict the creation of matching branches ([available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)).

## Lab 7.7: Refspec surgery

1. **Listed but not switchable.** `git ls-remote` asks the server and prints everything it advertises. `git switch <name>` can create a branch only from a remote-tracking branch in your clone, and the single-branch refspec `+refs/heads/main:refs/remotes/origin/main` had never created `origin/release/0.1`.
2. **What `set-branches` wrote.** With `--add`, one more value of `remote.origin.fetch`: `+refs/heads/release/0.1:refs/remotes/origin/release/0.1`. Without `--add` and with `"*"`, it replaced all values with the single wildcard refspec `+refs/heads/*:refs/remotes/origin/*`.
3. **The negative refspec.** It changes which refs of the server later fetches select. It deletes nothing: `origin/dependabot/pip/requests-2.33`, created by the fetch in step 3, stayed until `git branch -r -d` removed it. Even `git fetch --prune` would have left it, because the branch still exists on the server. The next fetch printed nothing because the bot branch was no longer selected and everything else was up to date.
4. **A fetch without a ref.** The result was in `FETCH_HEAD`, and the objects in the object database. A ref named on the command line that no configured refspec maps is fetched without creating a ref. After `+refs/pull/*/head:refs/remotes/origin/pr/*` was appended, every fetch maps `refs/pull/7/head` to `refs/remotes/origin/pr/7`, a ref that keeps the commit reachable and gives it a name.
5. **Refused, then overwritten.** The first time, Git refused to fetch into the branch that was checked out, because the index and the working tree would no longer have matched `HEAD`: the same reason for which a push into a checked-out branch is refused (section 12.9). With a detached `HEAD` no branch is checked out, so the protection did not apply. The second time, the server's `release/0.1` (`bd50a6d`) was an ancestor of your local commit (`66c5d63`), so moving your branch to it was not a fast-forward. Without `+` the fetch would have rejected the update as `(non-fast-forward)`; the `+` in the pasted refspec forced it.
6. **`release/0.1@{1}`.** A repository with a working tree logs every update of a branch (`core.logAllRefUpdates` is true there by default). The forced fetch added the entry `fetch: forced-update`, and the entry before it is your commit. A bare repository keeps no reflog by default, so the same accident in a `--mirror` clone, or a forced push to the server itself, leaves no such record.
